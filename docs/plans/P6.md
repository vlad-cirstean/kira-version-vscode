# P6 — Refs & checkout

Plan for the P6 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

_Reviewed and accepted. All eight of this plan's open questions have been resolved by the
orchestrating session — see "Open questions", where each resolution is recorded inline. Three of
them became spec corrections (§7.9's tag-asymmetry sentence, §7.10's revert-button sentence,
§10's P13 row), already in the tree. The implementer takes that section as settled context._

**Goal:** the phase where the app stops being a reader. Everything through P5 queried git and
rendered the answer; `driver.write()` — the serialized write queue P1 built, with its
generation counter and its invalidation listeners — has never had a single production caller.
P6 is the phase that gives it eleven, and in doing so establishes the shape every later
mutating phase (P8's fetch/push/pull, P9's stash, P10's reset) copies: **pre-flight → confirm →
execute → reconcile**, with pre-flight as pure functions in `core` and execution as one queued
spawn behind one typed error union.

Concretely, the row asks for: the branch list and a full tag list with the whole of §7.9's
manipulation table; create / switch / detached-checkout / delete / rename for branches; revert
(§7.10) with merge-parent selection and conflict prediction; linked-worktree detection (D12);
the undo slot (§7.12) seeded by branch and tag deletion; the in-progress / conflicted-state
banner (§7.11) with VS Code merge-editor delegation, Continue and Abort; and the full checkout
pre-flight engine (§7.5).

Three things make this phase harder than its item count suggests, and each is settled below
before any work item refers to it. First, §7.5's classification is a *set* question, not a
prediction question, and getting that wrong in either direction produces a plausible,
shippable, wrong answer. Second, the conflicted-state banner is a small piece of UI sitting on
top of a state machine read from `.git` files that the watcher does not currently notice at
all. Third, this is the first phase where the thing on screen can be stale in a way that
*matters* — a ref list that lags a checkout is a cosmetic annoyance; a "Continue" button
enabled against a repository that no longer has unmerged paths is a failed spawn in the user's
face.

## The hard parts, settled before the work items

### §7.5's classification is a set intersection, and it is exact

§7.5 gives the algorithm in three lines and it is tempting to read it as an approximation of
what git will do — something to be refined later with a real merge simulation. It is not. It is
*exactly* what git does, and the probes below prove it in the one direction that would have
been the excuse for refining it.

```
D = paths git reports as locally modified, staged, or untracked
      (status --porcelain=v2 -z --untracked-files=normal)
T = paths the checkout will rewrite
      (git diff --name-only -z HEAD <target>)

D ∩ T = ∅   → clean carry.  git carries the local changes across. No prompt (§7.5).
D ∩ T ≠ ∅   → blocked.      Name the exact files.
```

The case that settles it is probe P1/CASE 2c: a locally modified file whose content is
**byte-identical to the target's version** — the one case where a content-aware predictor would
say "this carries fine" — is still refused by git, with the same "Your local changes … would be
overwritten" message. Git's index-based check is a *path* check with a dirty-bit, not a content
check. So a content-aware pre-flight would be more sophisticated, more expensive, and **wrong**:
it would tell the user a checkout will succeed and then watch it fail. The pure set
intersection is not the cheap approximation; it is the correct answer, and that is why §7.5's
engine takes two path lists and no object ids.

Two refinements the intersection needs, both from the probes and both invisible if you only
test the happy path:

- **The tracked and untracked halves are different sets and produce different copy.** An
  untracked local file at a path the target tree *adds* is `blockedByUntracked`, and git's own
  message for it ("The following untracked working tree files would be overwritten by
  checkout: … Please move or remove them") is the confusion §7.5 calls out by name. It is a
  different message and a different remedy from the tracked case; the classifier keeps them as
  two blocker kinds, not one list with a flag.
- **Ignored files are outside `D` by construction and git silently overwrites them.** With
  `--untracked-files=normal` an ignored file never appears in status, so it is never in `D`,
  so the intersection never sees it — and probe P5's ignored-file case confirms git overwrites
  it without a word. This is git's behaviour and P6 reproduces it rather than diverging; it is
  recorded here so a later reader does not mistake it for an oversight, and so nobody "fixes"
  it by passing `--untracked-files=all`, which would drag every ignored build artefact into `D`
  and block half the checkouts in a real repository.

### The fifth blocker §7.5 does not name

§7.5 lists four outcomes. A fifth exists and is exactly the question D12 says worktree badges
must answer:

> `fatal: 'feature2' is already used by worktree at '/tmp/kv-probe/d-wt'` (exit 128)

A branch checked out in a **linked worktree** cannot be checked out here, and cannot be
deleted, and no amount of stashing or discarding changes that. It is not a dirty-worktree
problem; it is a ref-ownership problem, and folding it into `blockedByTracked` would produce
a "commit or stash your changes" instruction that cannot possibly help. So `CheckoutBlocker`
carries a fifth member, `worktreeConflict`, naming the branch and the worktree path — which is
the same fact the branch list renders as D12's badge, from the same query. This is P6 adding a
case §7.5's four-item list does not enumerate rather than reinterpreting one it does; noted in
"Open questions" #8 so the divergence is recorded rather than discovered — and confirmed there by
the orchestrating session.

**Where the fact comes from, and why it costs nothing.** `git for-each-ref` has a
`%(worktreepath)` field. Adding it to `parse/refs.ts`'s format string gives, per branch, the
absolute path of the worktree that has it checked out — for free, inside the spawn the ref list
already makes. No `git worktree list`, no second process. One trap, from probe P6: the field is
also populated for the branch checked out in *this* worktree (`main HEAD=[*]
wt=[/tmp/kv-probe/i]`), so "checked out elsewhere" is `worktreepath !== <this session's
toplevel>`, not `worktreepath !== ""`. The session already knows its own toplevel — `discovery.ts`
resolved it at open.

### Where `merge-tree` belongs, and where it does not

D2 raises the git floor to 2.38 specifically for `merge-tree --write-tree`, and it is easy to
reach for it in the wrong place. Settled:

- **Checkout pre-flight does not use it.** Per the section above, the answer is a set
  intersection and a merge simulation would give a *different*, wrong answer.
- **Revert prediction does**, and it needs an option `parse/mergeTree.ts` does not currently
  emit. `mergeTreeArgs(base, other)` produces `merge-tree --write-tree --messages --name-only
  <base> <other>`, which makes git compute its own merge base. For a revert that is the wrong
  base: probe P2 showed the two-argument form reporting a revert **clean** that in fact
  conflicts, because git picked a merge base that made the inverse patch trivial. The correct
  invocation is

  ```
  git merge-tree --write-tree --messages --name-only --merge-base=<C> HEAD <C>^<mainline>
  ```

  — "merge, into HEAD, the tree of `C`'s mainline parent, treating `C` itself as the base",
  which *is* the inverse patch. The `<C>^<mainline>` spelling unifies the two cases §7.10
  separates: `<C>^1` for a non-merge (git's own default `-m` semantics) and `<C>^<N>` for a
  merge with mainline `N`. So `mergeTreeArgs` grows an optional `mergeBase`, and revert
  prediction is one spawn with no special-casing between merges and non-merges.
- **A multi-commit revert is predicted on the first commit only**, and the UI says so. §7.10's
  multi-revert is one invocation applying commits newest-first, and predicting the second
  requires the tree the first produces — a sequence of `merge-tree` calls chaining `--write-tree`
  outputs. That is real work with a real failure mode (the intermediate trees are not commits
  and cannot be `HEAD`), it is not asked for, and the honest thing is a prediction scoped to
  what it actually covers plus an explicit "later commits are not predicted" line. `--abort`
  remains the escape hatch, which is what §7.10's "all-or-nothing" rests on anyway.

### The in-progress state machine

§7.11's detection list is six state files plus status's `u` records. The probes turned it into a
machine with a precedence order, because more than one can be true at once.

| Detected | Kind | `--continue` | `--abort` | Notes |
|---|---|---|---|---|
| `rebase-merge/` or `rebase-apply/` | `rebase` | **no** (§9) | `git rebase --abort` | `rebase-merge/head-name` gives `refs/heads/<branch>`, `onto` the target sha |
| `MERGE_HEAD` | `merge` | `git merge --continue` | `git merge --abort` | |
| `CHERRY_PICK_HEAD` | `cherryPick` | `git cherry-pick --continue` | `git cherry-pick --abort` | |
| `REVERT_HEAD` | `revert` | `git revert --continue` | `git revert --abort` | |
| `BISECT_LOG` | `bisect` | **no** | `git bisect reset` | report-only, see below |
| none of the above, `u` records present | `unmergedOnly` | no | no | a resolved-then-reset state, or `git checkout -m`; the banner still names the files |

Precedence is top-down because a rebase that stops on a conflict *also* leaves the sequencer
files a cherry-pick would, and a rebase reported as a cherry-pick would offer a `--continue`
that fails. `AUTO_MERGE` is deliberately **not** in the list: probe P4 found it left behind
after an aborted cherry-pick, so it is a stale-artefact trap, not a state signal.

**Four facts the machine depends on, all verified:**

1. **`status --porcelain=v2` cannot be used to identify the operation.** During a rebase it
   reports `# branch.head (detached)` — the branch name is gone. The operation comes from the
   state files; status contributes only the unmerged paths and the "is it resolved yet"
   question.
2. **`git <op> --continue` launches an editor.** With no TTY it fails `rc=1` and *leaves the
   operation in progress* — "error: There was a problem with the editor 'editor'." §4.3's env
   hygiene list has `GIT_TERMINAL_PROMPT`, `GIT_OPTIONAL_LOCKS`, `GIT_PAGER` and `LC_ALL` but
   **not** `GIT_EDITOR`. With `GIT_EDITOR=true` the same continue commits cleanly, `rc=0`. This
   is a `buildGitEnv()` change (W6), not a per-call one: any op that can reach a commit-message
   editor gets it, and a driver that can hang waiting for an editor is a driver bug regardless
   of which subcommand triggers it.
3. **Continue's enablement is a status question, not a state-file question.** §7.11: "enabled
   only once `status` reports no unmerged paths", and "we watch `.git/index` and enable it the
   moment the user finishes resolving." The watcher already classifies `index` in the session's
   own `gitDir` as `worktreeChanged` — so the wiring exists; what does not exist is anything
   subscribing to it for status. W8 makes the banner's state a derived value that re-queries on
   `worktreeChanged`, which is why the banner does not need a poll or a second event.
4. **Rebase is report-only, and that is §9's instruction, not a shortcut.** §9 defers rebase to
   v2 and says v1 must "*report* a rebase in progress and refuse to interfere." So the banner
   names it, lists the unmerged paths, offers **Abort** (which is refusal-to-interfere's
   escape hatch, not participation) and Resolve-in-VS-Code, and does not offer Continue. Same
   for bisect, which has no conflict to resolve at all — it gets a name and `git bisect reset`.

**What "gates other operations" means, precisely.** §7.11 says mutating operations "that git
would refuse anyway" are disabled with the banner as the explanation. Probed: git refuses
`switch` during merge / cherry-pick / rebase (`fatal: cannot switch branch while merging`), and
would refuse reset and another revert. Git does **not** refuse branch-create or tag-create
during a revert — both succeed. So the gate covers exactly checkout, revert, and (later)
reset and stash-pop, and leaves branch/tag creation, renaming and every read alone. Gating more
than git does would be inventing a restriction and calling it safety.

### The undo slot, and its "visible omission" mechanism

§7.12 asks for an `UndoSlot` in `core` "populated by each op's executor, so adding a new
destructive operation without an undo entry is a visible omission rather than a silent one."
That last clause is a design instruction, not a description, and it is worth being literal
about it: the mechanism is a **total mapping from operation kind to undo policy**, so a new
`OpRequest` member fails to typecheck until someone states its policy.

```ts
type UndoPolicy =
  | { kind: "undoable"; capture(...): Promise<UndoRecord> }
  | { kind: "notUndoable"; reason: string };   // shown in the UI, not swallowed

const UNDO_POLICY: { readonly [K in OpRequest["kind"]]: UndoPolicy } = { … };
```

A mapped type over the union's discriminant. Add `op.reset` at P10 without an entry and
`tsc` fails. That is the whole trick, and it is why the slot lives in `core` beside the
operation model rather than in the executor.

**Two things the probes settled about what "recovery" means:**

- **A deleted branch's recovery is a sha *and* its upstream config.** `git branch -D feature`
  removes `branch.feature.remote` and `branch.feature.merge` along with the ref (probe P4).
  `git branch feature <sha>` restores the ref and *not* the tracking, so an undo that stops at
  the ref silently downgrades the branch. The capture reads `git config --get-regexp
  '^branch\.<name>\.'` before deleting and the undo replays it.
- **A deleted annotated tag's recovery is `update-ref`, not `git tag -a`.** The tag *object*
  survives `git tag -d` — probe P3 read it out of the odb afterwards with `cat-file -p`. So
  `git update-ref refs/tags/<name> <tagObjectSha>` restores it byte-identically, tagger and
  date and message intact. Re-creating it with `git tag -a -m` would forge a **new** object with
  a new tagger date, which is not "restoring a deleted annotated tag" and would fail the exit
  criterion honestly read. The tag-object sha must be captured from `for-each-ref` *before* the
  delete: git's own `Deleted tag 'ann-tag' (was 55a486d)` prints an abbreviated sha, and it
  prints the tag object for annotated tags and the commit for lightweight ones — two different
  things under one message.

Both P6 rows of §7.12's table are therefore "capture before, replay after", never "parse git's
output". Reset and stash-drop rows stay empty until P10 and P9, with `notUndoable` explicitly
absent rather than `notUndoable` asserted — they are simply not `OpRequest` members yet.

### One `op.run`, not eleven request keys

Every earlier phase added one contract key per operation because every earlier operation had a
distinct result. P6's eleven do not: §7's whole point is that they share a shape. So P6 adds a
single `op.run` request whose `params.op` is a discriminated union and whose result is one
`OpResult` carrying `{ok, error?, undo, head, inProgress}`.

Three reasons, in order of weight:

1. **The uniform result is the reconcile step.** Every op answers the same three post-conditions
   — where is HEAD now, is there an operation in progress now, what can be undone now — and
   returning them from the call closes the window between "the write finished" and "the watcher
   debounce fires", which is exactly the window in which a UI shows a stale branch name.
2. **`REQUEST_KEYS` stays legible.** Eleven keys now and ~eight more across P8–P10 turns a
   runtime set into a wall. A union member is the same type-safety with a tenth of the surface.
3. **It is where the write queue's serialization is visible.** One entry point, one queue, one
   place to assert "two concurrent ops do not interleave".

What it costs: the params union is less self-documenting than eleven named keys, and a reader
of `contract.ts` has to follow one indirection. Accepted, and mitigated by keeping *pre-flight*
as its own explicit keys (`preflight.checkout`, `preflight.revert`) — those genuinely have
different shapes and different results, and they are the half a reader looks up first.

### Write-queue discipline, TOCTOU, and what pre-flight guarantees

Pre-flight is a *read* and the operation is a *write*, and between them the user can edit a
file. This plan does not pretend otherwise:

> **Pre-flight is advice, not a lock.** The operation is issued regardless of what pre-flight
> said, and the typed error from a genuine failure is surfaced with git's own text. Pre-flight
> exists to explain a refusal *before* it happens and to make the safe cases silent, not to
> guarantee the unsafe ones cannot occur.

This matters for the shape of `op.run`'s error path: `DirtyWorktree` and
`UntrackedWouldBeOverwritten` are not "impossible" outcomes that indicate a pre-flight bug —
they are the race, and they render as the same blocked-checkout copy the dialog would have
shown, with the same remedies. It also means the executor never re-runs pre-flight server-side
"to be sure"; that would double the spawns and close nothing.

Ordering inside the driver is already correct and P6 relies on it rather than adding to it:
`driver.write()` serializes, bumps `#generation`, and fires `#invalidationListeners` **on
success**, and `RepoService`'s `#openSession` already subscribes `driver.onInvalidated` →
`#handleSignal(session, "refsChanged")`. So a successful op already invalidates the graph and
emits `repo.changed` with no new plumbing. The one gap: `onInvalidated` does not fire on a
*failed* write, and a failed write can still leave state (a conflicted revert leaves
`REVERT_HEAD`). W8 handles that by having the op executor re-read head + in-progress state after
every op, success or failure, and putting the answer in `OpResult` — which it needs for
reconciliation anyway.

## What the git probes settled

Nine behaviours this plan depends on, checked against real `git` (2.43.0 in this container;
above D2's 2.38 floor, so nothing below is version-contingent) rather than assumed. The
implementer should not re-derive these; they should extend them. Scripts are throwaway; the
facts are not.

**P1 — the §7.5 intersection is exact, including the case that would justify a smarter one.**
`T = git diff --name-only -z HEAD topic` → `added-on-topic.txt\0shared.txt\0`. Then:

| Case | Local state | Outcome |
|---|---|---|
| 1 | modify `untouched.txt` (∉ `T`) | `Switched to branch 'topic'`, rc 0, edit carried |
| 2 | modify `shared.txt` (∈ `T`) | `error: Your local changes to the following files would be overwritten by checkout:` rc 1 |
| 2b | **stage** a change to `shared.txt` | identical message, rc 1 — staged and unstaged are one set |
| 2c | make `shared.txt` **byte-identical to the target's version** | identical message, rc 1 |
| 3 | untracked `added-on-topic.txt` (∈ `T`, added by target) | `error: The following untracked working tree files would be overwritten by checkout:` rc 1 |
| 3b | untracked `scratch.txt` (∉ `T`) | rc 0, file survives |

2c is the load-bearing one: it rules out a content-aware pre-flight as *wrong*, not merely
expensive.

**P2 — revert prediction needs `--merge-base`.** `git merge-tree --write-tree --messages
--name-only HEAD <C>^` lets git choose a base and reports a conflicting revert as clean. With
`--merge-base=<C>` the same three-argument call returns the conflicting paths and exit 1. The
clean case returns a tree oid on line 0 and exit 0 — the shape `parseMergeTreeOutput` already
handles.

**P3 — the tag facts, all four of them.**
- `for-each-ref` with `%(objecttype)` discriminates annotated (`tag`) from lightweight
  (`commit`) in one pass. `%(contents:subject)` on a *lightweight* tag returns the **commit's**
  subject, so the discriminator must be `objecttype`, never "does it have a subject".
- `git tag -d ann-tag` prints `Deleted tag 'ann-tag' (was 55a486d)` — abbreviated, and the *tag
  object* sha, not the commit. The tag object is still in the odb afterwards (`cat-file -t` →
  `tag`).
- `git update-ref refs/tags/ann-tag <tagObjectSha>` restores it with its original tagger date
  and subject.
- **`git tag -f <name> <sha>` on an annotated tag silently downgrades it to lightweight**
  (`objecttype` goes `tag` → `commit`). So §7.9's "move it" for an annotated tag must re-supply
  `-a -m`, or it destroys the annotation while claiming to move the tag.
- `git tag <name>` on an existing name: `fatal: tag 'ann-tag' already exists`, rc 128.

**P4 — branch operations and their exact refusals.**

```
git branch feature          (exists)  → fatal: a branch named 'feature' already exists              128
git branch -d feature       (unmerged)→ error: the branch 'feature' is not fully merged.              1
git branch -D feature                 → Deleted branch feature (was d657c6e).            [stdout]     0
git branch -m feature2 main (exists)  → fatal: a branch named 'main' already exists                 128
git branch -D main          (current) → error: cannot delete branch 'main' used by worktree at '…'    1
git switch feature2         (in a wt) → fatal: 'feature2' is already used by worktree at '…'        128
```

Renaming the *current* branch succeeds and `HEAD` follows it. Deleting a branch also deletes
`branch.<name>.remote` and `branch.<name>.merge`. `git worktree list --porcelain` gives the same
worktree→branch mapping `%(worktreepath)` does, at the cost of an extra spawn — hence W4's
choice.

**P5 — the in-progress state files, and what each refuses.**

```
cherry-pick conflict → .git/{AUTO_MERGE, CHERRY_PICK_HEAD, MERGE_MSG}
                       git switch → fatal: cannot switch branch while cherry-picking
merge conflict       → .git/{AUTO_MERGE, MERGE_HEAD, MERGE_MSG}
                       git switch → fatal: cannot switch branch while merging
rebase conflict      → .git/rebase-merge/{head-name, onto, git-rebase-todo, stopped-sha, …}
                       git switch → fatal: cannot switch branch while rebasing
                       status v2  → # branch.head (detached)
revert --no-commit
  on a conflict      → .git/{REVERT_HEAD, MERGE_MSG}, u-record `u UD N…`, still rc 1
multi-commit revert  → .git/sequencer/{abort-safety, head, opts, todo}
```

Also: an **ignored** file whose path is in `T` is overwritten silently on checkout, and a
tracked file *deleted on the target* while locally modified is a plain `blockedByTracked`.

**P6 — `GIT_EDITOR=true`, `%(worktreepath)`, and the tag asymmetry.**

```
git merge --continue                       → error: There was a problem with the editor 'editor'.  rc 1
                                             (MERGE_HEAD still present — the op did NOT finish)
GIT_EDITOR=true git merge --continue       → [main ab753bc] Merge branch 'side'                    rc 0

git for-each-ref --format='…%(worktreepath)…' refs/heads
  refs/heads/main|commit|618e64b|…|*|/tmp/kv-probe/f
  refs/heads/side|commit|9c86379|…| |/tmp/kv-probe/f-wt          ← the linked worktree
git for-each-ref --sort=-v:refname refs/tags → v10, v9, lw, ann   (version-aware, as §7.9 asks)
```

And the asymmetry itself, run end to end against a local bare remote: with `lw` pushed, `git tag
-d lw` locally, then **`git fetch origin` prints `* [new tag] lw -> lw` and the tag is back.**
See "Open questions" #1: this is the opposite of what §7.9's sentence used to say, which has
since been corrected in the spec to match.
`git push origin --delete nosuchtag` → `error: unable to delete 'nosuchtag': remote ref does not
exist`.

**P7 — the DWIM checkout, and the error strings for classification.**

```
git switch topic          (only origin/topic exists) → Switched to a new branch 'topic'
                                                       branch 'topic' set up to track 'origin/topic'.
git switch --no-guess topic                          → fatal: invalid reference: topic
git switch --detach <bad sha>                        → fatal: reference is not a tree: <sha>
git branch -m nope nope2                             → fatal: no branch named 'nope'
git tag -d nope                                      → error: tag 'nope' not found.
git revert --no-edit <bad sha>                       → fatal: bad object <sha>
```

`git switch <name>` silently *creates a local branch* when only a remote-tracking ref matches.
That is a helpful default in a terminal and a bad one in a UI that just showed the user a list
labelled "remote branches" — the user asked to look at `origin/topic`, not to create `topic`.
So P6 passes `--no-guess` on every switch and offers branch-creation as its own explicit,
labelled action (W5, judgment call 3).

**P8 — which stream each failure is on, and one live misclassification.**

```
revert conflict     stdout: Auto-merging f.txt / CONFLICT (content): Merge conflict in f.txt
                    stderr: error: could not revert 6915287... c1
cherry-pick conflict stderr: error: could not apply 13110c3... cpx
push an existing,
diverged tag        stderr:  ! [rejected]        t1 -> t1 (already exists)
```

Two consequences for `errors.ts`. `classifyGitError`'s `Conflict` pattern is `/could not
apply|CONFLICT \(/` — revert says "could not **revert**", and the `CONFLICT (` half is on
*stdout*, which the classifier cannot see by design. So **a conflicting revert currently
classifies as `Unknown`.** And the `NonFastForward` pattern `/! \[rejected\]/` would claim the
tag-already-exists rejection, which is a different problem with a different remedy. Both are
W6.

**P9 — `--discard-changes`, and what it does not discard.**

```
git switch --discard-changes topic   (tracked block)   → Switched to branch 'topic'   rc 0
git switch --discard-changes topic   (untracked block) → error: Untracked working tree file
                                                          'added.txt' would be overwritten by
                                                          merge.                        rc 128
```

So §7.5's "discard" route is `git switch --discard-changes <target>` — one spawn, no
`checkout -f`, no manual `restore`. And it **cannot** clear an untracked block; note the
message differs from the plain checkout's ("by merge", singular, no path list header) and needs
its own classifier pattern.

### What P1 could not exercise, and why P6 is where it becomes wrong

Four defects, all P1's, all unreachable until now, all fixed in this phase's diff (the same
convention P4 used for P3's and P5 used for P1's):

1. **`classifyGitError` cannot see a conflicting revert** (probe P8). `Conflict`'s pattern
   matches "could not apply" but revert says "could not revert", and the `CONFLICT (` half is on
   stdout. The header comment already predicts this — "a known gap for whichever phase (P6+)
   first routes a real `git merge` through the driver". This is that phase.
2. **`NonFastForward` swallows a tag-already-exists rejection**, because `! [rejected]` matches
   first. A more specific pattern must be ordered before it.
3. **`buildGitEnv()` has no `GIT_EDITOR`**, so `git <op> --continue` — the button §7.11 requires
   — fails and leaves the operation in progress. §4.3's env list in the spec is updated in the
   same commit, per `AGENTS.md`'s "the spec stays the map".
4. **`watcher.ts` classifies neither `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, nor
   `sequencer/`**, and its `REF_ISH_NAMES` set is only consulted for paths under
   `commonDir` — but in a **linked worktree** these files live in the per-worktree `gitDir`
   (`.git/worktrees/<name>/`), where `classify()` recognises only `index`. So the banner would
   never appear in a linked worktree, which is precisely a case D12 says we support. W7.

## W1 — `core/src/model/{ref,tag,operation}.ts`

Pure types and pure functions, no I/O — `packages/core`'s standing rule.

**`ref.ts` grows two fields.** `checkedOutIn: string | undefined` and `annotation:
TagAnnotation | undefined`, matching the contract above. `RefRecord` keeps `objectId` as the
raw `%(objectname)` — for an annotated tag that is the *tag object*, and W3's undo depends on
it staying that way, so the field gets a comment saying so.

**`tag.ts` (already named in §3.1's tree, never written).** `TagAnnotation`, plus the two pure
predicates the rest of the phase leans on:

```ts
export function isAnnotated(ref: RefRecord): boolean;       // objectType === "tag"
export function tagTargetCommit(ref: RefRecord): string;    // peeledObjectId ?? objectId
```

Trivial, and worth naming rather than inlining: `peeledObjectId ?? objectId` appears in the
badge placement, the checkout target, the revert target and the tag list, and getting it
backwards on an annotated tag produces a checkout of a tag object, which git refuses with
`reference is not a tree`.

**`operation.ts` (new).** `InProgressKind`, `InProgressOperation`, `OpRequest`, `OpErrorKind`,
`OpResult` — the discriminated union the whole phase is typed against — plus one pure function:

```ts
export function classifyInProgress(input: {
  readonly stateFiles: InProgressStateFiles;   // what `ops/conflict.ts` read off disk
  readonly unmergedPaths: readonly string[];
}): InProgressOperation | null;
```

`InProgressStateFiles` is a plain record of booleans and captured strings (`mergeHead`,
`cherryPickHead`, `revertHead`, `bisectLog`, `rebaseMergeDir`, `rebaseApplyDir`,
`rebaseHeadName`, `rebaseOnto`, `sequencerDir`) — deliberately *data*, so the precedence table
in "The hard parts" is a pure function over it and gets a unit test per row, including the
rebase-shadows-sequencer case and the `unmergedOnly` fallthrough.

`canContinue` and `canAbort` are computed here, not in the UI: `canContinue` is false for
`rebase` (§9) and `bisect` always, and true otherwise **regardless of `unmergedCount`** — the
*enablement* is `canContinue && unmergedCount === 0`, and keeping the two facts separate is
what lets the banner say "resolve the remaining 2 files, then Continue" rather than hiding the
button.

**Done when:** `classifyInProgress` has a unit test per row of the precedence table plus the
two shadowing cases; `isAnnotated` / `tagTargetCommit` are used by W5 and W13 rather than
reimplemented; nothing in `core/src/model/` imports anything outside `core`.

```ts
export function classifyCheckout(input: {
  readonly target: { kind: RefKind | "sha"; name: string };
  readonly dirty: readonly DirtyPath[];      // from status: path + tracked/untracked
  readonly rewritten: readonly string[];     // T, from diff --name-only HEAD <target>
  readonly targetTreePaths: ReadonlySet<string> | null;  // see below
  readonly inProgress: InProgressOperation | null;
  readonly checkedOutIn: string | undefined; // D12, from the ref row
  readonly stashAvailable: boolean;          // false at P6; P9 flips it
}): CheckoutPreflight;
```

The body is the intersection, split by trackedness, plus the three non-path blockers. Two
details that are easy to get wrong and are therefore stated:

- **`targetTreePaths` is `null` at P6, and the untracked test uses `rewritten` alone.** §7.5's
  untracked clause is "untracked file in `T` **that exists in the target tree**". For a
  checkout, every path in `T = diff --name-only HEAD <target>` is either changed or added *by
  the target*, and a path an untracked local file can occupy is by construction one HEAD does
  not have — so "in `T`" and "in the target tree" coincide for untracked paths, and no
  `ls-tree` spawn is needed. The parameter exists so the test matrix can state the distinction
  explicitly and so a later phase with a different `T` (a stash pop, a reset) can supply it.
- **The blocker list is ordered and the order is asserted.** `inProgressOperation` first (it
  makes every other remedy moot), then `worktreeConflict`, then `blockedByUntracked`, then
  `blockedByTracked` — because the dialog renders the first blocker as its headline and the
  rest as detail, and an "in progress" repository that also has dirty files must not lead with
  "commit or stash your changes".

The test matrix, which is the point of the item: the six probe-P1 cases plus a clean tree, a
dirty-but-disjoint tree with *both* tracked and untracked members, both blocker kinds at once,
each of the three non-path blockers alone and in combination, a `sha` target (always
`detaches`), a tag target, a remote-branch target with and without a local counterpart, an
empty `T` (checkout of the current HEAD), and `stashAvailable` in both states asserting only
that `routes` changes.

**`revert.ts`** — `classifyRevert(...)`: dirty-tree blocker, the mainline requirement (one entry
per merge among `shas`, with every parent's sha and subject so the picker never re-queries),
the in-progress blocker, `detachedHead` as a note rather than a blocker (§7.10), and the
prediction folded in from whatever `merge-tree` returned. `verdict` is `blocked` if any blocker
holds, `willConflict` if the prediction found paths, else `clean`. Tested against: a non-merge,
a two-parent merge, an octopus merge (the parent list is 3+ and every entry is offered), a
merge with `mainline` already supplied, a dirty tree, an in-progress op, detached HEAD, and a
multi-sha request asserting `predictedFor === shas[0]`.

**`tag.ts`** — `classifyTagCreate(...)`: name validity (see below), existing-name detection with
the `-f` "move it" route, and — the one non-obvious rule, from probe P3 — **a `force` on an
existing *annotated* tag requires a message**, because `git tag -f <name> <sha>` without `-a -m`
silently downgrades it to lightweight. The verdict carries
`requiresAnnotationToPreserve: boolean` so the dialog can say why the message box is not
optional for that one case.

**Name validation is a pure prefilter, then a spawn.** §7.5 and §7.9 both say "validated with
`git check-ref-format --branch` before spawning". Probe P3 found a hazard: `git
check-ref-format --branch '@{-1}'` **exits 0** and prints `cp` — it *resolves* the `@{-N}`
shorthand rather than validating a literal name. So `core` rejects any name containing `@{`,
a leading `-`, or an empty string before the spawn is even proposed, and the spawn validates
the rest. (The probe also shows `check-ref-format refs/heads/HEAD` exits **0** while
`check-ref-format --branch HEAD` exits 128 — the `--branch` form is the correct one and the
spec already says so.)

**Done when:** every row of the matrices above is a named test; `bun test packages/core` covers
`preflight/` at every branch; no function in `preflight/` takes a driver, a service, or
anything async.

```ts

  | { readonly kind: "notUndoable"; readonly reason: string };

  branchDelete:    { kind: "undoable" },
  tagDelete:       { kind: "undoable" },
  checkout:        { kind: "notUndoable", reason: "switch back to the previous ref" },
  branchCreate:    { kind: "notUndoable", reason: "delete the branch" },
  branchRename:    { kind: "notUndoable", reason: "rename it back" },
  tagCreate:       { kind: "notUndoable", reason: "delete the tag" },

```

Every `notUndoable` reason is real user-facing text, not a placeholder, because §7.12's "we
never present an undo we cannot honour" is only honest if the alternative is *stated*. The UI
does not render these as disabled undo buttons; it renders nothing, and the reason is the
tooltip on the (cleared) undo affordance when the last op was one of these.

**The `bounded window`.** §7.12 says the affordance is "active for a bounded window after any
destructive operation". No duration is specified anywhere in the spec. This plan picks
**"until the next operation, until the repo closes, or until the recovery object is no longer
resolvable"** — the last being checked at `undo.run` time with `git cat-file -e <sha>^{commit}`,
which turns "bounded" into a fact about the repository rather than a timer the user cannot see
disappear. A wall-clock expiry would make a button vanish mid-sentence for no reason the user
can perceive. Raised as open question 6 rather than assumed to be what the spec meant, and
confirmed there.

**Done when:** adding a member to `OpRequest` without an `UNDO_POLICY` entry fails `bun run

idempotent-safe (a second call returns `null`); the slot lives on the session and dies with it.

## W8 — `RepoService`

The largest item, and the one that changes the service's character. Five additions:

**1. `refs(repoId)`** — two spawns (W4), parsed into `RefRow`s, with `checkedOutIn` computed as
`worktreepath === session.toplevel ? undefined : worktreepath || undefined`. Cached on the
session and dropped on `refsChanged`, alongside the `detailCache` that `#handleSignal` already
clears — the same policy P5 chose for detail, for the same reason (a ref's identity is stable;
its `track` and its `worktreepath` are not).

**2. `statusSummary(repoId)`** — `status()` (P1, unused until now) plus `ops/conflict.ts`'s state
files, folded through `classifyInProgress` and a new pure `summarizeStatus()` in
`core/src/model/status.ts`. `summarizeStatus` is where porcelain-v2's `u` records become counts
and paths, and it is worth stating that the seven `u` XY combinations git emits (`DD AU UD UA DU
AA UU`) all count as one unmerged path — the stage detail is already modelled by P1's
`UnmergedEntry` and P6 needs only the path list and the count.

**The `dirtyPaths` cap.** §7.5 requires naming the exact files; a repository mid-`node_modules`
can have tens of thousands. `dirtyPaths` is capped at **200** with `dirtyTruncated` set beyond
it, reusing `collectWithCap` (already in this file). The *intersection* is computed over the
full, uncapped set — capping the input would produce a wrong verdict, capping the display
produces a shorter dialog. That distinction is the whole reason the cap is here and not in the
parser.

**3. Pre-flight orchestration** — `preflightCheckout` and `preflightRevert`, each: gather the
reads in parallel, call the pure classifier, return. No decisions in the service; if a
conditional appears here that is not "which query do I need", it belongs in `core/src/preflight`.

**4. `runOp(repoId, op)`** — the executor. In order:

```
1. build argv           (ops/*, no policy)
2. capture undo         (UNDO_POLICY[op.kind] === "undoable" → read the sha + config FIRST)
3. driver.write(argv)   (serialized; bumps generation; fires onInvalidated on success)
4. read back            head + in-progress state, ALWAYS — success or failure
5. slot.set(record | null)   (null clears — §7.12)
6. return OpResult
```

Step 2 before step 3 is the entire correctness of undo: the sha must be read while the ref still
exists. Step 4 after *both* outcomes is what makes a conflicting revert — which fails with
`Conflict` and *leaves* `REVERT_HEAD` — produce an `OpResult` whose `inProgress` is populated,
so the banner appears from the operation's own reply rather than waiting on a watcher tick.

A `GitError` from step 3 is caught and mapped to `OpResult.error`, never rethrown: `op.run` is
the one request in the contract where a git failure is an expected outcome with a rendering,
not an exception. `GitCancelled` and `GitSpawnFailed` keep propagating, as everywhere else.

**5. `undoSlot`** — one `UndoSlot` per session, `undo.peek` reads it, `undo.run` takes the
record, validates the recovery object still resolves (`cat-file -e <sha>^{commit}`), replays
the argv list through `driver.write` in order, and returns an `OpResult` whose `undo` is `null`.

`RepoServicePort` in `rpcHandlers.ts` gains all five names.

**Done when:** `repoService.test.ts` covers the executor's ordering with a fake driver
(capture-before-write asserted by argv order); a failing write still returns a populated `head`
and `inProgress`; a non-undoable op clears a previously-set slot; the ref cache drops on
`refsChanged`; `dirtyPaths` truncates while the verdict does not.

## W12 — `ui/src/state/{refs,ops}.ts`

The renderer's half of §7's four-step shape, in two modules so the *data* and the *verbs* do not
share a file.

**`refs.ts`** — the ref list as reactive state: loads on repo open, reloads on `repo.changed`
with `kind === "refsChanged"`, exposes `branches` / `remoteBranches` / `tags` / `head`, and
derives the three things more than one component needs: the current branch's short name (for the
picker's button), a `Map<sha, RefRow[]>` for badge enrichment, and the set of branches with
`checkedOutIn` (D12's badge).

**`ops.ts`** — one exported function per user-facing action, each following the same four steps
so no component ever writes them out of order:

```
runCheckout(target, mode):
  1. preflight.checkout        → CheckoutPreflight
  2. if verdict !== "clean"    → open the dialog, await a route (or cancel)
  3. op.run                    → OpResult
  4. announce; refresh status; refresh refs; surface undo
```

Step 4's "refresh" is belt-and-braces on top of `repo.changed`: the event will arrive, but the
`OpResult` already carries `head` and `inProgress`, so the state applies those synchronously and
lets the event reconcile the rest. This is what keeps the toolbar from showing the old branch
name for the length of the watcher's debounce.

`ops.ts` also owns the **busy** flag and the **gate**: one in-flight operation at a time (the
driver serializes anyway; the UI must not offer a second), and `canRun(opKind)` returning false
with the banner's reason when `inProgress` is set and the op is one of the gated ones (checkout,
revert — see "The hard parts").

Every announcement goes through `liveAnnouncements.ts`, per P4's one-live-region rule, and every
outcome — including a failure — is announced. A destructive operation that silently does nothing
is the failure mode §6.4 already called out for the clipboard.

**Done when:** no `.vue` file calls `bridge.request("op.run", …)` directly; the four steps exist

## W15 — `dialogs/{CheckoutDialog,TagDialog,RevertDialog}.vue`

## W16 — `ConflictBanner.vue` and the gate

§7.11's "make it impossible to miss". A persistent banner across the top of the panel, above the
graph, present whenever `statusSummary.inProgress !== null`.

**Contents:** the operation named in the user's terms ("Reverting `abc1234`", "Rebasing `side`
onto `main`" from `headName`/`onto`, "Merging"), the unmerged path list, and up to three
actions:

| Action | Shown when | Enabled when |
|---|---|---|
| **Resolve in VS Code** | `capabilities.resolveConflict` | `unmergedCount > 0` |
| **Continue** | `inProgress.canContinue` | `unmergedCount === 0` |
| **Abort** | `inProgress.canAbort` | always (§7.11) |

Continue disabled-but-visible with "resolve the remaining N files first" is the point of keeping
`canContinue` and `unmergedCount` as separate facts (W1): the button is the affordance that
tells the user what finishing looks like. It re-enables on `worktreeChanged` — the watcher
already signals on `index`, which is exactly what `git add` touches, which is §7.11's "we watch
`.git/index` and enable it the moment the user finishes resolving."

**The gate.** `ops.ts`'s `canRun` (W12) returns false for checkout and revert while
`inProgress` is set, and the disabled control's tooltip is the banner's own sentence. Branch and
tag creation, renaming, the ref list, the graph and every read stay live — git allows them, and
§7.11's gate is scoped to "operations that git would refuse anyway".

**What P6 does *not* build of §7.11's fallback.** The paragraph describing a host without a
merge editor lists four things: Abort, Continue, `ExternalOpener`, and "a read-only view of the
conflict hunks". P6 builds the first two (they are host-independent) and neither of the last
two: `ExternalOpener` is not in `core/src/ports/` and has no v1 consumer until P12 (P5's plan
made the same call for the same reason), and the read-only hunk view is a diff-view variant with
no §10 exit criterion. Both are deferred by open question 3 rather than half-built. Under VS Code —
the only host v1 ships — `resolveConflict` is always true, so the fallback state is reachable
only in the harness, where it is a *tested* state showing Continue, Abort and the path list.

**Done when:** the banner appears for each of the five in-progress kinds against real
repositories (W21); a rebase shows no Continue and says why; Continue enables without a manual
refresh when the last conflict is staged in another window; Abort returns the repository to a
clean state and the banner disappears; the banner is announced by the live region on appearance;
gated controls are disabled with the reason, never hidden.

## W17 — The undo affordance

§7.12: a single-level **Undo last operation** in the toolbar, labelled with what it will undo,
with the recovery sha shown alongside.

Present only when `undo.peek()` returns a record. Label is the record's own (`Undo delete of
branch feature`), the recovery sha renders beside it as monospace text that is itself a copy
target (reusing P5's `clipboardActions.ts`), and the tooltip carries §7.12's honesty clause —
one level, does not restore uncommitted work.

Clicking runs `undo.run`, which replays the captured argv and clears the slot. A record whose

**Done when:** deleting a branch offers undo and restoring it restores the ref **and** its

tagger date and message are byte-identical to the original (asserted by comparing `cat-file -p`
before and after, not by comparing the ref); performing any second operation clears the slot;
no non-undoable operation ever renders the affordance.

## Judgment calls this plan made

1. **One `op.run` with a discriminated union, not eleven request keys.** Argued in full above:
   the uniform `OpResult` *is* the reconcile step, `REQUEST_KEYS` stays legible, and P8–P10 add
   union members instead of contract surface. Pre-flight keeps separate keys because those
   genuinely differ.
2. **§7.5's stash-and-carry route is absent at P6, not stubbed.** Stash is P9's whole row, and
   §7.5's route requires §7.6's pop *prediction* first — building a stash to satisfy a
   checkout dialog would drag most of P9 into P6. The dialog names it as a route that arrives
   later; `CheckoutPreflight.routes` is the seam, so P9's change is one array entry and one
   dialog branch. `AGENTS.md`'s "scope left out of a phase is left out entirely" applies to the
   mechanism, not to telling the user it exists.
3. **`--no-guess` on every switch, with branch creation as an explicit action.** Probe P7:
   `git switch topic` silently creates a local branch when only `origin/topic` exists. In a
   terminal that is a convenience; in a UI that just rendered a list headed "Remote branches" it
   is the app creating a ref the user did not ask for. `--no-guess` makes the DWIM impossible,
   and `CheckoutPreflight.createsTracking` turns it into a labelled choice.
4. **Blocked-by-untracked offers no discard route.** `git switch --discard-changes` refuses it
   (probe P9), so "discard" would mean *we* delete the user's untracked files — a destructive act
   with no git command behind it and no undo. The dialog names the files and states git's own
   remedy.
5. **Tags live as a section inside the branch picker, not as a second toolbar dropdown.** §6.2's
   toolbar has one `[branch ▾]` slot; §7.9 wants a dedicated tags list "alongside the branch
   list"; §6.3 says the panel is often under 600px. One dropdown with three sections satisfies
   all three. `TagList.vue` remains a real component with its own filter and actions.
6. **P6's confirmations are in-webview dialogs, not the `Dialogs` port.** §7's confirm step could
   route through `window.showWarningMessage`, and the port exists. But `CheckoutDialog` renders a
   *structured* pre-flight — file lists, routes, a mainline picker with subjects — that a native
   modal cannot show, and splitting confirmations between two surfaces by complexity would be
   worse than picking one. `Dialogs` keeps its single `pickFolder` method and P6 adds nothing to
   it. This also keeps every P6 surface reachable in the harness tier.
7. **Rebase and bisect get report-only banners.** §9's "v1 can *report* a rebase in progress and
   refuse to interfere" is the instruction. Abort is offered because refusing to interfere and
   trapping the user are different things.
8. **Revert prediction is scoped to the first commit and says so.** Chaining `merge-tree`
   `--write-tree` outputs across a multi-commit revert is real work with a real failure mode,
   is not asked for, and `--abort` already delivers the all-or-nothing guarantee §7.10 names.
9. **No `op.progress` stream at P6.** Every P6 operation is one local spawn; the one that can
   block is the narrow edge of a family P8 owns. Designing cancellation semantics blind, a phase
   early, is how a contract acquires a shape nobody wants.
10. **`ExternalOpener` is still not added.** §7.11's fallback names it, but it has one real v1
    consumer (§6.7's PR badge, P12) and the fallback path is unreachable under the only host v1
    ships. P5 made the same call; this plan keeps it, and open question 3 confirmed it.
11. **No new perf budget.** §5.1 names none for this surface, and inventing one would make a
    number authoritative that no one agreed to. A recorded Finding plus a spawn-count invariant
    is the honest version.

## Open questions for the orchestrating session — **all eight resolved**

Raised here rather than resolved by editing the spec. The orchestrating session has now ruled on
every one; each resolution is recorded inline below, and the two it turned into spec corrections
were made in the commit that recorded them. Nothing in this section is still open — the
implementer takes it as settled context, not as a decision to make.

1. **§7.9's tag-asymmetry sentence is backwards.** It said: *"Deleting a tag that exists on a
   remote warns that a `fetch` will not bring it back unless the remote copy is also deleted."*
   Probe P6, run end to end against a real remote: after `git tag -d lw`, a plain `git fetch
   origin` prints `* [new tag] lw -> lw` and **the tag is back**. That is the opposite. The
   asymmetry that actually makes tag deletion confusing is the *other* one — deleting locally
   does **not** delete on the remote, so the tag returns on the next fetch, and only
   `git push <remote> --delete` removes it for good. That reading also matches the same
   paragraph's next clause ("deleting locally must never silently touch the remote").

   **Resolved: the spec was wrong and the probe is right.** §7.9's sentence has been corrected
   to match observed behaviour. P6's warning copy — already written to reality — stands
   unchanged, and W15's `TagDialog` and W21's integration assertion both target the corrected
   reading: *deleting locally does not touch the remote; the next fetch brings it back; only
   `git push <remote> --delete <name>` removes it for good.*

2. **Cherry-pick belongs to no phase.** §7.13 lists it as a v1 operation, §6.4 puts it in the row
   context menu beside revert, and §10 gives it no row — P6's row does not name it and neither
   does any later one.

   **Resolved: cherry-pick is NOT added to P6.** It stays omitted exactly as this plan already
   specifies — no menu entry, no disabled placeholder, no `OpRequest` member, and no expansion of
   W5, W9 or W14 to accommodate it. P6 is already large and cherry-pick appears nowhere in its
   §10 exit criteria; `AGENTS.md`'s "scope left out of a phase is left out entirely" applies.

   It therefore **remains an unassigned gap in §10's phasing table** — a v1 operation (§7.13) and
   a menu entry (§6.4) that no phase row owns. Whoever plans the phase that picks it up should
   know it is cheap *given P6*: it shares revert's sequencer, this phase's conflict banner, the
   same `--continue`/`--abort`, the same `ops/conflict.ts` state reader and the same `OpResult`
   shape, so it is plausibly half a work item wherever it lands — most naturally alongside
   revert/reset work. **This plan deliberately does not assign it a phase number**; that is the
   call of whoever plans that later phase, and §10's table is left untouched so the gap stays
   visible rather than being quietly closed here.

3. **§7.11's fallback names two things with no phase and no consumer.** `ExternalOpener` ("open
   the conflicted file in the system default editor") is not in `core/src/ports/` and its only
   real v1 consumer is P12's; "a read-only view of the conflict hunks" is a diff-view variant
   with no §10 exit criterion. Under VS Code — the only v1 host — `resolveConflict` is always
   true and neither is reachable.

   **Resolved: defer both, no change.** This is the same call P5 made about `ExternalOpener` for
   the same reason (no v1 consumer, unreachable under the only host v1 ships). P6 builds neither
   and renders the reachable half of the fallback — Continue, Abort, the unmerged path list — as
   a tested harness state via `noCapabilities`. Judgment call 10 stands. No spec edit.

4. **§6.5/§6.6's "every mutating action is palette-reachable" has no phase row.** P13's row named
   the SCM title button and the status bar item; nothing named the `kiraVersion.*` commands, and
   today only `kiraVersion.focusGraph` is contributed. P6 is the first phase with mutating
   actions and therefore the first where the requirement can be violated.

   **Resolved: it belongs to P13 (Ship)**, as a final audit wiring a command for every mutating
   operation introduced across P6–P10 — the natural home, since P13 already owns §6.5's other two
   integration points. §10's P13 row and its exit criteria have been extended to say so.
   **P6 builds no parallel host-side quick-pick surface**, exactly as the scope boundary states:
   a second input path with its own dialogs is not in P6's row, and a palette entry that merely
   focuses the panel is the half-implementation `AGENTS.md` forbids.

5. **§7.9 mentions signed tags (`-s` when `tag.gpgSign`) and tag signature verification "under
   the same D20 rule"; neither appears in §10's P6 exit criteria.**

   **Resolved: deferred, no phase assigned, and left out entirely.** Cheap is not the test —
   presence in the row is, per `AGENTS.md`. P6 implements neither: `TagDialog` offers lightweight
   and annotated only, and no tag signature is read or rendered. No spec edit.

6. **§7.12's "bounded window" has no bound anywhere in the spec.**

   **Resolved: W3's interpretation is correct** — the slot lives until the next operation, until
   the repo closes, or until the recovery object no longer resolves (checked at `undo.run` time
   with `cat-file -e <sha>^{commit}`), and **not** on a wall-clock timer. A button that vanishes

## Findings

_Recorded during implementation. V1–V6 outcomes, and any decision made at the keyboard that this
plan did not anticipate — later phases read this section as part of the context they inherit._

### V1 — pre-flight agreement beyond the hand-built probe fixture

Extended to a symlink, a path containing a space, and a submodule, each in `D` and in `T`
(`tests/integration/checkoutSpecialPaths.test.ts`):

- **Symlink and space-path: agree.** Both are just strings to `status --porcelain=v2 -z` /
  `diff --name-only -z`; the classifier's plain set-intersection treats them exactly like any
  other tracked path, and the real `git switch` refuses each with `DirtyWorktree` exactly as
  predicted.
- **Submodule: disagrees, and the disagreement is real, not hypothetical.** A submodule whose
  locally checked-out commit has drifted from HEAD's recorded pointer is reported dirty by
  `status --porcelain`, and its path is in `T` whenever the target commit also moves the
  pointer — so the classifier predicts `blockedByTracked`. But `git switch` never touches a
  submodule's own checkout by default (that needs a separate `git submodule update`); it only
  rewrites the outer repo's recorded gitlink, so the real switch always succeeds and leaves the
  submodule exactly where the user had it, even when its checked-out commit genuinely differs
  from both the pre- and post-switch pointer. This is **over-blocking, never data-losing** — the
  worst case is a false "blocked" badge on a switch that would actually have succeeded — so it is
  recorded as a known limitation of the file-path-only classifier rather than fixed. P6 does not
  otherwise special-case submodules anywhere in its scope, and reworking the classifier to
  exclude gitlink paths (or check submodule state separately) is left for whichever later phase
  first needs submodule-aware checkout.

### V2 — `%(worktreepath)` on a prunable linked worktree

Confirmed at the keyboard: creating a worktree, then deleting its directory on disk directly
(never calling `git worktree remove`/`prune`), leaves `for-each-ref`'s `%(worktreepath)` reporting
the now-nonexistent path unchanged — it does not self-heal or go blank. `git worktree list
--porcelain` is the only place git itself surfaces the distinction, via a `prunable` line
(`"prunable gitdir file points to non-existent location"`); `for-each-ref` has no equivalent
signal. Critically, this is **not a functional bug**: a real `git branch -D` and a real `git
switch` against that branch both still refuse exactly as the badge predicts (`used by worktree
at '<stale path>'`), because git's own refusal is keyed off the *registration*, not the
directory's existence. The only gap is cosmetic — the badge would name a path that no longer
exists on disk, which could read as stale/confusing to a user who already deleted that worktree
by hand. Recorded as a caveat for whichever phase first adds worktree-management UI (an
`existsSync` check or a "prune" affordance would resolve it); P6 itself only reports, and its
report is accurate.

### V3 — Continue-enables-on-`index` via VS Code's own merge editor

Not independently verifiable in this environment: this is explicitly the one part of §7.11 that
depends on a host behaviour (VS Code's merge editor writing a resolved index) rather than on
anything this codebase controls, and confirming it end to end requires the `vscode` Playwright
tier driving a real VS Code host — out of reach for a harness-only, headless agent session. The
underlying mechanism (`status` reporting no unmerged paths enables Continue, independent of *how*
the index got there) is unit- and integration-tested via a hand-`git add`'d resolution in
`revertLifecycle.test.ts`; only the "VS Code's own editor did the resolving" half of V3 is
unverified here.

### V4 — `git tag -f -a -m` on an existing annotated tag

Verified (`tests/integration/tagAndBranchOps.test.ts`): forcing a move with `-a -m` preserves
`objecttype === "tag"` and lands the new message; `cat-file -p`/`for-each-ref` before and after
confirm the old message is gone, not silently kept.

### V5 — a conflicting revert's stderr on a non-English locale

Verified by code review rather than by an empirical non-English run: `buildGitEnv()`
(`packages/git/src/driver.ts`) copies `process.env` first and sets `env.LC_ALL = "C"`
**unconditionally, last** — nothing inherited from the host (`LANG`, `LC_MESSAGES`, etc.) can
survive that assignment, so every spawn this driver makes is forced to `C` regardless of the
host's own locale. An empirical end-to-end re-check (spawning git under a real non-English locale
and confirming the classifier still matches) was attempted but is not possible in this sandbox:
`locale -a` here lists only `C`, `C.utf8` and `POSIX` — no non-English locale is installed for
git's own gettext fallback to even attempt translating into. Recorded as: verified by reading the
one line that decides it, not re-confirmed empirically, because this environment cannot host the
attempt.

### V6 — `driver.write()` under two rapid, unawaited ops

Verified with a real test (`tagAndBranchOps.test.ts`): a `branchCreate` immediately followed by a
`branchDelete` of the same branch, neither awaited before the next is issued (the literal
"double-click Checkout" shape), only resolves both `ok: true` if the delete's write started after
the create's had fully completed — including `RepoService`'s own post-write read-back — which is
only possible because `driver.ts`'s `#writeQueue` is a strict FIFO array drained one entry at a
time by `#pumpWriteQueue()` (`#writeInFlight` blocks a second spawn from starting until
`#runWrite`'s `finally` clears it). The second op sees the first's real, completed result; nothing
about correctness here rests on the UI's own busy flag, though the UI still uses one for
responsiveness.

### Perf — `refs.list` wall time on `largeBranchy`

Measured directly (not asserted as a budget, per this plan's own reasoning): `refs.list` against
`largeBranchy(20000, { branchCount: 12 })` (13 total refs, 20,000 commits across 12 concurrent
branches) — 5 fresh-session runs: **3.8ms–8.6ms**, no trend with repeated runs. This is
consistent with `refs.list` being two spawns of `for-each-ref`/`branch --show-current` that scale
with *ref count* (13 here), not commit count (20,000) — the one invariant this plan does assert
(`tagAndBranchOps.test.ts`'s 30-extra-branches-and-tags test) confirms spawn count stays at
exactly two regardless of ref count; this wall-time number is the companion data point P7/P8
inherit when they add more to that same list.
