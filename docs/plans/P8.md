# P8 — Remote ops

**Goal (§10):** Fetch (incl. opt-in background auto-fetch, default off), push, decomposed pull with
strategy selection, force-push with lease + `--force-if-includes`, protected branches, askpass path,
progress + typed auth errors.

**Exit criteria (§10):** Integration tests against a local bare remote incl. non-ff rejection, lease
violation, hook rejection; no operation can hang on a prompt.

P8 is the first phase where the extension talks to a machine it does not control. Every prior phase's
git invocation was local, bounded, and either succeeded or failed in milliseconds; P6's whole
operation model is built on that assumption (one spawn, one result, an undo slot set on the way out).
A fetch over a slow link takes ninety seconds, can be cancelled, reports progress, may ask for a
password, and — if it asks for a password with nowhere to answer — hangs forever. That last case is
the one the exit criteria single out, and it is the reason this phase gets its own request key rather
than a fifth arm on `op.run`.

This plan is grounded in a set of live `git` probes (§"What the git probes settled" below), run
against git 2.43.0 with a real bare remote, a real pre-receive hook, and a real HTTP 401. Two of them
contradict the spec text this phase is supposed to implement. Both contradictions are surfaced as
open questions with recommendations rather than quietly implemented one way or the other.

## What the git probes settled

Run against git 2.43.0, in `scratchpad/p8`, with a real bare remote, a real `pre-receive` hook, and a
real HTTP 401 server. Following P6's precedent: claims below are observed, not assumed.

**1. `--force-with-lease=<ref>:<sha>` makes `--force-if-includes` a no-op.** This is the headline
finding and it contradicts §7.4.

| Invocation | Remote state | Result |
| --- | --- | --- |
| `push --force-with-lease=main:<stale-sha>` | moved | `! [rejected] main -> main (stale info)`, rc=1 |
| `push --force-with-lease --force-if-includes` (never fetched) | moved | `! [rejected] main -> main (stale info)`, rc=1 |
| `push --force-with-lease --force-if-includes` (fetched, **not** integrated) | moved | `! [rejected] main -> main (remote ref updated since checkout)` + hint, rc=1 |
| `push --force-with-lease=main:<correct-sha> --force-if-includes` (fetched, not integrated) | moved | `+ 3a55c77...d462520 main -> main (forced update)`, **rc=0** |
| control: same without `--force-if-includes` | moved | identical, rc=0 |

The last two rows are the proof. Supplying an explicit expect value satisfies the lease directly, and
`--force-if-includes` — which is defined as an *augmentation of the implicit lease*, checking that the
remote-tracking ref's tip is reachable from the reflog of the branch being pushed — has nothing left
to augment. The two protections are mutually exclusive in effect, and they guard different hazards:
the bare lease catches "someone else pushed and I never saw it"; `--force-if-includes` catches
"someone else pushed, I *did* fetch it, and I am about to overwrite it anyway". §7.4's stated
rationale for the explicit sha is that a background fetch could silently satisfy the lease — which is
*precisely* the hazard `--force-if-includes` was invented to close. §7.4 asks for both and gets one.
See **OQ4** and **D48**.

**2. `--prune-tags` deletes local-only tags.** `git fetch --prune --prune-tags origin` on a clone
carrying a tag that exists only locally printed `- [deleted] (none) -> localonly` and removed it.
§7.1 specifies `git fetch --prune --prune-tags <remote|--all>` as the fetch command line. Against
§1.1 ("never lose user work") that is a footgun in the default path: a locally-created tag not yet
pushed is user work, and `--prune-tags` is not undoable (§7.12 says fetch never offers undo). See
**OQ2** and **D49**.

**3. Non-ff push, verbatim.** `! [rejected]        main -> main (fetch first)`, plus
`error: failed to push some refs to ...` and the `hint:` block, rc=1. The existing `NonFastForward`
pattern matches.

**4. Hook rejection, verbatim.** With a `pre-receive` hook exiting 1:
```
remote: <the hook's own stderr, one line per `remote: ` prefix>
! [remote rejected] main -> main (pre-receive hook declined)
```
rc=1. The existing `HookRejected` pattern (`/hook declined/`) matches, and — importantly — is ordered
before `NonFastForward`, whose `! \[rejected\]` alternative would otherwise also fire on
`! [remote rejected]`. **The hook's own message is on `remote: `-prefixed lines and is the only thing
the user actually needs to see.** W11 extracts it.

**5. Push progress framing (stderr, `--progress`).**
```
Enumerating objects: 5, done.
Counting objects:  20% (1/5)\rCounting objects:  40% (2/5)\r...
Writing objects: 100% (3/3), 217 bytes | 217.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0
```
Within a phase, updates are **CR-separated**; a phase ends with LF. Percentages are `NN% (n/N)`.

**6. Fetch progress framing (stderr, `--progress`).** Server-side phases arrive `remote: `-prefixed;
local phases do not:
```
remote: Enumerating objects: 91, done.
remote: Counting objects:  31% (29/91)\r...
remote: Compressing objects: 100% (88/88), done.
Receiving objects: 100% (89/89), 3.42 MiB | 12.10 MiB/s, done.
Resolving deltas: 100% (74/74), completed with 1 local object.
From /path/to/rem
   d876420..b5c3142  main       -> origin/main
```
Same CR-within-phase / LF-at-phase-end framing. A trivially small fetch over local transport emits
*no* progress at all — the parser must treat "no progress lines" as normal, not as a stall.

**7. `GIT_ASKPASS` is honoured even with `GIT_TERMINAL_PROMPT=0`.** Called with exactly one argv,
the prompt text (`Username for 'https://example.invalid': `, then
`Password for 'https://alice@example.invalid': `); the answer is read from the helper's **stdout**.

**8. The three askpass failure shapes, all fail-fast.** Against a real 401, detached (no tty),
`GIT_TERMINAL_PROMPT=0`, `credential.helper=` (disabled):

| Case | stderr | rc |
| --- | --- | --- |
| No askpass at all | `fatal: could not read Username for 'http://…': terminal prompts disabled` | 128 |
| Askpass exits non-zero | `error: unable to read askpass response from '<path>'` then `fatal: could not read Username …: terminal prompts disabled` | 128 |
| Askpass answers, credentials wrong | `fatal: Authentication failed for 'http://…/repo.git/'` | 128 |

The middle row is the mechanism that makes "no operation can hang on a prompt" true by construction
rather than by timeout luck: **if our askpass broker decides not to answer — because the user
dismissed the prompt, or because the broker's own timer expired — it exits non-zero, git does not
retry or block, it falls straight through to the disabled terminal and dies.** All three shapes are
already matched by the existing `AuthFailed` pattern.

## The hard parts, settled before the work items

### 1. Where remote ops live in the contract: a new `remote.run`, not a fifth arm of `op.run`

P6's D-decision for `op.run` was "one key, not eleven", and extending its discriminated union is the
obvious move. It is the wrong one, for four reasons that are each individually sufficient:

1. **`runOp` sets the undo slot unconditionally.** `session.undo.set(record)` runs on every path, with
   `record === null` for non-undoable operations. §7.12 says push/force-push/fetch never offer undo —
   fine — but it *also* says "performing another operation clears the undo slot". Route a **background
   auto-fetch** through `runOp` and every auto-fetch tick silently destroys the user's undo slot for a
   commit they made two minutes ago. That is a §1.1 violation caused entirely by plumbing.
2. **Remote ops need progress correlated before the response exists.** `op.run`'s handler returns one
   `OpResult`; there is no id the UI could match progress events against until it comes back.
3. **Remote ops need explicit cancellation with a known post-state.** rpc's `cancel` frame is
   fire-and-forget: the client deletes the pending entry and rejects locally, and a late response is
   dropped. For a local checkout that is fine. For a fetch, the UI must learn *whether the fetch got
   far enough to move refs* — silently dropping the answer is the one thing it cannot do.
4. **The result shape differs.** A remote op's outcome includes which refs moved, whether an upstream
   was set, and (for pull) which strategy actually ran. `OpResult` has nowhere to put that.

So: **`remote.run`** (one key, five kinds — `fetch`, `push`, `pull`, `forcePush`, `deleteRemoteBranch`)
plus **`remote.cancel`**, and a **`remote.progress`** event. One new request key for five operations
still respects P6's "keep `REQUEST_KEYS` legible"; five keys would not. The `opId` is generated
**UI-side** and passed *in*, so progress can be correlated from the first byte. See **D51**.

`remote.run`'s result reuses `OpResult`'s reconcile discipline — it returns `head` and `inProgress`
exactly as `op.run` does, so `#applyResult` in `packages/ui/src/state/ops.ts` keeps working unchanged
and a conflicting pull lands in P6's existing banner — but it returns them inside a
`RemoteOpResult` that adds the remote-specific fields and, critically, **never carries an `undo`**.

### 2. Progress plumbing: a tee, not a second read path

`SpawnedProcess.stderr: Promise<Uint8Array>` is "Always collected, bounded" and `classifyGitError`
depends on that buffer existing at exit. Progress must not replace it.

W1 adds an **optional `onStderr?: (chunk: Uint8Array) => void` to `SpawnRequest`**, called from
`nodeProcessRunner`'s existing `collectStderr()` loop for each chunk *before* it is appended to the
buffer. Nothing else changes: the promise still resolves with the complete bounded buffer, the fake
runner in `testFakes.ts` gains a way to emit synthetic chunks, and every existing caller that passes
no callback is byte-for-byte unaffected. This is the minimum port change that makes progress possible
and it does not create a second, divergent way to read stderr.

The parser (`packages/git/src/progress.ts`, W3) is a small stateful decoder: it accumulates bytes,
splits on `\r` **and** `\n`, strips a leading `remote: `, and matches
`/^(.+?):\s+(\d+)% \((\d+)\/(\d+)\)/` for a phase with a percentage and
`/^(.+?):\s+(\d+), done\.$/` for a counted phase without one. Anything it does not recognise is
**dropped from progress but still lands in the error buffer** — an unrecognised line is not an error,
just not progress. It is a pure function of a byte stream to a sequence of `{phase, done, total}`,
which makes it unit-testable against the exact captured transcripts in the probes above with no
process at all.

**Throttling is host-side, at ~1 event per 100 ms per op, and always emits the final state of a
phase.** `Counting objects` alone produced 91 CR-separated updates on a 90-commit fetch; a real clone
produces thousands. Throttling in the UI would mean the frames were already built, serialized and
posted.

### 3. Cancellation: which operations may be killed, and which may not

§4.3: "a write that has already started is never killed." That rule exists because killing a local
write can leave `index.lock`, a half-written ref, or a partial sequencer state. P8 amends it, but
only exactly as far as the reasoning supports:

| Operation | Cancellable mid-flight? | Why |
| --- | --- | --- |
| `fetch` | **Yes** | A killed fetch leaves objects in the object store (garbage, collected later) and moves no ref the user sees. There is no lock and no half-state. |
| `pull` — fetch phase | **Yes** | Same as fetch. |
| `pull` — merge/rebase phase | **No** | This is a local write with every hazard §4.3 names. |
| `push` | **No** | The remote may have already accepted the push. A cancelled push has an **unknowable** outcome, and reporting "cancelled" when the remote's refs moved is worse than making the user wait. |
| `forcePush` | **No** | Same, and the stakes are higher. |
| `deleteRemoteBranch` | **No** | Same. |

So the driver gains **`writeStreaming()`** (W2): it goes through the *same* write queue, takes an
`onStderr` tee, and takes an explicit `killable: boolean`. When `killable` is false the signal only
prevents a *queued* op from starting, exactly as `write()` does today. When true, an abort after start
kills the child (SIGTERM, then SIGKILL after a grace period) and the result is reported as
`Cancelled`. The rule in §4.3 becomes "a write that has already started is never killed **unless it is
a network fetch, which holds no local lock and moves no ref until it completes**", which W20 writes
into the spec. See **D50**.

Cancelling *before* the push spawns is always available and is what the UI's cancel button does while
a push is queued behind another op.

### 4. Askpass: four independent guarantees, and one new port

The exit criterion is absolute: **no operation can hang on a prompt.** Four independent mechanisms
each make that true; the design does not rely on any one of them.

1. **`GIT_TERMINAL_PROMPT=0`** — already set by `buildGitEnv()`. Git will not prompt on a terminal.
2. **`detached: true` → `setsid()`** — already done by `nodeSpawn`. The child has no controlling
   terminal to prompt on even if (1) were removed. This is a pre-existing guarantee nobody documented;
   W12 documents it.
3. **The broker's own timeout.** Our askpass helper waits a bounded time for an answer from the
   extension host; on timeout or user-dismissal it **exits non-zero**. Probe 8 proves this does not
   hang or retry: git prints `error: unable to read askpass response` and dies with
   `terminal prompts disabled`.
4. **Op-level cancel.** The user can cancel from the toolbar, which (for fetch) kills the child and
   (for everything else) is bounded by (3) anyway.

**The mechanism** (`packages/git/src/askpass.ts`, W13): before spawning a remote op the broker writes a
`0700` shim into a per-session temp dir and points `GIT_ASKPASS` at it. On POSIX that is a two-line
`sh` script; the script execs the same Node binary the extension host runs on with a tiny helper
script, passing the socket path and the op id in the environment. The helper connects to a unix
domain socket the broker listens on, sends `{opId, prompt}`, waits with a timeout, and writes the
answer to stdout (probe 7: git reads the answer from stdout). Socket path lives in the session temp
dir at `0700`; the helper additionally presents a per-op random token so a stray process cannot
harvest credentials from the socket.

**We do not override a user's own `core.askPass` or `GIT_ASKPASS`.** §4.1 is explicit about config
fidelity, and a user who has configured a credential manager has configured it deliberately. The
broker reads `git config --get core.askPass` once per repo and, if it is set, leaves the environment
alone entirely. Same for an inherited `GIT_ASKPASS` in the host's own environment.

**The answer comes from a new `core` port.** Not `Secrets` (we store nothing — see below), not
`Dialogs` (which is a modal yes/no surface, not a masked text input). A new narrow port:

```ts
// packages/core/src/ports/credentialPrompt.ts
export interface CredentialRequest {
  /** git's own prompt text, verbatim — e.g. "Password for 'https://alice@github.com': ". */
  readonly prompt: string;
  /** True when the prompt asks for a secret and the input must be masked. */
  readonly masked: boolean;
  readonly signal?: AbortSignal;
}
export interface CredentialPrompt {
  /** Resolves with the user's answer, or `undefined` if they dismissed it or the signal fired.
   *  Must never hang: an implementation that cannot ask resolves `undefined` immediately. */
  ask(request: CredentialRequest): Promise<string | undefined>;
}
```

`host-vscode` implements it over `window.showInputBox({ password: masked, ignoreFocusOut: true })`;
the harness implements it with a fake that answers from a scripted queue, which is how the integration
tests drive the auth paths without a human. `masked` is derived from the prompt text (`/^Password
|passphrase/i`), defaulting to masked — erring toward hiding.

**We store nothing.** No `Secrets` port, no caching, no writing to git's credential helper. Git's own
credential helpers already do this and do it better; interposing would mean holding a user's
credential in our process across ops for no benefit. **D54.**

**Windows is a named gap.** The `sh` shim does not work there. The plan carries a Windows branch that
writes a `.bat` shim, but P8's integration tier runs on Linux (P4c) and the Windows path ships
untested-by-CI. Named honestly rather than pretended away — see **OQ8**.

### 5. Pull: decomposition and the strategy resolution order

§7.3 is unambiguous that plain `git pull` is never invoked. P8 runs `git fetch <remote> <refspec>`
followed by exactly one of `git merge --ff-only <upstream>`, `git merge <upstream>`, or
`git rebase <upstream>`.

**The strategy is resolved by a defaults-with-override ladder** (the shape D30 already established),
first match wins:

1. An explicit strategy in the `remote.run` params (the user picked one in the UI this time only).
2. `kiraVersion.pull.strategy`, if it is not `"auto"`. Values: `auto` (default), `ff-only`, `merge`,
   `rebase`.
3. `branch.<current>.rebase` — `true`/`interactive`/`merges` → rebase, `false` → merge.
4. `pull.rebase` — same mapping.
5. `pull.ff=only` → ff-only.
6. Fallback: **ff-only**.

Steps 3–5 are read in **one** spawn:
`git config --null --get-regexp '^(pull\.(rebase|ff)|branch\.<name>\.rebase)$'`. §7.3 requires we read
the user's git config; three separate `--get` spawns for that would be silly.

**The resolved strategy is always shown before the op runs**, with its provenance ("from your
`pull.rebase` setting", "kira-version default"). A user whose repo is configured to rebase must not
discover that by watching their history get rewritten.

**Autostash is P9's, and P8 leaves the seam.** §7.3 says a dirty worktree plus a non-ff pull should
offer autostash "implemented as our own stash/pop" — but stash is P9. P6 solved exactly this shape
with `CheckoutPreflight.routes` as the named seam for P9's `stashAndCarry`. `PullPreflight` gets the
same `routes` array, **empty at P8**, and the dirty+non-ff case reports `DirtyWorktree` with a message
naming stash as the manual step. Copying an established seam beats inventing a second one.

### 6. Protected branches: what exactly is gated

D19 already decided the *character* of this — "a typed confirmation, not a hard refusal", "friction,
not prohibition" — but it never enumerated **which operations** it gates. That is the open part, and
this plan closes it:

**Protected-branch gating applies to remote operations that destroy or rewrite remote history, and to
nothing else.** Concretely: `forcePush` (lease), `forcePush` (plain `--force`), and
`deleteRemoteBranch`. **Plain `push` is never gated** — pushing a fast-forward to `main` is the single
most common thing anyone does with `main`, and gating it would train users to type branch names
reflexively, which destroys the friction's value everywhere else.

The friction escalates:

| Operation on a protected branch | Friction |
| --- | --- |
| `push` (fast-forward) | none |
| `forcePush` with lease | typed confirmation: the user types the branch name |
| `forcePush` with plain `--force` | §7.4's second explicit confirmation **and** the typed branch name |
| `deleteRemoteBranch` | typed confirmation |

The **matcher is a pure function in `core`** (`packages/core/src/model/protectedBranch.ts`), not a
regex built at the call site: `matchesProtectedPattern(branch, patterns)`, glob semantics where `*`
matches any run of characters **except `/`** (so `release/*` covers `release/1.2` but not
`release/1.2/hotfix`; `**` is not supported and a pattern containing it is treated literally, with a
logged problem). Pure, unit-tested, and — being in `core` — usable by both the pre-flight and the UI's
own "this branch is protected" affordance without a round trip. Default:
`["main", "master", "release/*"]`, matching §7.4.

**The check is server-side authoritative and client-side advisory.** `remote.run` re-checks and
refuses with a `ProtectedBranch` error if the confirmation token is absent — a pre-flight is advice,
not a lock (P6's phrasing), and the host must not depend on the UI having asked.

### 7. Auto-fetch needs three things the service does not have

§7.1's guardrails: only while the window is focused **and** the panel is visible; never while another
op holds the write queue; a failure disables the timer for the session. Delivering that needs:

1. **Live settings.** `RepoServiceDeps.settings` is a frozen snapshot. W15 changes it to `() => Settings`
   to match `RepoHandlersDeps`, and `extension.ts` re-informs it on config change. Otherwise changing
   the interval requires a window reload, and — worse — the *first* setting of a non-zero interval
   would never take effect at all.
2. **A focus signal.** `extension.ts` subscribes `window.onDidChangeWindowState` and calls a new
   `service.setHostFocused(bool)`. **No new port**: this is the host pushing a fact in, the same
   direction `setUiVisible` already goes, and inventing a `WindowState` port to carry one boolean
   would be ceremony. Harness sets it from page visibility.
3. **Write-queue idleness.** The driver knows; nothing exposes it. W2 adds a `busy` getter.

**Auto-fetch is silent**: no progress events, no toolbar spinner, no error toast. It runs
`fetch --prune` on the current remote, and on failure logs at `warn` and **disables itself for the
session** (§7.1), surfacing that only as a subdued marker in the toolbar's fetch affordance. The first
tick waits a full interval — an auto-fetch racing the panel's cold start would compete with the
initial graph load for the write queue.

Default remains `0` (off), per D18.

### 8. The error taxonomy splits: `GitErrorKind` vs `OpErrorKind`

Until now these two unions have been near-mirrors. P8 makes them diverge, deliberately, and it is
worth naming why: **`GitErrorKind` is "what git said"; `OpErrorKind` is "what the operation
concluded".** Some P8 outcomes are the second without ever being the first.

`GitErrorKind` gains four members, all classified from real stderr, all ordered **before**
`NonFastForward` so its broad `! \[rejected\]` alternative cannot swallow them:

| New kind | Pattern source | Probe |
| --- | --- | --- |
| `LeaseViolation` | `/\(stale info\)/` | probe 1, rows 1–2 |
| `RemoteRefUpdated` | `/\(remote ref updated since checkout\)/` | probe 1, row 3 |
| `NetworkFailed` | `/Could not resolve host\|Connection (refused\|timed out)\|unable to access '.*': /` | — |
| `RemoteNotFound` | `/does not appear to be a git repository\|Repository not found/` | — |

`OpErrorKind` gains **`ProtectedBranch`** and **`Cancelled`** — neither of which git ever says,
because both are decisions we made — plus wire members mirroring the four above. `LeaseViolation` and
`RemoteRefUpdated` stay distinct rather than collapsing into one "someone else pushed" kind, because
their remedies differ: the first says *fetch and look*, the second says *you already fetched; you are
about to discard commits you have seen*.

`AuthFailed` needs no new pattern — probe 8 confirms all three real shapes already match.

export type RemoteOpKind =

export type PullStrategy = "ff-only" | "merge" | "rebase";

export type PullStrategySource =

         *  back. Re-verified host-side — a pre-flight is advice, not a lock. */
        readonly protectedConfirmation?: string }
    | { readonly kind: "deleteRemoteBranch"; readonly remote: string; readonly branch: string;
        readonly protectedConfirmation?: string };

  readonly ref: string;

  readonly to: string | null;     // null = deleted

 *  unchanged and a conflicting pull lands in P6's existing in-progress banner — but has no
 *  `undo` field at all, by construction (§7.12, D51). */
export interface RemoteOpResult {
  readonly ok: boolean;
  readonly error?: { readonly kind: OpErrorKind; readonly message: string;
                     /** A hook's own `remote: `-prefixed output, when kind is HookRejected. */
                     readonly remoteMessage?: string };
  readonly updates: readonly RefUpdate[];
  /** Which strategy actually ran, and why — pull only. */
  readonly strategy?: { readonly used: PullStrategy; readonly source: PullStrategySource };
  readonly upstreamSet?: boolean;
  readonly head: HeadState;
  readonly inProgress: InProgressState;
}

export interface RemoteProgress {
  readonly repoId: RepoId;
  readonly opId: string;
  /** git's own phase label, verbatim: "Counting objects", "Receiving objects", … */
  readonly phase: string;
  /** Absent for a counted-but-unbounded phase ("Enumerating objects: 91, done."). */
  readonly percent?: number;
  readonly done?: number;
  readonly total?: number;
  /** True for `remote: `-prefixed phases — work happening on the server, not here. */
  readonly remote: boolean;
}

### W2 — `GitDriver.writeStreaming()` and `busy`

```ts
  /**
   * A write that reports progress and, when `killable`, may be cancelled after it has started.
   *
   * §4.3's rule is "a write that has already started is never killed", and that rule is right for
   * every local write: killing one can strand `index.lock`, a half-written ref, or a partial
   * sequencer state. A network fetch has none of those hazards — it writes loose objects or a
   * packfile that a later `gc` collects, and moves no ref the user can see until it completes —
   * so it, and only it, is killable. Push is not: a cancelled push's remote outcome is
   * unknowable, and reporting "cancelled" for a push the server accepted is worse than making
   * the user wait. See D50.
   */
  writeStreaming(argv, opts: {
    onStderr?: (chunk: Uint8Array) => void;
    killable: boolean;
    signal?: AbortSignal;
    env?: Record<string, string>;   // the askpass broker's additions
  }): Promise<GitOutput>;
```

Same queue as `write()` — a remote op serializes against local writes exactly as before, which is what
makes §7.1's "never while another op holds the write queue" guardrail expressible at all. Kill is
SIGTERM, then SIGKILL after a grace period (~2 s), then the promise rejects with `GitCancelled`.
`onInvalidated` still fires only on success — plus, for a **killed fetch**, it fires too: a partial
fetch may have moved some remote-tracking refs, and the graph must not show stale ones.

Add `get busy(): boolean` (write queue non-empty or a write in flight). W15's scheduler reads it.

### W7 — `git/src/ops/fetch.ts`

```

```

`--prune` from the params (UI default on); `--prune-tags` from the params (UI default **off** —

### W8 — `git/src/ops/push.ts`

```

```

## Judgment calls this plan made

1. **A new `remote.run` key rather than extending `op.run`'s union.** Four independent reasons (undo
   slot, progress correlation, cancel semantics, result shape), any one of which would be enough. The
   cost is a second executor shape in `ops.ts`; the alternative is a background timer that silently
   eats the user's undo slot.
2. **`op.progress` yes, `op.finished` no**, despite §3.5 naming both. The request's own response *is*
   the finish; a second finish signal is a second source of truth that can arrive out of order. §3.5
   gets corrected rather than implemented.
3. **The event is named `remote.progress`, not `op.progress`.** §3.5's name predates the decision that
   remote ops are their own key family; keeping `op.` would imply P6's `op.run` emits it, which it does
   not and will not.
4. **Progress is an event, not a stream.** It is lossy by design, needs no credit-based backpressure,
   and has no completion of its own. Making it a stream would buy ordering guarantees for data whose
   whole point is that intermediate values are disposable.
5. **Throttling is host-side.** Throttling in the UI means the frames were already built, serialized,
   base64'd and posted — the expensive part — for updates nobody will ever see.
6. **Fetch is killable; push is not.** The asymmetry is not squeamishness: a killed fetch's outcome is
   knowable (nothing the user can see moved), a killed push's is not.
7. **Protected branches gate destructive remote ops only, never plain push.** Gating ordinary pushes to
   `main` would make the confirmation reflexive within a day and worthless everywhere.
8. **`--prune` on, `--prune-tags` off**, against §7.1's literal command line, on probe 2's evidence.
   §1.1 outranks a command line.
9. **Bare `--force-with-lease` + `--force-if-includes`**, against §7.4's literal command line, on probe
   1's evidence — plus two compensating mitigations (suppress auto-fetch while a force-push
   confirmation is open; re-read and compare the remote tip immediately before spawning) that recover
   what §7.4's explicit expect value was reaching for.
10. **One new port (`CredentialPrompt`), and none of the four §3.3 predicted.** No `Secrets` (we store
    nothing), no `Notifications` (progress is in-webview, per P6's precedent), no `GitHubAuth` (P8 is
    host-agnostic git, not a forge integration), no `ExternalOpener`.
11. **We never override a user's own `core.askPass`.** §4.1's config fidelity. A user with a credential
    manager configured has already solved this problem better than we can.
12. **`PullPreflight.routes` ships empty.** Copying `CheckoutPreflight.routes`'s established seam costs
    one field now and saves P9 from inventing a parallel mechanism.
13. **Auto-fetch is entirely silent.** A background operation the user did not initiate must not steal
    the progress affordance, and its failures must not produce a toast at 3pm on a flaky VPN.
14. **The service's `settings` dep becomes a thunk.** Not strictly required by any single feature, but
    an interval setting that needs a window reload to take effect is a bug report waiting to be filed,
    and the divergence from `RepoHandlersDeps` is already confusing.
15. **`remote.cancel` is an explicit request key, not the rpc `cancel` frame.** The frame drops late
    responses by design; a cancelled fetch's post-state is exactly what must not be dropped.
16. **No new perf budget this phase** (P6 judgment call 11's precedent). Remote-op latency is dominated
    by the network; a budget over it would measure the test fixture, not our code.
17. **Windows' askpass shim ships without CI coverage**, and is named as such rather than implied to be
    tested. P4c put the integration tier on Linux.

## Open questions for the orchestrating session

**OQ1 — Does background auto-fetch ship in P8 at all?**
§10's row says "incl. opt-in background auto-fetch, default off" and D18 already decided it. But it is
the one part of this phase that is not on any user-visible critical path, and it drags in three
infrastructural changes (live settings thunk, a focus signal, driver busy-ness) that touch
`repoService.ts` broadly.
**Recommendation: ship it.** The three changes it forces are each independently good — a service that
cannot see a settings change is a latent bug for every future setting, and the focus signal is one
line. Deferring it means doing W15 later anyway, with less reason to do it well. But if this phase
needs to shrink, W15 is the clean cut line: everything else stands without it.

**OQ2 — `--prune-tags`: on by default (as §7.1 literally says), off by default, or not offered?**
Probe 2: it deletes local-only tags, and fetch offers no undo (§7.12).
**Recommendation: `--prune` default on, `--prune-tags` default off, both exposed as explicit options
on the fetch affordance, and §7.1's command line corrected.** A user who wants tag pruning can ask for
it; a user who loses an unpushed tag to a background fetch has been failed by §1.1.

**OQ3 — Is `kiraVersion.fetch.autoInterval` in minutes, and are those the right names?**
This plan uses `kiraVersion.fetch.autoInterval` (minutes, 0 = off) exactly as §7.1 names it, plus
`kiraVersion.pull.strategy` and `kiraVersion.protectedBranches` (both named in §7.3/§7.4 prose).
**Recommendation: keep all three names verbatim from the spec, and minutes.** Settings are the hardest
thing to rename after release. The only genuine choice is the unit; VS Code's own git extension uses
`git.autofetchPeriod` in *seconds*, but minutes reads better at the values anyone actually wants and
0 means off either way. Flagging it because "the spec says minutes" and "the neighbouring extension
says seconds" are both defensible and a decision now is cheaper than a migration later.

**OQ4 — Force-push: adopt bare `--force-with-lease --force-if-includes`, contradicting §7.4?**
Probe 1 proves §7.4's command line cannot deliver what §7.4 says it delivers: an explicit expect value
makes `--force-if-includes` inert, and the two flags guard different hazards.
**Recommendation: yes — pass the bare lease plus `--force-if-includes`, correct §7.4, and record
D48.** With two mitigations for the hazard §7.4's explicit sha was reaching for: (a) suppress
auto-fetch while a force-push confirmation is open, and (b) re-read the remote tip immediately before
spawning and compare it to the one the dialog displayed. This is the single most consequential
question in the plan; W19 test 3 is written to encode whichever way it is answered.

**OQ5 — Is protected-branch enforcement a hard block or a confirm-through?**
D19 says "typed confirmation, not a hard refusal", "friction, not prohibition" — but D19 predates any
enumeration of *which* operations it covers, and the task brief asks this explicitly.
**Recommendation: confirm-through, exactly as D19 says, gating only force-push (both flavours) and
remote-branch deletion — never plain push.** A hard block in a local tool is theatre: the user has a
terminal, and a tool that refuses trains people to leave it. Add a genuine hard block *only* if a
future phase gains org-policy input it can trust, which nothing in v1 does.

**OQ6 — Does a remote op clear the undo slot?**
§7.12 says push/force-push/fetch never *offer* undo, and separately that "performing another operation
clears the undo slot". Read literally, an explicit fetch clears it.
**Recommendation: no remote operation ever touches the undo slot, in either direction.** A background
auto-fetch clearing it is indefensible; and once auto-fetch does not, an explicit fetch that does
creates an inconsistency the user cannot predict. §7.12's "another operation" should be read as
"another operation that changes local history", which is what makes the undo slot's single-slot design
safe in the first place. Needs confirming because it is a narrow reading of spec text.

**OQ7 — Should `remote.run` reject a second concurrent remote op, or queue it?**
This plan rejects with `OperationInProgress`.
**Recommendation: reject.** The driver's write queue would serialize them anyway, but a queued push
sitting invisibly behind a ninety-second fetch is a worse experience than being told to wait, and it
makes "which op does cancel cancel?" ambiguous.

**OQ8 — Does the Windows askpass shim ship in P8, untested by CI?**
The POSIX `sh` shim does not run on Windows; a `.bat` equivalent is straightforward but P4c put the
integration tier on Linux.
**Recommendation: write it, ship it, and mark it in the spec as untested-by-CI.** The alternative —
no askpass on Windows — means every HTTPS remote without a credential manager fails with `AuthFailed`
on that platform, which is a worse bug than an untested code path. Revisit when a Windows lane exists.

**OQ9 — Does `deleteRemoteBranch` belong in P8 at all?**
§10's P8 row does not name it. It is here because it is the *other* destructive remote operation, and
protected-branch gating is meaningless if the one operation that can destroy a protected branch outright
is not covered.
**Recommendation: include it.** It is ~20 lines on top of push (`git push <remote> --delete <branch>`),
it shares every mechanism already being built, and shipping protected branches without it leaves the
obvious hole. If it is cut, the protected-branch decision (D52) must say so explicitly.

**OQ10 — Progress throttle interval: 100 ms?**
Chosen as "faster than the eye needs, slower than the frame budget cares about". Not measured.
**Recommendation: 100 ms, and do not measure it.** It is a constant in one place (W3's
`throttleProgress`), trivially changed, and no gated metric depends on it. Named only so nobody
mistakes it for a researched number.

**OQ11 — Should the plain `--force` path exist at all in v1?**
§7.4 says it should, behind a second explicit confirmation. But `--force-with-lease
--force-if-includes` covers every legitimate use, and plain `--force` exists mostly to defeat a
protection the user is annoyed by.
**Recommendation: keep it, per §7.4.** The alternative is a user dropping to a terminal at the exact
moment they are doing something dangerous, with no protected-branch confirmation and no record. Better
inside the tool with maximum friction than outside it with none.

## Findings

_Recorded during this session's implementation of W17–W21 and its final full-suite verification
pass. Earlier work items (W1–W16, most of W19's own scenario file, the SPEC.md §7 corrections) were
already in place on disk from prior sessions of this same effort; what follows is what this
session itself did, found, and verified — not a re-claim of work it inherited._

### F1 — A real, previously-undetected contract-validation gap: `remote.*` was unreachable through the real codec path

While root-causing all 9 of W21's new Playwright tests failing identically (`window.__kiraHarness.
lastRemoteOp` staying `undefined`, the pull-strategy preview never populating, `ForcePushDialog`
never opening), the actual cause turned out to be nothing about the new test file or the new
scenarios: `packages/ipc/src/validate.ts`'s `REQUEST_KEYS`/`EVENT_KEYS` sets — the runtime half of
`assertContractShape`'s per-message method-name check — had never been updated when W17 added
`remote.pullPreflight`, `remote.pushPreflight`, `remote.run`, `remote.cancel` to `Contract` and
`remote.progress` to its events. Every one of those five calls has been throwing
`RpcError: ipc contract shape error … unknown request/event method` since W17 landed, silently,
on every real round trip through `createRpcClient`/`createRpcServer` — confirmed live via a
throwaway Playwright spec with a `page.on("console", …)` listener, which is what actually surfaced
the `RpcError` (a plain `page.evaluate()` swallows it: the promise the UI awaits rejects, `#runRemote`'s
`try`/`finally` clears `busy` without ever calling `#applyRemoteResult`, and nothing else in the app
logs it). This had gone unnoticed through the whole of W17–W20 because nothing before W21 exercised
the real codec for these methods: `mockBridge.ts`'s own handlers are called directly by
`createInMemoryChannelPair`'s RPC layer (which *does* go through `assertContractShape` — this is
exactly why it broke), but every unit test for the remote-ops UI state (`ops.test.ts`, if any) and
every `RepoService` integration test drives `RepoService` directly, never through
`createRpcClient`/`Server`. **W21's E2E suite is the first thing in this whole plan to prove the
wire format end-to-end for `remote.*`, and it caught a real bug the moment it existed to catch one.**

`validate.ts`'s own doc comment claimed "`contract.test.ts` fails if a key here and a key in
`Contract` ever drift apart" — no such test exists anywhere in `packages/ipc`; the comment was
either aspirational or referred to a test since deleted. Fixed two ways, not one: (1) added the
five missing keys, and (2) rebuilt `REQUEST_KEYS`/`EVENT_KEYS`/`STREAM_KEYS` from a
`Record<RequestKey, true>` / `Record<EventKey, true>` / `Record<StreamKey, true>` object literal
instead of a bare array literal — TypeScript's mapped-type checker requires every key of the type
to be present in a `Record<K, V>` literal, so a *future* `Contract` addition left out of this file
is now a compile error (`tsc --build` fails), not a silent runtime gap discoverable only by an E2E
test happening to exist. This makes the doc comment's original claim true going forward instead of
merely stated.

### F2 — Three genuine test-authoring bugs in `remoteOps.spec.ts`, found and fixed against the real (post-F1) app

Once F1's fix was in and the harness was rebuilt, re-running the same 9 tests surfaced two further,
unrelated issues — both in the new test file itself, not the product:

- **A `page.evaluate()` race.** `.click()` resolves once the DOM event dispatch completes, not once
  the async handler it triggered (`doFetch`/`doPush`/`runPull`/…, none of which the `@click`
  template binding awaits) finishes its own `await`-chain through to `remote.run`'s response. Five
  tests read `window.__kiraHarness.lastRemoteOp` via a bare, non-retrying `page.evaluate()`
  immediately after the triggering click, occasionally (and, once F1 was fixed, *always*, since the
  round trip is what F1 had been failing on) racing ahead of it. Fixed by first `await`-ing an
  auto-retrying `expect(page.getByTestId("live-announcements")).toHaveText(…)` — set by
  `OpsState`'s own announcement logic only once `#runRemote` actually resolves — before reading
  `lastRemoteOp`, the same ordering `refOps.spec.ts`/`undo.spec.ts` already use for `op.run`/
  `undo.run`'s own argv assertions.
- **A wrong assumption about `ForcePushRoute.plain`.** Two force-push tests asserted
  `plainForce: undefined` on the lease route's own `RemoteOpParams`; `ForcePushDialog.vue`'s
  `confirmLease()` always resolves `{ plain: false, confirmToken }` — `plain` is a real boolean on
  every route, never `undefined` (only the plain-`--force` route sets it `true`). Fixed the two
  assertions to expect `plainForce: false`.

All 9 tests pass now, individually and as part of the full 290-test `--project=harness` run (no
regressions elsewhere from either the `validate.ts` fix or the `shell.spec.ts` global-type edit).

### F3 — TypeScript project references do not merge an unimported file's ambient globals across projects

Documented here because it cost real time and the fix is non-obvious: `apps/harness/src/main.ts`'s
`declare global { interface Window { __kiraHarness: {…} } }` is **not** visible to
`tests/e2e/harness/*.spec.ts`'s own `tsc --build`, even though `tests/tsconfig.json` lists
`apps/harness` (transitively, via `packages/core`) as a project *reference* — `--build` mode's
references only order builds, they do not fold a referenced project's global augmentations into a
dependent project's own file set unless something in the dependent project actually imports the
file. `tests/` is not a bun workspace member (only `packages/*`/`apps/*` are) and has no
`node_modules/@kira-version/*` symlink, so it never could import `main.ts` anyway. The real,
load-bearing declaration every existing E2E spec relies on is a **hand-duplicated mirror** already
living in `shell.spec.ts` (its own doc comment says as much for `HarnessOpRequest`/
`HarnessOpResult`) — W21's `lastRemoteOp` hook, and its two supporting types
`HarnessRemoteOpParams`/`HarnessRemoteOpResult` (mirroring `packages/ipc/src/contract.ts`'s
`RemoteOpParams`/`RemoteOpResult`), were added there, not to `main.ts` alone, following that same
convention.

### F4 — Design decision: three scenarios, not one scenario with branch-switching

`apps/harness/src/scenarios/remoteOps.ts` builds three named scenarios (`remoteOps`,
`remoteOpsPull`, `remoteOpsDiverged`) from one shared commit topology via a `buildScenario()`
factory, rather than one scenario a test checks out a second branch inside of. Reason, found by
reading `mockBridge.ts`'s own `applyOp`'s `"checkout"` case: it never recomputes
`session.status.upstream` — that field is seeded once from the scenario and mutated only by a
remote op itself — so a test that checked out `feature-behind` mid-test from a `main`-headed
scenario would still see `main`'s own ahead/behind counts. This is a real, narrow limitation of the
mock's "current branch only" status model (matching `preflightPush`'s own doc comment for the real
`RepoService`), not something worth teaching the mock to recompute for three tests' sake.

### Gaps, named honestly

- **No automated "plain `git pull` appears nowhere" grep test exists**, despite the exit-criteria
  bullet above describing one ("asserted by a grep test, the way other never-do rules are") — no
  such other never-do grep test exists in this codebase either, so that clause was aspirational
  when written. This session performed the check by hand instead:
  `grep -rn '"pull"' packages/git/src packages/core/src packages/host-vscode/src apps/harness/src`
  finds only the `RemoteOpKind`/discriminant string `"pull"`, never a `git pull` argv;
  `grep -rn "\bgit pull\b" …` finds exactly two hits, both prose — `ops/pull.ts`'s own doc comment
  contrasting itself against `git pull`'s implicit merge, and `errors.test.ts` quoting git's own
  error-hint text verbatim in a fixture string. `packages/git/src/ops/pull.ts`'s actual argv
  builders (`ffOnlyArgs`/`mergeArgs`/`rebaseArgs`) spawn `merge --ff-only`, `merge --no-edit`, and
  `rebase` — never `pull` — confirming the decomposition by inspection, not merely by absence of
  the string. Adding a real automated version of this check was judged out of scope for W21's own
  stated deliverable and left for whoever next touches this area.
- **The no-hang guarantee is demonstrated two ways, not the three the plan's own exit-criteria
  prose names** ("no askpass configured; askpass helper exits non-zero; `CredentialPrompt` never
  resolves and the broker's timeout fires"). `repoService.test.ts` has "a configured
  `CredentialPrompt` that declines completes promptly" and "the askpass broker's own timeout fires
  when the prompt never resolves" — the first stands in for both "no askpass configured" and "the
  askpass helper exits non-zero", since both present to the broker identically (no answer
  forthcoming); a `CredentialPrompt` that declines is the harness-reachable way to provoke that.
  Worth a third, more literal test (a fixture askpath script that actually exits non-zero against a
  real `git http-backend`) if this distinction ever matters operationally, but it was not added
  here.
- **Windows askpass coverage remains CI-untested.** The `.bat` shim path exists in
  `packages/git/src`'s askpass broker but this sandbox (and, so far as this session could confirm,
  this repo's CI) only runs Linux; nothing in this session's verification exercised it.
- **The pre-existing `deleteRemoteBranch` vs `tagDeleteRemote` UI wiring gap** — noticed while
  reading `BranchPicker.vue`'s row menu for W21 (its "Delete on origin" action still calls the older
  `tagDeleteRemote` op kind, not P8's own `RemoteOpKind: "deleteRemoteBranch"`) — was left alone.
  It predates this session, is not part of W17's stated toolbar/dialog scope (fetch/pull/push/
  force-push only), and `mockBridge.ts`/`RepoService` both still implement `deleteRemoteBranch`
  correctly on the wire; only the one context-menu entry point never reaches it. Flagged here so a
  later phase does not rediscover it from scratch.
- **The mock bridge's pull semantics remain a simplified stand-in, by design.** `mockBridge.ts`'s
  `applyRemoteOp` reuses real `@kira-version/core` logic for push/force-push classification
  (`classifyPush`, `matchProtectedBranch`) and for the pull-strategy ladder
  (`resolvePullStrategy`), but the pull *outcome* itself is a bare "reset the local ref to the
  remote tip if behind and clean" — no actual merge, rebase, or conflict simulation. This is
  intentional (`remoteOps.ts`'s own doc comment states it): proving real git pull/merge/rebase
  semantics, including conflicts, is `tests/integration/repoService.test.ts`'s job (W19, against a
  real bare remote), not the Playwright harness's. W21's E2E tests assert on the wire the UI sends
  and the dialogs it opens, not on git's own integration behaviour.
