# P5 — Commit detail

Plan for the P5 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** the pane P4 built the *region* for and deliberately left empty. P4 shipped the shell,
the breakpoints, the resize handle, the overlay drawer and a placeholder that says in as many
words "The detail view itself arrives in P5." This phase fills it: message with trailers,
a file tree with statuses and counts, an in-app unified diff opened by clicking a file, the
"Open in editor" and line-mapped **"Go to file"** actions (D14a), a parent selector for merges,
and copy actions — including the sha button P4 rendered `disabled` on purpose.

It is also the phase that first makes the app read *file content*. Everything before it read
history: shas, parents, identities, subjects, decorations. P5 reads trees, blobs and patches,
which is why it is the phase that grows the two ports §3.3 has been carrying with no consumer
(`Clipboard`, `EditorIntegration`), the phase that finds out whether `cat-file --batch` survives
a path with a space in it (it does not — see below), and the phase P7 later reuses wholesale:
§6.8 says branch review's file tree, diff view, "Go to file" and `commit.detail` "are P5's and
P2's, used as they stand."

## The hard parts, settled before the work items

### D14a — what "Go to file" actually does

§6.4 and D14a between them specify an action that is easy to describe and easy to get subtly
wrong. Stated as the implementation actually behaves:

**The user is looking at a unified diff of one file at one commit and puts the cursor on a
line. "Go to file" opens that file's content, at the corresponding line, and it always opens
*something*.**

The three user-facing stories D14a names — a file **deleted** since, a file **renamed** since,
and a file that has **never existed on disk at all** because it was only ever added on a commit
that is not an ancestor of what is checked out — are three ways of arriving at one question,
and the implementation asks that question exactly once:

> Does `<repoRoot>/<path>` exist on disk right now?

- **Yes** → open the live working-tree file and put the cursor on the mapped line.
  `EditorIntegration.reveal({kind:"file"}, line)`.
- **No** → open the same read-only blob content the diff view is already rendering from —
  `<rev>:<path>` read through the persistent `cat-file --batch` — as a virtual document, at the
  same mapped line. `EditorIntegration.reveal({kind:"virtual"}, line)`.

**Why the fallback cannot fail, and why that is the whole point.** The virtual side addresses
content by *object*, not by checkout: `git cat-file --batch` answers `<rev>:<path>` out of the
object database, and the object database does not care whether `<rev>` is an ancestor of `HEAD`,
whether the branch is checked out, or whether the working tree exists. The resolution
deliberately **never consults `HEAD`, the index, or reachability** — the two facts it uses are
"is there a file at that path on disk" and "is there an object at `<rev>:<path>`", and the second
is true for every commit the graph can show you. That is precisely why the never-existed case —
a feature branch you have not checked out, a commit on a branch you have never touched — lands
rather than failing, and it is why this action goes further than VS Code's own diff-editor "Go
to File", which only handles the trivial case where the path exists at the checked-out path.

Three consequences worth writing down because each is a place an implementation drifts:

1. **A path that exists on disk but is a *different* file is not detected, and that is
   accepted.** Someone may have created an unrelated `src/util.ts` since. Existence is the test;
   the mapped line lands where it lands. Detecting "same file" would mean a content comparison
   with no correct answer, and the alternative — refusing to open the live file — is worse.
2. **Which revision, and which path, depends on the change kind.** For a `deleted` file the
   content only exists on the pre-image side, so the target is `<selected parent>:<originalPath ??
   path>` and the mapping targets the old side. For everything else (`added`, `modified`,
   `renamed`, `copied`, `typeChanged`) the target is `<commit>:<path>` and the mapping targets
   the new side. A `renamed` file's live-file check uses the **new** path, because that is the
   name the file has at this commit.
3. **A binary or over-the-size-gate blob is not opened in a text editor.** The outcome is
   `unavailable` with the reason, rendered as a one-line message, not an empty tab.

The action returns its outcome over the wire (`liveFile` / `virtualBlob` / `unavailable`) rather
than resolving silently, for two reasons: the UI has to say which one happened ("Opened the
historical version — this path is not in your checkout"), and it is what makes the four cases
assertable in Playwright without a filesystem (W12, W13).

### The line map

Mapping a cursor position in a unified diff to a line number in a target revision is the one
genuinely algorithmic thing in this phase, so it is specified here rather than left to the
keyboard. It lives in `packages/core/src/model/diff.ts` as a pure function over the parsed diff
and is unit-tested exhaustively (this is exactly `AGENTS.md`'s "cursor/page arithmetic with real
boundary cases" clause).

**Step 1 — numbering, done once at parse time.** A hunk header carries everything needed:
`@@ -oldStart,oldLines +newStart,newLines @@ heading`. Walking a hunk's raw lines while
maintaining two counters assigns every rendered row its old-side and new-side numbers:

```
o = hunk.oldStart ; n = hunk.newStart
for each raw line:
  " …"  → context : { oldLine: o++, newLine: n++ }
  "-…"  → del     : { oldLine: o++, newLine: undefined }
  "+…"  → add     : { oldLine: undefined, newLine: n++ }
  "\…"  → "\ No newline at end of file": consumes no number; sets a flag on the previous line
```

Two facts about hunk headers that the parser must handle and that are verified against real git
below: **a count of `1` is omitted** (`@@ -1 +1 @@`), and a header may carry a **section
heading** after the closing `@@` (`@@ -15,6 +15,7 @@ n`). The walk's own invariant —
`o - oldStart === oldLines` and `n - newStart === newLines` at the end of each hunk — is
asserted, not assumed; a mismatch means a malformed patch and fails loudly, per `validate.ts`'s
discipline, rather than half-rendering.

**Step 2 — the map.** `mapDiffLineToRevision(hunks, rowIndex, side)`, where `side` is `"new"`
or `"old"` per the change kind above:

| The cursor is on | Answer |
|---|---|
| a row that carries a number on `side` (context always does; `add` on the new side; `del` on the old side) | that number — the common case, and exact |
| a row with **no** number on `side` (`add` mapped to old, `del` mapped to new) | scan backwards within the same hunk for the nearest row that has a `side` number; answer is **that number + 1**. If the hunk has none before it, answer is `hunk.<side>Start` |
| a hunk-header row | `hunk.<side>Start` |
| the file header, or a diff with no hunks | `1` |

The backwards scan is the case worth explaining. A deleted line has no counterpart in the new
revision — but the content that *followed* it does, and it sits immediately after the last
surviving line above the cursor. Landing there puts the reader's eye where the removed text used
to be, which is the only useful answer available. Result is clamped to `≥ 1`.

**The general form, for the record.** The per-row table above is a precomputed instance of the
one piece of arithmetic that actually defines the mapping: for an old-side line `L` in territory
no hunk covers, the new-side line is `L + Δ`, where `Δ` is the cumulative net insertion of every
hunk that ends before `L` — equivalently `Δ = (newStart + newLines) − (oldStart + oldLines)` of
the last such hunk, and `0` before the first hunk. The parse-time walk computes exactly that,
incrementally, which is why P5's own call sites never need the closed form. It is recorded here
because it is what a future refinement (see "Open questions") would use, and because a reader
of the table should be able to see that it is a mapping and not a lookup table that happens to
work.

### The second map — drift, and why the live-file branch needs it

The map above answers a question about one commit: *which line of `<rev>:<path>` is the cursor
on?* That is the final answer for the **virtual** branch, because the document that opens **is**
`<rev>:<path>` — the number and the content come from the same object.

It is **not** the final answer for the **live** branch. There the document that opens is the
working-tree file, which may have drifted arbitrarily far from `<rev>` since. A line number that
is exact in the historical revision points at unrelated text in the file the user is about to
read, and the drift is largest exactly when the commit is old — the case where a reader most
needs the help. D14a's cited precedent is GitLens's enhanced "Open File", and GitLens maps
through the intervening history rather than reusing the historical number. So P5 does too:

> When the outcome resolves to `liveFile`, the historical line is re-mapped through a second
> diff — `<rev>` against the **working tree** — before the cursor is placed.

Four things make this cheap and safe rather than a second subsystem:

1. **It is one spawn, on an explicit user action.** `git diff <rev> -- <path>` is git's native
   revision-to-working-tree form: one process, no temp file, no stdin plumbing. It is nowhere
   near §5.1's ≤ 80 ms commit-select budget, which covers detail population and not this.
2. **The path is the same on both sides, by construction.** The live branch only fires when
   `pathExistsInCheckout(path)` is true, so the very path being diffed exists on disk. A file
   renamed since would have failed that test and gone virtual. Rename detection is therefore not
   just unnecessary here but undesirable, and the argv says `--no-renames`.
3. **It is the same arithmetic, reused rather than rewritten.** W1 exports a second entry point,
   `mapLineAcrossDiff(hunks, line, from)`, whose whole body is: find the row whose `from`-side
   number is `line` and hand that row index to `mapDiffLineToRevision(hunks, row, otherSide)`;
   if no row carries it — the line sits in unchanged territory `--unified=3` never emitted —
   apply the closed form `line + Δ` from the section above. Both semantics fall out for free: a
   line **deleted** from the working tree hits `mapDiffLineToRevision`'s backwards scan and lands
   where the removed text used to be, and a line in untouched territory shifts by the net
   insertion above it.
4. **It can only refine, never break.** If the drift diff has no hunks (the file is byte-identical
   to `<rev>`), or reports the path as having no post-image at all (untracked or ignored on disk,
   so git cannot see the file `pathExistsInCheckout` found — probe P6 pins both signals), or
   exceeds the same 1 MB patch cap the rest of the phase uses, the re-map is **skipped and the
   original line is used**. The refinement is strictly additive: every case that worked without
   it still works, which is what makes it safe to land in the same phase as the action itself.

**Working tree, not `HEAD`.** The comparison is against the bytes on disk, including uncommitted
changes, because the on-disk file is the document the editor is about to show. Diffing
`<rev>..HEAD` instead would cost exactly the same one spawn and be wrong in precisely the
situation the user is most likely to be in — mid-edit, with unstaged changes above the target
line, landing off by the size of their own uncommitted work. Probe P6 shows the two forms
disagreeing by exactly that amount on a repository built to have it. The one residual gap is a
file with **unsaved editor buffer** changes, where on-disk and buffer differ; reaching into the
dirty buffer is out of `EditorIntegration`'s vocabulary and the inaccuracy is momentary and small, so
it is accepted and recorded rather than chased.

This does not contradict §10's exit criterion ("lands on the mapped line in the live file … and
in the virtual historical blob **at that same mapped line**"): that sentence contrasts the two
branches — both land on *the* line rather than at the top of the file — and does not require the
live branch to skip refinement. The exit criteria below assert the drift case explicitly.

## What the git probes settled

Five behaviours this plan depends on, checked against real `git` (2.43.0 in this container;
above the 2.38 floor, so nothing below is version-contingent) rather than assumed. The
implementer should not re-derive these; they should extend them.

**P1 — `--numstat -z` frames a rename as two records, and gets the counts wrong.** For a commit
that renames `old.txt` → `new.txt` with one line changed:

```
diff-tree --numstat -z            →  "10\t0\tnew.txt\0"  "0\t10\told.txt\0"
diff-tree --numstat -M -C -z      →  "1\t1\t\0"  "old.txt\0"  "new.txt\0"
diff-tree --name-status -M -C -z  →  "M\0" "bin.dat\0" "R077\0" "old.txt\0" "new.txt\0"
```

Without `-M`, a 77%-similar rename reports **+10 −10**. With it, **+1 −1** — the truth — framed
as an empty third tab-field followed by two NUL-separated path records, exactly the
non-uniform-framing shape `parseNameStatusRecords` already handles for `R`/`C`. This is W2's
work item.

**P2 — a pathspec filters *before* rename detection, so a per-file diff of a renamed file must
name both paths.** Same commit, three invocations:

```
diff-tree -r -p -M -C <sha> -- new.txt            → "new file mode", "--- /dev/null", +10 lines
diff-tree -r -p -M -C <sha> -- old.txt new.txt    → "similarity index 77%", "rename from/to", +1 −1
diff-tree -r -p -M -C <sha>                       → the same correct rename diff
```

Passing only the new path makes a rename render as a whole-file addition. This is why
`commit.fileDiff` carries `originalPath` on the wire and why the argv builder passes both paths
when one exists. It is the single most likely way this phase ships something that looks right
and is wrong.

**P3 — `cat-file --batch` accepts `<rev>:<path>` directly, and its `missing` reply echoes the
input.** `HEAD:new.txt` returns `<oid> blob 36` plus content; `HEAD:nope.txt` returns
`HEAD:nope.txt missing`. So no change to `catFile.ts`'s protocol is needed to read a blob by
path — **except** that the reply echoes the *input string*, and `#tryParseHeader` splits the
header line on spaces and requires exactly two parts for `missing`. A path with a space in it
produces `HEAD:my file.txt missing` — four parts — which falls through both branches and
**throws `unrecognised header line`**. Verified. P5 is the first consumer that can pass a path
here at all, so this is P5's to fix (W2).

**P4 — the diff shapes the parser must handle, all observed:** `@@ -1,5 +1,5 @@`, a header with
a section heading (`@@ -15,6 +15,7 @@ n`), an omitted count (`@@ -1 +1 @@`), `\ No newline at end
of file` on both sides, a deleted file (`+++ /dev/null`, `@@ -1,21 +0,0 @@`), and a binary file
rendered as `Binary files a/bin.dat and b/bin.dat differ` with no hunks.

**P5 — `%(trailers:only=true,unfold=true)` works at the floor, and `%b` still contains the
trailer block.** `git show -s --format='%G?%x1f%b%x1f%(trailers:only=true,unfold=true)'` returns
the body *including* `Signed-off-by:`/`Co-authored-by:` lines and the trailer block again,
unfolded, as its own field. So git parses the trailers for us (its rules for what counts as a
trailer paragraph are subtle and not worth reimplementing), and the remaining work is splitting
the trailer paragraph off the body for display — W1's `splitTrailerBlock`. Incidental
observation: `%G?` on a repo with `gpg.format=ssh` and no `allowedSignersFile` writes a line to
**stderr** and still exits 0 with `N`; the driver classifies on exit code, so this is harmless,
but a reader of the logs should not mistake it for a failure.

**P6 — `git diff <rev> -- <path>` compares against the working tree, uncommitted changes
included, and reports a path git cannot see as a whole-file deletion.** This is the drift
re-map's command (W3's `worktreeDiff`). Built a repo, committed `f.txt`, committed two inserted
lines at the top, then added a *third* line on disk without committing:

```
git diff <base> -- f.txt        →  @@ -1,3 +1,6 @@   +Y0 +X1 +X2      (working tree: all three)
git diff <base> HEAD -- f.txt   →  @@ -1,3 +1,5 @@   +X1 +X2          (HEAD: uncommitted lost)
```

Two observations settle the design. First, the one-revision form is the whole reason the choice
of "working tree" costs nothing: it is the *same single spawn* as the `<base> HEAD` form and it
is the only one of the two that sees the user's unstaged edit — a reader mid-edit would land two
lines off with the `HEAD` form, and the whole point of the re-map is not to be off. Second, the
`null` condition has a precise, checkable signal rather than a heuristic: taking a file out of
the index while leaving it on disk yields

```
deleted file mode 100644 / +++ /dev/null / @@ -1,3 +0,0 @@
```

— a post-image of `/dev/null`. So "git cannot see the on-disk file" is read off the patch header,
not guessed, and an identical file produces **zero bytes** of output, which is the other `null`
case. Also confirmed in passing: `--no-optional-locks` is a **`git`-level** option and must
precede the subcommand — `git --no-optional-locks diff …`, not `git diff --no-optional-locks …`,
which exits 129 with a usage message. `driver.ts`'s `buildGitArgv` already places it correctly
for reads, so `worktreeDiff` must not repeat it in its own argv.

### What P1 left approximate, and why P5 is where it becomes wrong

`combineFileChanges` (`packages/git/src/queries.ts`) says so itself: because `numstat` runs
without `-M`/`-C`, a rename's line counts are "the best available approximation of 'lines
changed', not a true diff between the two". Probe P1 puts a number on the approximation: a
one-line edit inside a renamed file reports **+10 −10** instead of **+1 −1**. Nothing has ever
rendered those counts, so nothing has ever been wrong on screen. P5's exit criterion is "tree
correct for renames", so P5 fixes it: `numstatArgs` gains `-M -C`, `parseNumstatRecords` gains
the two-path record shape, and `combineFileChanges` joins on the new path directly instead of
reconstructing a rename from two independent records. Recorded here rather than in P1's Findings
because the fix ships in this phase's diff — the same convention P4 used for the defects it
inherited from P3.

### The `cat-file` header bug P5 is the first consumer to hit

Probe P3 above. `catFile.ts`'s `#tryParseHeader` cannot parse `HEAD:my file.txt missing`.
Until now every oid handed to that session was a 40-hex-character sha with no spaces, so the bug
was unreachable. P5 passes `<rev>:<path>` strings. The fix is to recognise the missing reply from
its **suffix** (` missing`) and treat everything before it as the echoed request, rather than
splitting on spaces and counting fields — three lines, and a unit test with a spaced path, added
to `catFile.test.ts`.

One further protocol constraint the same change must respect: `cat-file --batch` reads **one
request per line**, so a path containing a newline (legal in git) cannot be requested through the
batch session at all. `-z` batch input exists only from git 2.42, above our floor but not
guaranteed. The blob reader therefore falls back to a one-shot `git show <rev>:<path>` spawn —
argv, no line protocol — for the vanishingly rare path with a `\n` in it. Named because "no
skipped validation" means this case gets an answer, not an exception.

## The contract entries P5 adds

`CONTRACT_VERSION` 3 → **4**, which `wrapVersioned`/`validate.ts` enforce: the host, the harness
mock and the UI move in one commit or the app refuses to start. All wire types below are
**structural copies** of `packages/core`'s own, per §3.1's B3 rule, kept honest by extending
`tests/unit/ipc/wireConformance.test.ts` — the same discipline `PackedCommitChunk` already
follows.

```ts
// ---- new structural copies -------------------------------------------------------------

export interface CommitTrailer { readonly token: string; readonly value: string; }

export type FileChangeKind =
  | "added" | "modified" | "deleted" | "renamed" | "copied" | "typeChanged" | "unmerged";

export interface FileChange {
  readonly kind: FileChangeKind;
  readonly path: string;
  /** Set for `renamed`/`copied` only — and load-bearing: a per-file diff of a rename must
   *  name both paths in its pathspec or git renders it as a whole-file add (probe P2). */
  readonly originalPath: string | undefined;
  readonly similarity: number | undefined;
  readonly additions: number | undefined;   // undefined when isBinary
  readonly deletions: number | undefined;
  readonly isBinary: boolean;
}

export type SignatureStatus = "G" | "B" | "U" | "X" | "Y" | "R" | "E" | "N";

export type DiffLineKind = "context" | "add" | "del";

export interface DiffLine {
  readonly kind: DiffLineKind;
  /** Without the leading marker character. */
  readonly text: string;
  readonly oldLine: number | undefined;
  readonly newLine: number | undefined;
  /** git's `\ No newline at end of file`, attached to the line it followed. */
  readonly noNewlineAtEof: boolean;
}

export interface DiffHunk {
  readonly oldStart: number; readonly oldLines: number;
  readonly newStart: number; readonly newLines: number;
  /** Whatever git put after the closing `@@` — rendered in the hunk header row. */
  readonly heading: string;
  readonly lines: readonly DiffLine[];
}

export type FileDiffBody =
  | { readonly kind: "text"; readonly hunks: readonly DiffHunk[] }
  | { readonly kind: "binary"; readonly oldBytes: number | undefined;
      readonly newBytes: number | undefined }

  | { readonly kind: "liveFile"; readonly path: string; readonly line: number }

      readonly line: number }

      readonly reason: "notInRevision" | "binary" | "tooLarge" };

"commit.detail": {
```

## W1 — `core/src/model/diff.ts`: the model, the two maps, the trailer split

Four exports, all pure, no I/O, no framework — `packages/core`'s standing rule.

**1. The types.** `DiffLine`, `DiffHunk`, `FileDiffBody`, `FileDiff`, `CommitTrailer`, as
declared in the contract section above. `CommitDetail` in `model/commit.ts` grows `trailers` and
`signature.signer` alongside its existing `signatureStatus` (kept as
`signature: { status, signer }` — one field, not two, since a signer with no status is
meaningless).

**2. `mapDiffLineToRevision(hunks, rowIndex, side)`.** The algorithm is specified in full under
"The line map" above and is not restated here. What this item owes beyond the code is the test
matrix, which is the point of putting it in `core`:

- a context row, mid-hunk, both directions;
- an `add` row mapped to `"new"` (exact) and to `"old"` (backwards scan);
- a `del` row mapped to `"old"` (exact) and to `"new"` (backwards scan);
- the **first** row of a hunk being an `add` or a `del`, so the backwards scan finds nothing and
  falls back to `hunk.<side>Start`;
- a hunk header row and the file header row;
- a multi-hunk diff, asserting that the second hunk's numbers come from its own header and not
  from a running counter (the bug this design exists to prevent);
- an added file (`@@ -0,0 +1,N @@`) mapped to `"old"` — every row falls back, and the answer is
  clamped to `1`, not `0`;
- a deleted file (`@@ -1,N +0,0 @@`) mapped to `"new"`;
- a hunk with omitted counts (`@@ -1 +1 @@`);
- a row following a `\ No newline at end of file` marker, asserting the marker consumed no
  number.

**3. `mapLineAcrossDiff(hunks, line, from)`.** The drift re-map from "The second map" above —
`from` is `"old"` or `"new"`, and the answer is the corresponding line on the other side. It is
deliberately a thin wrapper and not a second algorithm: locate the row carrying `line` on the
`from` side and delegate to `mapDiffLineToRevision(hunks, thatRow, otherSide)`; if no row carries
it, return `line + Δ` where `Δ` is the closed form from "The line map" — the cumulative net
insertion of every hunk ending at or before `line` on the `from` side, and `0` before the first
hunk. Returns `line` unchanged when `hunks` is empty. Result clamped to `≥ 1`. Its own cases,
on top of the matrix above, which it inherits by delegation:

- a line **above** the first hunk (`Δ = 0`, unchanged) and a line **below** the last (`Δ` from
  that hunk);
- a line **between** two hunks, asserting `Δ` comes from the nearer preceding hunk and not from
  the sum of all hunks after it;
- a line **deleted** on the `from` side, asserting the backwards-scan semantics arrive through
  the delegation rather than being reimplemented;
- a hunk that is a pure insertion (`@@ -10,0 +11,3 @@`) and one that is a pure deletion,
  asserting `Δ`'s sign in each direction;
- `hunks` empty → identity;
- a line beyond the end of the file → still `line + Δ`, not an error (the caller may be pointing
  past a truncated read, and an off-the-end line is a harmless editor no-op).

**4. `splitTrailerBlock(body, trailers)`.** git hands us the trailer text (probe P5) but `%b`
still contains it. Returns the body with its trailer paragraph removed. The rule, stated so it is
testable rather than felt: **take the final blank-line-separated paragraph of the body; drop it
iff at least one trailer was returned and every one of its lines either matches
`^[A-Za-z][A-Za-z0-9-]*:` or is a folded continuation (begins with whitespace).** Cases: no
body; a body that is *only* trailers (result is an empty body, not the trailers again); a body
whose last paragraph contains a colon-prefixed line that is not a trailer (git returned no
trailers, so nothing is dropped); a folded trailer whose value wraps across lines; a trailer
paragraph followed by trailing blank lines.

This earns a unit test under `AGENTS.md`'s narrow policy on the strength of that case list —
it is a text-splitting rule with genuine boundary cases, not a round-trip.

**Done when:** the four exports type-check with `packages/core`'s no-I/O rule intact, and every
case above is covered. `mapLineAcrossDiff` contains no line arithmetic that
`mapDiffLineToRevision` does not — deleting the delegation and inlining a second walk should be
visibly a rewrite, not a refactor. Nothing in this item knows what a webview or a git process is.

## W2 — `git/src/parse/diff.ts`, and the two things P1 left for its first consumer

**1. The unified-diff parser.** Input is the bytes of one file's patch (the argv is W3's); output
is a `FileDiffBody`. It handles, because probe P4 observed every one of them: the `diff --git`
header, `similarity index` / `rename from` / `rename to`, `new file mode` / `deleted file mode`,
`index <old>..<new> <mode>`, `--- a/x` / `+++ b/y` (including `/dev/null` on either side),
`@@` headers with and without a section heading and with omitted counts, the three line markers,
`\ No newline at end of file`, and `Binary files a/… and b/… differ`.

Classification into `FileDiffBody`'s five shapes:

- **`binary`** — the `Binary files … differ` line, with sizes filled from
  `cat-file --batch-check` on the two blob oids the `index` line already carries (no extra
  spawn: the batch-check process is persistent and this is two round trips on an existing pipe).
- **`lfsPointer`** — D22 says "a pointer file is recognisable from its first line", and it is
  recognisable *in the patch itself*: the first content line of the first hunk is
  `version https://git-lfs.github.com/spec/v1`, followed by `oid sha256:…` and `size N`.
  Sniffing the patch rather than re-reading the blob costs nothing and is the only detection
  point that works for both sides at once. The label the UI renders is "LFS object, not fetched"
  (§11.2 D22's own words) plus the declared size.
- **`tooLarge`** — the patch exceeded W3's byte cap (see below).
- **`empty`** — a `diff --git` header with no hunks and no binary line: a pure mode change, or
  a rename with 100% similarity. The UI says which; it does not render an empty scroller.
- **`text`** — everything else.

Bytes, not strings, until the last moment: the parser decodes with the same
non-fatal `TextDecoder` every other parser in `parse/` uses, so a file with invalid UTF-8 renders
replacement characters rather than throwing. Line endings are left exactly as git emits them —
`core.autocrlf` is the user's business (§4.1) and rewriting them here would make the diff
disagree with the editor beside it.

Unit tests (recorded fixtures under `tests/fixtures/porcelain/`, via `recordPorcelain.ts`, per
this repo's convention): each of the five shapes, the three header variants, both `\ No newline`
positions, a multi-hunk patch, and a patch whose hunk line counts disagree with its header —
which must throw, not silently render.

**2. The numstat rename fix.** `numstatArgs` gains `-M -C` so it agrees with `nameStatusArgs`.
`parseNumstatRecords` learns the two-path record shape probe P1 documents: when the third
tab-field is empty, the next two records are `originalPath` and `path`.
`combineFileChanges` then joins on the new path for every kind, and its rename branch — which
today reconstructs a rename from an independent add and delete — collapses to the same code path
as everything else. Its existing doc comment goes with it. `tests/fixtures/porcelain/` gains a
recorded rename-with-edit fixture, and `diffTree.test.ts` asserts **+1 −1**, not +10 −10.

**3. The `cat-file` header fix.** Recognise ` missing` by suffix instead of by field count
(probe P3), so a path with a space in it resolves rather than throwing. Add the one-shot
`git show <rev>:<path>` fallback for a path containing a newline, which the line-oriented batch
protocol cannot express at our git floor. Two tests in `catFile.test.ts`: a spaced path that is
missing, and a spaced path that is found.

**Done when:** `bun test` covers the five body shapes and the three header variants; the rename
fixture reports the true counts; a spaced path round-trips through the batch session in both the
found and missing directions.

## W3 — `RepoService`: three queries, two caches, and one filesystem question

Five additions to `packages/git/src/repoService.ts`, each threading the caller's `AbortSignal`
through to `driver.read` — this is what keeps the ≤80 ms budget honest under keyboard
navigation, where a fast `↑`/`↓` run fires a detail request per row and every superseded one
must die rather than queue behind the live one. Same abort-on-supersede discipline §7.8 names
for search; the machinery (`ctx.signal` → `ReadOptions.signal`) already exists from P4 W2.

```ts
detail(repoId, sha, parentIndex, signal?): Promise<CommitDetailPayload>
fileDiff(repoId, sha, path, originalPath, parentIndex, signal?): Promise<FileDiffPayload>
blob(repoId, rev, path): Promise<BlobResult>          // for the virtual document source
worktreeDiff(repoId, rev, path, signal?): Promise<readonly DiffHunk[] | null>   // drift re-map
pathExistsInCheckout(repoId, path): boolean
```

**`detail`** is a thin wrapper over `queries.commitDetail`, which already exists and already
takes a `parentIndex`. Its `showBodyAndSignatureArgs` format widens to
`%G?%x1f%GS%x1f%(trailers:only=true,unfold=true)%x1f%b` — **body stays last**, preserving the
invariant that file's comment already states (a stray `0x1f` in a message can only corrupt the
last field). `%GS` gives the signer, which is what turns a `%G?` code into a sentence a user can
act on; it costs no extra process. W1's `splitTrailerBlock` runs on the result.

**`fileDiff`** builds:

```
diff-tree -r -p -M -C --no-commit-id --no-color --no-ext-diff --no-textconv \
          -z --unified=3 <baseSha|--root> <sha> -- [<originalPath>] <path>
```

`diff-tree` rather than §4.4's literal `git diff <base> <head> -- <path>`, for two concrete
reasons: `--root` handles a root commit natively (`git diff` would need the empty-tree oid
hard-coded, which is hash-algorithm-dependent), and an explicit `<parent> <sha>` pair is exactly
what the merge parent selector needs. Same command family the file tree already uses. This is a
judgment call, recorded below, not a contradiction of the spec — §4.4's line describes the intent.
`--no-ext-diff` and `--no-textconv` matter: a user's configured external diff driver or textconv
filter must not be spawned by a panel repaint.

Both paths are passed when `originalPath` exists — probe P2 is the reason.

**`worktreeDiff`** is the drift re-map's one command, and it is the only place in this phase that
diffs against something mutable:

```
diff --no-color --no-ext-diff --no-textconv --no-renames -z --unified=3 <rev> -- <path>
```

`git diff <rev> -- <path>` — one revision, no second revision — is git's native
revision-against-working-tree form, so the comparison includes uncommitted changes without a temp
file or a stdin pipe (probe P6). `--no-renames` because the path is fixed on both sides by
construction (see "The second map"); `--no-ext-diff` / `--no-textconv` for the same reason as
`fileDiff`. It goes through `driver.read`, so `--no-optional-locks` is already prepended by
`buildGitArgv` — it must **not** be repeated inside the diff argv, where git rejects it as an
unknown option (probe P6). That flag matters more here than anywhere else in the phase: this is
the one command that touches the working tree, and a cursor placement must never take the index
lock or write a refreshed index as a side effect.

It returns `null` — meaning *do not re-map* — in three cases, and the caller then uses the
historical line unchanged:

- **no output at all** — the on-disk file is byte-identical to `<rev>:<path>` (probe P6: zero
  bytes);
- **no post-image** — the patch says `+++ /dev/null` / `deleted file mode`, which is what git
  reports for a path it cannot see: untracked, or ignored, even though `pathExistsInCheckout`
  found a file there (probe P6). Read off the header, not inferred from the hunks;
- **over the 1 MB patch cap** — the same constant `fileDiff` uses, or a spawn that failed.

`null` is a refinement declining to fire, never an error, and it is not surfaced on the wire.

**It is deliberately not cached.** The other two caches key on immutable object identity; this
one's answer changes on every keystroke in the user's editor. A third cache would need the one
piece of invalidation machinery the other two are structured to avoid, to save a single spawn on
an action that happens at human speed. Recording the reason here is what stops a later phase
adding it.

**The two caches, and why they are different.** §5.5 calls for a "diff text LRU (cap by bytes,
not entries)":

- **Diff cache** — keyed `<baseSha>:<sha>:<path>`, capped by total bytes (**4 MB**, a named
  constant), evicted least-recently-used, dropped with the repo session. Its contents are
  genuinely immutable: two tree oids and a path determine a patch forever. It is **never
  invalidated by the watcher**, and saying so is the point — the absence of invalidation
  machinery here is a fact about git objects, not an oversight.
- **Detail cache** — keyed `<sha>:<parentIndex>`, capped by entry count (**64**), and
  **dropped on `refsChanged`**, because one field of it is not immutable: `decoration` (`%D`) is
  a fact about refs, not about the commit. A re-fetch is ~20 ms, so dropping the whole entry is
  cheaper to reason about than patching one field of it.

A single per-file patch is also capped: above **1 MB** the body is `tooLarge` and the patch is
never materialized into hunks. `catFile.ts`'s existing 10 MB blob gate covers the blob side, and
its own comment already says the "too large to display" copy is this phase's.

**`pathExistsInCheckout`** is the whole of D14a's live-vs-virtual decision, and it is one
`fs.existsSync(join(session.identity.root, path))`. `packages/git` is the package that owns the
filesystem (`nodeFileWatcher.ts` already lives there), so this needs no new port and no spawn.
Deliberately *not* `git ls-files` or `cat-file -e HEAD:<path>`: the question is "is there a file
on disk at that path", and the index and HEAD both answer a different question — a tracked file
deleted in the worktree, or an untracked file present in it, would each get the wrong answer.
Path traversal is refused (a `path` escaping the root after normalization returns `false` and
logs), because this value arrives from the webview.

**Done when:** both commit queries are cancellable and a superseded request's process is actually
killed (asserted by spawn counting in W16); the diff cache evicts by bytes; the detail cache
clears on a `refsChanged`; `pathExistsInCheckout` returns false for `../../etc/passwd`;
`worktreeDiff` returns hunks for a file edited but not committed since `<rev>`, and `null` for an
identical file and for an untracked one.

## W5 — The two ports, and the virtual document

Both port files are already named in §3.1's tree and both rows are already in §3.3's table. This
item writes the interfaces and the one shipped implementation of each.

**`core/src/ports/clipboard.ts`:**

```ts
export interface Clipboard { writeText(text: string): Promise<void>; }
```

One method. §3.3's row says "copy sha, branch, message"; branch copying arrives with P6's ref
surface and needs nothing more from the port. The VS Code implementation is
`vscode.env.clipboard.writeText`. A failure **propagates** — it is not swallowed into a boolean —
so `rpc.ts`'s `toWireError` carries the reason across and the UI can say what went wrong. §6.4:
"If the clipboard write fails, say so; a copy affordance that silently does nothing is worse than
none."

**`core/src/ports/editorIntegration.ts`** is the richer one, and §3.3 says so ("the one port
whose contract is genuinely richer than a single call"). It must describe a native diff, a
reveal-at-a-line, and a lazily-materialized read-only document — without knowing that git exists:

```ts
export type DocumentRef =
  /** An absolute path on disk. */
  | { readonly kind: "file"; readonly path: string }
  /** Content the app produces on demand; `label` is the filename the host shows, which is also
   *  what drives its syntax highlighting. */
  | { readonly kind: "virtual"; readonly key: string; readonly label: string }
  /** The empty side of an add or a delete. */
  | { readonly kind: "empty"; readonly label: string };

export interface VirtualDocumentSource {
  /** Resolves the text for a key previously handed to `openDiff`/`reveal`; `undefined` if it
   *  is no longer resolvable (the repo was closed). */
  provide(key: string): Promise<string | undefined>;
}

export interface EditorCapabilities {
  readonly openInEditor: boolean;
  readonly goToFile: boolean;
}

export interface EditorIntegration {
  readonly capabilities: EditorCapabilities;
  /** Registered once, at activation. */
  registerVirtualDocuments(source: VirtualDocumentSource): Disposable;
  openDiff(req: { left: DocumentRef; right: DocumentRef; title: string }): Promise<void>;
  /** Opens `ref` and puts the cursor on `line` (1-based). */
  reveal(ref: DocumentRef, line: number): Promise<void>;
}
```

`packages/host-vscode/src/ports/editorIntegration.ts` implements it with
`vscode.workspace.registerTextDocumentContentProvider`, `vscode.commands.executeCommand("vscode.diff", …)`
and `window.showTextDocument(doc, { selection })`. Four details that are the difference between
this working and nearly working:

1. **The scheme is `kira-version`**, registered once in `activate()`, disposed with the
   extension. The URI is `kira-version:/<opaque key>/<basename>` — the key is opaque to VS Code
   and meaningful only to the `VirtualDocumentSource`, and **the last path segment is the real
   filename**, because that is what VS Code resolves the language mode from. A virtual blob that
   opens without syntax highlighting is the most visible way to get this wrong.
2. **Content is cached by VS Code per URI and we never invalidate it.** A `<rev>:<path>` blob is
   immutable, so `onDidChange` is never fired and the provider needs no event emitter. Stating
   this is what stops someone adding one.
3. **`vscode.diff` gets two virtual URIs**, not a virtual URI against the working file: both
   sides of a historical diff are historical. An added file's left side is the `empty` ref; a
   deleted file's right side is.
4. **`capabilities` is a constant `{ openInEditor: true, goToFile: true }` here**, and it is what
   `app.init` reports. The conflict-resolution capability §7.11 and D15 describe is **not** added
   in this phase — the port grows it at P6, where it has a consumer.

`extension.ts` constructs both ports beside the existing four and passes them into
`KiraGraphViewProvider`, which passes them into `createRepoHandlers`. It also constructs
`Storage` at last? — no: `Storage` still has no consumer, and P3's own comment on that
(`extension.ts`'s header) stands untouched.

**Done when:** both ports compile with no `vscode` import outside `host-vscode` (the existing
import-boundary check proves it); the provider is registered and disposed with the extension;
`capabilities` reaches the UI through `app.init`.

## W6 — `rpcHandlers.ts`

Five handlers and one registration, following the file's own stated rule — "no policy beyond
mapping".

`RepoServicePort` widens to include `detail`, `fileDiff`, `blob`, `worktreeDiff` and
`pathExistsInCheckout`, so W16's tests can still drive a structural fake through the real server.

`commit.detail` and `commit.fileDiff` forward, passing `ctx.signal`. `clipboard.write` calls the
port and logs `label`, never `text`.

**`editor.openDiff`** resolves both sides into `DocumentRef`s and calls the port. For a rename it
labels the left with `originalPath` and the right with `path`, and titles the tab
`<basename> (<shortSha>^ ↔ <shortSha>)` — the rename arrow lives in the file tree, and a title
that fits is worth more than one that is complete.

**`editor.goToFile`** is D14a's decision procedure, in the order stated at the top of this plan
and in no other order:

```
1.  service.pathExistsInCheckout(repoId, path)
1a.   hunks = await service.worktreeDiff(repoId, rev, path, ctx.signal)   // drift re-map
      final = hunks === null ? line : mapLineAcrossDiff(hunks, line, "old")
      → reveal({kind:"file", path: join(root, path)}, final)
                                                              → { kind:"liveFile", line: final }
2.  service.blob(repoId, rev, path)
      missing   → { kind: "unavailable", reason: "notInRevision" }
      binary    → { kind: "unavailable", reason: "binary" }     // NUL byte in the first 8 KB
      tooLarge  → { kind: "unavailable", reason: "tooLarge" }   // catFile's existing gate
      found     → reveal({kind:"virtual", key, label: basename(path)}, line)
                                                              → { kind:"virtualBlob", line }
```

**Step 1a is the drift re-map, and it belongs here rather than in the UI** for three reasons: the
handler already holds the `RepoService` and the diff machinery, so it costs no new plumbing;
doing it client-side would mean a *second* round trip on a user-visible action, where this is one
handler doing two things behind one call; and it lets `GoToFileOutcome.liveFile.line` mean "the
line the cursor is actually on", which is what the UI's announcement quotes back to the user. The
`from` side is `"old"` because `worktreeDiff`'s pre-image is `<rev>` — the revision `line` was
mapped in — and its post-image is the working tree.

The step **cannot** encounter a path missing from the working tree: it runs only on the branch
that `pathExistsInCheckout` already answered true for. Everything else that can go wrong —
identical file, path git cannot see, patch over the cap — arrives as `null` from `worktreeDiff`
and falls back to the unmapped `line` (W3). A failed spawn is caught and treated the same way: a
refinement that cannot run must never turn a working "Go to file" into an error.

The `VirtualDocumentSource` registered at W5 is implemented here, over `service.blob`: the key
encodes `<repoId>\0<rev>\0<path>` and resolving it is one `cat-file` round trip on the session
that is already open. A key whose repo has since been closed resolves to `undefined`, and VS Code
shows an empty document rather than the extension throwing — which is the honest outcome, since
the content genuinely is no longer reachable.

**Done when:** all five handlers are bound and logged like their neighbours; a `goToFile` for a
path that exists on disk, a path that does not but whose blob does, and a path whose blob does
not, each return their own outcome branch — asserted in W16 against a real repository — and a
`liveFile` result for a file edited since `<rev>` reports a `line` **different from** the one
passed in, by exactly the net insertion above it.

## W7 — `state/detail.ts` and `CommitMeta.vue`

**`state/detail.ts`** is the pane's state machine, and keeping it out of the SFC is what lets
W13 test the transitions and P7 mount the same components in a sidebar. It holds, all
`shallowRef`:

- `sha` (the selected commit, mirrored from `SelectionState`), `parentIndex`, `detail` (the
  payload or `undefined` while loading), `error`;
- `mode: "detail" | "diff"`, `selectedFile` (an index into `detail.files`), `diff`;
- `listMode: "tree" | "flat"`, `filter`.

And the rules that make the ≤80 ms budget and the keyboard model work:

- **One in-flight request per kind.** Selecting a new commit aborts the previous
  `commit.detail`; moving the file cursor aborts the previous `commit.fileDiff`. The
  `AbortController` is held here, not in a component.
- **A response for a sha that is no longer selected is dropped**, not rendered — the same
  sequence discipline `GraphViewState` already applies to stream chunks. Aborting is not
  sufficient on its own: an abort raced by a resolution still resolves.
- **Changing `parentIndex` re-requests the detail** (the file list is per-parent) and resets
  `selectedFile` and `mode` — the file you were reading may not be in the other parent's diff at
  all, and silently keeping a stale selection is how a diff ends up labelled with the wrong path.
- Selecting a **different commit** resets `parentIndex` to 0, `mode` to `"detail"` and clears
  `diff`. Selecting the **same** commit again is P4's toggle and does not reach this class.

**`CommitMeta.vue`** renders §6.4's items 1 and 3 — message at the top, details at the bottom,
with the file tree between them, which is §6.4's stated order ("message, then files, then
details") and its stated reason (the tree is what the user came for).

- **Message**: subject, then the trailer-stripped body, with **URL and issue linkification**.
  Linkification is a plain regex pass producing `<a>` elements built as DOM (never `innerHTML`),
  opened through `ExternalOpener`— which does not exist yet as a port. **Decision: v1 P5 renders
  URLs as `<a href>` and lets the host's own webview link handling take them**, which VS Code
  does natively for a webview link, and adds no port with one consumer. Issue references
  (`#123`) are *not* linkified here: without §6.7's repository resolution there is nothing to
  link them to, and a link that goes nowhere is worse than plain text. Recorded as an open item
  for P12, which is the phase that learns what `#123` means.
- **Trailers** render as a small definition list under the body, with `Co-authored-by` and
  `Signed-off-by` getting the treatment §6.4 names them for.
- **Details**: full and short sha (each its own copy button, W10), parents as short shas,
  author and committer with both timestamps **shown only when they differ** (§6.4), every ref
  pointing at this commit reusing P4's `refBadges.ts` builder, and the signature line.
- **Signature** maps `%G?` to text — Good / Bad / Good, unknown validity / Good, expired
  signature / Good, expired key / Good, revoked key / Cannot check / (nothing at all for `N`).
  With `%GS` this becomes "Good signature by Alice", which is the only form of it worth showing.
  An unsigned commit shows no row, not an empty one.
- **A parent sha is a button that selects that commit** when it is in the loaded range
  (`CommitStore.rowOfSha` ≠ −1) and is rendered inert with a title saying "not loaded — load
  more history to reach it" when it is not. Loading pages up to an arbitrary commit is §5.1.1's
  search-result behaviour and belongs to P11; a button that silently does nothing does not.

**Done when:** the pane populates for a commit with no body, a commit whose body is entirely
trailers, a merge, a root commit, a signed commit and an unsigned one, without a special case
leaking into the template.

## W8 — `FileTree.vue` and `fileTreeModel.ts`

§6.4 item 2: "hierarchical, collapsible, with per-file status (A/M/D/R/C), rename arrows, and
`+adds/−dels`. Directory rows aggregate their children's counts. Toggle between tree and flat
list; a filter box within the tree."

**`fileTreeModel.ts`** is the pure half: a flat `readonly FileChange[]` folds into a directory
tree, directories aggregate their descendants' additions and deletions and file counts, and
single-child directory chains collapse into one row (`src/main/java/` rather than three rows) —
which is what VS Code's own Explorer does and what keeps a short panel readable. It also
produces the flat list and applies the filter, so both list modes share one code path and the
filter cannot behave differently between them. The filter matches on the full path,
case-insensitively, substring — not fuzzy, not regex; §7.8 owns search semantics and this box is
not it.

**Status and colour.** §6.1: "Git status colours come from git's own tokens … so a modified file
in our file tree is the same colour as in the Explorer." `A/M/D/R/C/T/U` map to
`--vscode-gitDecoration-addedResourceForeground` and its siblings through the `--kv-*` layer, and
the letter is rendered as text beside the colour, because §6.1 also forbids colour-only meaning.

**Renames** render `originalPath → path` with the arrow, truncating the common prefix (a file
moved within a directory shows `old.ts → new.ts`, not two full paths). The similarity score is in
the row's title attribute, which is where a number that is occasionally interesting but never
worth the width belongs.

**The parent selector** lives in this component's header rather than in a file of its own — it is
a `<select>` of `parents.length` entries that exists only for merges, and §3.1's tree does not
anticipate a component for it. Entries read `Parent 1 · a1b2c3d · <subject>`, with the subject
filled in from `CommitStore` when that parent is loaded and omitted when it is not. Default is
parent 0, per §4.4. Octopus merges (three or more parents) get the same control with more
entries; nothing special-cases two.

**The render cap, and why there is no second virtualizer.** A commit can touch thousands of
files (a bulk rename, a vendored-dependency update, a merge of a long branch), and §5.1's ≤80 ms
covers "detail pane populated". Rendering 4,000 rows into the DOM will not make it. The answer is
**not** a second virtualizer: `AGENTS.md`'s prefer-a-library rule is about non-trivial
infrastructure, and the honest observation is that this list does not need one — a commit's file
count is bounded by what one commit did, and the pathological case is rare. So the tree renders
at most **500 rows** and, past that, shows a "Show all N files" row that lifts the cap for the
current commit. Explicit degradation, one constant, no new machinery. If W15's measurement says
the cap is in the wrong place the escalation ladder is: raise the cap → render the *flat* list
through the same SlickGrid `CustomDataView` adapter `CommitGrid.vue` already establishes. That
would be a Finding with a number in it, not a redesign.

**Keyboard**, while focus is in the tree: `↑`/`↓` move the file cursor (and, per §6.4, the diff
follows it), `→`/`←` expand and collapse a directory, `Enter` opens the selected file's diff,
`Home`/`End` jump. Directory rows are skipped by `↑`/`↓` when the list is in flat mode, because
there are none.

**Done when:** the tree is correct for a commit containing an add, a modify, a delete, a rename
with edits, a copy, a type change, a binary file and an LFS pointer; directory counts equal the
sum of their descendants; the filter narrows both modes identically; a 5,000-file commit renders
the cap and its "show all" row.

## W9 — `DiffView.vue`: the third region

§6.4: clicking a file "opens its diff for that commit — this is the primary interaction of the
pane, not a secondary action", rendered in the in-app unified view, "which opens as a third
region: on wide panels it takes over the detail pane with a back affordance to the file tree; on
narrow panels it opens as a full-width overlay."

**Presentation, per breakpoint** (P4's `breakpoint` computation in `App.vue` is reused, not
recomputed):

| Breakpoint | Detail pane | Diff |
|---|---|---|
| `≥ 900` (wide) | docked right | takes over the pane; header carries a back affordance |
| `600–900` (narrow) | docked right, collapsed by default | same take-over |
| `< 600` (overlay) | overlay drawer | full-width overlay over the graph |

**The diff body** is a two-column layout — a gutter of old/new line numbers, then the content —
using `--vscode-editor-font-family`/`-size` so it matches the editor beside it (§6.1). Added and
removed lines take their backgrounds from `--vscode-diffEditor-insertedTextBackground` and
`removedTextBackground`, with `+`/`−` glyphs carrying the same distinction for high-contrast and
for anyone who cannot rely on the colour. Hunk headers are their own row, showing git's section
heading when there is one. `\ No newline at end of file` renders as a muted marker on the line it
belongs to.

**The non-text bodies each get one honest row**, never a rendered approximation: "Binary file —
not shown (12.4 KB → 12.9 KB)"; "LFS object, not fetched — 48.2 MB" (D22); "File too large to
display (14.1 MB, limit 1 MB)"; "No content change — file mode changed" / "renamed with no
changes". §6.4: "binary files and LFS pointers are labelled rather than rendered as garbage."

**The `Esc` chain.** `App.vue`'s handler already says in a comment that P5 "inserts a step above
this one rather than reimplementing the tail". It becomes: an open menu (none in P5) → the diff
view → the detail pane or drawer. One handler in `App.vue`, as §6.6 requires, driven by
`DetailState.mode`.

**The keyboard model, and the one thing §6.4 leaves to be reconciled.** §6.4 says "Arrow keys
move between files in the tree with the diff following the selection, so a commit can be reviewed
file by file without the mouse" — and it also says the diff *takes over the pane*, which means
the tree is not on screen while the diff is. Both sentences are satisfiable; they are not
satisfiable by binding plain `↑`/`↓` to two things at once. The resolution:

- **Focus in the tree** → `↑`/`↓` move the file cursor and the diff follows it. This is §6.4's
  sentence, unmodified, and it is the flow at the moment the user is choosing what to read.
- **Focus in the diff** (after `Enter`, a click, or the take-over) → `↑`/`↓` scroll the diff,
  because that is what arrow keys do inside a scrollable region and taking that away would be a
  worse surprise than the one we are avoiding. File-to-file movement stays keyboard-reachable
  through **`Alt+↑`/`Alt+↓`** and through the diff header's own prev/next buttons, which also
  carry the position ("3 of 12 · src/foo.ts") so the review has a sense of progress.
- `←`, `Backspace`, the back affordance and `Esc` all return to the tree, where plain arrows
  resume moving files.

This is recorded as a judgment call rather than assumed, and it is worth stating in the plan
because a reader of §6.4 alone would reasonably build the other thing.

**Done when:** the diff opens from a tree click and from `Enter`; it follows the file cursor
while focus is in the tree; the back affordance and `Esc` return to the tree; the three
breakpoint presentations each render; the five body shapes each render their own row; and no
diff request outlives the selection that made it.

## W10 — "Open in editor", "Go to file", and the copy actions

**The two editor actions** live in the diff view's header and are rendered **only when
`capabilities.openInEditor` / `capabilities.goToFile` are true** — the feature detection §3.3
asks for, exercised for the first time here.

"Go to file" needs a cursor position, so the diff view tracks a **focused row**: the row the user
last clicked or arrowed to, defaulting to the first row of the first hunk. It is rendered with a
subtle current-line background (`--vscode-editor-lineHighlightBackground`) so the action's target
is visible before it is taken — an action whose result depends on an invisible cursor is one the
user cannot aim.

The click path is then exactly the algorithm from the top of this plan:

```
side  = change.kind === "deleted" ? "old" : "new"
rev   = side === "old" ? baseSha : sha
path  = side === "old" ? (originalPath ?? path) : path
line  = mapDiffLineToRevision(hunks, focusedRow, side)      // core, W1 — a line in `rev`
outcome = await bridge.request("editor.goToFile", { repoId, rev, path, line })
```

**The UI maps once and only once.** The drift re-map for a live file happens inside the handler
(W6 step 1a), not here — so this call site never needs a second request, and `outcome.line` is
always the line the cursor actually landed on, whichever branch fired. That is what the
announcement quotes, which is why it is always true and not merely usually true.

The outcome is announced through the existing polite live region and shown inline for a
moment: "Opened src/foo.ts at line 47", "Opened the version from a1b2c3d — this path is not in
your checkout", or "src/foo.ts is not in a1b2c3d". The second string is the one that matters:
the virtual-blob fallback is not a failure and must not read like one. The first quotes
`outcome.line`, never the locally computed `line`; on a file that has drifted they differ, and
showing the historical number next to a cursor sitting somewhere else is the specific bug this
sentence exists to prevent.

The extra spawn step 1a costs sits on an explicit user action and outside §5.1's ≤ 80 ms budget,
which measures commit-select → detail populated. No perf metric is added for it (W15), per
`AGENTS.md`'s rule about measuring only a real question — a single `git diff` on a click is not
one.

For a **binary, LFS or too-large** body both actions are hidden — there is no line to map and
nothing a text editor should be asked to open. "Open in editor" remains available for a binary
file, because `vscode.diff` renders binaries with its own image/binary handling and that is
strictly better than our row of text; "Go to file" does not.

**The copy actions** are three, and they use the `Clipboard` port through `clipboard.write`:

| Where | Copies |
|---|---|
| The commit list's sha column button — P4 shipped it `disabled` with a title saying P5 lands it | the **full** sha (what you paste into a command) |
| `CommitMeta.vue`'s details block: two buttons | the full sha; the short sha |
| `CommitMeta.vue`'s message block | the full message (subject + body, trailers included) |
| A file row's context affordance in `FileTree.vue` | that file's path |

Feedback is immediate and names what was copied ("Copied full SHA"), through the live region plus
a ~1.5 s inline confirmation. A rejected `clipboard.write` renders "Couldn't copy — <reason>" in
the same place and logs; §6.4 is explicit that silence is the one unacceptable outcome.

**Done when:** the sha column button is enabled and its P4 placeholder title is gone; every copy
site reports success and failure; a mock clipboard rejection produces a visible message, asserted
in W13; and "Go to file" on a live file that has been edited above the cursor since the commit
places the cursor on the **shifted** line, with the announcement naming that same number —
asserted in W13 against the harness and in W16 against a real working tree.

## W12 — The harness on P5's surface

`apps/harness/src/mockBridge.ts` gains handlers for all five requests plus `capabilities` on
`app.init`, and `Scenario` gains the fixture data they serve. This is the item that decides how
much of P5 is testable without a git process, so it is specified rather than left to the
implementer's judgment.

**`Scenario` grows:**

```ts
/** Per-sha detail, served by `commit.detail` — keyed by sha, then by parentIndex. */
readonly details?: Readonly<Record<string, readonly CommitDetailFixture[]>>;
/** Per-sha, per-path diff bodies served by `commit.fileDiff`. */
readonly diffs?: Readonly<Record<string, FileDiffBody>>;
/** D14a's one question, modelled: which paths exist in "the checkout". */
readonly checkoutPaths?: readonly string[];
/**
 * The drift between `<rev>` and "the working tree", per `<rev>\0<path>`: the hunks the real
 * host would get from `worktreeDiff`. Absent means no drift — the re-map is skipped and the
 * historical line is used, exactly as `worktreeDiff` returning `null` does.
 */
readonly worktreeDrift?: Readonly<Record<string, readonly DiffHunk[]>>;
/** Which capabilities this scenario's "host" reports — `undefined` means all true. */
readonly capabilities?: { openInEditor: boolean; goToFile: boolean; clipboard: boolean };
```

**The harness models an editor, and this is in character rather than a test hook.** §2.2 calls
the harness "a real second consumer", and a host that can open documents is exactly what
`EditorIntegration` abstracts. So `editor.goToFile` in the mock runs the *same decision
procedure* as the real handler — **step 1a included**, with `worktreeDrift` standing in for
`worktreeDiff` and the same `mapLineAcrossDiff` from `@kira-version/core` doing the arithmetic,
since the harness may import `core` even though it may not import `git`. `checkoutPaths.includes(
path)` stands in for `fs.existsSync` and the scenario's own fixtures stand in for the object
database, and the mock records what it did on `window.__kiraHarness.lastEditorAction`. That makes
all four D14a cases *and* the drift re-map deterministic and assertable in the fast tier; the
real filesystem branch is W16's job, on a real repository. `clipboard.write` writes through
`navigator.clipboard.writeText` and records the call, so both the success and the rejection paths
are drivable.

**Four new scenarios**, each existing to make one thing assertable:

- **`detail`** — one commit with a body, two trailers, a signature, refs, and a file tree
  containing an add, a modify, a delete, a rename-with-edits, a copy, a binary file, an LFS
  pointer and an over-cap file. The workhorse.
- **`merge`** — a three-parent (octopus) merge whose three parents produce *different* file
  lists, so switching the parent selector visibly changes the tree and cannot be faked by a
  stable fixture.
- **`goToFile`** — one commit touching four files whose `checkoutPaths` produces one of each
  outcome: a path present in the checkout (live file), a path deleted since, a path renamed
  since, and a path from a commit that is not an ancestor of the checkout — plus a fifth whose
  blob is missing entirely (`unavailable`). The three middle cases are three user stories with
  one implementation, and the scenario exists to prove all three reach the same fallback. The
  live-file path carries `worktreeDrift` with an insertion above the target line, so the
  re-mapped and historical numbers are **provably different** and a regression that drops step 1a
  fails rather than passing quietly; a *sixth* file is live with no drift entry, pinning the
  `null` path where the two numbers agree.
- **`noCapabilities`** — the same commit as `detail` with all three capabilities false, so the
  feature-detection path (no "Open in editor", no "Go to file", no copy buttons) has a target.

**Done when:** every request in the contract has a mock handler; the four scenarios load from
`?scenario=`; and the mock's `goToFile` and the real handler share their decision order by
construction (a comment in each pointing at the other, since the harness may not import
`@kira-version/git`).

## W14 — The accessibility pass

§6.6 makes keyboard reachability and ARIA a v1 requirement, and P4 established both the bar and
the tooling (`@axe-core/playwright` over all four theme kinds, already a pinned devDependency).
This item extends `a11y.spec.ts` to the pane rather than starting a second approach.

- **The file tree is a `tree`** — `role="tree"`, `role="treeitem"` with `aria-expanded` on
  directories, `aria-level`, and a single roving `tabindex` on the file cursor. In flat mode it is
  a `listbox`/`option` pair, because a flat list is not a tree and announcing it as one is worse
  than announcing nothing. The toggle changes the role, which is legitimate and is the reason the
  two modes are one component rather than two.
- **The diff is a `table`** of rows with old-number, new-number and content cells, so a screen
  reader can read "line 42, added, `const x = 1`" rather than a wall of text. Each row's
  accessible name states its kind in words; the `+`/`−` glyph is `aria-hidden`, since the kind is
  already in the name.
- **Focus order** across the pane's three regions is stated and tested: entering the pane lands
  on the file cursor; the back affordance and the two editor actions are reachable; leaving the
  diff returns focus to the file it was showing, not to the top of the tree.
- **Announcements** ride the existing live region: the outcome of "Go to file", what a copy
  copied, and "showing 500 of 4,213 files" when the cap applies.
- **No colour-only meaning**: every status carries its letter, every diff line carries its glyph.

**Done when:** axe reports no serious or critical violations on the populated pane and the open
diff in any of the four theme kinds; the whole pane is operable from the keyboard alone, scripted
end to end in `commitDetail.spec.ts`.

## W15 — Perf: the ≤80 ms budget, measured where it actually lives

§5.1: "Commit select → detail pane populated ≤ 80 ms." `AGENTS.md` says to measure when a real,
concrete question is at stake. There are two here and they live on opposite sides of the wire, so
they are measured separately rather than conflated into one number that could not be attributed.

**The host half — the real question.** Populating the pane costs **four git spawns** (metadata,
body+signature+trailers, numstat, name-status; three of them concurrent) plus parsing. Whether
that fits in 80 ms on a real repository is not answerable from the harness, which has no git.
So `tests/perf/historyPipeline.ts` — which already stands up a real generated repository and a
real `RepoService` — gains two metrics rather than a fifth script being added to `test:perf` for
one number:

| Metric | What | Bar |
|---|---|---|
| `commitDetailMs` | median over 20 commits including one merge and one commit touching 500 files | ≤ 80 ms, gated |
| `commitDetailCachedMs` | the same selection repeated — the cache path a keyboard walk actually takes | recorded, not gated |
| `fileDiffMs` | median over 20 files including one 5,000-line file | recorded, not gated (§5.1 sets no budget for it) |

**The renderer half** is asserted where it is cheap: `graphUi.ts` gains a recorded-only
`detailPaintMs` (selection to the pane's file tree being in the DOM, mock latency zero, so it
measures render cost alone) and the `detail` scenario's 5,000-file commit is what makes the W8
render cap's number meaningful rather than assumed. `commitDetail.spec.ts` additionally asserts
a wall-clock ceiling on the harness so a gross regression fails the fast tier, with the honest
note that a mock-backed number is not §5.1's number.

**If `commitDetailMs` misses**, the ladder is named in advance so it is not invented under
pressure: (1) drop the separate body/signature `show` and fold it into the metadata `show` — one
fewer spawn, at the cost of the field-corruption invariant that call was split for; (2) skip the
`numstat` run for a commit whose `name-status` is above the render cap, showing statuses without
counts for that outlier; (3) reuse a persistent process. Only after all three would the ≤80 ms
bar itself be a Finding.

**Done when:** `commitDetailMs` reports against a committed baseline and is within budget, or the
miss is attributed by structure (spawn count, parse, wire) rather than reported as a number.

## W16 — Integration: real git, real repositories

`tests/integration/commitDetail.test.ts`, against repositories built by
`tests/fixtures/generateRepo.ts` — the tier where the things the harness models are checked
against the thing itself.

- A commit with a **rename plus an edit**: the tree reports the true `+1 −1` (the P1 fix), the
  per-file diff renders as a rename and **not** as a whole-file add (probe P2's trap), and the
  `similarity` matches git's own.
- A **merge**: `parentIndex` 0 and 1 produce different file lists; an **octopus** merge exposes
  all its parents; a **root** commit's detail against the empty tree is a real diff, not an error.
- **Binary** and **LFS-pointer** files classify correctly; an over-cap file reports `tooLarge`.
- **`editor.goToFile`'s three branches against a real checkout**: a path present on disk resolves
  `liveFile`; a path deleted since resolves `virtualBlob`; a file added on a **branch that is not
  an ancestor of HEAD** resolves `virtualBlob` — the case D14a exists for, and the one that is
  only convincing against a real object database. A path missing from the revision resolves
  `unavailable`.
- **The drift re-map against a real working tree**, which is the half the harness can only model.
  Take a commit, then in a *later* commit insert N lines above a known line of the same file, and
  assert `goToFile` at that line returns `liveFile` with `line + N`. Then, without committing,
  insert M more lines above it on disk and assert the answer moves to `line + N + M` — the
  assertion that pins "working tree, not `HEAD`", and the one that would still pass a
  `<rev>..HEAD` implementation if it were omitted. Finally `git rm` nothing and instead make the
  path **untracked** (delete it from the index, leave it on disk): `worktreeDiff` returns `null`,
  the outcome stays `liveFile`, and the line is the unmapped historical one.
- **Blob-by-path reads through `cat-file --batch`**, including a path with a **space** in it in
  both the found and the missing directions (the W2 fix), and a path with a newline taking the
  one-shot fallback.
- **Cancellation**: a superseded `commit.detail` kills its processes — asserted by spawn
  counting through the existing fake `ProcessRunner`, the same technique
  `repoService.test.ts` already uses.

**Done when:** every bullet passes against a real `git` on this machine, and each of the three
`goToFile` branches is reached by a genuinely different repository state rather than by a flag.

## Judgment calls this plan made

1. **`diff-tree -r -p` rather than §4.4's literal `git diff <base> <head> -- <path>`.** `--root`
   handles a root commit without hard-coding the empty-tree oid (which differs under SHA-256),
   and an explicit `<parent> <sha>` pair is what the merge parent selector needs. Same command
   family the file tree already uses. §4.4's line describes the intent, not the argv.
2. **The line map *is* re-applied across the commit → working-tree drift, and against the
   working tree rather than `HEAD`.** Resolved by the orchestrating session on D14a's own
   precedent: the decision names GitLens's enhanced "Open File", and GitLens maps through the
   intervening history rather than reusing the historical number. One extra `git diff <rev> --
   <path>` on an explicit user action, mapped through the same arithmetic (`mapLineAcrossDiff`
   delegating to `mapDiffLineToRevision`), buys accuracy that grows with the age of the commit —
   exactly where a reader needs it most. It runs **inside** the `editor.goToFile` handler
   (W6 step 1a), so the wire's `line` in means "in `<rev>`", the outcome's `line` means "where
   the cursor is", and the UI never makes a second round trip. Working tree rather than `HEAD`
   because the same one spawn buys the uncommitted-changes case too, and landing off by the size
   of the user's own unstaged edit is the failure mode a mid-edit reader would hit first. Made
   strictly non-regressive by W3's `null` contract: identical file, untracked path, over-cap
   patch or failed spawn all fall back to the unmapped line.
3. **`fs.existsSync` on the working tree, not `git ls-files` or `cat-file -e HEAD:<path>`.** The
   question D14a asks is "is there a file on disk at that path"; the index and HEAD each answer a
   different question and would each get a real case wrong (a tracked file deleted in the
   worktree; an untracked file present in it).
4. **The file tree gets a render cap, not a second virtualizer.** A commit's file count is
   bounded by what one commit did; the outlier degrades explicitly through a "show all" row
   rather than silently through jank. Named escalation ladder in W8.
5. **Plain `↑`/`↓` change files in the tree and scroll in the diff; `Alt+↑`/`Alt+↓` change files
   from inside the diff.** §6.4 asks for both "arrows move between files" and "the diff takes
   over the pane", and this is the reading that satisfies both without binding one key to two
   jobs. W9 states it in full.
6. **Issue references are not linkified.** §6.4 asks for "URL and issue linkification"; without
   §6.7's repository resolution there is nothing for `#123` to point at, and a link that goes
   nowhere is worse than plain text. URLs are linkified; issues wait for P12, which is the phase
   that learns what the repository is.
7. **The detail cache is dropped on `refsChanged`, the diff cache never is, and the drift diff is
   not cached at all.** A commit's tree is immutable; its `%D` decoration is not; the working
   tree changes on every keystroke. Three different policies because there are three different
   answers to "when does this stop being true", and stating them is what stops a later phase
   adding invalidation the diff cache does not need — or a cache the drift diff must not have.
8. **The harness models an editor rather than stubbing one out.** §2.2 calls it a real second
   consumer; `EditorIntegration` is exactly the kind of capability a second host implements, and
   modelling it is what makes all four D14a cases — and, via `worktreeDrift`, the re-map —
   assertable in the fast tier.
9. **`ExternalOpener` is not added.** URLs in a commit message are `<a href>` elements the
   webview's own link handling takes. The port has one real consumer (§6.7's PR badge) and it
   arrives with P12.

**A real gap, found and closed: the newline blob-path fallback.** W2's own section of this plan
describes, in prose, a fallback for a blob path containing a newline — "the blob reader therefore

repoService.ts`) — a plain `git show <rev>:<path>` spawn, no line-oriented request framing, used

`--batch-check` probe first, since a newline path is vanishingly rare and paying for a second
round trip is not worth the code), decodes and binary-sniffs it exactly as the batch path does,
and reports `missing` for a failed spawn (mirroring `worktreeDiff`'s own "a refinement that cannot
run gets a `null`/safe answer, never an exception" convention). Covered by
`tests/integration/commitDetail.test.ts`'s `"a path containing a newline reads through the
one-shot fallback, found and missing"`, against a real file whose name contains an actual embedded
newline byte.
