# P10 — Reset, and cherry-pick

**Goal (§10):** Reset — soft/mixed/hard with per-mode consequence copy, pre-flight counts, typed
confirmation for hard-with-dirty, reflog-backed undo completing the undo slot (§7.12). **Also picks
up cherry-pick (single commit, §7.13)** — named as a v1 operation with no phase of its own since P6
shipped without it; it reuses P6's sequencer state reader, conflict banner and `OpResult` shape
rather than inventing a second mechanism.

**Exit criteria (§10):** Integration tests assert repository state per mode; undo restores; guarded
during in-progress operations. Cherry-pick: the same conflict-banner/continue/abort path proven for
revert, exercised for cherry-pick too.

P10 is the phase that closes the undo slot. Every previous phase added an operation and then had to
write a `notUndoable` reason for it — including `revert`, whose reason is literally *"Revert the
revert, or use Reset once it ships."* Reset is the operation §7.12's table was designed around, and
it is the last of the four `undoable` rows to arrive. That framing matters for the plan: the
mechanism is entirely built, and the phase's real work is being **honest about what the undo
restores** — because the probes below show §7.7's own stated undo rule is *wrong*, and following it
literally leaves the repository in a worse state than the one the user asked to undo.

Cherry-pick, by contrast, is the smallest operation this project has added since P6. Everything it
needs already exists: `CHERRY_PICK_HEAD` is already one of the six state files
`readInProgressStateFiles` reads, `classifyInProgress` already has a `cherryPick` arm that returns
`canContinue: true, canAbort: true`, `continueArgs`/`abortArgs` already emit
`cherry-pick --continue`/`--abort`, `classifyGitError` already matches `could not apply`, and
`revertMergeParents` already builds the `-m` picker's data. The user-visible feature is one
`OpRequest` arm, one pre-flight, one menu item and one dialog. What P10 adds that P6 did not build
is the **`--skip`** escape — probe 6 finds a real state (an empty pick) where the banner as it
stands offers a Continue that cannot succeed.

Both halves share one structural risk, and it is the same one P9 hit: `merge-tree` predicts the
wrong thing unless it is told the right merge base. Probe 2 is the cherry-pick-shaped twin of P9's
probe 2 and reproduces a **false clean** — a genuinely conflicting pick reported as clean — from the
identical cause.

This plan is grounded in live probes run against **git 2.43.0** in this sandbox (the repo's floor is
2.38, D2), against real repositories built one per case. Output below is copied from those runs, not
reconstructed.

## What the git probes settled

All run on **git 2.43.0**, `LC_ALL=C`, in throwaway repos built one per case (a shared repo
contaminates the dirty-tree matrix — the first attempt at probe 7 produced a wrong answer for
exactly that reason). Output verbatim.

### Probe 1 — what each reset mode does to a dirty tree, and the truth about untracked files

Fixture per mode: three commits; then a modified tracked file, a **staged new file**
(`staged-new.txt`), a genuinely **untracked** file, and an **ignored** file.

```
########## reset --soft to c1 ##########
--- status AFTER ---
1 A. N... 000000 100644 100644 <sha> <sha> .gitignore
1 A. N... 000000 100644 100644 <sha> <sha> staged-new.txt
1 MM N... 100644 100644 100644 <sha> <sha> tracked.txt
? untracked.txt
--- files present ---
added.txt  ign.txt  staged-new.txt  tracked.txt  untracked.txt
--- tracked.txt ---
v3
DIRTY

########## reset --mixed to c1 ##########
Unstaged changes after reset:
M	tracked.txt
--- status AFTER ---
1 .M N... 100644 100644 100644 <sha> <sha> tracked.txt
? .gitignore
? staged-new.txt
? untracked.txt
--- files present ---
added.txt  ign.txt  staged-new.txt  tracked.txt  untracked.txt
--- tracked.txt ---
v3
DIRTY

########## reset --hard to c2 ##########
HEAD is now at 1790b2a c2
--- status AFTER ---
? ign.txt
? untracked.txt
--- files present ---
added.txt  ign.txt  tracked.txt  untracked.txt
--- tracked.txt ---
v2
```

Three things this settles, two of which the spec does not currently say:

1. **`--soft` and `--mixed` never touch the working tree.** `tracked.txt` still reads
   `v3\nDIRTY` after both. §7.7's copy is correct for these two.
2. **`--hard` destroyed `staged-new.txt`** — a file that existed only in the index and the
   worktree — while leaving `untracked.txt` and the ignored `ign.txt` untouched. The common
   shorthand "hard reset never touches untracked files" is **not** the rule; the rule is *`--hard`
   resets the index and the worktree to the target tree, so anything the index knows about is
   restored to the target's version or removed, and anything the index does not know about is left
   alone*. A staged-but-uncommitted new file is on the losing side of that line, and a `git add`
   away from being invisible in a naive "untracked files are safe" pre-flight.
3. **`--mixed` unstages rather than destroys**: `staged-new.txt` and `.gitignore` become `?`
   (untracked) rather than disappearing. Nothing is lost on disk — but the *index staging itself*
   is gone, which probe 5 shows is unrecoverable.

**Consequence for the plan:** `ResetPreflight.destroys` (the `--hard` list) is computed as
*(staged ∪ unstaged tracked paths) ∪ (staged-new paths)*, and explicitly **excludes** untracked and
ignored files. The dialog's dirty count says all four categories; the destruction warning names only
the first three.

### Probe 2 — cherry-pick's `merge-tree` prediction is wrong without `--merge-base=<sha>^`, and wrong in the **false-clean** direction

The exact P9-probe-2 twin, on a diverged history. Topic changes `f.txt` `X→Y`, then `Y→X`
(a self-undo); the pick is that second commit. `main` independently changed `X→M`.

```
=== merge-tree WITHOUT --merge-base ===
b7e7fff28de8e40b6f14cfb5b895bcba75d22ab7

rc=0 <-- 0 means PREDICTED CLEAN
=== merge-tree WITH --merge-base=<pick>^ ===
c8f474a4eb5e5b8f2df9fdda5fbb7cbbb3c350d0
f.txt

Auto-merging f.txt
CONFLICT (content): Merge conflict in f.txt
rc=1 <-- 1 means predicted conflict
=== the real cherry-pick ===
Auto-merging f.txt
CONFLICT (content): Merge conflict in f.txt
error: could not apply bf253f3... topic: Y->X (undo)
rc=1
u UU N... 100644 100644 100644 100644 <sha> <sha> <sha> f.txt
```

Left to itself, `merge-tree HEAD <pick>` uses `merge-base(HEAD, pick)` — the fork point — against
which the picked commit's *tree* is identical to the base (topic undid itself), so the pick's side
reads as "no change" and the merge is trivially clean. The real cherry-pick applies
`diff(<pick>^, <pick>)`, which is `Y→X` against a worktree holding `M`: a conflict.

**`--merge-base=<sha>^<mainline>` is mandatory**, exactly as D56 made it mandatory for the stash.
For a non-merge commit the argument is `<sha>^`; for a merge commit picked with `-m <n>` it is
`<sha>^<n>`, which is the same construction `#predictRevert` already uses (its
`` `${firstSha}^${effectiveMainline}` `` other-side argument) — read from the other end.

The full argv this phase commits to:

```
git merge-tree --write-tree --messages --name-only --merge-base=<sha>^<mainline|1> HEAD <sha>
```

### Probe 3 — reset during an in-progress operation: `--soft` refuses, `--mixed`/`--hard` **silently abandon it**

```
########## mid-merge, reset --soft HEAD~1 ##########
MERGE_HEAD present before
fatal: Cannot do a soft reset in the middle of a merge.
rc=128
MERGE_HEAD STILL present
u UU N... 100644 100644 100644 100644 <sha> <sha> <sha> f.txt

########## mid-merge, reset --mixed HEAD~1 ##########
MERGE_HEAD present before
Unstaged changes after reset:
M	f.txt
rc=0
MERGE_HEAD GONE

########## mid-merge, reset --hard HEAD~1 ##########
MERGE_HEAD present before
HEAD is now at 78b4416 base
rc=0
MERGE_HEAD GONE

########## mid-cherry-pick, reset --mixed ##########
CHERRY_PICK_HEAD present before
Unstaged changes after reset:
M	f.txt
rc=0
CHERRY_PICK_HEAD GONE
no sequencer dir
```

This is the strongest justification in the phase for §7.11's gate. Git refuses only the *soft*
case; `--mixed` and `--hard` mid-merge or mid-cherry-pick succeed with exit 0 and **delete the state
file**, abandoning the operation with no warning and no way back through `--abort`. A UI that offers
reset mid-conflict is offering a footgun git itself does not label.

So `reset` joins `GATED_OP_KINDS`, and — because a pre-flight is advice, not a lock (D52's own
reasoning) — `#prepareOp` re-checks the in-progress state host-side and returns an `earlyError` of
`OperationInProgress` rather than relying on the menu having been disabled.

Also captured here, for W7:

```
########## bad sha ##########
fatal: Could not parse object 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'.
rc=128
fatal: ambiguous argument 'notaref': unknown revision or path not in the working tree.
rc=128
```

The second matches `classifyGitError`'s `NotFound` (`unknown revision or path`). **The first does
not match anything** and classifies as `Unknown` today — a pre-existing hole, not one P10 creates,
but P10 is the phase that hits it (a reset target is a raw sha from the graph).

### Probe 4 — `rev-list --count <sha>..HEAD`, and the one-sidedness trap

```
=== linear ancestor: rev-list --count HEAD~2..HEAD ===
2
=== diverged target 'other': --count other..HEAD ===
2
=== diverged: --count --left-right other...HEAD ===
2	2
=== is-ancestor check ===
is-ancestor(other) rc=1
is-ancestor(HEAD~2) rc=0
=== detached HEAD ===
1
# branch.oid fe906edf5783d7b771928b54fe389c6e377ca0a2
# branch.head (detached)
=== count to same commit ===
0
=== forward reset (target ahead) ===
other..HEAD = 2 ; HEAD..other = 2
```

`rev-list --count <sha>..HEAD` answers *"how many commits leave"* correctly in every case — but on
a **diverged** target it is a half-truth, because it says nothing about the two commits the reset
would *bring in*. The output is identical (`2`) for "reset back two commits on a line" and for
"jump sideways onto a divergent branch tip, discarding two and adopting two", and those are very
different things to confirm. `--count --left-right <sha>...HEAD` (three dots) gives both numbers in
**one spawn**, and `merge-base --is-ancestor` distinguishes the two shapes with exit status.

`ResetPreflight` therefore carries `leaving` **and** `gaining`, and the dialog says "moves `main`
back 2 commits" when `gaining === 0` and "moves `main` to a different line of history — 2 commits
leave, 2 arrive" when it is not. Detached HEAD counts work normally; the branch name is simply
absent (`# branch.head (detached)`).

### Probe 5 — the reflog, and the undo replay §7.7 currently gets **wrong**

Reflog after each mode is uniform and unhelpful for distinguishing them:

```
--- reflog -n 2 (after reset --soft) ---
da84c24 HEAD@{0}: reset: moving to da84c24f32c3d63dce5fd05eb53f9082de8182c5
04a0a42 HEAD@{1}: commit: gitignore
```

`reset: moving to <sha>` regardless of mode. Reading the mode back out of the reflog is impossible;
capturing `rev-parse HEAD` **before** the write (the same shape as the other three `#capture*Undo`
methods) is both sufficient and simpler. **That part of §7.7 is fine.**

The replay is not. §7.7 says *"`git reset --hard <prev>` for hard; `git reset --soft <prev>`
otherwise"*. Applied to a `--mixed` reset:

```
=== undo a --mixed reset with 'reset --soft <prev>' (SPEC's rule) ===
after mixed:
? b.txt
? c.txt
after 'undo' (--soft):
1 D. N... 100644 000000 000000 <sha> <sha> b.txt
1 D. N... 100644 000000 000000 <sha> <sha> c.txt
? b.txt
? c.txt

=== same, undone with --mixed (mode-matched) ===
(clean if empty)          <-- clean

=== undo a --soft reset with --soft ===
(clean if empty)          <-- clean

=== undo a --hard reset with --hard ===
9a7c265 c3
2a127d8 c2
2bcb5f2 c1
(clean if empty)          <-- clean
```

Undoing a mixed reset with `--soft` moves HEAD back but leaves the index at the *reset* state, so
every file the returned commits added is now **staged as a deletion** while simultaneously sitting
on disk as untracked. That is not "back where we were"; it is a third state the user never asked
for, and one that will silently commit two file deletions if they hit commit.

**The correct rule is mode-matched replay: undo a `--<mode>` reset with `reset --<mode> <prev>`.**

One more thing the same probe settles, and the plan must state it plainly:

```
=== mixed reset destroying real index staging ===
before:
1 M. N... 100644 100644 100644 <sha> <sha> a.txt      <-- staged
1 .M N... 100644 100644 100644 <sha> <sha> b.txt      <-- unstaged
after mixed-reset then mixed-undo:
1 .M N... 100644 100644 100644 <sha> <sha> a.txt      <-- now UNSTAGED
1 .M N... 100644 100644 100644 <sha> <sha> b.txt
```

A `--mixed` reset destroys the *index staging* itself, and no replay restores it — the pre-reset
index was never written to the object database. **Undo of a mixed reset restores the branch pointer
and the commits, not what was staged.** This is the same class of honesty §7.12 already applies to
`--hard` ("it does not restore uncommitted work"), extended one mode further. W19 adds it to §7.12.

### Probe 6 — cherry-pick's states: conflict, continue, and the **empty pick** the banner cannot handle

Conflicting pick — channels, state files, and the continue path:

```
--- stdout/stderr split ---
STDOUT bytes: 63
Auto-merging f.txt
CONFLICT (content): Merge conflict in f.txt
STDERR bytes: 349
error: could not apply 3abb7db... topic change
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git cherry-pick --continue".
hint: You can instead skip this commit with "git cherry-pick --skip".
hint: To abort and get back to the state before "git cherry-pick",
hint: run "git cherry-pick --abort".
--- status v2 ---
u UU N... 100644 100644 100644 100644 <sha> <sha> <sha> f.txt
--- state files ---
AUTO_MERGE
CHERRY_PICK_HEAD
MERGE_MSG
--- continue with unresolved ---
error: Committing is not possible because you have unmerged files.
fatal: Exiting because of an unresolved conflict.
rc=128
--- resolve + continue ---
[main 498644b] topic change
rc=0
```

Unlike P9's conflicting pop (stderr empty, D57's whole detection problem), a conflicting cherry-pick
writes `could not apply <sha>...` to **stderr**, which `classifyGitError`'s existing `Conflict`
pattern already matches. No new detection mechanism. `CHERRY_PICK_HEAD` is present, unmerged paths
are present, `classifyInProgress` returns `cherryPick` with Continue and Abort both enabled, and
Continue correctly refuses while paths are unmerged — exactly the banner's existing contract.

The **empty pick** is the case P6 never met:

```
=== empty cherry-pick (change already present) ===
The previous cherry-pick is now empty, possibly due to conflict resolution.
If you wish to commit it anyway, use:

    git commit --allow-empty

Otherwise, please use 'git cherry-pick --skip'
On branch main
You are currently cherry-picking commit fb2e20c.
  (all conflicts fixed: run "git cherry-pick --continue")
  (use "git cherry-pick --skip" to skip this patch)
nothing to commit, working tree clean
rc=1
--- status v2 ---
(empty = clean tree)
CHERRY_PICK_HEAD PRESENT
--- unmerged count --- 0
--- skip --- rc=0 ; no CHERRY_PICK_HEAD
```

`CHERRY_PICK_HEAD` present, **zero** unmerged paths, clean worktree. `classifyInProgress` classifies
this as `cherryPick` with `canContinue: true` — and Continue is exactly the thing that cannot work
(git's own message says so: use `--skip`, or `commit --allow-empty`). Also note the whole message,
including the "previous cherry-pick is now empty" line, arrives on **stdout**, so `classifyGitError`
cannot see it: detection is by `exitCode !== 0` + `CHERRY_PICK_HEAD` present + **no** unmerged paths,
the same exit-code-plus-read-back shape P9's `StashConflict` uses.

`--empty=drop` is **not available** on this git (`rc=129`, usage dump: `git cherry-pick`'s option
list at 2.43 has `--allow-empty`, `--keep-redundant-commits`, but no `--empty=`), so the plan cannot
avoid the state by asking git to skip it up front. It must be handled after the fact.

### Probe 7 — cherry-pick and a dirty tree: **not** revert's blanket blocker

Six independent repos, one per case. The picked commit modifies `a.txt` and adds `n.txt`.

| Case | Setup | Result |
| --- | --- | --- |
| **A** | unstaged change to an *unrelated* file (`b.txt`) | **rc=0, succeeds.** `b.txt` still `.M` afterwards. |
| **B** | **staged** change to an *unrelated* file | `error: your local changes would be overwritten by cherry-pick.` / `hint: commit your changes or stash them to proceed.` / `fatal: cherry-pick failed` — **rc=128** |
| **C** | unstaged change to `a.txt` (a file the pick touches) | `error: Your local changes to the following files would be overwritten by merge:` `a.txt` / `Please commit your changes or stash them before you merge.` / `Aborting` — **rc=128**, no `CHERRY_PICK_HEAD` |
| **D** | **staged** change to `a.txt` | same message as B — **rc=128** |
| **E** | **untracked** `n.txt` in the way of the file the pick adds | `error: The following untracked working tree files would be overwritten by merge:` `n.txt` / `Please move or remove them before you merge.` — **rc=128**, no `CHERRY_PICK_HEAD`; identical content is refused too (`E2 rc=128`) |
| **F** | **revert** with an unrelated unstaged dirty file | **rc=0, succeeds** |

Three findings:

1. Cherry-pick tolerates unrelated **unstaged** dirt (A) and refuses **any** staged change (B, D),
   related or not. A blanket "dirty tree blocks" pre-flight would refuse case A, which git allows,
   and would be wrong in the annoying direction (a user with one unrelated edit told they cannot
   pick).
2. The two path-scoped refusals (C, E) are **atomic** — nothing applied, no state file — and both
   are computable pre-flight by set intersection against the picked commit's own path list, which is
   exactly `classifyCheckout`'s `targetTreePaths` D∩T pattern.
3. **Case F contradicts §7.10's own text about revert.** §7.10 says a dirty tree means git will
   refuse; probe F shows a revert of an unrelated commit succeeding with an unstaged dirty file. Not
   P10's operation to fix, but W19 records the correction because P10's `classifyCherryPick` sits
   right beside `classifyRevert` and the asymmetry would otherwise read as an inconsistency the
   implementing agent should "fix" by copying the wrong one.

`CherryPickPreflight`'s blockers are therefore path-scoped, not blanket: `stagedChanges` (any),
`localChangesWouldBeOverwritten` (unstaged ∩ commit paths), `untrackedWouldBeOverwritten`
(untracked ∩ commit-added paths), plus `inProgressOperation` and `mainlineRequired`.

### Probe 8 — cherry-picking a merge commit: the `-m` requirement, and P6's picker is reusable

```
--- cherry-pick MERGE without -m ---
error: commit dbc4b7b... is a merge but no -m option was given.
fatal: cherry-pick failed
rc=128
--- cherry-pick MERGE -m 1 ---
Auto-merging f.txt
CONFLICT (content): Merge conflict in f.txt
error: could not apply dbc4b7b... merge feat
rc=1
--- status ---
u UU N... 100644 100644 100644 100644 <sha> <sha> <sha> f.txt
CHERRY_PICK_HEAD present
--- abort --- rc=0
```

Identical wording and identical exit code to revert's own merge refusal, which is why
`revertMergeParents` — a `rev-list --parents` + subject read, with nothing revert-specific in it —
is reusable verbatim. `RevertParentChoice` is likewise already the right shape. The `-m` picker,

**`error: commit … is a merge but no -m option was given.` matches no pattern in `errors.ts`** — a
fourth classifier gap (W7).

### Probe 9 — cherry-pick's undo, and why the replay is `reset --keep`, not `reset --hard`

```
=== plain pick, then reset --hard <prev> ===
rc=0 ; log back to 'main commit' ; status clean
=== reflog ===
9636bae HEAD@{0}: cherry-pick: side commit
a8fade7 HEAD@{1}: commit: main commit

=== detached HEAD pick ===
PREV2=a8fade7…  ; pick rc=0 ; HEAD=8b2e548… ; (detached)
reset --hard PREV2 → a8fade7…      <-- works identically detached

=== --no-commit pick ===
rc=0 ; status: 1 A. … s.txt ; no CHERRY_PICK_HEAD ; HEAD unmoved
reset --hard <prev> → rc=0 ; status clean ; no CHERRY_PICK_HEAD
```

and, on the interesting case — undoing a pick that ran with unrelated dirt in the tree (probe 7A):

```
=== pick with unrelated unstaged dirt, undo via reset --keep ===
pick rc=0 ; keep rc=0
log: main / base ; status: 1 .M b.txt ; b.txt still reads "dirty"   <-- dirt PRESERVED
=== same, undo via reset --hard ===
hard rc=0 ; b.txt: "b"                                              <-- dirt DESTROYED
=== reset --keep when it WOULD lose work on a file the undo must change ===
error: Entry 'a.txt' not uptodate. Cannot merge.
fatal: Could not reset index file to revision '571f9c3…'.
keep rc=128 ; log still shows the picked commit                     <-- refused, nothing changed
```

A cherry-pick is legal with unrelated unstaged dirt (probe 7A), so `reset --hard <prev>` as its undo
would **destroy work the operation itself never touched** — an undo that loses data is worse than no
undo. `git reset --keep <prev>` moves the branch pointer back, resets the files the move actually
changes, keeps unrelated local modifications, and **refuses with exit 128 changing nothing** when it
cannot do that safely. That refusal is a good outcome, not a failure mode: `undoRun` surfaces it as
an ordinary failed `OpResult` and the commit stays.

Two honest limits, both stated in the UI (hard part 5):

- `--no-commit` picks move no ref, so there is no branch pointer to restore; their "undo" would be a
  worktree/index revert, which is a different and more dangerous operation. **P10 sets no undo slot
  for a `noCommit` cherry-pick** (`notUndoable`, reason given).
- A cherry-pick that ended in **conflict** did not create a commit either. Its escape hatch is the
  banner's Abort, which is what git provides and what the user should use; the undo slot is not set.

So the undo slot is set only for a cherry-pick that actually produced a commit — precisely the case
where `<prev>` is meaningful.

### Probe 10 — does reset have a `--merge-base` trap of its own?

**No, and this is one sentence rather than a section because it is worth confirming rather than
assuming.** Reset performs no merge: it writes a ref, and optionally the index and worktree, from a
single named tree. `merge-tree` is never invoked on the reset path, there is no "other side", and
therefore no base to choose wrongly. The trap reset *does* have is probe 4's one-sidedness, which is
a *counting* error, not a merge-base error, and is fixed by `--left-right` rather than by an argv
flag on a predictor that is not there.

## The hard parts, settled before the work items

### 1. §7.7's undo rule is wrong, and the plan changes the spec rather than the code

The single most important outcome of the probes. §7.7 prescribes `reset --hard <prev>` for a hard
reset and `reset --soft <prev>` otherwise; probe 5 shows the `otherwise` half leaves phantom staged
deletions after a mixed reset. The rule this phase implements — and W19 writes into §7.7 and §7.12 —
is **mode-matched**: the `UndoRecord.replay` for a `reset` op is `["reset", "--<the same mode>",
"<prev>"]`.

This means `UndoRecord` must know the mode at capture time, which it does: `#prepareOp` has the
whole `OpRequest`. No new plumbing.

The accompanying honesty, in the undo button's own tooltip and in the announcement:

| Reset mode | What undo restores | What it does not |
| --- | --- | --- |
| soft | branch pointer, index, worktree — a full round trip | — |
| mixed | branch pointer and the commits; the working tree was never touched | **what was staged**: the pre-reset index is gone and is not in the object database (probe 5) |
| hard | branch pointer and the commits | the uncommitted work the reset destroyed — §7.12 already says this |

### 2. The typed confirmation: when it fires, what is typed, and where it is enforced

§7.7: *"Hard reset with a dirty tree requires a typed confirmation."* Read against probe 1, "dirty"
must mean **"there is something `--hard` will actually destroy"** — i.e. `destroys` is non-empty —
not "status is non-empty". A repo with one untracked scratch file is not at risk from a hard reset
(probe 1 leaves it alone), and demanding a typed token there is exactly the reflexive-confirmation
failure D52 rejected for plain pushes.

What is typed: the **short sha of the reset target**, following `ForcePushDialog.vue`'s
`typedBranch`/`confirmToken`/exact-match shape. Not a fixed word like `DELETE` — the point of a
typed confirmation is to make the user look at the specific object they are acting on, which is what
D19 bought and what the branch name does for a force push.

Where it is enforced: **both**. The dialog gates its own confirm button, *and* `#prepareOp` re-checks
`op.confirmToken === <short sha of resolved target>` and returns an `earlyError` of
`ProtectedBranch`… no — a new, honest kind: `ConfirmationRequired`. Reusing `ProtectedBranch` would
be a lie in the error taxonomy. D52's *pattern* is reused; its *kind* is not.

### 3. "Stash first" is a stash-then-stop, not P9's stash-and-carry — and this is deliberate

The brief asks whether §7.7's "stash first" routes through P9's `#stashAndCarry`. **It does not, and
the shape is the reason.** `#stashAndCarry` is push → run middle → **pop back**. Popping back after
a hard reset would restore precisely the changes the user just asked to be rid of — it would make
the reset a no-op with extra steps, and against a moved HEAD the pop is likely to conflict on top of
that.

What "stash first" means for reset is: **push the changes to the stash, then run the reset against a
now-clean tree, and stop.** The work is preserved *in the stash*, retrievable deliberately, which is
the alternative §7.7 is offering to destruction. Concretely `ResetPreflight.routes` carries
`"stashFirst"`, and `OpsState.runReset` implements it as two sequential `op.run` calls
(`stashPush` → `reset`) with a combined announcement, not as a call into `#stashAndCarry`.

A secondary consequence worth stating: because the changes are stashed, the reset that follows is
**no longer destructive**, so the typed confirmation is not required on that path. The route is the
friction; asking for both would be theatre.

The one piece of `#stashAndCarry` that *is* reused is its failure discipline: if the middle op
fails, say so **and** say the changes are in the stash. W14's announcement copies that sentence
almost verbatim.

### 4. Where the "commits leaving" list comes from, and how long it is

`leaving`/`gaining` are counts from one `rev-list --count --left-right <target>...HEAD` spawn
(probe 4). §7.7 also asks for the *list*. A second spawn,
`rev-list --max-count=<cap+1> --format=… <target>..HEAD`, gives it; the `+1` is how the dialog knows
to say "and N more" without a third count. Cap at **10** — the dialog is a confirmation, not a log
view, and the graph behind it already shows the commits.

The list is only fetched when `leaving > 0`, which is not always: a reset to a commit *ahead* of
HEAD, or to HEAD itself, is legal and has an empty list. The `leaving === 0 && gaining === 0` case
(reset to HEAD) is not an error — for `--hard` it is a very common "discard all my changes" idiom —
and the dialog says exactly that instead of "moves 0 commits".

### 5. Two more entries in the undo slot, and the slot's totality mechanism holds

The brief asks this directly: reset and cherry-pick share the single session-scoped `UndoSlot` with
branch-delete, tag-delete and stash-drop. **The mechanism needs no change.** `UNDO_POLICY` is
`{ readonly [K in OpRequest["kind"]]: UndoPolicy }`, a mapped type over the `OpRequest` discriminant,
so adding the two new arms *without* adding two keys is a `tsc` error. That is the entire extension:

```ts
reset: { kind: "undoable" },
cherryPick: { kind: "undoable" },
```

with the per-op decision of whether a record is *actually captured* living in `#prepareOp`, as it
already does for `branchDelete` (which captures nothing when the branch does not resolve). A policy
of `undoable` means "this kind can produce a record", not "this call will".

The sharing itself needs no arbitration: one slot, last-write-wins, cleared by the next op — §7.12's
stated design, and P10 adds no exception to it. The single new subtlety is that `cherryPick` is the
first `undoable` kind whose undo is **conditional on the outcome**: no commit created (conflict, or
`--no-commit`) means no record, and the slot is cleared rather than set. `runOp` already calls
`undo.set(record | null)` unconditionally, so this is expressible today.

### 6. `--skip`, and the third banner button

Probe 6's empty pick leaves `CHERRY_PICK_HEAD` with zero unmerged paths, which `classifyInProgress`
reports as `cherryPick` with `canContinue: true`. Pressing Continue in that state runs
`cherry-pick --continue`, which git refuses. The banner would be offering a button that cannot work.

The fix is small and stays inside the existing model: add `canSkip` to `InProgressOperation`, true
for `cherryPick` and `revert` only (the two sequencer operations that have `--skip`), add
`skipArgs(kind)` beside `continueArgs`/`abortArgs`, add an `opSkip` arm to `OpRequest`, and have
`ConflictBanner.vue` render a third button when `canSkip` is true. The banner already renders
conditional Continue/Abort; this is a third of the same.

**Why not instead special-case "empty pick" as its own in-progress kind?** Because the state is not
distinguishable from a *fully-resolved* conflicted pick by state files alone — both are
`CHERRY_PICK_HEAD` + zero unmerged paths, and the second is the state where Continue is exactly
right. Only the failed op's own exit code distinguishes them, and that is transient. Offering both
buttons and letting the user choose is honest; guessing which one they meant is not. The banner
copy therefore names the choice when there are no unmerged paths: *"Continue to commit the pick, or
Skip if this change is already present."*

### 7. Reset's pre-flight is a description; cherry-pick's is a prediction

Worth stating because it changes what each dialog may promise. `ResetPreflight` answers questions git
can answer by looking (what is dirty, how many commits move, is HEAD detached) — every field is a
fact, and there is no TOCTOU window worth engineering around beyond the host-side re-check.
`CherryPickPreflight` contains a `merge-tree` prediction and therefore inherits D57's whole posture:
exact **about the merge**, blind to the two path-scoped refusals of probe 7 (which are handled as
blockers by set intersection), and reconciled after the fact — `runOp`'s read-back tells us whether
the executed pick agreed with the prediction, and a disagreement is announced rather than swallowed,
exactly as `#reconcileStashPop` does today.

### 8. Detached HEAD

§7.7: on a detached HEAD, reset is *"presented as what it is — moving nothing but HEAD"*. Probe 4
confirms the counts work and `status --porcelain=v2 --branch` reports `# branch.head (detached)`.
`ResetPreflight.branch` is `null` there, and the dialog swaps its headline from "Move `main` to…" to
"Move HEAD to… — you are not on a branch, so no branch is changed." Not a blocker, not a warning
banner; a different sentence. Cherry-pick on a detached HEAD works identically (probe 9) and gets the
same one-line note §7.10 already gives revert.

**`preflightCherryPick(repoId, sha, mainline)`** — mirrors `preflightRevert` closely:

```ts

  this.#statusAndInProgress(session),
  revertMergeParents(session.driver, [sha]),

  const resolved = await this.#resolveObject(op.target);          // probe 3's bad-sha guard
  if (resolved === null) return { …, earlyError: "NotFound" };
  if (op.mode === "hard") {
    const destroys = /* recomputed host-side from a fresh status */;
    if (destroys.length > 0 && op.confirmToken !== resolved.slice(0, 7))
      return { argvList: [], undo: null, earlyError: "ConfirmationRequired" };
  }
  const prev = await this.#resolveHeadSha();
  return {
    argvList: [resetArgs(op.mode, op.target)],
    // hard part 1: MODE-MATCHED replay, not §7.7's stated `--soft` for non-hard.
    undo: {
      label: `Undo ${op.mode} reset of ${branchLabel}`,
      recoverySha: prev,
      replay: [["reset", `--${op.mode}`, prev]],
    },
  };
}
case "cherryPick": {
  if (!canRunOp(inProgress, "cherryPick"))
    return { …, earlyError: "OperationInProgress" };
  const prev = await this.#resolveHeadSha();
  return {
    argvList: [cherryPickArgs(op.sha, { mainline: op.mainline, noCommit: op.noCommit })],
    // Probe 9: `--keep`, not `--hard` — a pick is legal with unrelated dirt in the tree, and an
    // undo that destroys work the operation never touched is worse than no undo. The undo is
    // withheld entirely (see below) unless the pick actually created a commit.
    undo: op.noCommit
      ? null
      : { label: `Undo cherry-pick of ${short(op.sha)}`, recoverySha: prev,
          replay: [resetKeepArgs(prev)] },

}
case "opSkip": {
  const args = skipArgs(inProgress?.kind ?? null);
  if (args === null) return { …, earlyError: "OperationInProgress" };
  return { argvList: [args], undo: null };
}
```

// Probe 6: an empty pick exits non-zero with CHERRY_PICK_HEAD set, a clean worktree and ZERO

## Judgment calls this plan made

1. **Mode-matched undo replay, overriding §7.7's stated rule.** Probe 5 shows the spec's rule is
   wrong. The plan implements the correct behaviour and changes the spec, rather than implementing
   a documented bug.
2. **Typed confirmation gated on `destroys`, not on "dirty".** An untracked-file-only tree is not
   at risk (probe 1) and a confirmation there would be reflexive — D52's own argument.
3. **The typed token is the target's short sha**, not a fixed word. Mirrors D19's branch-name token:
   the friction should make you look at *this* object.
4. **`ConfirmationRequired` is a new `OpErrorKind`, not a reuse of `ProtectedBranch`.** The pattern
   is shared; the taxonomy should not claim a protection that does not exist.
5. **"Stash first" is stash-then-stop, not P9's stash-and-carry.** Hard part 3. This is the one place
   the plan declines to reuse an existing mechanism, and the reason is that carrying the changes back
   would undo the reset.
6. **No blanket dirty blocker on cherry-pick.** Probe 7A: git allows it, so we allow it. The blockers
   are path-scoped set intersections.
7. **`reset --keep` for cherry-pick's undo**, not `reset --hard`. Probe 9: `--hard` would destroy
   unrelated work the pick never touched, and `--keep`'s refusal is a correct outcome.
8. **No undo slot for a `--no-commit` or conflicted pick.** No commit was created; §7.12's "we never
   present an undo we cannot honour" applies literally.
9. **`canSkip` on the model rather than a special-cased empty-pick in-progress kind.** The empty
   state and the fully-resolved state are indistinguishable from state files alone (hard part 6);
   offering both buttons is honest, guessing is not.
10. **`opSkip` as an `OpRequest` arm rather than a parameter on `opContinue`.** It is a different
    verb with a different outcome; a boolean flag on continue would read as a modifier.
11. **Two counts (`leaving`/`gaining`) from one `--left-right` spawn**, rather than §7.7's single
    count. Probe 4: the single count is a half-truth on a diverged target.
12. **A 10-commit cap on the leaving list.** A confirmation dialog is not a log view.
13. **`CONTRACT_VERSION` → 11 with two pre-flight keys**, rather than folding reset's pre-flight into
    `status.get`. Every other operation with a decision to make has its own `preflight.*` key; reset
    is the most consequential of them.
14. **Reuse `revertMergeParents` verbatim** rather than writing a cherry-pick twin. It contains
    nothing revert-specific (probe 8).
15. **Fix `errors.ts`'s `Could not parse object` gap in this phase** even though it predates P10.
    P10 is the first phase whose primary input is a raw sha from the graph, so it is the phase that
    hits it.
16. **Record §7.10's over-strong dirty-tree claim (probe 7F) in the spec without changing revert's
    behaviour.** Correcting prose is in scope; changing an operation another phase owns is not.
17. **Cherry-pick's `merge-base` argument is `<sha>^<m>` with `HEAD` as base** — the inverse of
    `#predictRevert`'s arrangement. Pinned by a unit test because the mistake is invisible in review.
18. **Reset does not join the graph's ref-drag or any other affordance.** §7.7's entry point is the
    commit row; one entry point, one dialog.
19. **The stash-first route drops the typed confirmation.** Requiring both would be theatre once the
    work is preserved (hard part 3).

## Open questions for the orchestrating session

**OQ1 — Should the reset dialog default to a mode, and which?** *Recommendation:* default to
**mixed**, git's own default and the only mode that is destructive to nothing on disk. Soft as the
default under-communicates ("nothing happened"); hard as the default is indefensible.

**OQ2 — Should `--hard` be reachable at all without first offering stash-first?** *Recommendation:*
yes, reachable, but with stash-first as the primary button (W11 region 6). §7.7 says "offers", not
"requires", and a user discarding a botched experiment should not be forced to litter the stash.

**OQ3 — Is the short sha the right typed token, or should it be the full sha?** *Recommendation:*
short (7 chars), matching what the graph displays. A 40-character token is copy-pasted rather than
read, which defeats the purpose.

**OQ4 — Should `EmptyCherryPick` auto-skip?** *Recommendation:* no. Leave the repository in the
state git left it and let the banner offer Skip. Auto-skipping silently discards a commit the user
explicitly asked to apply — and probe 6's message shows git itself declines to choose.

**OQ5 — Should cherry-pick offer `-x` (append "cherry picked from…")?** *Recommendation:* not in
P10. It is a message-content decision with team-convention implications; §7.13 does not name it, and
it is a one-line addition whenever someone asks.

**OQ6 — Should `--skip` also appear for revert, or cherry-pick only?** *Recommendation:* both — git
supports it for both (they share the sequencer), `canSkip` is already computed per kind, and a
banner that offers Skip for one sequencer op and not the other is arbitrary from the user's side.

**OQ7 — Does the reset dialog need a diff preview of what `--hard` will destroy?** *Recommendation:*
no. A path list is enough for a confirmation, the detail pane already shows the working-tree diff,
and a diff inside a modal is a second scroll region in the most consequential dialog in the app.

**OQ8 — Rename `revertMergeParents` → `mergeParentChoices`?** *Recommendation:* rename with an alias
export, exactly as P9 did for `MergeOutcomePrediction`/`RevertPrediction` (OQ11 there). Two callers
with two different operations makes the revert-specific name actively misleading. If the orchestrator
prefers zero churn in P6's files, keep the name and add a comment.

**OQ9 — Should reset be reachable from the branch picker (reset current branch to a ref)?**
*Recommendation:* not in P10. §7.7's entry point is a commit in the graph; a second entry point is a
P13 palette-audit question when every mutating op gets a command.

**OQ10 — Should the undo slot be cleared by the `stashPush` half of the stash-first route, given the
`reset` that follows will set it?** *Recommendation:* let it happen — `runOp` clears unconditionally
and the reset immediately overwrites it. Carving an exception into a mechanism whose whole value is
that it has none would be a poor trade for a slot that is replaced microseconds later.

**OQ11 — Should `ResetPreflight` be recomputed live as the user changes mode in the dialog?** The
`destroys` list and `requiresTypedConfirmation` both depend on the mode. *Recommendation:* compute
all three modes' `destroys` client-side from the one pre-flight's `dirty` breakdown (it is a pure
function of data already in hand — no round trip), rather than re-requesting on every radio change.
Follow `previewRevertMainline`'s round-trip pattern only where the *server* knows something new,
which here it does not.

**§7.7 (Reset)** — four edits:

1. **Correct the undo rule.** Replace *"`git reset --hard <prev>` for hard; `git reset --soft
   <prev>` otherwise"* with: **the replay matches the mode of the reset it undoes** — `reset
   --<mode> <prev>`. Record why: undoing a `--mixed` reset with `--soft` moves HEAD back but leaves
   the index at the reset state, staging a deletion for every file the returned commits added
   (P10 probe 5).
2. **Correct the `--hard` row's untracked claim.** `--hard` resets the index and worktree to the
   target tree: it destroys tracked modifications **and staged-but-uncommitted new files**, and
   leaves genuinely untracked and ignored files alone (P10 probe 1). The pre-flight's destruction
   list is exactly that set.
3. **Widen the pre-flight count.** `rev-list --count <sha>..HEAD` answers what leaves and is silent
   on what arrives; on a diverged target both numbers matter. The pre-flight reads
   `rev-list --count --left-right <sha>...HEAD` — one spawn, both counts — plus a capped subject
   list.
4. **Scope the typed confirmation and name the stash-first shape.** The confirmation is required
   when a hard reset would actually destroy something, not merely when `status` is non-empty; the
   token is the target's short sha and it is re-checked host-side (D19/D52's pattern). "Stash
   first" is stash → reset → **stop**, not P9's stash-and-carry: popping the changes back would
   restore exactly what the reset removed. On that route the tree is clean and the typed
   confirmation is not required.

**§7.10 (Revert)** — one correction: the claim that a dirty worktree means git will refuse the
revert is too strong. A revert of a commit touching unrelated paths succeeds with unstaged
modifications present (P10 probe 7F); the real refusals are path-scoped, and identical in shape to
cherry-pick's (§7.13).

**§7.11 (In-progress state)** — three edits:

1. Add `--skip` to the banner's verbs, for cherry-pick and revert (the two sequencer operations git
   gives one). The banner's model carries `canSkip` beside `canContinue`/`canAbort`.
2. Record the **empty-pick state**: `CHERRY_PICK_HEAD` present, worktree clean, **zero** unmerged
   paths. Continue cannot succeed there; `--skip` is git's own named remedy, and the state is
   indistinguishable from a fully-resolved pick by state files alone, so the banner offers both
   and says which is which (P10 probe 6).
3. Record **why** reset is gated: `--soft` mid-merge is refused by git, but `--mixed` and `--hard`
   **succeed and delete the state file**, abandoning the operation silently (P10 probe 3). The gate
   is not a convenience — it is the only thing standing between the user and an unrecoverable
   abandonment.

**§7.12 (Undo)** — three edits:

1. The reset row's recovery becomes mode-matched (see §7.7 above).
2. Extend the honesty bullet: `--hard` does not restore uncommitted work — **and `--mixed` does not
   restore what was staged.** A mixed reset destroys the index staging itself, which was never
   written to the object database and cannot be replayed (P10 probe 5).
3. Add a cherry-pick row: recovery is the pre-pick HEAD, replayed as **`git reset --keep <prev>`**,
   which preserves unrelated local modifications and refuses rather than lose work (P10 probe 9). No
   undo is offered for a `--no-commit` pick or a pick that ended in conflict — neither created a
   commit, and the banner's Abort is the correct escape for the second.

**§7.13 (Other v1 operations)** — expand cherry-pick from a name into its shape: single commit,
`-m` required for a merge commit, `merge-tree` prediction with `--merge-base=<sha>^<mainline>`,
path-scoped pre-flight blockers (any staged change; unstaged dirt overlapping the commit's paths;
untracked files at paths the commit adds), and P6's existing sequencer banner for the conflict path.

**§10 (phasing)** — P10's row updated in the P9 style:

> **Done.** Reset (soft/mixed/hard) and single-commit cherry-pick, both through `op.run`, both
> gated mid-operation, both undoable. Reset's undo replay is mode-matched (D61) and its typed
> confirmation is scoped to what `--hard` actually destroys (D62). Cherry-pick reuses P6's
> sequencer reader, banner and `OpResult` wholesale, adding only `--skip` (D65).
>
> Met — W18's `resetLifecycle.test.ts` asserts repository state for all three modes against
> probe 1's matrix; `cherryPickLifecycle.test.ts` drives a conflicting pick through the same
> banner/continue/abort path `revertLifecycle.test.ts` proved for revert, plus skip from the empty
> state; undo restores per mode and refuses cleanly where `--keep` cannot proceed; both ops return
> `OperationInProgress` mid-merge with `MERGE_HEAD` intact.

**§11 (decisions)** — six new entries:

| # | Decision |
| --- | --- |
| **D61** | **A reset's undo replays the same mode, not `--soft`.** §7.7's original rule (`--hard` for hard, `--soft` otherwise) leaves the index at the reset state when undoing a `--mixed`, staging a deletion for every file the returned commits added — a third state the user never asked for, one commit away from real damage. The replay is `reset --<mode> <prev>` with `<prev>` captured by `rev-parse HEAD` before the write. The reflog cannot supply the mode (every reset logs `reset: moving to <sha>`), so capture-before is the mechanism, exactly as for branch/tag delete and stash drop. |
| **D62** | **The typed confirmation is gated on what would actually be destroyed, and the token is the target's short sha.** `reset --hard` destroys tracked modifications and staged-but-uncommitted new files, and leaves untracked and ignored files alone; a tree dirty only with untracked files is not at risk, and demanding a token there is the reflexive confirmation D52 rejected. The token is re-checked host-side and its own `OpErrorKind` is `ConfirmationRequired` — D19/D52's pattern is reused, their `ProtectedBranch` kind is not, because the taxonomy must not claim a protection that does not exist. |
| **D63** | **"Stash first" is stash-then-stop, not P9's stash-and-carry.** `#stashAndCarry` ends by popping the stash back, which after a reset would restore precisely the changes the user asked to be rid of, against a moved HEAD. Reset's route is `stash push` → `reset` → stop: the work is preserved deliberately in the stash, retrievable on the user's terms. Because the tree is clean by then, the reset is no longer destructive and the typed confirmation is not required on that path. |
| **D64** | **Cherry-pick's prediction always passes `--merge-base=<sha>^<mainline>`, with `HEAD` as the base and the commit as the other side.** Left to itself git picks `merge-base(HEAD, sha)`, against which a commit that undoes an earlier commit on its own branch reads as no change at all — reporting a genuinely conflicting pick as clean (P10 probe 2). This is D56's stash rule in a second shape, and it is the exact inverse arrangement of revert's prediction (which passes `<sha>^<m>` as the *other* side): a revert applies the diff backwards, a pick forwards. |
| **D65** | **Cherry-pick's pre-flight blockers are path-scoped, and `--skip` joins the banner.** Git tolerates unrelated unstaged modifications during a pick and refuses any staged change, any unstaged change overlapping the commit's own paths, and any untracked file at a path the commit adds — three atomic refusals, all computable by set intersection (§7.5's D∩T). A blanket dirty-tree blocker would refuse what git allows. Separately, an *empty* pick leaves `CHERRY_PICK_HEAD` with zero unmerged paths, where Continue cannot succeed; the state is indistinguishable from a fully-resolved pick by state files alone, so the banner offers both Continue and Skip and names the choice rather than guessing. |
| **D66** | **A cherry-pick's undo is `reset --keep <prev>`, and is withheld when no commit was created.** A pick is legal with unrelated dirt in the tree, so `reset --hard` would destroy work the operation never touched; `--keep` moves the pointer, resets only what the move changes, and refuses with exit 128 changing nothing when it cannot do that safely — a refusal `undo.run` surfaces as an ordinary failed result. A `--no-commit` pick and a pick that ended in conflict both moved no ref, so no undo is offered for either: §7.12's "we never present an undo we cannot honour", read literally. |

## Exit criteria

- [ ] Reset is reachable from a commit row's context menu, disabled with the banner's reason while
      an operation is in progress.
- [ ] The reset dialog shows the target and subject, the mode picker with §7.7's per-mode
      consequence copy, the dirty breakdown, and — for a diverged target — **both** the leaving and
      the arriving counts.
- [ ] **Exit criterion 1:** integration tests assert repository state per mode against probe 1's
      matrix, including that `--hard` removes a staged-but-uncommitted new file and leaves untracked
      and ignored files alone.
- [ ] A hard reset that would destroy something requires the typed short sha; the token is
      re-checked host-side and a missing/wrong one is `ConfirmationRequired` with nothing spawned.
- [ ] A hard reset with a clean-of-destruction tree requires **no** typed confirmation.
- [ ] "Stash first" is offered as the primary alternative, runs stash → reset → stop, preserves the
      changes in the stash, and does not require the typed confirmation.
- [ ] **Exit criterion 2:** undo restores after each mode, with a **mode-matched** replay; a test
      pins that the spec-as-originally-written `--soft` replay would leave staged deletions.
- [ ] The undo affordance states, per mode, what it does not restore — uncommitted work for `--hard`,
      the index staging for `--mixed`.
- [ ] Undo after `gc --prune=now` refuses cleanly via the existing `cat-file -e` check, writing
      nothing.
- [ ] Reset on a detached HEAD is presented as moving nothing but HEAD, with no branch named.
- [ ] **Exit criterion 3:** `reset` and `cherryPick` both return `OperationInProgress` mid-merge,
      and `MERGE_HEAD` still exists afterwards.
- [ ] Cherry-pick is reachable from the same row menu, with the same gating.
- [ ] The cherry-pick prediction is computed with `--merge-base=<sha>^<mainline>`, and a test
      asserts the prediction *without* it is wrong on a fixture built for the purpose.
- [ ] Cherry-picking a merge commit without `-m` is prevented pre-flight, and the parent picker
      re-predicts when a mainline is chosen.
- [ ] Each of probe 7's blockers blocks with its own paths and its own remedy; an unrelated unstaged
      modification does **not** block.
- [ ] **Exit criterion 4:** a conflicting cherry-pick surfaces in the existing banner with
      Continue/Abort/Skip; abort restores, resolve+continue commits, and an empty pick reports
      `EmptyCherryPick` and is cleared by Skip.
- [ ] A successful pick sets an undo whose replay is `reset --keep`; a `--no-commit` or conflicted
      pick sets none, with the reason stated.
- [ ] An executed pick that disagrees with its prediction is announced as a mismatch.
- [ ] `errors.ts` classifies all four probe-found messages (`Could not parse object`, cherry-pick's
      short dirty-worktree wording, the mid-merge soft-reset refusal, the missing `-m`).
- [ ] `CONTRACT_VERSION` is 11 and both new request keys round-trip through the real codec.

      it.
