# P11 — Search

**Goal (§10):** an input with case/whole-word/regex toggles, a Commits/Refs/Both scope selector,
hybrid client-side + git-backed matching, next/previous navigation with a match count, live regex
validation, and abort-on-supersede.

**Exit criteria (§10):** *Semantics table fully covered by tests (each toggle × scope); ≤120 ms
budget met; malformed regex never throws.*

P11 is the first phase whose feature is defined by a **semantics table** rather than by a git
operation. Every previous phase asked "what does git do here, and how do we not lie about it";
this one asks "what does *matching* mean, and can we say it once instead of three times". That
distinction is the whole plan, because §7.8 as written specifies matching **twice** — once as a
JavaScript predicate over already-loaded rows, once as a `git log --grep/--author` command line —
and the exit criterion demands that the two agree on every cell of a 3-toggle × 3-scope grid.

The probes below say the two cannot be made to agree, for four independent reasons, and that they
do not need to:

1. **§7.8's proposed argv does not compute what §7.8's prose says it computes.** `--grep=<p>
   --author=<p> --committer=<p>` is an **AND across the three categories**, not the OR the prose
   describes (probe 1). `--all-match` does not fix it — it changes how multiple `--grep`s combine
   with *each other* and has no effect on `--author` at all (probe 1c). A single user pattern that
   should match *any* of six fields is not expressible as one `git log` invocation.
2. **git cannot match a bare sha prefix at all** through `--grep` (probe 3). A separate mechanism
   (`rev-parse --disambiguate`) exists, needs ≥4 hex digits, matches blobs and trees as readily as
   commits, and is not restricted to reachable objects.
3. **Word boundaries are a portability trap.** `\b` happens to work in git's ERE on this glibc
   sandbox (probe 2, S), but that is a GNU `regcomp` extension, not POSIX, and macOS — the
   authoritative platform (D27) — is exactly where it cannot be relied on. `-P` works here but is
   a *build-time* capability no version comparison can answer (`capabilitiesForVersion` is a pure
   version derivation, §4.2), so gating on it would add the first spawn-probed capability this
   codebase has.
4. **Doing the matching ourselves costs nothing.** Measured on the tree's own 100k-commit fixture:
   `git log --grep` that matches *nothing* still takes **~700 ms**, because git walks and inflates
   every commit either way; a full `git log --format=…%b` scan of the same repository takes
   **~860 ms** and adds ~150 ms of host-side JS to filter it (probes 5, 6). git's own filter saves
   pipe bytes, not walk cost. Three OR-ing spawns cost **~730 ms of CPU** at 30k commits where one
   scan costs **270 ms** (probe 5b).

So this plan takes the one decision the phase turns on: **the query never reaches git.** git is
asked for the *records*; the matching — all of it, both halves — is one compiled `RegExp` in
`packages/core/src/search/`, applied to the loaded `CommitStore` on the main thread and to the
streamed tail records in the extension host. One matcher, three call sites (loaded commits, tail
commits, refs). The semantics table then has exactly one implementation to be covered by tests,
which is what makes the exit criterion satisfiable rather than aspirational; "malformed regex never
throws" becomes a single `try { new RegExp(…) } catch` at the one place a pattern is compiled; and
the ≤120 ms budget is met with ~4× headroom by a measured column-scan strategy (probe 9), where the
obvious per-row implementation misses it outright at 100k rows.

This plan is grounded in live probes run against **git 2.43.0** in this sandbox (the repo's floor is
2.38, D2) and against the tree's own cached 100k-commit fixtures plus a purpose-built 30k-commit
repository with realistic multi-line bodies and five distinct authors. Output below is copied from
those runs, not reconstructed.

## What the git probes settled

All run on **git 2.43.0**, in throwaway repositories built for the purpose, plus the tree's own
cached fixtures. Output is copied verbatim.

The shared five-commit probe repository, built so that every field §7.8 names is matched by a
*different* commit — which is what makes an AND/OR question answerable at all:

```
e642e65 Frank <frank@x.com>          | Widget Bot <bot@ci.example> | committer-only match
3acc456 Eve <eve@widget.org>         | Eve <eve@widget.org>        | subwidgetary nonsense
0a64deb Carol Widget <carol@…>       | Dave Zebra <dave@…>         | unrelated change
bfa840a Bob Jones <bob@corp.io>      | Bob Jones <bob@corp.io>     | add WIDGETS to the list
218224d Alice Smith <alice@…>        | Alice Smith <alice@…>       | Fix the widget cache
                                                     (body: "body mentions Zebra here")
```

### Probe 1 — `--grep` / `--author` / `--committer` are **AND**ed, and §7.8's own argv is therefore wrong

```
$ git log --format='%h %s' -i --grep=widget --author=widget --committer=widget
3acc456 subwidgetary nonsense
```

Only the one commit that matches **all three** comes back — not the union. Adding `--all-match`
changes nothing:

```
$ git log --format='%h %s' -i --all-match --grep=widget --author=widget --committer=widget
3acc456 subwidgetary nonsense
```

The decisive case is a pattern pair with **disjoint** matches (`Zebra` appears only in 218224d's
body; `Widget` appears as an author only on 0a64deb):

```
$ git log --format='%h %s' --grep=Zebra --author=Widget
(no output, exit 0)
```

Empty. Categories are ANDed. What `--all-match` actually controls is how multiple patterns *within*
the message category combine:

```
$ git log --format='%h %s' --grep=Zebra --grep=WIDGETS        # default: OR
bfa840a add WIDGETS to the list
218224d Fix the widget cache

$ git log --format='%h %s' --all-match --grep=Zebra --grep=widget   # AND
218224d Fix the widget cache
```

…and it has **no effect on header patterns**, which are always ORed among themselves and ANDed
against the message category:

```
$ git log --format='%h %an %s' --author=Widget --author=Bob             # OR
0a64deb Carol Widget unrelated change
bfa840a Bob Jones   add WIDGETS to the list

$ git log --format='%h %an %s' --all-match --author=Widget --author=Bob  # still OR
0a64deb Carol Widget unrelated change
bfa840a Bob Jones   add WIDGETS to the list

$ git log --format='%h %s' --author=Bob --committer=Zebra                # AND
(no output)
```

**Settled.** A single user pattern that must match *any* of subject / body / author name / author
email / committer name / committer email **cannot be expressed as one `git log` invocation.** The
only argv-level route is one spawn per category, unioned by us — three processes per keystroke,
measured in probe 5b. §7.8's sentence naming `--grep=<pat> --author=<pat> --all-match?` is a spec
error, corrected by spec edit 1.

Two facts worth keeping, since the plan's own matcher must reproduce them: `--grep` matches the
**whole commit message, subject and body together** (`--grep=Zebra` finds 218224d, whose Zebra is in
the body), and `--author`/`--committer` match against the raw `Name <email>` header line as one
string — `--author='corp.io'` and `--author='Bob Jones <bob@corp'` both hit bfa840a.

### Probe 2 — regex engines, case folding, and the word-boundary trap

```
$ git log -P --grep='wid(get)'      → 3acc456, 218224d          (PCRE available on this build)
$ git log -P --grep='\bwidget\b'    → 218224d
$ git log -E --grep='\bwidget\b'    → 218224d                   (exit 0 — glibc ERE, a GNU extension)
$ git log -E --grep='\<widget\>'    → 218224d                   (also a GNU extension)
$ git log    --grep='\bwidget\b'    → 218224d                   (BRE, same GNU regcomp)
$ git log -F --grep='widget cache'  → 218224d                   (fixed strings)
$ git log -F -i --grep='WIDGETS'    → bfa840a                   (-i folds under -F too)
$ git log -F --author='Smith <alice' → 218224d                  (-F/-i/-E apply to header patterns too)
```

`-i`, `-E`, `-F` and `-P` are query-*wide* flags: they govern `--grep`, `--author` and `--committer`
alike, which is convenient but irrelevant once probe 1 has ruled the single-process route out.

**Settled, and the part that matters:** `\b` working under `-E` here is a property of **glibc's**
`regcomp`, not of POSIX ERE and not of git. macOS is v1's only supported platform (D27) and is
precisely where a BSD `regcomp` may reject or silently mis-handle it. `-P` works on this build but
PCRE is a **compile-time** option (`USE_LIBPCRE`); `capabilitiesForVersion` derives capabilities
from the version number alone and structurally cannot answer "was this binary built with PCRE" — it
would need the first spawn-probed capability in the codebase, plus a fallback path for the answer
"no". §7.8's "git has no word-boundary flag" is *true in spirit and imprecise in letter*: git has
three word-boundary spellings, none of them portable. Spec edit 1 restates it accurately.

### Probe 3 — git cannot match a sha prefix, and the mechanism that can is not a `log` filter

```
$ git log --grep='218224' --format='%h %s'
(no output)                       # --grep sees the message, never the object name

$ git rev-parse --disambiguate=2182
218224de37bc2bd96d5e1222af096aed5016c814

$ git rev-parse --disambiguate=218
(no output, exit 0)               # <4 hex digits: silently nothing, NOT an error

$ git rev-parse --disambiguate=2182 | while read o; do echo "$o $(git cat-file -t $o)"; done
218224de37bc2bd96d5e1222af096aed5016c814 commit
```

On the 100k fixture `git rev-parse --disambiguate=abcd` runs in **4–8 ms**, so it is cheap; but it
lists **every object type** (a blob or tree sharing the prefix comes back too), it is not restricted
to the walk's rev set or to reachability, and it has a hard **≥4 hex digit** floor below which it
returns nothing at all rather than complaining.

**Settled.** A `--grep`-based design needs `--disambiguate` as a *fourth* mechanism alongside three
`log` spawns, with type filtering and reachability filtering layered on top. The scan design needs
nothing: `%H` is already in every record, and a prefix test is a byte compare. The ≥4-digit floor is
still worth adopting as *our* floor (a 1–3 character hex query would match a large fraction of any
repository and drown the real hits) — grounded in git's own choice rather than invented.

### Probe 4 — malformed patterns: git dies, and dies *after* we have already spawned

```
$ git log -E --grep='foo('  → fatal: command line, 'foo(': Unmatched ( or \(              exit=128
$ git log -P --grep='foo('  → fatal: command line, 'foo(': missing closing parenthesis    exit=128
$ git log    --grep='*['    → fatal: command line, '*[': Invalid regular expression       exit=128
$ git log -E --grep='[a-'   → fatal: command line, '[a-': Unmatched [, [^, [:, [., or [=  exit=128
```

git exits 128 with a `fatal:` line — which `classifyGitError` would file as `Unknown`, since none of
its ordered patterns match. A `RegexInvalid` kind *could* be added. It should not be: the same
question has to be answered client-side anyway, because JS's own `RegExp` constructor throws, and
"never throws" is a promise about the keystroke, not about a subprocess:

```
"foo("     → Invalid regular expression: missing )
"[a-"      → Invalid regular expression: missing terminating ] for character class
"a{2,1}"   → Invalid regular expression: numbers out of order in {} quantifier
"*"        → Invalid regular expression: nothing to repeat
"(?<"      → Invalid regular expression: invalid group specifier name
"\\"       → Invalid regular expression: \ at end of pattern
```

**Settled.** Validation is a `try { new RegExp(source, flags) } catch` at compile time, before
anything spawns and before any row is touched; the message is user-showable once the constant
`Invalid regular expression: ` prefix is stripped. git never sees an invalid pattern because git
never sees a pattern at all. No new `OpErrorKind`, no `errors.ts` change.

### Probe 5 — the cost of letting git filter, versus filtering ourselves (100k commits)

Against the tree's own cached `large(100000)` fixture (packed, with a split commit-graph), three
runs each, `$F` = the existing `LOG_FORMAT`:

```
1 full scan, no body      833 / 854 / 870 ms     19,607,418 bytes
2 full scan + %b          856 / 897 / 914 ms     19,707,418 bytes
3 --grep literal, 0 hits  747 / 698 / 675 ms              0 bytes
4 --grep ERE, ~40% hits   970 / 1021 / 1017 ms    8,029,931 bytes
5 --author scan           1352 / 1341 / 1305 ms  19,607,275 bytes
6 no --topo-order + %b    800 / 806 / 834 ms     19,707,275 bytes
7 rev-parse --disambiguate  8 / 4 / 4 ms
```

A `--grep` that matches **nothing** still costs ~700 ms: git walks and inflates every commit object
regardless, and the filter only decides whether to *print*. The full scan with bodies costs ~90 ms
more than that. `--author` matching is the **slowest** of the lot. Adding `%b` to the format costs
~40 ms and, on this fixture, ~100 KB.

### Probe 5b — the same question at 30k commits with realistic bodies

The 100k fixture has one author and no bodies, which flatters the scan. A purpose-built 30k-commit
repository (five authors, a 4-line body with a `Signed-off-by` trailer on every commit, built by
`fast-import` and repacked with a commit-graph, mean message ~200 bytes):

```
A scan, no body                  275 / 262 / 254 ms    5,621,979 bytes
B scan + %b                      273 / 276 / 270 ms   10,230,840 bytes
C --grep -F -i, ~57% hits        391 / 345 / 350 ms    3,214,335 bytes
D --grep -F -i, 0 hits           221 / 223 / 217 ms            0 bytes
E --author -F -i                 330 / 328 / 319 ms    2,244,014 bytes
F three spawns (grep+author+committer), sequential
                                 703 / 725 / 756 ms
```

**Settled.** Doubling the output bytes by adding `%b` costs **~3 ms** (B vs A). The three-spawn
union — the only argv shape that computes what §7.8's prose describes — costs **2.7×** a single
full scan. There is no performance argument for letting git do the matching, and there is a
correctness argument against it (probes 1–3). Hard part 2 takes the decision.

### Probe 7 — tag annotations: the body is not fetched, and fetching it breaks the ref parser

```
$ git for-each-ref --format='REF=%(refname)|TYPE=%(objecttype)|SUB=[%(contents:subject)]|BODY=[%(contents:body)]' refs/tags
REF=refs/tags/lightweight-1|TYPE=commit|SUB=[committer-only match]|BODY=[plain
]
REF=refs/tags/v1.0.0|TYPE=tag|SUB=[Release 1.0.0]|BODY=[Body line one about widgets.
Body line two mentioning Zebra.
]
REF=refs/tags/v1.0.1|TYPE=tag|SUB=[Hotfix]|BODY=[]
```

Two facts. First, a **lightweight** tag borrows the pointed-at commit's subject *and body* — exactly
the trap `parse/refs.ts`'s own header comment already documents for `%(contents:subject)`, now
applying to the body too; the existing `objecttype === "tag"` gate covers both. Second, and
structurally: the body **contains raw LF**, and `for-each-ref` records are **LF-framed**
(`REFS_RECORD_DELIMITER = 0x0a`), on the stated invariant that no field can contain one. Adding
`%(contents:body)` to `TAG_REFS_FORMAT` as it stands would corrupt every subsequent record.

`for-each-ref` has no `-z`, but its format string accepts a literal NUL:

```
$ git for-each-ref --format='%(refname)%1f%(contents:body)%00' refs/tags | od -c | tail -3
… Z e b r a . \n \0 \n r e f s / t a g s / v 1 . 0 . 1 037 \0 \n

$ git for-each-ref -z --format='%(refname)' refs/tags
error: unknown switch `z'
```

**Settled.** `%00` embeds a real NUL and `for-each-ref` still appends its own `\n` after each ref, so
NUL framing works with a leading-`\n` trim. W4 moves the **tags-only** spawn (`refsArgs("tags")`,
whose every record is already known to be a tag) to NUL framing and adds `%(contents:body)` there;
the `heads`/`all` spawns keep LF framing untouched. Blast radius is one args builder, one parser
branch and one delimiter constant.

### Probe 8 — killing a scan mid-stream

```
killedAtMs=85  bytesRead=202455  exitCode=null signal=SIGTERM totalMs=89
killedAtMs=97  bytesRead=203335  exitCode=null signal=SIGTERM totalMs=102
killedAtMs=75  bytesRead=203995  exitCode=null signal=SIGTERM totalMs=80
$ pgrep -a git
(nothing)
```

**Settled.** A `git log` killed 200 KB into a 19.7 MB stream dies on SIGTERM within ~5 ms of the
kill, leaves no orphan, and reports `exitCode: null`. `driver.read()` already turns exactly this
into `GitCancelled` (it re-checks `controller.signal.aborted` *after* exit), so supersede needs no
new machinery — only an `AbortSignal` threaded from the request to the spawn.

### Probe 9 — the ≤120 ms budget: the obvious client-side matcher **misses it**

A `CommitStore` filled with 100,000 rows (5 distinct identities, realistic subjects), matched
row-at-a-time through the store's existing public accessors — the implementation anyone would write
first — five runs each:

```
naive subjectAt+authorAt+shaAt, literal:  195.2 / 153.9 / 130.5 / 130.4 / 134.8 ms   hits=40000
naive, regex:                              78.8 /  71.7 /  54.2 /  61.6 /  50.3 ms   hits=40000
subjects only, subjectAt, literal:         41.4 /  38.9 /  35.0 /  43.1 /  49.4 ms   hits=0
```

The full-field literal case is **130–195 ms — over budget**, and the cost is not the matching: it is
`String.prototype.toLowerCase()` allocating per row and `authorAt`/`committerAt` materialising an
object per row.

### Probe 9b — the column-scan matcher meets it with ~4× headroom

Same 100k rows, same queries, but: **one compiled `RegExp` for every mode** (literal escaped,
whole-word wrapped, `i` for case-insensitive — so no `toLowerCase()` anywhere), the **interner
dictionary matched once per query** into a `Set<number>` and the four identity columns then scanned
as integers, the **sha prefix compared as bytes** against `ShaTable`'s own storage, and only the
subject decoded per row:

```
dictionary size = 10, subject bytes = 2,499,996
  literal 'widget' (i)             22.4 / 23.6 / 16.7 / 16.8 / 15.7 ms   hits=40000
  literal 'widget' (case-sensitive) 20.3 / 18.7 / 19.1 / 18.4 / 18.9 ms  hits=20000
```

### Probe 10 — two JavaScript-side traps the semantics table must encode

```
-- whole-word with punctuation edges
  needle "widget" in "the widget cache":  naive-\b=true   smart=true
  needle "(#12"   in "fix (#123)":        naive-\b=false  smart=false
  needle "#123"   in "fix (#123)":        naive-\b=false  smart=true
  needle "v1.2"   in "tag v1.2.0 here":   naive-\b=true   smart=true
-- lookbehind support: true
-- catastrophic backtracking:
  (a+)+$ on 30 a's + b:  false   853 ms
```

First trap: wrapping a pattern in `\b…\b` unconditionally is **wrong when an edge character is not
a word character**. Searching `#123` with whole-word on finds nothing, because `\b` before `#`
asserts a boundary that is not there. The correct construction is conditional — `\b` when the edge
character is `\w`, a lookaround (`(?<!\w)` / `(?!\w)`) when it is not — and lookbehind is available
in every runtime this project targets. `(#12` correctly stays unmatched under both (the `2` is
followed by `3`), which is the case that proves the smart form is not merely permissive.

Second trap: **a user-typed regex can hang.** `(a+)+$` against a 31-character string takes 853 ms.
Applied to 100,000 subjects that is not a slow search, it is a frozen webview — against §7.8's
"Search never blocks the UI". Hard part 4 handles it.

### Probe 11 — the two walks agree on order, which is what makes concatenation legal

```
$ git log --all --decorate=full --topo-order --format='%H' | head -2000 | md5sum
585bc1c3f60ac91cabf8843a155f09ab  -
$ git log --all --decorate=full --topo-order --format='%H' | head -2000 | md5sum
585bc1c3f60ac91cabf8843a155f09ab  -

$ diff <(… --format='%H' …) <(… --format='%H%x1f%s%x1f%b' … | cut -d$'\x1f' -f1)
ORDER IDENTICAL (500 rows)
```

And the record framing survives a body (probe repo, `%H%x1f%an%x1f%s%x1f%b`):

```
… 9 6 6 3 9 b c e 037 F r a n k 037 c o m m i t t e r - o n l y   m a t c h 037 p l a i n \n \0 3 a c c …
```

**Settled.** Two separate invocations of the same argv produce the same order, and adding `%b` does
not change it — so the loaded rows really are a **prefix** of the scan's own sequence, and appending
de-duplicated tail hits after the loaded ones yields a globally ordered result list without sorting
anything. `splitLimitedFields`' documented "last field absorbs extra delimiters" behaviour makes
`%b` safe as the final field (a body containing a stray `0x1f` corrupts nothing before it), exactly
as `%s` is safe today. Note the trailing `\n` git emits before the NUL — the parser trims it.

## The hard parts, settled before the work items

### 1. The store has no body, and §7.8 requires matching one

`LOG_FORMAT` is ten fields ending in `%s`. There is no `%b`, so `CommitStore` holds no body and the
client-side half **structurally cannot** match one. Three routes:

- **Add `%b` to the paging walk and store bodies.** Rejected. §5.5's memory discipline is the
  reason `SubjectBuffer` exists; probe 5b measures bodies at ~4.6 MB per 30k commits (~150 MB at
  100k, before JS string overhead), against an idle-memory budget of 250 MB for the whole renderer
  at 100k. A feature that matches text would double the app's memory to do it.
- **Fetch bodies on demand for the visible rows only.** Rejected: a search must answer about rows
  that are *not* visible.
- **Accept the split, and say so.** Adopted. The **loaded-rows half matches five fields** (subject,
  author name/email, committer name/email) plus the sha prefix; the **tail half matches six**,
  adding the body, because the scan streams `%b` and pays ~3 ms for it (probe 5b) without keeping it.

This is the one place the two halves genuinely differ, and it is a difference in *available data*,
not in semantics — the same `matchCommitFields` predicate runs on both, with `body: ""` for a
loaded row. The consequence is real and must be surfaced, not buried: **a commit whose body matches
but whose subject does not is found by the tail scan even when that commit is already loaded.** The
de-duplication in W10 therefore keys on sha and prefers the *loaded* row (it has a row index, so it
can be highlighted and scrolled to) while keeping the tail's `matchedFields` — so the user sees one
hit, correctly labelled "body", pointing at a row on screen. Body-only hits are labelled in the
dropdown (`in message body`) precisely because they are the ones whose highlight-in-place has
nothing to highlight in the message column.

### 2. One pattern, six fields: the query never reaches git

Probes 1, 3, 5 and 5b together settle the phase's central question. Laid out as the choice it is:

| Route | Fields covered in one query | Processes / keystroke | Cost (100k) | Semantics implementations to test |
| --- | --- | --- | --- | --- |
| §7.8's literal argv (`--grep` + `--author` + `--committer`) | **AND**, not OR — wrong answer (probe 1) | 1 | ~700 ms | 2 (JS + git), which disagree |
| Three spawns unioned + `rev-parse --disambiguate` | all six, plus sha | 4 | ~2.1 s CPU (probe 5b, extrapolated) | 2, plus a portability gate on `\b`/`-P` (probe 2) |
| **One `git log` scan, matched host-side** | all six, plus sha | **1** | **~1.1 s incl. JS, first hit ~33 ms** (probe 6) | **1** |

The third is adopted. What it buys, in order of importance:

- **One semantics table.** The exit criterion says *"Semantics table fully covered by tests (each
  toggle × scope)"*. With one matcher that is a table of unit tests over a pure function. With two
  it is a table that must be asserted twice against two regex engines with different dialects, and
  a class of bug (a query that behaves differently above and below the load frontier) that no test
  can rule out in general.
- **`\b` and `-P` stop mattering.** JS regex is the same on macOS, Linux and Windows. No spawn-probed
  capability, no fallback path for a git built without PCRE, no BSD-vs-GNU divergence (probe 2).
- **Sha-prefix matching is free** — `%H` is in the record (probe 3).
- **"Never throws" becomes structural** — the only compilation site is ours (probe 4).
- **It is the fastest option measured**, not a correctness-for-speed trade (probes 5, 5b).

What it costs, stated plainly: git streams ~20 MB of commit records to the extension host per
full-repository search (probe 5), and the host burns ~250 ms of CPU per 100k commits filtering it.
Neither crosses the wire — only capped, matched hits do. The cost is bounded by supersede
(one scan per repo at a time) and by debounce (W11), and it is paid only for the *tail*: the
already-loaded rows never spawn anything.

**Consequence for §3.1's tree:** `core/src/search/gitArgs.ts` — "translate a query into git log
arguments" — describes work that no longer exists, and cannot exist in `core` anyway, since
`WalkSpec` and `logSessionArgs` live in `packages/git`. Its replacement (`SCAN_FORMAT`,
`logScanArgs`, `parseScanRecord`) goes next to its siblings in `packages/git/src/parse/log.ts`, so
the scan's rev set is literally `logSessionArgs`' rev set and cannot drift from it. Spec edit 4
deletes the line rather than leaving a file whose name lies about what the phase built.

### 3. The tail scan is a plain read, not a third walk session (and not the second one's pipe)

The orchestrating session asked this to be settled explicitly against D38, which created P7's
separate `reviewWalk`. Three candidates:

- **Reuse the paused `LogSession`'s process by changing its arguments.** Impossible, and worth
  saying why rather than only that it is: a process's argv is fixed at `execve`; the session is
  *mid-walk*, paused by backpressure with `#pendingRecords` and `#splitter` state that a search
  would have to consume and could not put back; and `#loadedCount` — which drives the `--skip`
  fallback after a reclaim — would be silently wrong afterwards. Reading a search's answer out of
  that pipe corrupts the panel's paging.
- **A third walk session (`searchWalk`), the way D38 added `reviewWalk`.** Rejected. D38's reasoning
  is specific and does not transfer: a *review* walk needs `LogSession`, `CommitStore`,
  `dictionaryMarks`, `nextSeq` and `lastRemaining` because it **pages, caches and packs chunks for
  the wire**, and sharing the panel's copies would destroy the panel's cache. A search walk pages
  nothing (it runs once to the end or is killed), caches nothing (its result is a list of shas), and
  packs nothing (no chunk crosses the wire). It has zero of the five fields, and a `SearchWalk`
  interface would be an empty extension of `WalkLike`.
- **`driver.read(logScanArgs(walk), { signal })`.** Adopted. It is a one-shot cancellable read of a
  read-only command — the definition of what `driver.read` is for. It correctly takes one of the
  four bounded read-pool slots for the ~1 s it runs: that is a *burst* read, exactly what the pool
  exists to throttle, and precisely unlike `LogSession` and `catFile`, whose own doc comments
  explain that a *permanently held* process must sit outside the pool. `GitRead.records(0x00)`
  already delivers the NUL-split records the parser wants.

`RepoSession` gains **no new field.** The one piece of per-session state search needs — "the scan
currently in flight, so a new one can supersede it" — is derived from the request's own
`AbortController` (hard part 6); the service holds at most a `#searchAbort` map keyed by repoId, and
even that is optional, since a superseded request is aborted by the *client* through `rpc.ts`'s
existing cancel path. W8 keeps one nullable controller per session purely so a repo close kills an
in-flight scan, matching how `close()` already disposes the review walk.

### 4. A user-typed regex can hang, and §7.8 promises it will not

Probe 10 measures `(a+)+$` at 853 ms against a 31-character string. Nothing in §7.8 anticipates
this, and the mitigations are all imperfect:

- **A worker.** The obvious answer, and unavailable: the `CommitStore` lives on the main thread by
  design (§5.5, D3a), and shipping 100k rows to a worker per keystroke costs far more than the
  13–38 ms the match itself takes.
- **Static analysis of the pattern.** Rejected — nested-quantifier detection is a heuristic that
  both over- and under-fires, and rejecting a pattern the user legitimately wants is worse than a
  slow search.
- **A time-boxed, chunked scan.** Adopted. `searchLoadedCommits` takes a `budgetMs` (default 120,
  §5.1's own number) and checks `performance.now()` every 1,024 rows; on exceeding it, the scan
  stops and reports `{ complete: false, scannedRows }`, and the UI renders "showing matches from
  the first N of M loaded commits" with a "keep searching" affordance rather than silently
  truncating. Between slices it yields (`await Promise.resolve()` / a scheduled callback) so input
  stays responsive on a slow query.

**The residual, named rather than hidden:** a single `RegExp.test()` call on a single string cannot
be interrupted, so a pathological pattern can still block for the duration of *one* row's match —
bounded in practice by subject length (tens of characters) rather than by row count, but not by
anything the code enforces. Worst observed shape (probe 10) is ~850 ms for one such call. This is
documented in the matcher's own doc comment and in §7.8's spec edit, in the same spirit as P9's
byte-identical-shas limitation: a real, understood boundary of the approach, not a bug to be
discovered later. The host-side scan carries the same guard for the same reason — a runaway match
there blocks the extension host's event loop, not just a search.

### 5. Combining the two halves without duplicates, and without sorting

The result list is built once per query settle, in `ui/src/state/search.ts`:

1. **Refs group** (scope `refs`/`both`): `RefsState`'s three lists, matched by the same compiled
   query, emitted in the order §7.8 specifies — local branches, remote-tracking branches, tags —
   each hit carrying its `kind` so `v1.2.0` the tag is never rendered as `v1.2.0` the branch.
2. **Loaded-commit hits** (scope `commits`/`both`): row indices from `searchLoadedCommits`, already
   in walk order because the store *is* the walk in order.
3. **Tail hits**: from `search.run`, filtered by `store.rowOfSha(sha) < 0` — an O(1) `ShaTable`
   probe per hit, on a list capped at `limit`.

Probe 11 is what makes step 3 a *filter* rather than a merge: the scan runs the identical argv the
paging walk runs (same `walkArgs`, same `--topo-order`, same `--decorate=full`), two invocations of
which produce byte-identical ordering, so the loaded rows are a prefix of the scan's sequence and
every surviving tail hit sorts after every loaded hit by construction. Nothing is sorted, nothing is
compared by date, and the ordering claim is pinned by an integration test (W17) rather than assumed.

The **match count** §7.8 requires is `loadedHits.length + tailTotalMatches − overlap`, where
`tailTotalMatches` is counted by the scan over *every* commit (not just the capped ones) and
`overlap` is the number of tail hits filtered out in step 3. When the scan was capped or the
client-side scan hit its time box, the count is rendered with a `+` and the "searched N of M"
line — an honest lower bound rather than a wrong number.

### 6. Where search's request and its abort live on the contract

D51 gave remote ops their own key (`remote.run`) and their own cancel (`remote.cancel`); D55 routed
stash through the existing `op.run`. Search is a third shape and takes a third answer:

**One new request key, `search.run`, and no cancel key at all.**

- **A new key, not an arm of an existing one.** There is nothing to be an arm *of*: `op.run` is the
  write executor (it sets the undo slot unconditionally — D55's whole argument — and search writes
  nothing), and `graph.*` is the paging walk's own vocabulary. §3.5 has named `search.run` since
  before P0; this phase makes it real with the shape the design actually needs.
- **No `search.cancel`.** This is the deliberate contrast with D51. `remote.cancel` exists because
  cancelling a *write* is a decision with consequences: it may be **refused** (a push past its
  killable phase, D50), its post-state must be read back and reported, and the caller must learn
  which of those happened — none of which fits a request's own `AbortSignal`. A search is a read.
  `rpc.ts` already carries per-request cancellation end to end (`bridge.request(k, p, signal)` →
  `{t:"cancel", id}` → the handler's `ctx.signal`), `driver.read` already threads a signal to the
  spawn, and probe 8 confirms the kill is clean and orphan-free. Adding a cancel key would be a
  second, weaker path to something the transport already does correctly — and would have to
  reinvent request/response correlation, since a bare "cancel search on repo X" cannot say *which*
  search. **A superseded query aborts its git process** (§7.8) is therefore implemented by
  `AbortController` in `SearchState`, one line, no wire change.
- **A discriminated-union result, so the handler cannot throw.** `search.run` returns
  `{ kind: "ok", … } | { kind: "invalidPattern", message }`. The host compiles the incoming query
  with the same `compileQuery` the UI uses; an invalid one — which the UI would not send, but a
  second client or a future caller might — comes back as data. `RepoOpenResult`'s own union is the
  precedent (§3.5 renders outcomes explicitly rather than inferring them from a thrown error).

`CONTRACT_VERSION` goes **11 → 12**.

### 7. Where three toggles and a scope are persisted

§7.8 says the toggles are persisted; it does not say where, and the two candidates carry different
meanings.

**`PersistedViewState`, version 3 → 4. Not `SETTINGS`.**

`SETTINGS` (D25) is *configuration*: it generates `contributes.configuration`, appears in VS Code's
settings UI, is documented for users, and is the right home for things a user decides once and
rarely revisits (`graph.pageSize`, `pull.strategy`, `protectedBranches`). Search toggles are the
opposite: they are the state of a widget, flipped several times a minute, exactly like `dateFormat`
and `fileListMode`, which are already in `PersistedViewState` for precisely this reason. Putting
them in `SETTINGS` would mean a settings-file write on every click of `Aa` and a user-facing
configuration entry for a button.

The version bump is the mechanism's own discipline: `parsePersistedViewState` discards a v3 blob
whole rather than half-applying it (its doc comment: *"a half-applied older state is a bug that
reproduces once per upgrade"*), so the first launch after this phase resets column widths and the
remembered scroll row once. That is the accepted, established cost of every field this project has
added to that type since P3.

**The query text itself is not persisted.** Restoring a stale search string into the box on reveal
is §6.8's own argument against a remembered comparison base, applied here: a query is a question
about *now*.

### 8. Highlight-in-place, and what "navigable" means for a hit that is not a commit row

§7.8 asks for three things at once: results highlighted in place, navigable with `Enter`/
`Shift+Enter`, and a match count. Two of the three are unambiguous; the third needs a decision,
because a ref hit and a not-yet-loaded commit hit have nowhere to be highlighted.

- **Highlight in place** is the message column's formatter wrapping matched spans of the subject in
  `<span class="kv-search-hit">`, built as DOM nodes (`enableHtmlRendering: false` is already set,
  and every existing formatter uses `textContent` — so this is XSS-safe by construction, not by
  escaping). A query change bumps a `searchGeneration` and `CommitGrid.vue` calls
  `invalidateAllRows()`, reusing the exact mechanism it already has for `graphView.generation`.
- **`Enter`/`Shift+Enter` navigate the commit matches**, in list order, wrapping at both ends,
  moving grid selection and scrolling the row into view. Ref hits are *selected* from the dropdown
  (arrow keys + Enter within the list) and, per §7.8, scroll to and highlight the commit they point
  at — for an annotated tag, `peeledObjectId`, which `RefRow` already carries. Making
  `Enter`/`Shift+Enter` cycle refs too would mean "next match" sometimes moves the grid and
  sometimes moves a dropdown cursor, which is the kind of mode the toolbar cannot afford.
- **The match count** is the commit count (loaded + tail, de-duplicated), rendered as `n of N` beside
  the input the way a find widget does; the ref group carries its own count in its group header.
  §7.8's "two result groups in one dropdown, refs first" is a rendering statement, and the counts
  follow the grouping.

Selecting a tail hit that is **not yet loaded** runs W13's `revealSha`: `graphView.loadMore()` in a
loop until `store.rowOfSha(sha) >= 0` or the history is exhausted — `loadAll()`'s existing loop
shape, with the same single `AbortController` so one cancel reaches whichever page is in flight —
then selects and scrolls. This is §5.1.1's own sentence (*"Selecting such a result loads the pages
up to it"*) implemented, and it is announced through `liveAnnouncements.ts` because on a large
repository it can take several pages.

## The contract entries P11 adds

### `packages/core/src/search/query.ts` (new)

```ts
export type SearchScope = "commits" | "refs" | "both";

/** The three toggles and the scope, as the box holds them. Text is raw user input — never
 *  pre-escaped, never pre-lowercased: escaping is `compileQuery`'s job and case folding is the
 *  `i` flag's. */
export interface SearchQuery {
  readonly text: string;
  readonly caseSensitive: boolean;
  readonly wholeWord: boolean;
  readonly regex: boolean;
  readonly scope: SearchScope;
}

/** git's own floor for `rev-parse --disambiguate` (probe 3), adopted as ours: below it a hex
 *  query matches a large fraction of any repository and buries the real hits. */
export const MIN_SHA_PREFIX = 4;

export type CompiledQuery =
  | { readonly kind: "empty" }
  /** `message` is the runtime's own text with its constant `Invalid regular expression: `
   *  prefix stripped — shown inline under the box (§7.8), never thrown (probe 4). */
  | { readonly kind: "invalid"; readonly message: string }
  | {
      readonly kind: "ok";
      /** The one RegExp every match in this phase goes through. Never carries `g`/`y` — a
       *  stateful `lastIndex` shared across ~100k `test()` calls is a correctness bug, not an
       *  optimisation. */
      readonly pattern: RegExp;
      /** Set iff `text` is 4-40 hex digits, in any mode: the sha-prefix arm of §7.8's Commits
       *  scope. Lower-cased. */
      readonly shaPrefix: string | null;
    };

export function compileQuery(query: SearchQuery): CompiledQuery;
```

Compilation, in order — this **is** the semantics table W16 tests:

| Toggle state | `source` | `flags` |
| --- | --- | --- |
| literal | `escapeRegExp(text)` | — |
| regex | `text` verbatim | — |
| + case-insensitive (default) | unchanged | `i` |
| + case-sensitive | unchanged | (none) |
| + whole word | `<lead>source<trail>` where `lead` = `\b` if the effective first character is `\w`, else `(?<!\w)`; `trail` = `\b` if the effective last character is `\w`, else `(?!\w)` (probe 10) | unchanged |

`escapeRegExp` escapes `.*+?^${}()|[]\` — and, deliberately, not `/` or `-`, which are literal
outside a character class. In **regex + whole word**, the edge test reads the raw pattern's first
and last characters, which is a heuristic on a pattern like `(foo|bar)`; the honest rule, and the
documented one, is that the lookaround form (`(?<!\w)` / `(?!\w)`) is used whenever the edge is not
an unambiguous word character, since a lookaround is correct in strictly more cases than `\b`.

## The work items

### W1 — `core/src/search/query.ts`

The whole toggle semantics, as a pure function, in one file. `compileQuery` never throws:
`new RegExp` is the only fallible call and it is inside a `try`.

```ts
const REGEX_METACHARACTERS = /[.*+?^${}()|[\]\\]/g;
export function escapeRegExp(text: string): string {
  return text.replace(REGEX_METACHARACTERS, "\\$&");
}

const HEX_PREFIX = /^[0-9a-fA-F]{4,40}$/;
const INVALID_PREFIX = "Invalid regular expression: ";
const WORD_EDGE = /\w/;

export function compileQuery(query: SearchQuery): CompiledQuery {
  const text = query.text;
  if (text.length === 0) return { kind: "empty" };
  let source = query.regex ? text : escapeRegExp(text);
  if (query.wholeWord) {
    const first = text[0] as string;
    const last = text[text.length - 1] as string;
    // `\b` asserts a boundary that is NOT there when the edge character is not a word
    // character — `#123` with whole-word on would match nothing (probe 10). A lookaround is
    // correct in strictly more cases, so it is the fallback rather than the exception.
    const lead = !query.regex && WORD_EDGE.test(first) ? "\\b" : "(?<!\\w)";
    const trail = !query.regex && WORD_EDGE.test(last) ? "\\b" : "(?!\\w)";
    source = `${lead}(?:${source})${trail}`;
  }
  try {
    const pattern = new RegExp(source, query.caseSensitive ? "" : "i");
    return {
      kind: "ok",
      pattern,
      shaPrefix: HEX_PREFIX.test(text) ? text.toLowerCase() : null,
    };
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error);
    return {
      kind: "invalid",
      message: message.startsWith(INVALID_PREFIX) ? message.slice(INVALID_PREFIX.length) : message,
    };
  }
}
```

Two details that are decisions, not incidentals. The `(?:…)` wrapper around `source` under
whole-word is required: without it, `\bfoo|bar\b` binds the alternation wrong. And the `i` flag is
the *only* case mechanism — nothing in this phase calls `toLowerCase()` on a row's field, which is
what probe 9's 130–195 ms measured and probe 9b's 13–38 ms avoids.

### W2 — `CommitStore` column views

Five accessors, no behaviour change, no new state. `internedStrings()` returns `StringInterner`'s
backing array (a new small getter on `intern.ts` beside its existing `get(id)`); `identityColumns()`
returns the four `GrowableColumn.view()`s that already exist; `shaBytes()`/`shaWidthBytes` forward to
`ShaTable.rangeView(0, rowCount)` and its own width; `subjectBytes()`/`subjectOffsets()` expose
`SubjectBuffer`'s two arrays.

Each carries a doc comment saying it is a **view, not a copy, and valid only until the next
`append`** — a matcher that holds one across a `loadMore` is reading a reallocated buffer. In
practice `searchLoadedCommits` acquires them at the top of a scan and never awaits inside it (the
time-box yield re-acquires), which is the invariant to state at both ends.

### W5 — the matcher

`matchCommitFields` is a straight OR over seven tests, returning the fields that hit; it is the
function W16's semantics table is written against, and it is deliberately allocation-light on the
miss path (the common case) — an empty frozen array constant, not a fresh `[]`.

`searchLoadedCommits` is probe 9b's strategy, in four passes over one row loop:

```ts
export function searchLoadedCommits(store, query, opts): LoadedScanResult {
  const rows = store.rowCount;
  const dict = store.internedStrings();
  // 1. Once per query, over the dictionary rather than over the rows: 40k strings cost single-
  //    digit ms (probe 9b) and turn four string matches per row into four integer probes.
  const ids = new Set<number>();
  for (let id = 0; id < dict.length; id++) {
    if (query.pattern.test(dict[id] as string)) ids.add(id);
  }
  const [an, ae, cn, ce] = store.identityColumns();
  const shas = store.shaBytes();
  const width = store.shaWidthBytes;
  const subjects = store.subjectBytes();
  const offsets = store.subjectOffsets();
  const prefix = query.shaPrefix; // bytes + an optional odd trailing nibble
  const deadline = performance.now() + opts.budgetMs;
  const hits: { row: number; fields: readonly SearchField[] }[] = [];
  let total = 0;
  let row = 0;
  for (; row < rows; row++) {
    // 2. Time box, checked on a power-of-two boundary so the check itself is not the cost.
    if ((row & 1023) === 0 && performance.now() > deadline) break;
    const fields = matchLoadedRow(row, ids, an, ae, cn, ce, shas, width, prefix, subjects, offsets, query);
    if (fields.length === 0) continue;
    total++;
    if (hits.length < opts.limit) hits.push({ row, fields });
  }
  return { hits, total, truncated: total > hits.length, complete: row >= rows, scannedRows: row };
}
```

`matchLoadedRow` checks in *cheapest-first* order — identity ids (integer `Set.has`), then the sha
prefix (byte compares, only when `prefix !== null`), then the subject (the one decode). The subject
is decoded with a module-level `TextDecoder` over `subjects.subarray(start, end)`; `body` is passed
as `""` (hard part 1).

The odd-nibble case matters and is easy to get wrong: a 5-hex-digit prefix is two whole bytes plus
the high nibble of the third, so the comparison is `bytes[k] === prefixBytes[k]` for the whole bytes
and `(bytes[n] >> 4) === lastNibble` for the remainder — with a unit test per parity (W16).

`matchRef` matches `shortName` first (the common case), then the annotation's `subject` and `body`
for a tag, and returns `refName` / `tagAnnotation` accordingly. Its `pr` parameter exists, is
documented as P12's, and is never passed in this phase.

### W8 — `RepoService.searchCommits`

```ts
async searchCommits(
  repoId: string,
  query: SearchQueryParams,
  limit: number,
  signal: AbortSignal,
): Promise<SearchRunResult> {
  const session = this.#sessions.get(repoId);
  assertDefined(session, `searchCommits: unknown repo ${repoId}`);
  const compiled = compileQuery({ ...query, scope: "commits" });
  if (compiled.kind === "invalid") return { kind: "invalidPattern", message: compiled.message };
  if (compiled.kind === "empty") return { kind: "ok", hits: [], total: 0, truncated: false, scanned: 0, complete: true };

  // The SAME WalkSpec the panel's own paging walk uses (judgment call 3) — same scope, same
  // stash inclusion — so every hit is a row the graph can actually reveal, and so probe 11's
  // prefix property holds between the two.
  const walk = this.#walkSpecFor(session);
  const read = session.driver.read(logScanArgs(walk), { signal });
  const hits: CommitSearchHit[] = [];
  let total = 0, scanned = 0, complete = true;
  const deadline = Date.now() + SEARCH_SCAN_BUDGET_MS;
  try {
    for await (const record of read.records(0x00)) {
      if (record.length === 0) continue;
      scanned++;
      if ((scanned & 1023) === 0 && Date.now() > deadline) { complete = false; read.cancel(); break; }
      const parsed = parseScanRecord(record);
      const fields = matchCommitFields(toCommitFields(parsed), compiled);
      if (fields.length === 0) continue;
      // The stash rows the panel itself filters out are not search results either (P9 W12).
      if (session.stashRowFilter.excludes(parsed.sha)) continue;
      total++;
      if (hits.length < limit) hits.push(toHit(parsed, fields));
    }
    await read.done;
  } catch (error) {
    if (error instanceof GitCancelled) throw error; // rpc.ts turns this into a cancelled response
    throw error;
  }
  return { kind: "ok", hits, total, truncated: total > hits.length, scanned, complete };
}
```

Notes the implementing agent should not have to rediscover:

- **`read.records(0x00)` already exists** and does the incremental NUL splitting; do not hand-roll a
  splitter here.
- **The scan runs to git's own end** even after `hits` is full, because `total` must be exact
  (§7.8's match count). `limit` caps the wire payload, not the walk.
- **`SEARCH_SCAN_BUDGET_MS`** is the host-side twin of hard part 4's client-side box — a ceiling on
  how long one search may hold a read-pool slot and the host's event loop. 5,000 ms, ~4.5× probe 6's
  measured 1.1 s at 100k, so it fires only on a genuinely pathological pattern or a repository far
  past this project's stated ceiling; `complete: false` is what the UI renders as "searched N of M".
- **One in-flight scan per session.** `#searchAbort: Map<repoId, AbortController>` — a new scan
  aborts the previous one before spawning, and `close(repoId)` aborts whatever is running, matching
  how `close` already disposes `logSession` and `reviewWalk`. This is belt-and-braces behind the
  client's own supersede (hard part 6); it exists so a disposed webview cannot strand a 1-second
  walk.

`SearchState`, shaped like `RefsState`/`StashState` (constructor takes the bridge, `setRepoId`,


Behaviour:

- **Per keystroke, synchronously:** recompile; if `invalid` or `empty`, clear results and stop —
  nothing spawns, nothing is requested. Otherwise run `searchLoadedCommits` and `matchRef`s. Both
  are pure and measured at 13–38 ms (probe 9b).
- **Debounced, 200 ms, only when `text.length >= MIN_TAIL_QUERY` (2):** abort the previous
  `search.run` and issue a new one with the current `AbortController`. A one-character query would
  match most of a repository and spawn a 1-second walk on the first keystroke of every search;
  two characters is the threshold, and it is a constant with a comment, not a magic number.
- **On `repo.changed { refsChanged }`:** refs hits recompute for free (they are a `computed` over
  `RefsState`). The tail is *not* re-run automatically — a search is a question the user asked at a
  moment, and silently re-spawning a 1-second walk on every background fetch is the auto-refresh
  behaviour §7.1's own auto-fetch guardrails exist to avoid. A "results may be stale" hint appears
  instead.
- **`next()` / `previous()`** move `activeIndex` over `commitHits`, wrapping, and emit the reveal
  request W13 consumes.

## Judgment calls this plan made

1. **The query never crosses the boundary into git.** The single largest call, taken on probes 1–6
   and detailed in hard part 2. The alternative (three spawns plus `--disambiguate`) is defensible
   on paper and loses on every axis measured: correctness, portability, process count, latency, and
   number of semantics implementations to test.
2. **`search.run` is a request that runs to completion, not a stream.** Probe 6 measures ~1.1 s to
   scan 100k commits and ~33 ms to the first hit, which is a real argument *for* streaming. It is
   declined because the user is not waiting on it: the loaded-rows half renders in tens of
   milliseconds with no round trip, and the tail only ever *appends* to a populated dropdown. A
   stream would add a second `streams` entry, credit-based backpressure, and partial-result
   reconciliation to save under a second on a list nobody is blocked on. Recorded as OQ2 so a later
   phase can revisit it against real use rather than against this estimate.
3. **Search walks the panel's own rev set, not `--all` unconditionally.** §5.1.1 says search
   "queries git across the whole history regardless of what is loaded" — *loaded*, not *scoped*. If
   `kiraVersion.graph.scope` is `head`, a result from an unwalked branch could never be revealed,
   scrolled to, or highlighted; the reveal loop in W13 would page to exhaustion and fail. Using
   `session`'s own `WalkSpec` also preserves probe 11's prefix property, which the whole result-merge
   depends on. Stash inclusion follows the same rule, through the existing `stashRowFilter`.
4. **A 4-hex-digit floor for sha-prefix matching**, adopted from git's own `--disambiguate` floor
   (probe 3) rather than invented. Below it the query is treated as ordinary text — which is what a
   user typing `add` means anyway.
5. **Whole-word uses lookarounds where `\b` is wrong**, per probe 10, rather than the `\b…\b`
   wrapping §7.8 describes. §7.8's own sentence stays true (the pattern *is* wrapped); the wrapping
   is conditional, and spec edit 1 says so.
6. **`Enter`/`Shift+Enter` navigate commit matches only**, not refs (hard part 8). A "next match"
   key that sometimes moves the grid and sometimes moves a dropdown cursor is a mode.
7. **Toggles persist in `PersistedViewState`, not `SETTINGS`** (hard part 7), accepting the one-time
   v3→v4 discard of column widths and scroll position that every prior field addition also cost.
8. **The client-side scan is time-boxed at 120 ms and reports how far it got**, rather than running
   to completion however long that takes. A search that silently blows its own budget on a
   pathological pattern is exactly the "Search never blocks the UI" failure §7.8 forbids; a search
   that says "matches in the first 40,000 of 100,000 loaded commits" is honest and still useful.
9. **Tag annotation bodies are fetched, at the cost of a framing change to one spawn** (probe 7,
   W4). The alternative — matching only the annotation's subject line — would make §7.8's "tags
   additionally match on their annotation message" false for exactly the tags where it matters most
   (a release tag whose notes are its body).
10. **No new `OpErrorKind`, no `errors.ts` change, no new capability probe.** Probes 2 and 4 both
    end at "this only matters if git sees the pattern", and it does not.

## Open questions for the orchestrating session

Each carries the answer this plan recommends; the implementing agent should proceed on the
recommendation unless told otherwise.

**OQ1 — Should the tail scan run at all when the history is already fully loaded?**
*Recommendation: no.* When `graphView.exhausted` is true, the store *is* the whole rev set, and the
only thing the tail adds is body matching (hard part 1). Spawning a 1-second walk per query to find
body hits on a repository the user has fully paged in is the wrong trade at, say, 5,000 commits and
the right one at 100,000. Recommend: skip the tail when `exhausted && store.rowCount <= 20_000`, and
run it otherwise, with the threshold a named constant. The dropdown's "search message bodies"
affordance runs it on demand in the skipped case.

**OQ2 — Request or stream for `search.run`?**
*Recommendation: request* (judgment call 2). Revisit if real use shows the ~1.1 s tail on a 100k
repository reads as a hang rather than as a progressive append; the change would be additive
(`streams: { "search.stream": … }`) and would not alter the matcher or any semantics.

**OQ3 — Default result cap (`limit`)?**
*Recommendation: 200 tail hits and 500 loaded hits*, with `total` always exact. 200 is well past
what a dropdown can usefully show and small enough that the wire payload stays a few tens of KB.
The exact count is what makes a cap acceptable — "12 of 4,318" is useful; "200" alone is a lie.

**OQ4 — Does the Refs scope search the *current* ref list only, or re-read refs per query?**
*Recommendation: current list only.* `RefsState` is already reloaded on every `refsChanged` (P6
W12); re-reading per keystroke would add a spawn to a path §7.8 explicitly says costs "no process
and no network round trip to a keystroke".

**OQ5 — Should a search result be highlighted in the grid even when the dropdown is closed?**
*Recommendation: yes, while the query is non-empty.* That is what "highlighted in place *and*
navigable" means; closing the dropdown to see the graph should not erase the highlights. `Esc`
clears the query, which clears both.

**OQ6 — Where does the scope selector live: inside the search box or beside it?**
*Recommendation: inside*, as a small leading control, like VS Code's own find widget's toggles. §6.2
gives the toolbar one `Search […]` slot, and §6.3's 600px breakpoint has no room for a second
toolbar control.

**OQ7 — Should `searchable(n)`'s fixture cache force a rebuild of the existing `.cache/large`
entries?**
*Recommendation: no.* `generateRepo.ts`'s cache key already includes a source hash, so adding a new
generator invalidates only its own entries — but AGENTS.md's note that a `generateRepo.ts` change
makes the next `test:integration` slower applies, and the implementing agent should expect one slow
run, not investigate it.

**OQ8 — Does the review sidebar view (§6.8) get a search box too?**
*Recommendation: no.* §7.8 describes the panel's search; the review view is a bounded, non-
virtualized tree of tens or hundreds of rows (D42) where the browser's own find is adequate, and
`NullViewStateStore` (D41) means it could not persist the toggles anyway. Not building it is a scope
decision, and it is recorded in the scope boundary rather than left implicit.

## The spec edits this phase makes

### 1. §7.8 — the Commits bullet, rewritten (probes 1–6, 10)

Replace the paragraph beginning *"**Commits.** Matches over subject, body…"* through *"…since git
has no word-boundary flag."* with:

> - **Commits.** Matches over subject, body, author name/email, committer name/email, and sha
>   prefix (4 or more hex digits — git's own `--disambiguate` floor, below which a prefix matches
>   too much to be useful). Executed **client-side over already-loaded commits** for instant
>   feedback — this is what makes the ≤120 ms budget achievable — and simultaneously handed to git
>   for the not-yet-walked tail.
>
>   **The pattern itself never reaches git.** The tail query is the *same* `git log` walk the graph
>   already pages (`--decorate=full --topo-order -z --format=…`, the panel's own rev set) with the
>   commit body added to the format; the matching is done on the records as they stream, by the
>   same compiled matcher the client-side half runs. This is not a preference: `git log`'s
>   `--grep`, `--author` and `--committer` are **ANDed across categories**, so a single pattern that
>   must match *any* of six fields cannot be expressed as one invocation (`--all-match` governs how
>   multiple `--grep`s combine with each other and has no effect on `--author` at all); `--grep`
>   cannot match an object name, so a sha prefix needs a separate `rev-parse --disambiguate`; and
>   git's regex dialect is the platform's, so word boundaries (`\b`, `\<`) are a GNU `regcomp`
>   extension and Perl regexes depend on whether the binary was built with PCRE. Measured against a
>   100,000-commit repository, a `--grep` matching *nothing* costs ~700 ms and a full scan of the
>   same history costs ~860 ms, because git walks and inflates every commit either way — so letting
>   git filter buys pipe bytes, not time, and costs one semantics implementation per engine.
>
>   Toggles compile into one regular expression: literal patterns are escaped, case-insensitivity
>   is the `i` flag, and whole-word wraps the pattern in `\b…\b` — or, when an edge character is not
>   a word character, in `(?<!\w)…(?!\w)`, since `\b` before `#` asserts a boundary that is not
>   there and would make `#123` unmatchable.
>
>   The one asymmetry between the two halves is data, not semantics: the loaded-commit store holds
>   no message body (§5.5), so a body-only match is found by the tail scan even for a commit that is
>   already on screen. Such hits are labelled as body matches, since there is nothing in the message
>   column to highlight.

| # | Question | Decision |

| D67 | How one user pattern matches six commit fields | **It never reaches git: `git log` supplies the records, one compiled `RegExp` in `core/search/` supplies the matching — for the already-loaded rows and the streamed tail alike.** §7.8's own `--grep=<p> --author=<p> --all-match?` does not compute what §7.8's prose describes: `--grep`/`--author`/`--committer` are **ANDed across categories** and `--all-match` governs only how multiple `--grep`s combine with each other (P11 probe 1).
