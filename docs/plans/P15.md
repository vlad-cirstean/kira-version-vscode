# P15 — IPC wire format migration

Plan for the P15 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Sequencing note.** §10's P15 row says this phase is "deliberately last, after every other phase
including P14", and that sentence describes v1's intended production order. It has not been
edited: the user's instruction to design and implement P15 *now*, ahead of P7 and the rest, is a
direct out-of-sequence instruction, not a retroactive rewrite of the phasing table. Whether the
row should carry a note recording that P15 was worked early is open question 2 below, for the
orchestrating session — not for this plan to decide by editing the row.

**The brief, in full:** *"replace today's JSON-shaped `structured clone` wire encoding (§3.5)
with FlatBuffers, for lower serialization overhead on large payloads (e.g. graph streaming)."*
That is the whole of the P15 row's design content. This plan designs the migration, measures
what it would buy, and — because the measurements are unambiguous and they point the other way —
recommends a different change that delivers what the brief actually asks for ("lower
serialization overhead on large payloads") at a fraction of the cost, and delivers **8x more of
it** than FlatBuffers could.

That conclusion is not a way of avoiding the work. The FlatBuffers design is worked out in full
below — schema layout, codegen, versioning reconciliation, scope, transport seam — precisely so
that the decision is made against a real design rather than a vague one, and so the orchestrating
session can override this recommendation with a work program already sized and ordered
(appendix, F1–F8) if it wants to.

## What "the wire format" concretely is today

The placeholder calls it "JSON-shaped `structured clone`". That is half right, and the half it
gets wrong is the half that matters. Read against the tree:

| Layer | File | What it actually does |
|---|---|---|
| The contract | `packages/ipc/src/contract.ts` | 21 requests, 2 events, 1 stream. Plain TS interfaces. **Not** JSON — no `JSON.stringify` appears anywhere in `packages/ipc`. |
| The frame | `packages/ipc/src/rpc.ts` L61–80 | A nine-member `Frame` union (`req`/`res`/`evt`/`open`/`chunk`/`end`/`credit`/`cancel`), each wrapped by `wrapVersioned` into `{version, body}`. |
| The envelope | `packages/ipc/src/validate.ts` | `CONTRACT_VERSION = 5`; `unwrapVersioned` throws `ContractVersionMismatchError` on arrival. `assertContractShape` additionally rejects an unknown method name or a non-string `kind`. |
| The encode step | `packages/ipc/src/codec.ts` | `encode()` **does not encode anything.** It returns `{payload: message, transfer}` — the message unchanged, plus a walked-out list of every `ArrayBuffer` it found, for a transport that can transfer. `decode()` is the identity function. |
| The channel | `MessageChannelLike` (`rpc.ts` L30) | `post(message, transfer?)` / `onMessage(handler)` / `close()`. ~10 lines per host. |
| The only real host | `packages/host-vscode/src/transport.ts` | `webview.postMessage(toWireSafe(message))`. **No transfer list** — `@types/vscode` exposes none. |

So today's wire format is: **plain JS object graphs, handed to whatever the host's channel does
with them.** There is no serializer of ours in the path. `packages/ipc` has no opinion about
bytes at all.

The one place the app already reaches for a binary representation is
`packages/core/src/store/commitStore.ts`'s `packSlice`/`appendPacked` — §5.5's column-wise store,
packed into `PackedCommitChunk`: seven `ArrayBuffer` fields (`shas`, `parentOffsets`,
`parentShas`, `identityIds`, `times`, `subjectBytes`, `subjectOffsets`), a delta string
dictionary, and a decorations array. It is the **only** `ArrayBuffer` on the whole contract —
`grep`ped: `PackedCommitChunk` is the sole producer, `graph.stream`'s `chunk.commits` the sole
consumer. Everything else on the contract is small structured data.

`RepoService.CHUNK_ROWS = 500`, so a 5,000-commit page (`kiraVersion.graph.pageSize`, D9)
crosses the wire as **ten chunks of 500 rows**, ~420 KB of packed columns in total.

### And then there is the thing that makes this phase different from what it looks like

`packages/host-vscode/src/transport.ts` — the only production transport — does this immediately
before its one `postMessage`:

```ts
function toWireSafe(value: unknown): unknown {
  if (value instanceof ArrayBuffer) return Array.from(new Uint8Array(value));
  ...
}
```

Every `ArrayBuffer` becomes a **plain JS array of numbers**, one element per byte. This is
P4c's finding 5 (`docs/plans/P4c-linux-test-infra.md`, "the single most consequential bug this
plan found"): against a real, downloaded VS Code build, a bare `ArrayBuffer` sent through a
`WebviewView`'s `postMessage` arrived in the webview as `{}` and a `Uint8Array` as
`{"0":123,"1":185,…}`. A genuine `Array` survives, so a genuine `Array` is what gets sent.

**This is the actual wire format on the only host that ships**, and it is neither structured
clone nor a packed buffer. It is a 420 KB payload expanded into 420,028 JS numbers, then
serialized by VS Code. Any FlatBuffers design has to answer to *this* boundary, not to the one
§3.5 describes.

## What is actually measured, and what it says

Everything below was run in this container (Linux, Bun 1.x, system git 2.43). **D27 makes macOS
authoritative for results**, so these are directional-but-real numbers, not the final word; W11
re-runs them where it matters. Each is reproducible from the harnesses named.

### The existing perf harness already isolates the wire hop, and it exonerates the format

`tests/perf/streamRoundTrip.ts` (P2's W17) times `packSlice → structuredClone → appendPacked`
over a 5,000-row page of `largeBranchy(100_000)`. Re-run for this plan against the committed
baseline in `tests/perf/streamRoundTrip.budget.json`:

```
✓ packMs:            baseline= 7.86   actual= 7.63
✓ cloneMs:           baseline= 0.36   actual= 0.21   (structuredClone WITH a transfer list)
✓ appendMs:          baseline=43.07   actual=46.47
· cloneMsNoTransfer  (recorded, not gated):  1.43     (full structured clone, no transfer)
· wireBytesFirstPage (recorded, not gated):  420,028
· roundTripMs100k    (recorded, not gated):  749.09
```

Read that column honestly. Of the ~54 ms one 5,000-row page costs on this path, **serialization
is 0.21–1.43 ms of it**. The dominant cost, by a factor of thirty, is `appendMs` — the
receiver's `appendPacked`, which re-interns the dictionary, hashes 500 shas per chunk into
`ShaTable`, decodes subjects and rebuilds the parent CSR. **No wire format changes that number**,
because it is not decoding; it is building the store the layout algorithm reads. FlatBuffers'
zero-copy access does not remove it either — the columns still have to land in the growable
`Uint32Array`s `CommitStore` owns, and the shas still have to be hashed to answer
`rowOfSha`.

So the premise "serialization overhead on large payloads" is, on the harness's own boundary,
**not measurable against anything else in the pipeline.** That is the first finding, and it would
be enough to stop here — except that the harness's boundary is not the one that ships.

### The boundary that ships costs 8x what the harness's does, and it is not the format's fault

Probe (`wirebench4.ts`), modelling the real host exactly: one 5,000-commit page as ten 500-row
chunks, each through `packSlice` → the host transform → `JSON.stringify` (VS Code's own webview
serialization, see below) → `JSON.parse` → rebuild the seven buffers. The only difference
between the two rows is **how the seven `ArrayBuffer`s are represented**:

| Per 5,000-commit page (10 × 500-row chunks) | Wall time | Wire bytes |
|---|---|---|
| `Array.from(new Uint8Array(buf))` — **today, shipping** | **47.1 ms** (64.3 ms cold) | **1,328,105** |
| the same chunks, buffers as base64 strings | **6.1 ms** (10.5 ms cold) | **562,418** |

Both rows include the identical `packSlice` work, so the ~41 ms difference is entirely the
buffer representation. Broken out on a single 5,000-row chunk (`wirebench.ts`, median of 3):

```
  29.83 ms   encode  toWireSafe (ArrayBuffer -> number[])
   7.49 ms   JSON.stringify of that
  18.09 ms   JSON.parse
  17.65 ms   rebuild number[] -> ArrayBuffer          =  73.06 ms   1,333,417 bytes
   ---
   0.56 ms   encode  base64 columns
   0.30 ms   JSON.stringify
   0.44 ms   JSON.parse
   1.17 ms   rebuild base64 -> ArrayBuffer            =   2.47 ms     560,395 bytes
```

And the heap: 20 retained `Array.from()` copies of one 420,028-byte page measured an RSS delta of
90.8 MB — **4.54 MB per page, per side**, transiently, against §5.1's ≤80 MB first-page renderer
budget. base64 costs 560 KB of string.

§5.1 gives a first page 400 ms. Today's representation spends ~47 ms of that — 12% — on nothing
but turning bytes into numbers and back. **That is the real "serialization overhead on large
payloads" the P15 row is reaching for**, and it has nothing to do with JSON vs FlatBuffers.

### Now measure FlatBuffers against the same page

Same probe, path C: the whole chunk built into one FlatBuffer table with seven byte-vectors, a
string vector for the dictionary, and the scalars — hand-built with `flatbuffers@25.9.23`'s
`Builder` exactly as generated accessors would.

```
   0.67 ms   build the flatbuffer                       420,312 bytes
   0.11 ms   read all seven columns back (zero-copy subarrays)
   0.71 ms   base64 it (the boundary tax it cannot avoid)  ->  560,416 chars
   0.31 ms   base64 -> bytes
  15.75 ms   ...or Array.from() it, the transform today's host applies to any buffer
```

Laid side by side, component for component, on the same 5,000-row chunk — both including the
`JSON.stringify`/`JSON.parse` of the resulting base64 string (0.43 / 0.22 ms for a 560 KB string,
measured separately):

| | base64 over the existing packed columns | FlatBuffers, then base64 |
|---|---|---|
| build / encode | 0.56 | 0.67 + 0.71 |
| `JSON.stringify` | 0.30 | 0.43 |
| `JSON.parse` | 0.44 | 0.22 |
| decode / access | 1.17 | 0.31 + 0.11 |
| **total** | **2.47 ms** | **2.45 ms** |
| wire bytes | 560,395 | 560,416 |

**Dead even.** Not "FlatBuffers wins a little" — the two are the same answer, because both are
"420 KB of already-columnar binary, base64'd", and `packSlice` was already doing the part that
matters. FlatBuffers is faster to decode (one base64 string, not seven) and slower to encode (it
builds a second buffer before base64'ing it), and the two cancel. What it costs on top is a
schema language, a code generator, a native binary, a build step and a second versioning story.

### On the non-columnar payloads, FlatBuffers is measurably *worse*

The other candidate "large payload" is `commit.fileDiff`, whose body is a deep, string-heavy tree
of `DiffHunk`/`DiffLine`. `repoService.ts`'s `MAX_PATCH_BYTES = 1 * 1024 * 1024` caps it, so the
realistic worst case is a ~1 MiB patch — 13,273 diff lines across 133 hunks (`wirebench3.ts`):

| 1 MiB-capped `commit.fileDiff` | Encode | Decode | Wire bytes |
|---|---|---|---|
| JSON (today) | 4.46 ms | 7.92 ms (parse) | 2,110,400 |
| FlatBuffers (table per line) | **10.84 ms** | ~0 (zero-copy) | 1,397,428 |
| FlatBuffers, then base64 for this host | 10.84 + 1.75 ms | +0.9 ms | **1,863,240** |

FlatBuffers is **2.4x slower to encode** than `JSON.stringify` here and saves 12% of wire bytes
after the base64 tax. Its zero-copy read is unusable in practice: the diff view materializes Vue
rows from the lines anyway, so the decode never happens in bulk — and pushed to an unrealistic
20k-line diff the gap widens (41.48 ms to build vs 7.22 ms to stringify). String-heavy tables are
FlatBuffers' worst shape, and this contract's non-columnar payloads are all string-heavy.

### And the small payloads are not a problem to begin with

| Payload | `JSON.stringify` | `JSON.parse` | bytes |
|---|---|---|---|
| `repo.changed` event | 0.000 ms | 0.001 ms | 63 |
| `commit.detail`, 400-file tree | 0.071 ms | 0.232 ms | 48,744 |
| `refs.list`, 1,200 refs (a deliberately extreme repo) | 0.668 ms | 1.389 ms | 378,288 |

Against §5.1's ≤80 ms commit-select budget, `commit.detail` spends 0.3 ms on the wire. There is
no bottleneck here to optimize, and converting these to FlatBuffers would mean writing and
generating schemas for **21 requests, 2 events, 1 stream and roughly 45 named types** to save
fractions of a millisecond.

## The FlatBuffers migration, designed

This section answers the six questions a real migration has to answer. It is written as though
the migration were happening, so the recommendation below is a judgment about a concrete design
rather than a shrug.

### 1. Schema definition and codegen — and the toolchain problem

**The runtime is fine.** `flatbuffers@25.9.23` on npm: **Apache-2.0**, zero dependencies, ~28 KB
of ESM source, ships `.d.ts`. It clears `AGENTS.md`'s fully-open-source bar with no
community-edition or paid-tier trap. If the only cost were this package, it would be cheap.

**The compiler is not.** `.fbs` → TypeScript needs `flatc`, a C++ binary. Verified against the
npm registry, from this container:

- **`flatc-bin@23.5.26`** — `package.json` declares `"bin": {"flatc-bin": "bin/flatc"}`, and
  **`bin/flatc` does not exist in the published tarball.** It ships `bin/flatc-darwin` (a Mach-O
  universal binary, x86_64 + arm64) and `bin/flatc.exe`, and nothing else. So `npx flatc-bin`
  fails outright, there is **no Linux binary at all**, and it is one unaffiliated maintainer
  republishing Google's release assets, two years stale.
- **`flatc@1.1.0`** — a 2018 wrapper whose `postinstall` downloads and *compiles* FlatBuffers
  **1.9.0** from source (or fetches a Windows exe). Seven years stale, and its `license` field is
  the non-SPDX `"SEE SEPARATE LICENSE FILE"`.
- Google's own binaries are published as GitHub release assets per platform. That is the
  supportable route, and it means **vendoring a platform-specific binary into the repo or
  fetching it in a build step** — a first for this project, which today builds with Bun, Vite and
  Biome and nothing native.

Consequences either way:

- A `postinstall` download makes `bun install` network-dependent and platform-dependent — and
  P4c exists precisely because this project cares about the tree being buildable on Linux for
  development even though D27 ships macOS only. `flatc-bin` cannot serve that lane.
- Vendoring binaries means checking a ~6.5 MB Mach-O (plus, for the dev lane, a Linux ELF) into
  a repository whose largest committed artefacts today are PNG visual baselines.

**Where the schemas and generated code would live** (if it happened): `packages/ipc/schema/*.fbs`
(one file per contract area: `frame.fbs`, `graph.fbs`, `refs.fbs`, `diff.fbs`, `ops.fbs`) with
generated output at `packages/ipc/src/generated/` — **committed to the tree**, and verified in CI-
less fashion by a `--check` mode, exactly the pattern `scripts/gen-settings.ts` and
`scripts/gen-lane-palette.ts` already establish (`bun run check:settings`,
`bun run check:lane-palette` both compare generated output against the tree and fail on drift).
That precedent is the one genuinely good news in this section: the project already knows how to
make generated code non-forgettable, so `check:schema` would slot into `bun run check` with no
new idea required. What it does *not* solve is that `bun run gen:schema` would then be the one
generator in the repo that cannot run without a native binary the repo does not have.

### 2. Versioning — reconciling two schemes that do not want to be reconciled

Today: one number, `CONTRACT_VERSION = 5`, checked on every frame by `unwrapVersioned`, and §3.5's
rule is "a schema mismatch fails loudly rather than half-working". Both halves of the wire come
from one build (`html.ts` injects the version into the webview's bootstrap island), so the number
is a tripwire against a stale build, not a compatibility negotiation.

FlatBuffers' versioning is the opposite in spirit: append-only fields, `deprecated` rather than
removal, never renumber, and readers tolerate writers of other versions **by design**. The two do
not conflict, but the second is worthless here: there is no cross-version traffic to tolerate.
The reconciliation is therefore not a merge, it is a subordination, and it should be stated
explicitly rather than left to be discovered:

> `CONTRACT_VERSION` stays the **only** compatibility authority. FlatBuffers' evolution rules are
> observed as *source hygiene* — append-only, never renumber, `deprecated` not deleted, because
> renumbering a field silently misreads old data during a partial rebuild — and every schema
> change bumps `CONTRACT_VERSION` regardless of whether FlatBuffers would have tolerated it.
> No `file_identifier`-based negotiation, no per-table version fields, no dual-read path.

That is a clean answer, and it is worth recording even under the recommendation below, because it
is the answer for **any** future binary format, not just FlatBuffers.

### 3. Scope — whole contract, or hot paths only?

**Hot paths only, if at all.** The evidence is in the measurement tables above: `repo.changed`
costs 1 µs, `commit.detail` 0.3 ms, and `refs.list` at a deliberately extreme 1,200 refs costs
2 ms. Converting ~45 types across 24 contract keys to generated accessors to save microseconds is
the kind of trade `AGENTS.md`'s "measure when there's a real, concrete question at stake" rule
exists to prevent. The only payloads with a defensible claim are `graph.stream`'s
`PackedCommitChunk` (420 KB/page) and `commit.fileDiff` (≤1 MiB patch) — and FlatBuffers loses on
both, by 0.7 ms of gain on the first and 6 ms of loss on the second.

There is also a structural cost to a partial conversion that is easy to miss: `contract.ts`'s
types are **structural copies** of `packages/core`'s, kept honest by
`tests/unit/ipc/wireConformance.test.ts` because `ipc` may not import `core` (§3.1's B3 rule).
Generated FlatBuffers accessors are classes with getters, not interfaces — they are *not*
assignable to core's readonly-interface shapes in either direction, so `wireConformance.test.ts`'s
whole mechanism (compile-time assignability both ways) stops working for every converted type and
has to be replaced by hand-written adapters plus round-trip tests. That is a real regression in
the project's best defence against `ipc`/`core` drift, and it lands on exactly the types most
worth protecting.

### 4. The `Transport` abstraction — inside the envelope, not replacing it

If FlatBuffers happened, it would live **inside** the existing envelope, not replace it. The
frame union, request correlation, stream credits and cancellation in `rpc.ts` are transport
semantics, not payload encoding, and they are the part of `packages/ipc` with real behaviour
worth not disturbing (`rpc.test.ts`, `codec.test.ts`). The seam is the two functions that already
exist for it:

```ts
function post(channel, frame)     { channel.post(...encode(wrapVersioned(frame))) }
function receive(channel, handle) { channel.onMessage(raw => handle(unwrapVersioned(raw))) }
```

`encode`/`decode` in `codec.ts` are today the identity plus a transfer-list walk. **They are the
correct and only place a payload encoding belongs**, whatever that encoding is. This is true of
the recommendation below as much as of FlatBuffers, and it is the one architectural conclusion
this plan reaches that does not depend on which format wins.

What FlatBuffers would *not* get to do is what makes it fast elsewhere: hand the receiver one
buffer and let it read in place. See the next point.

### 5. Both host directions — and why the transferable win is unavailable

There is one host (`packages/host-vscode`; Electron was removed, `docs/plans/P4b-remove-electron.md`).
Three facts constrain what is possible, and the third is the decisive one:

1. §4.1's system-Git decision is orthogonal — it shapes what data exists, not how it crosses.
2. `webview.postMessage` **takes no transfer list.** `@types/vscode`'s signature has no second
   argument; `host-vscode/src/transport.ts` accepts one only for `MessageChannelLike` parity and
   ignores it. So every buffer is copied on this boundary no matter what. FlatBuffers' "one
   buffer, transferred, read in place" story is already half gone before the format is chosen.
3. **Raw bytes do not survive the boundary at all** (P4c finding 5). So a FlatBuffer — which *is*
   a `Uint8Array` — would have to be base64'd or `Array.from()`'d exactly like today's columns
   are. Measured above: `Array.from()` of the flatbuffer costs 15.75 ms/page, base64 0.71 ms.
   Either way, **the receiver gets a string, decodes it into a fresh buffer, and reads from that**
   — the copy FlatBuffers exists to avoid, reintroduced by the host.

This is the crux. On the one host v1 ships, FlatBuffers' central advantage is unavailable *by
construction*, and what remains is "a compact binary encoding of columnar data" — which
`packSlice` already is.

**Why fact 3 deserves one more look, though.** Reading VS Code's own source (fetched from
`microsoft/vscode@main` while writing this plan):

```ts
// src/vs/workbench/api/common/extHostWebview.ts
export function shouldSerializeBuffersForPostMessage(extension: IExtensionDescription): boolean {
  const version = normalizeVersion(parseVersion(extension.engines.vscode));
  return !!version && version.majorBase >= 1 && version.minorBase >= 57;
}
// src/vs/workbench/api/common/extHostWebviewMessaging.ts
//   gated true  -> JSON.stringify(message, replacer)  // ArrayBuffers become {$$vscode_array_buffer_reference$$}
//   gated false -> JSON.stringify(message)            // ArrayBuffer -> {} ; Uint8Array -> {"0":…}
// src/vs/workbench/api/browser/mainThreadWebviews.ts
//   $postMessage -> deserializeWebviewMessage(...) -> webview.postMessage(message, arrayBuffers)
```

`packages/host-vscode/package.json` declares `"engines": {"vscode": "^1.134.0"}` → `majorBase 1`,
`minorBase 134` → the gate should be **true**, and `MainThreadWebviews.$postMessage` is shared by
`WebviewPanel` and `WebviewView` alike. Yet the shapes P4c actually observed — `{}` for an
`ArrayBuffer`, `{"0":123,…}` for a `Uint8Array` — are *exactly and only* what the **ungated**
branch produces. So one of the following is true, and nobody knows which: the gate evaluated
false for a reason not yet identified (a manifest read differently under
`--extensionDevelopmentPath`, an older VS Code than the manifest claims to target, a realm
mismatch on `instanceof ArrayBuffer` inside the extension host), or VS Code's own path is broken
for this configuration.

That question is worth a cheap probe (W1) **before** any encoding work, because if the gate can
be made to pass, ArrayBuffers cross natively, `toWireSafe` deletes itself, and the per-page tax
drops to `cloneMsNoTransfer`'s ~1.4 ms with no encoding of ours at all. It does not change the
FlatBuffers verdict — a natively-carried `ArrayBuffer` makes the *existing* packed format free
too — but it changes which branch of the recommendation ships.

### 6. Testing implications

`tests/unit/ipc/wireConformance.test.ts` today is a **compile-time** artefact: it asserts
assignability between `core`'s types and `ipc`'s structural copies in both directions and does
not send a byte anywhere. It would not catch a single one of the failure modes a format migration
introduces, and — as noted in §3 above — a FlatBuffers conversion would *break* the mechanism it
uses rather than extend it.

Worse, the boundary the automated suites exercise is not the boundary that ships.
`apps/harness/src/mockBridge.ts` pipes frames through `structuredClone(message, {transfer})` — a
**higher-fidelity, faster** channel than the real host's, one that carries `ArrayBuffer`s
perfectly. Every Playwright interaction, visual and accessibility spec runs against it. So the
entire test estate is blind to the one transform that costs 47 ms a page, which is exactly how
P4c's bug survived to be found by hand in a real VS Code build. **Any wire work in this phase has
to close that hole**, whatever format wins.

## Recommendation

**Decline FlatBuffers for v1. Fix the encoding that is actually costing 47 ms a page, and put it
where `packages/ipc` can own it.**

The brief asks for "lower serialization overhead on large payloads". Measured, on the host that
ships, per 5,000-commit page:

| | Wall time | Wire bytes | Toolchain cost |
|---|---|---|---|
| Today | 47.1 ms | 1,328,105 | — |
| **base64 buffers (recommended)** | **6.1 ms** | **562,418** | none — a platform builtin |
| FlatBuffers (+ base64, forced by the host) | the same, to within 0.02 ms per chunk | 560,416 | `.fbs` schemas, a native `flatc` with no working npm distribution, committed generated code, a second versioning story, and the loss of `wireConformance.test.ts`'s mechanism |
| FlatBuffers, if raw bytes could cross (they cannot) | ~1.5 ms | 420,312 | the same |

The recommended change captures **41 of the 47 ms** — 87% of the available win — with a platform
builtin and no schema machinery. FlatBuffers on top of it captures nothing further: 2.45 ms
against 2.47 ms per chunk, which is noise. And on `commit.fileDiff`, the contract's other large
payload, FlatBuffers is 6 ms *slower*.

This is the same discipline `docs/plans/P6a-test-perf.md` applied when its own measurements
falsified three of its premises: the honest output of a measurement is sometimes "the thing you
were going to build is not the thing that is slow".

### The decisions

Continuing from §11's highest, **D32**.

| # | Question | Decision |
|---|---|---|
| **D33** | FlatBuffers for the IPC wire format | **Declined for v1, on measured grounds — not deferred vaguely.** On the one host v1 ships, `webview.postMessage` carries no transfer list and (P4c) no raw bytes, so FlatBuffers' zero-copy/transferable advantage is unavailable by construction and its payload must be base64'd exactly like today's packed columns. Measured component-for-component on a 5,000-row chunk it is *indistinguishable* from base64-over-the-existing-format (2.45 ms vs 2.47 ms, 560,416 vs 560,395 bytes); on a 1 MiB `commit.fileDiff` it is 2.4x slower to encode; on every small request it is irrelevant. Against that it costs `.fbs` schemas, a native `flatc` with no working npm distribution (`flatc-bin@23.5.26`'s declared `bin` is absent from its own tarball and it ships no Linux binary; `flatc@1.1.0` builds FlatBuffers 1.9 from source), committed generated code, and the loss of `wireConformance.test.ts`'s compile-time drift check. Reopen only if a host arrives whose transport carries binary natively **and** a payload is measured where encoding, not `appendPacked`, is the bottleneck. |
| **D34** | Where a payload encoding lives | **In `packages/ipc/src/codec.ts`, declared per transport — never hand-rolled per host.** `encode`/`decode` are already the seam (`rpc.ts`'s `post`/`receive` are their only callers) and are today near-identity. A transport declares what it can carry; `codec.ts` applies the matching transform. `host-vscode/src/transport.ts`'s `toWireSafe` is deleted, not moved: a host's channel adapter is ~10 lines of `postMessage` plumbing (§3.5) and must not be where the wire format is decided, which is how the 47 ms became invisible to every test in the tree. |
| **D35** | The encoding for a transport that cannot carry binary | **base64, via `Uint8Array.prototype.toBase64` / `Uint8Array.fromBase64` where present, with a small feature-detected fallback.** Measured against the alternatives on a 420,028-byte page: base64 → 560,048 JSON bytes, 0.43 ms stringify / 0.22 ms parse / 0.20 ms decode; latin1 binary-string → 653,020 JSON bytes (JSON escaping of control bytes inflates it *past* base64) at 4x the stringify cost; hex → 840,064 bytes. base64 is both the smallest and the fastest, and the platform builtin encodes 420 KB in 0.49 ms. The **packed columnar format itself does not change** — `packSlice`/`appendPacked`, the interning scheme and `PackedCommitChunk`'s field list are untouched. |
| **D36** | What the encoding applies to | **Buffers, wherever they appear on the contract — which today is exactly `PackedCommitChunk`'s seven fields.** Not a per-key allowlist and not "the graph stream": `codec.ts` already walks the message generically (`collectTransferables`), and a rule expressed as "every `ArrayBuffer`" cannot be forgotten by the next phase that adds one. This is the "hot paths only" answer to the scope question, expressed structurally instead of as a list. |
| **D37** | The real host's boundary is tested and budgeted | **Both, this phase.** `wireConformance.test.ts` gains a genuine round trip through each declared encoding, and `tests/perf/streamRoundTrip.ts` gains a gated metric modelling the real VS Code path — because the harness's `structuredClone`-with-transfer bridge is strictly *better* than what ships, so no existing suite can see a regression on the boundary that matters. This is the standing rule the phase leaves behind, not a one-off. |

## The changes P15 makes

### `packages/ipc/src/codec.ts` — from identity to a real codec

```ts
/** What a transport's channel can actually carry across its boundary. Declared by the transport,
 *  not inferred: the VS Code webview's answer is a fact about VS Code (P4c), and getting it
 *  wrong silently produces `{}` on the far side rather than an error. */
export type BufferEncoding = "native" | "base64";

/** A buffer that has been encoded for a transport that cannot carry bytes. The tag is what lets
 *  `decodeBuffers` find them again without a schema — `collectTransferables`'s traversal in
 *  reverse. */
interface EncodedBuffer {
  readonly $buf: "b64";
  readonly d: string;
}

export interface EncodedMessage<T> {
  readonly payload: T;
  readonly transfer: readonly ArrayBuffer[];
}

/** `native`: unchanged behaviour — the message is passed through and every ArrayBuffer collected
 *  into a transfer list for a channel that has one. `base64`: every ArrayBuffer is replaced by an
 *  `EncodedBuffer` and the transfer list is empty, since there is nothing left to transfer. */
export function encode<T>(message: T, encoding: BufferEncoding): EncodedMessage<unknown>;
export function decode<T>(payload: unknown, encoding: BufferEncoding): T;
```

Three properties the implementation must have, each for a reason found while planning:

- **The traversal is the one already there.** `collectTransferables` walks
  `ArrayBuffer` → `ArrayBuffer.isView` → `Array` → plain object. `encodeBuffers` walks the same
  shapes and rebuilds; `decodeBuffers` walks looking for the `$buf` tag. Three traversals of the
  same shape rule, so they live beside each other in one file and are tested together.
- **`ArrayBuffer.isView` is handled, not assumed away.** `toWireSafe` today returns views
  untouched with a comment that nothing on the contract sends one. That is true *today*; the
  codec must not inherit the assumption, because a `Uint8Array` on this boundary arrives as
  `{"0":…}` — silently wrong data, not an error.
- **Zero-length and non-UTF8 buffers round-trip.** A repository with a single commit produces a
  chunk whose `parentShas` is empty; subject bytes are arbitrary UTF-8 that may be invalid.
  base64 handles both, and the tests must say so rather than assume it.

### `packages/ipc/src/rpc.ts` — the two seams, unchanged in shape

```ts
export interface MessageChannelLike {
  /** What this channel can carry. `native` keeps today's behaviour exactly. */
  readonly bufferEncoding: BufferEncoding;
  post(message: unknown, transfer?: readonly ArrayBuffer[]): void;
  onMessage(handler: (message: unknown) => void): () => void;
  close(): void;
}
```

`post()` and `receive()` gain `channel.bufferEncoding` as an argument to `encode`/`decode`.
Nothing else in `rpc.ts` moves — not the frame union, not the credit gate, not correlation, not
cancellation. The one place `rpc.ts` bypasses `post()` today (the raw
`channel.post(wrapVersioned({t:"credit",…}))` in the chunk handler) carries no buffers, but it
must go through `post()` anyway so there is exactly one path (W3).

### `packages/ipc/src/validate.ts`

`CONTRACT_VERSION` 5 → **6**. Both halves of the wire ship in one build, so this is a tripwire
against a stale webview, not a negotiation — which is precisely the case it protects: a
half-reloaded webview decoding base64 as a number array would produce a plausible, wrong graph.

### `packages/host-vscode/src/transport.ts` and `src/webview/main.ts`

`toWireSafe` is deleted. `createWebviewChannel` declares `bufferEncoding` (W1's outcome decides
`"native"` or `"base64"`) and `createVsCodeChannel` in the webview declares the same. The long
doc comment on `transport.ts` explaining the number-array workaround is replaced by a short one
pointing at this plan's W1 finding — the fact stays recorded, it just stops being expressed as
code in the wrong layer.

**Both halves must agree**, and they cannot be allowed to disagree by editing one file. They are
one build, so the value comes from a single shared constant exported by `packages/ipc`, not from
two literals — W5's own exit condition.

## W1 — Probe: is the number-array workaround still necessary?

**The question.** VS Code's `shouldSerializeBuffersForPostMessage` gates on
`extension.engines.vscode >= 1.57`; this extension declares `^1.134.0`;
`MainThreadWebviews.$postMessage` is shared between `WebviewPanel` and `WebviewView`. So the gate
*should* pass and `ArrayBuffer`s *should* arrive intact — yet P4c observed exactly the shapes the
ungated `JSON.stringify(message)` branch produces.

**How.** Temporarily restore a raw `ArrayBuffer` on the wire (one field is enough) and log, in the
webview, `Object.prototype.toString.call(chunk.shas)` and the first key of the received object,
under `bun run test:e2e:vscode`. Three outcomes and what each means:

- **It arrives as a real `ArrayBuffer`** → the gate passes now; W5 declares `"native"`,
  `toWireSafe` was a workaround for something since fixed or for a condition not reproduced, and
  the per-page tax is `cloneMsNoTransfer` (~1.4 ms). Record what changed.
- **It arrives as `{$$vscode_array_buffer_reference$$: true, index: 0}`** → the gate passes but the
  webview-side reconstruction is not reaching our listener, which is a different (and probably
  fixable) bug in how `webview/main.ts` reads `event.data`. Report it; do not paper over it.
- **It arrives as `{}`** → the gate is false. Record the actual `engines.vscode` the extension
  host sees and the running VS Code version, then W5 declares `"base64"` and the phase proceeds
  as planned.

**Done when:** the outcome is recorded in Findings with the observed shape and the VS Code
version, and W5's declaration follows from it rather than from this plan's guess.

## W2 — `packages/ipc/src/codec.ts`

The file today is 60 lines: `encode` (identity + transfer walk), `decode` (identity),
`dedupeTransferList`, `collectTransferables`. It becomes the codec D34 says it should be, keeping
every existing export's behaviour under `"native"`.

- `BufferEncoding`, the `EncodedBuffer` tag, `encode(message, encoding)`, `decode(payload, encoding)`.
- base64 via `Uint8Array.prototype.toBase64` / `Uint8Array.fromBase64` when present, with a
  chunked `btoa`/`String.fromCharCode` fallback — measured at 0.49 ms for 420 KB with the

  rule is satisfied by the platform itself here; no dependency is added.
- `dedupeTransferList` keeps its assertion and is called only on the `"native"` path (under

- The traversal handles `ArrayBuffer`, `ArrayBuffer.isView`, `Array` and plain objects — the same

**Done when:** `encode(m, "native")` is byte-for-byte what `encode(m)` returns today, transfer
list included; `decode(encode(m, "base64").payload, "base64")` reproduces every buffer exactly;

## Judgment calls this plan made

1. **Recommending against the phase's own stated technology.** The P15 row asks for FlatBuffers;
   the measurements say FlatBuffers cannot deliver what the row wants on the host that ships.
   `AGENTS.md`'s measurement rule exists for exactly this — a real, concrete question where a
   measurement changes the decision. Presenting the design and then the verdict, rather than
   quietly shipping the design, is what makes the recommendation reviewable. Open question 1
   hands the override back to the orchestrating session.
2. **base64, not a denser custom encoding.** latin1 binary strings are 1 byte/char and look
   denser, but JSON escaping of control bytes inflates them to 653,020 bytes — *larger* than
   base64's 560,048 — at 4x the stringify cost. Measured, then decided.
3. **The encoding is per transport, not per contract key.** A per-key allowlist ("encode
   `graph.stream`, pass everything else through") would be a second place to forget something the
   next time a phase puts a buffer on the wire. `codec.ts` already walks the whole message;
   D36 makes that walk the rule.
4. **`CONTRACT_VERSION` bumps, even though both halves always ship together.** The bump is
   defensive and cheap, and the case it guards is real: VS Code recreates the webview on every
   hide/reveal (§2.1, no `retainContextWhenHidden`), so a stale bundle meeting a fresh extension
   host is not hypothetical. Decoding base64 as a number array would produce a plausible, wrong
   graph rather than an error, which is the exact half-working failure §3.5 forbids.
5. **Eleven work items, not twenty-two.** Sized to the work rather than to P6's shape. Said
   plainly in "Ordering" rather than padded.
6. **`appendPacked`'s 46 ms is named and left alone.** It is the largest single cost on this path
   and it is a store question, not a wire question. Fixing it inside a wire-format phase would be
   scope creep into `packages/core`'s hottest code with no row asking for it; naming it with a
   number is the useful thing this phase can do about it.
7. **No `.fbs` file is added "just in case".** `AGENTS.md`: scope left out is left out entirely,
   not half-implemented. If the override comes, the appendix is the plan.

## Open questions for the orchestrating session

Raised here rather than resolved by editing the spec or by proceeding on an assumption.

1. **This plan recommends against FlatBuffers, which is what the P15 row asks for.** The evidence
   is in "Recommendation": on the only host, the transferable/zero-copy win is unavailable by
   construction; FlatBuffers ties base64-over-the-existing-format on the graph stream and loses by
   6 ms on the largest diff; and it costs a native toolchain with no working npm distribution.
   Three ways forward, and this is the orchestrating session's call, not the planner's:
   **(a) accept D33** and ship W1–W11 as written; **(b) override D33** and ship the appendix's
   F1–F8 instead (or after); **(c) narrow** — ship W1–W11 now and re-open FlatBuffers if and when
   a host arrives whose transport carries binary natively. This plan recommends (a), with (c) as
   the standing disposition.
2. **§10's P15 row says "deliberately last, after every other phase including P14", and P15 is
   being worked now, ahead of P7.** The row has deliberately not been edited — that sentence
   describes v1's intended production order and the instruction to work it early does not rewrite
   it. Should the row gain a short note recording that it was designed and implemented out of
   sequence (and, if D33 stands, that its content changed)? That is a spec edit and belongs to the
   orchestrating session.
3. **If D33 stands, does the P15 row's title still fit?** "IPC wire format migration" remains
   accurate — the wire format does change, from number-arrays to base64-tagged buffers — but the
   row's *description* names FlatBuffers explicitly and its exit criteria are "to be defined at
   design time". W10 proposes replacing the description and exit criteria with what this plan
   actually ships; confirm before the implementer rewrites the row.
4. **§3.5 currently states, of the only host, "`webview.postMessage` (structured clone,
   `ArrayBuffer` transferable)".** Both halves of that parenthesis are false in production:
   `webview.postMessage` exposes no transfer list, and raw buffers did not survive it (P4c). The
   correction is W10's, but its *content* depends on W1's outcome, so the implementer must write
   it after the probe, not before. Flagged so the sequencing is deliberate.
5. **Is a compression step wanted on top?** 562 KB per page of base64 could be deflated further,
   and `CompressionStream` is a platform builtin. Not measured, not in the row, and not in this
   plan's scope — but it is the obvious next question and it should be answered deliberately
   rather than left implicit.
6. **`appendPacked` at 46 ms/page is the real remaining cost on the graph path** (~85% of the
   post-W5 round trip). It belongs to no phase. Should it get one?

## Appendix — the FlatBuffers work program, if D33 is overridden

Numbered `F1–F8` rather than `W…` so that nothing in this plan reads as though it is scheduled.
This is what the orchestrating session would be approving under open question 1(b). It **replaces**
W2–W8; W1, W9, W10 and W11 stand either way, and the base64 codec is still needed underneath
(F6), because a FlatBuffer is bytes and bytes do not cross this host's boundary.

| # | Item | Notes |
|---|---|---|
| F1 | Obtain a supportable `flatc` | Neither npm route works (see "Schema definition and codegen"). Realistically: vendor Google's release binaries per platform, or add a build-from-source step. Decide *and* record the license and provenance of whatever is vendored, per `AGENTS.md`'s open-source rule. |
| F2 | `packages/ipc/schema/graph.fbs` | The `PackedCommitChunk` table: seven `[ubyte]` vectors, `[string] dictionary`, the scalars, and `decorations` (a nested table, or a JSON string — the decorations array is the one field with no natural FlatBuffers shape). |
| F3 | `scripts/gen-schema.ts` + `check:schema` | Modelled exactly on `scripts/gen-settings.ts`: generate into `packages/ipc/src/generated/`, commit the output, and add `--check` to `bun run check` so drift fails. This is the part that works well; F1 is the part that does not. |
| F4 | `codec.ts` learns a third encoding | `"flatbuffers"` alongside `"native"`/`"base64"`, applied to `graph.stream` chunks only (per "Scope"), with everything else unchanged — a partial conversion, because a full one is not defensible on the measurements. |
| F5 | Adapters + round-trip tests replacing `wireConformance`'s mechanism | Generated accessors are classes, not interfaces, so the compile-time assignability check stops covering `PackedCommitChunk`. Hand-written `toWire`/`fromWire` adapters plus exhaustive round-trip tests are the replacement, and they are strictly weaker. |
| F6 | The base64 layer anyway | A FlatBuffer is a `Uint8Array`; on this host it must still be encoded. F6 is W2 by another name. |
| F7 | `CONTRACT_VERSION` → 6, and the versioning rule written down | Per "Versioning" above: `CONTRACT_VERSION` stays the sole authority; FlatBuffers' append-only/never-renumber rules are enforced as source hygiene, with `check:schema` the enforcement point. |
| F8 | Re-measure | `hostBoundaryMs` under FlatBuffers vs base64, on macOS. This plan's probes predict a difference of well under 1 ms per page; if the real number is materially better, that is a finding worth having and it belongs in this plan's Findings either way. |

**Honest expectation, stated up front:** F1–F8 is roughly three to five times the work of W1–W11,
adds a native binary to a toolchain that has none, weakens the `ipc`/`core` drift check, and — on
every payload measured while writing this plan — lands within ~1 ms per page of what W1–W11
achieves without any of it.

## Findings

_Recorded during implementation. V1–V5 outcomes, and any decision made at the keyboard that this
plan did not anticipate — later phases read this section as part of the context they inherit._

### V1 — the VS Code buffer gate

**The gate is false. `toWireSafe` stays necessary and W5 declares `"base64"`.**

Probed exactly as prescribed: `packages/host-vscode/src/transport.ts`'s `post()` was
temporarily changed to `webview.postMessage(message)` (no `toWireSafe`), and
`src/webview/main.ts`'s `onMessage` listener temporarily logged
`Object.prototype.toString.call(chunk.shas)`, `shas instanceof ArrayBuffer`, the first key of
the received value, and its `byteLength`, for the first `graph.stream` chunk — captured via a
temporary `page.on("console", …)` in `tests/e2e/vscode/panel.spec.ts`, all three edits reverted
immediately after the run (`git diff` was empty before continuing to W2).

Downloaded and ran against a **real VS Code 1.136.1** (linux-x64 stable, fetched directly —
`@vscode/test-electron`'s own bundled downloader could not complete a request against
`update.code.visualstudio.com` from this sandbox's network policy, ECONNRESET mid-TLS-handshake
on every attempt including through an explicit `https-proxy-agent`, while a plain `curl` through
the same proxy succeeded immediately over HTTP/2 — a Bun HTTP-client-specific incompatibility
with this container's proxy relay, not a policy block; `curl`ing the archive directly into
`.vscode-test/vscode-linux-x64-1.136.1/` with its `is-complete` marker let the library's own
existing-local-install fallback path pick it up with no further network calls). `1.136.1`
satisfies `packages/host-vscode/package.json`'s declared `engines.vscode: "^1.134.0"` (it is in
fact newer), so `shouldSerializeBuffersForPostMessage`'s `>= 1.57` check should, per its own
source quoted above, gate **true**.

Observed on the wire regardless:

```
[W1 PROBE] toString=[object Object] isArrayBuffer=false isUint8Array=false firstKey=undefined byteLength=undefined
```

`Object.keys(shas)[0]` is `undefined` — no own enumerable keys at all — which is exactly the
shape of `{}`. This is precisely the plan's third bullet: **"It arrives as `{}` → the gate is
false."** P4c's finding still holds, unchanged, on this newer VS Code build and this newer
`engines.vscode` floor: a bare `ArrayBuffer` sent through this extension's `WebviewView` does not
survive VS Code's own `postMessage` serialization, whatever `shouldSerializeBuffersForPostMessage`
computes internally. Nobody outside this sandbox has root-caused which of the plan's two
candidate explanations (the manifest read differently under
`--extensionDevelopmentPath`, or a `WebviewView`-specific gap in VS Code's own gated path) is
correct, and this plan does not attempt to — the fact that matters for W5 is the observed shape,
not the reason.

**Consequence for W5:** the VS Code transport declares `"base64"`, not `"native"`. `toWireSafe`
is still deleted (D34: the transform moves into `packages/ipc/src/codec.ts`, generalized and
tested, rather than staying a hand-rolled one-off in `host-vscode`), but the per-page cost stays
in the ~6 ms/560 KB range this plan measured for base64, not the ~1.4 ms/420 KB `"native"` would
have bought.

### V2 — the numbers on macOS

**Not re-measured — no macOS machine is reachable from this sandbox.** This implementation ran
entirely inside a Linux container (the same constraint P4c's own Findings record for the VS Code
e2e tier); D27 makes macOS the authoritative platform, so the committed `hostBoundaryMs`/
`hostWireBytes` baselines (4.74 ms / 563,748 B, `tests/perf/streamRoundTrip.budget.json`) are a
Linux/Bun number, not the platform-of-record's own. Recorded as a gap for whoever next runs this
suite on macOS to close, not silently presented as though it were the authoritative figure —
consistent with how V4's real-webview numbers below are also this container's Chromium/Electron
build, not a macOS one.

### V3 — `Uint8Array.prototype.toBase64` in the real webview

**Native, not the fallback — measured directly, not assumed.** Probed the same way as W1: a
temporary `console.log` of `typeof Uint8Array.prototype.toBase64` / `typeof
Uint8Array.fromBase64` added to `packages/host-vscode/src/webview/main.ts`'s module scope, a
temporary `page.on("console", …)` listener added to `panel.spec.ts`, one real run against VS
Code 1.136.1, both edits reverted immediately after (`git diff` empty before continuing).
Observed:

```
[W11 V3 PROBE] toBase64=function fromBase64=function
```

Both are real functions in this build's actual Chromium/V8, so `hasNativeToBase64`/
`hasNativeFromBase64` (`codec.ts`) resolve `true` in production and the fast path this plan
measured at ~0.49 ms for 420 KB is what actually runs — not the `btoa`/`atob`-chunked fallback,
whose cost the plan flagged as unmeasured and potentially load-bearing if it were the one
shipping. It is not.

### V4 — the first-page budget, at the real boundary

**Measured directly in the real webview; does not move a first-paint-scale budget.** Probed the
same way as V3: a temporary read of `performance.getEntriesByName("kira:first-paint"|
"kira:layout-complete")` (the same marks `tests/perf/graphUi.ts` reads against the harness)
added right after `connection-state` in `panel.spec.ts`, one real run against a 10-commit
repository through VS Code 1.136.1, reverted immediately after. Observed:

```
[W11 V4 PROBE] {"firstPaint":130.9,"layoutComplete":282.7}
```

Both comfortably inside §5.1's 300 ms/400 ms budgets, on this container's Electron/Chromium
build. `tests/perf/budgets.json`'s own committed numbers (`kira:first-paint` 469 ms,
`kira:page-parsed` 356 ms) are unmoved by this phase and could not have been: they are measured
against `apps/harness`'s mock bridge, which was never on the `toWireSafe`/base64 path at all — it
hands `PackedCommitChunk` across via `structuredClone`, `mockBridge.ts` declaring `"native"`
(W6). The real host's own boundary cost is `hostBoundaryMs`, and it is small relative to a
first-paint-scale number by construction: `RepoService.CHUNK_ROWS` (500) means the very first
chunk to arrive pays roughly a tenth of the measured 4.74 ms/page figure — under half a
millisecond — against a first paint measured in the hundreds of milliseconds. The pre-W5
`toWireSafe` path would have cost more (this plan's own historical ~47 ms/page implies a
comparable ~4.7 ms first-chunk share), but that is still an order of magnitude below the noise
floor of a paint measured at 130 ms. **The saving this phase delivers is cumulative across a full
history load (every subsequent page), not visible in first paint** — consistent with why V5,
below, and not this item, is what should get a phase of its own next.

### V5 — `appendPacked`, re-confirmed and handed on

**Re-confirmed: ~40 ms/page on this machine, the largest single cost left on this path.**
`tests/perf/streamRoundTrip.budget.json`'s freshly committed baseline (W8) records `appendMs` at
39.91 ms for one 5,000-row page — in the same range as the plan's own cited ~46 ms figure, and
now roughly **8x** `hostBoundaryMs` (4.74 ms) for the same page: the wire hop this phase fixed is
no longer the dominant cost, the store-side append is. Explicitly *not* fixed here, per this
plan's own scope boundary and judgment call 6 — `appendPacked` is `packages/core`'s hottest code
and a store question, not a wire-format one. Whichever phase picks it up next inherits this
number rather than a suspicion.

### Judgment calls made at the keyboard (beyond the plan's own pre-recorded list above)

- **W8's metric scope.** The plan's own wording ("`encode` → `JSON.stringify` → `JSON.parse` →
  `decode`") was read literally rather than folding `packSlice`/`appendPacked` into the same timed
  section — both already have their own gated metrics (`packMs`, `appendMs`), and folding them in
  would have double-counted V5's own cost into a number meant to isolate exactly what W1's finding
  is about.
- **W9's row-0 assertion had to scroll back to the top.** `expectAllRowsLoaded` (pre-existing)
  scrolls the grid's viewport to its very bottom to prove the last row arrived; on a repo as
  small as `linear(10)`, that scroll evicts row 0 from the DOM under SlickGrid's own
  virtualization — the same virtualization `expectAllRowsLoaded`'s own doc comment already names
  as the reason it checks the *last* row rather than a `.slick-row` count. Scrolling back to the
  top before asserting row 0's content is the fix; not a defect in the virtualization itself.
- **A pre-existing, unrelated flake surfaced during W9 verification**: the suite's second test
  (untouched by this phase) once timed out under this container's load running three heavy VS
  Code Electron launches back to back in serial; re-run alone and re-run as part of the full
  serial suite both passed immediately after. Consistent with the `cloneMs` flakiness already
  noted at W8 — container-load noise, not a regression from any W-item.
