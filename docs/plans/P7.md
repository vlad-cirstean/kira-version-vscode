# P7 — Branch review

Plan for the P7 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**Goal:** the phase where the app grows a *second surface*. Everything through P6 lived in one
webview, in one view container, mounting one root component, against one per-repo history walk.
P7 adds a sidebar view with its own activity-bar container, a second `WebviewViewProvider`, a
second mount root over the same `packages/ui` bundle, and a second — deliberately ephemeral —
walk over the same streaming machinery, scoped to `<base>..<branch>` instead of `--all`.

Concretely the row asks for: the sidebar webview view and its container (§2.1); **Review branch
changes** on the branch-picker and ref-badge context menus; the base resolver (upstream →
detected default branch → ask, never a silent guess) with the header base picker and
`review.resolveBase` (§3.5); the `<base>..<branch>` range-scoped walk over P2's existing
streaming machinery; and a commit list whose rows expand into P5's file tree and whose files open
P5's unified diff, "Open in editor" and line-mapped "Go to file" (D14a) unchanged (§6.8).

Three things make this phase harder than "reuse P5's components in a narrow column" suggests, and
each is settled below before any work item refers to it. First, **the streaming machinery is
per-repo singleton state**, not a function you can call with different arguments: one
`LogSession`, one `CommitStore`, one `dictionaryMarks` map, one `nextSeq`, one `staleReason`, all
fields of one `RepoSession` — so a range walk that reuses them corrupts the graph's cache, and a
range walk that *doesn't* reuse them needs a second session object with a defined lifetime.
Second, **base resolution has four outcomes, not one**, and three of them (ask, fully-merged,
unrelated) must be distinguishable from each other and from "the walk hasn't run yet" before a
single row is painted — which decides where the check lives. Third, **P5's components are
reusable, but the surface they mount into is not**: `App.vue` owns the repo, the selection, the
grid, the live region and the persisted view state, and none of that is what the review view
needs.

## The hard parts, settled before the work items

### The streaming machinery is a singleton, and that is the whole design problem

§3.5 says the range walk is *"the existing streaming walker with a different argv rather than a
second pipeline"*. That is true of the **walker** and false of the **session**. Read what a walk
actually touches (`repoService.ts` L477–517, L611–669):

```
RepoSession {
  logSession           one paused `git log`, one `--skip` cursor, one ref snapshot, one remaining cache
  store                one CommitStore — rows 0..N of THIS walk
  dictionaryMarks      row -> interner size, for THIS walk's string dictionary
  nextSeq              chunk sequence for THIS walk
  lastRemaining        THIS walk's remaining count
  staleReason          "re-walk from scratch on the next stream"
}
```

Every one of those is per-walk state that happens to live on a per-repo object because, until
now, a repo had exactly one walk. Give `graph.stream` a `range` parameter and reuse the same
fields and the panel's history is destroyed the moment a review opens: `store.clear()`, a
`dictionaryMarks` reset, a `logSession` swap, and the next panel chunk packed against a
dictionary base its interner has never seen (which `CommitStore.appendPacked` asserts on —
loudly, which is the only mercy in that scenario).

So: **the wire shape is shared, the session is not.** `RepoSession` gains one nullable
`reviewWalk` slot holding its own `LogSession`, `CommitStore`, `dictionaryMarks`, `nextSeq`,
`lastRemaining` and the `{base, branch}` it was opened for. `streamGraph`/`loadMore`/`status`
take an optional `range` and select which of the two walks to serve. Nothing about
`packSlice`/`appendPacked`/`CHUNK_ROWS`/the chunk envelope changes, which is exactly what §3.5's
sentence is actually promising.

One slot, not a map: §6.8 is explicit that *"the view holds exactly one review session. Reviewing
another branch replaces its contents rather than opening a second view."* A `Map` keyed by range
would model a thing the UI cannot produce and would need an eviction policy nobody asked for.
Opening a walk for a different `{base, branch}` disposes the previous one in place.

### The review walk never resumes, and that is what makes §5.4's exclusion mechanical

The panel's `resumeThroughRow` exists to answer *"replay the rows you still have, don't re-run
git"* — §5.4's whole contract. §6.8 excludes the review view from that contract in three
sentences: it *"persists no view state through `setState`, is not rehydrated from the host cache
on reveal, and takes no part in §5.4's 'the same rows repaint without re-running git'"*.

Rather than write that as a rule someone must remember, P7 makes it structural at three points,
each independently sufficient:

1. **The host ignores `resumeThroughRow` when `range` is present.** A ranged `streamGraph` always
   emits from row 0 with `source: "git"`. There is no cache branch to take.
2. **The webview persists nothing.** `mount()` requires a `ViewStateStore`; the review entry
   passes a `NullViewStateStore` (`read()` → `null`, `write()` → discard), exported from
   `packages/ui`. `acquireVsCodeApi().setState` is never called from the review view at all.
3. **The provider drops the walk on dispose.** `reviewView.ts`'s `onDidDispose` calls
   `service.endReview(repoId)`, which disposes the `reviewWalk` slot's `LogSession` and drops its
   store. VS Code destroys a hidden webview view (§2.1); the session is gone with it.

Reopening therefore re-resolves the base and re-walks, by construction rather than by policy.

**The one trap here, stated so it is not discovered:** `panelView.ts` calls
`service.setUiVisible(webviewView.visible)` on visibility change, and `setUiVisible(false)` pauses
**every** session's watcher and arms the 5-minute eviction timer that resets the graph's store
(`repoService.ts` L700–710, L1536–1541). `reviewView.ts` must **not** call it. Hiding the sidebar
would otherwise pause the panel's watcher and start a countdown to discarding the graph's loaded
pages — a §5.4 violation caused by a feature that has nothing to do with §5.4. Asserted in W20.

### Base resolution has four outcomes, and three of them must be known before the first row

§6.8 names the resolution order (upstream naming a *different* branch → detected default branch →
ask) and, separately, two degenerate states (fully merged → "nothing to review" naming both refs;
no merge base → say so, *"detected with a `git merge-base` check before the walk rather than
discovered by the user halfway down a very long list"*).

Read together, the review view has four mutually exclusive states before it can paint a list, and
"the walk produced no chunks" distinguishes exactly none of them from a walk that failed or has
not started. So all four are decided **host-side, in one request**, before the stream is opened:

| State | How it is determined | What the view shows |
|---|---|---|
| `ask` | no base resolved at all (step 3) | base picker focused, empty list, no walk opened |
| `unrelated` | `git merge-base <base> <branch>` exits non-zero with no output | "`<branch>` and `<base>` share no common history" — no walk opened |
| `empty` | `git rev-list --count <base>..<branch>` is `0` | "nothing to review — `<branch>` adds no commits to `<base>`" — no walk opened |
| `ready` | count > 0 | open the stream; `commitCount` seeds the header before a single chunk lands |

`rev-list --count <base>..<branch>` is one cheap spawn and it is not extra work: `LogSession`
needs a total for `remaining()` anyway (`#countTotal`, L243), so the ranged session takes the
already-computed count instead of running its own. Two spawns total for a resolution
(`merge-base`, `rev-list --count`), plus at most one more for `origin/HEAD` — against a
`for-each-ref` snapshot the service already caches.

This is why the override is a **second `review.resolveBase` call with an explicit base**, not a
client-side re-walk against a candidate the first response already handed over: `merge-base` and
the range count must be recomputed for whatever the user picked, and a base the user chose can be
just as unrelated or just as fully-merged as one we detected. Doing the checks in one place, for
both paths, is what stops "override" from being a route around the guarantees the default path
gives. §6.8's "re-runs the comparison in place, without reopening the view" is satisfied — the
view never unmounts; it re-requests, re-renders its header, and re-opens its stream.

### The resolution rule, exactly

Step 1's qualification carries the weight and is easy to get subtly wrong. `RefRow.upstream` is a
**full refname** (`parse/refs.ts` L119; `core/src/model/ref.ts` L36: *"Full refname of the
upstream"*), e.g. `refs/remotes/origin/develop`. The rule:

```
upstreamShort = upstream with "refs/remotes/<remote>/" or "refs/heads/" stripped
if upstreamShort !== branch.shortName   ->  base = upstream's short form, reason "upstream"
else                                    ->  fall through to step 2
```

- `feature-x` tracking `refs/remotes/origin/feature-x` → `feature-x` === `feature-x` → **fall
  through**. This is the ordinary case §6.8 spends a paragraph on: comparing against it would show
  only the commits not yet pushed.
- `feature-x` tracking `refs/remotes/origin/develop` → `develop` ≠ `feature-x` → **honour it**.
- `feature-x` tracking `refs/heads/main` (a local upstream — `branch.<n>.remote = .`) →
  `main` ≠ `feature-x` → **honour it**. Legal, rare, and the rule handles it without a special
  case, which is why the comparison strips both prefixes rather than only the remote one.
- A branch with `track: "gone"` still has an `upstream` string. The rule is about what the branch
  *declares it forked from*, not about whether that ref currently resolves — but a base that does
  not exist cannot be walked, so a resolved base is verified with the same `merge-base` call that
  answers `unrelated`, and a base that resolves to nothing falls through to step 2 with the
  reason recorded. (V6.)

Step 2 is `git symbolic-ref --short refs/remotes/origin/HEAD`, then the first member of
`kiraVersion.review.baseCandidates` that exists as a local or remote-tracking ref — checked
against the `for-each-ref` snapshot the service already has, not with a spawn per candidate.

Step 2's remote name is `origin`, literally, per §6.8 and §4.4. Not "the first remote", not "the
branch's own remote": §6.8 says `origin/HEAD` and §4.4 spells the command out. A repository whose
only remote is `upstream` falls through to `baseCandidates`, which is the honest outcome and one
the ask-state covers if it fails too.

### The reuse boundary with P5 — three components unchanged, one degradation, one seam

Read against the actual code, not the row's word "unchanged":

**`DiffView.vue` — unchanged, and D14a genuinely works here.** `goToFile()` computes
`rev = side === "old" ? diff.baseSha : diff.sha` (L166) — both object ids from
`commit.fileDiff`'s own result, neither derived from HEAD or the working tree. The host's
`editor.goToFile` handler decides live-file vs. virtual-blob from `pathExistsInCheckout` alone
(`repoService.ts` L895). Reviewing a branch that is not checked out therefore lands in the
virtual blob at the mapped line with **zero changes**, which is precisely the case §6.8 says
"Go to file" is worth more here than anywhere else. No new prop, no new param, no new capability.

**`DetailState` / `DetailActions` — unchanged.** `DetailState` is keyed on a sha and takes its
repo id through `setRepoId`. One instance per *expanded row* (see below), constructed with the
review view's own `BridgeClient`. `createDetailActions` takes a `repoId: () => string | undefined`
thunk and a `DetailState`; nothing in it knows about `App.vue`.

**`FileTree.vue` — unchanged, with one honest degradation.** Its only non-`FileChange` input is
`store: CommitStore`, used solely to label the merge-parent selector with each parent's subject
(`parentOptions`, L249–259) via `store.rowOfSha(sha)`. The review view passes **its own** range
walk's `CommitStore`. A merge inside `<base>..<branch>` will routinely have a parent *outside* the
range — the base side of the merge — for which `rowOfSha` returns `-1` and the label falls back to
`Parent 2 · a1b2c3d` without a subject. That path already exists and is already correct
(`row !== -1 ? … : undefined`); it is a *less informative* label, not a broken one. This plan does
**not** add a subject-lookup round trip to fix it: §6.8 requires the merge parent selector to be
present and to work, which it is and does, and a `commit.detail` per parent purely to enrich a
`<select>` option is work no requirement asks for. Recorded here so a reviewer does not read the
missing subject as a bug. (Exit criteria checks the selector functions; V5 confirms the fallback
renders.)

**`DetailPane.vue` — reused, but not as the review row's body.** It renders message → files →
details for one commit, with the diff taking over the whole pane. A review row that expands into
*that* would put a full `CommitMeta` message block and a details block inside every expanded row,
which §6.8's step 2 does not ask for (*"expands … into that commit's file tree"*). So
`ReviewCommitRow.vue` composes `FileTree.vue` directly over its own `DetailState`, and the diff
opens as the full-height overlay §6.8 step 3 specifies — reusing `DiffView.vue` and P5's own
`.kv-detail-drawer--diff` overlay treatment from `App.vue`'s narrow breakpoint, which is what
§6.8 means by *"the treatment §6.4 already defines for the panel's narrow breakpoint, reused
rather than reinvented"*. `DetailPane.vue` itself is not mounted in the sidebar; its *parts* are.
This is the one place the row's word "unchanged" needs qualifying, and it qualifies in our favour:
nothing is modified, one composite is simply not used.

**The one genuine seam change: `refBadges.ts` must say which ref a badge is.** §6.8 requires that
right-clicking a *branch badge* in the message column reviews that branch — *"the one place in the
app where a right-click on a row means something other than 'act on this commit'"*. Today
`CommitGrid.vue`'s `handleContextMenu` (L236) resolves the cell and emits a commit-scoped menu
regardless of what was under the pointer, and `buildBadgeElement` (L128) writes `className`,
`title`, an icon and a label — nothing that identifies the ref. W14 adds `data-ref-kind` /
`data-ref-name` to the badge element and a `closest("[data-ref-kind]")` hit-test in
`handleContextMenu`, which is a five-line change in each file and the smallest thing that makes
the requirement possible. It is a seam, not a redesign, and it is named here rather than
discovered.

### One bundle, two roots — and why the review view is not `App.vue` in a narrow column

§6.8 settles this: *"The review view mounts the same `packages/ui` bundle with a different root
component, selected from the initial state the host injects (`html.ts`, §3.1), so
`vite.config.ts`'s one-build-one-entry rule still holds."* `main.ts`'s `MountOptions` gains
`view: "graph" | "review"` and mounts `AppRoot` or `ReviewViewRoot` accordingly.

It cannot be `App.vue` at a narrow width because `App.vue` owns `GraphViewState` (and with it the
lane-layout worker), `SelectionState`, the SlickGrid instance, the toolbar, the repo picker, the
persisted `viewState`, the conflict banner and the undo slot — every one of which is either wrong
for the review view or actively harmful in it (a layout worker computing lanes for a list that
draws none; a `setState` write from a view that must not persist). §6.3's breakpoints are about
the panel's own regions; the sidebar is not a fourth region of the panel, which is the whole of
D29.

**The review view therefore does not run the layout worker.** `ReviewSessionState` (W10) consumes
`graph.stream` chunks into a `CommitStore` and stops there — no `LayoutClient`, no `LayoutStore`,
no `layoutInput`. That is a real divergence from `GraphViewState`, and it is why W10 extracts the
chunk-application logic both need (`appendPacked`, reset-on-`from:0`, the counters, the
corrupt-chunk re-open) into one small `packedStream.ts` module rather than letting a second,
subtly-different copy exist. Two callers is enough to justify one shared implementation, per
`AGENTS.md`'s "prefer a library over a hand-rolled equivalent" applied at module scope; the
alternative (duplicate ~40 lines, leave P4's hot path untouched) is open question 8.

### The review list is a tree, not a grid

§5.3's virtualized-grid rule exists because the panel renders 100k rows. The review list renders a
branch's own commits — §6.8: *"tens or hundreds, not the 100k the graph is built for"* — and every
row **expands**, which a fixed-row-height virtualized grid does not do. VS Code's own comparable
surfaces (Source Control, Search Results) are non-virtualized trees at this scale.

So `ReviewView.vue` renders plain rows, not SlickGrid (D42). The bound is §5.1.1's page: the first
page is `kiraVersion.graph.pageSize` commits and everything past it is behind an explicit **Load
more**, exactly as §6.8 requires. A user who presses Load more on a 40,000-commit "branch" gets
5,000 plain rows, which is a real cost — accepted, because it takes a deliberate action on a
degenerate input, and because the alternative is virtualizing a tree of expandable rows to serve a
case §6.8 itself calls "the rare enormous range". Open question 3 offers the orchestrating session
the other lever (a smaller first page for ranged walks) if it disagrees.

Row content is §6.8 step 1's list — subject, short sha, author, relative date — read directly off
the `CommitStore` and formatted with `dateFormat.ts`'s `formatRelativeDate`, the same pure
function `columns.ts` uses. No graph column: *"a range of one branch has nothing interesting to
draw."*

### How the view is told which branch to review

Three entry points (§6.8), one target, and a webview that may or may not currently exist:

```
panel webview: BranchPicker / ref badge menu -> "Review branch changes"
      |
      | review.open { repoId, branch }                       (request, panel -> host)
      v
host: reveal `kiraVersion.review` (executeCommand `<viewId>.focus`), remember the pending target
      |
      +-- view was hidden -> resolveWebviewView runs -> html.ts injects {view:"review", repoId, branch}
      |
      +-- view already visible -> server.emit("review.target", {repoId, branch})   (event, host -> review)
      v
review webview: repo.open(repoId) -> review.resolveBase -> graph.stream with a range
```

Both arms are needed and neither is redundant: `resolveWebviewView` runs on reveal-from-hidden and
is the only chance to seed a cold webview; it does *not* run when the view is already visible, and
§6.8 requires reviewing a second branch to replace the contents of the open view.

`kiraVersion.reviewBranch` (the palette) reveals the view with **no branch**, and the view renders
its own "pick a branch to review" state — the branch picker focused over an empty list, the exact
same vocabulary §6.8's step-3 ask-state already establishes for a missing base. That keeps the
prompt in the webview, where the harness can drive it and Playwright can screenshot it, and avoids
building a host-side quick-pick surface (which is the thing P6's own open question 4 declined to
build for its eleven operations). §6.8 says "prompting for the branch" without saying where; open
question 2 puts the alternative to the orchestrating session.

The branch list the picker offers comes from `refs.list`, which the review view's own
`createRepoHandlers` serves from `RepoService.refs`'s per-session cache — no second query shape,
and `refListModel.ts`'s fold is reused for sorting/filtering/capping.

## The contract entries P7 adds

`CONTRACT_VERSION` 6 → **7**, which `wrapVersioned`/`validate.ts` enforce: host, harness mock and
UI move in one commit or the app refuses to start. `REQUEST_KEYS` gains two keys, `EVENT_KEYS`
gains one. Wire types are **structural copies** of `packages/core`'s own per §3.1's B3 rule, kept
honest by extending `tests/unit/ipc/wireConformance.test.ts`.

```ts
// ---- branch review ------------------------------------------------------------------------

/** A `<base>..<branch>` two-dot range (§6.8/D30). Both are short ref names as the UI shows them
 *  (`main`, `origin/develop`, `feature-x`) — never full refnames, never object ids: the range is
 *  a question about two *refs*, and a sha in `base` would make "how it was resolved" unanswerable. */
export interface CommitRange {
  readonly base: string;
  readonly branch: string;
}

export type BaseResolutionReason =
  /** §6.8 step 1: the branch's upstream, and it names a *different* branch. */
  | "upstream"
  /** §6.8 step 2: `origin/HEAD`, or the first existing `review.baseCandidates` member. */
  | "defaultBranch"
  /** The user picked it from the header picker — resolution was skipped entirely. */
  | "override"
  /** §6.8 step 3: nothing detected. `base` is null and no walk is opened. */
  | "none";

/** What a `<base>..<branch>` comparison *is*, decided before the first row is painted — see
 *  "Base resolution has four outcomes" above for why this cannot be inferred from an empty walk. */
export type ReviewRangeState =
  | { readonly kind: "ready"; readonly commitCount: number }
  /** `rev-list --count` is 0: fully merged, or the branch IS the base. §6.8's "nothing to
   *  review — `<branch>` adds no commits to `<base>`", which the UI renders naming both refs. */
  | { readonly kind: "empty" }
  /** `merge-base` found nothing: `<base>..<branch>` would list the branch's entire history as
   *  though it were all new (§6.8). */
  | { readonly kind: "unrelated" }
  /** No base at all. Only ever paired with `reason: "none"`. */
  | { readonly kind: "ask" };

/** One entry in the header picker's shortlist. The picker's *full* branch list comes from
 *  `refs.list`, which the review view already loads — this is only the handful worth ranking to
 *  the top, each with the reason it is offered. */
export interface BaseCandidate {
  readonly ref: string;
  readonly kind: RefKind;
  /** Never "override" — a candidate is a thing we detected, not a thing the user chose. */
  readonly reason: Exclude<BaseResolutionReason, "override" | "none">;
}

export interface BaseResolution {
  readonly branch: string;
  /** `null` iff `reason === "none"`. */
  readonly base: string | null;
  readonly reason: BaseResolutionReason;
  readonly range: ReviewRangeState;
  readonly candidates: readonly BaseCandidate[];
}
```

The two requests and the one event:

```ts
/**
 * §6.8/D30. Called once when the view targets a branch (no `base`), and again with an explicit
 * `base` each time the header picker overrides it — the `merge-base` and range-count checks must
 * run for a chosen base exactly as they do for a detected one, so both paths land here rather
 * than the override taking a shortcut through the candidate list the first call returned.
 */
"review.resolveBase": {
  params: { repoId: string; branch: string; base?: string };
  result: BaseResolution;
};

/**
 * §6.8's entry points, from the *panel* webview: reveal the sidebar view on this branch. The
 * host reveals the view and either seeds a cold resolve (`html.ts`'s bootstrap island) or pushes
 * `review.target` to an already-open one. Returns nothing — the panel does not wait on, and is
 * not told about, what the review view then finds.
 */
"review.open": {
  params: { repoId: string; branch: string };
  result: Record<string, never>;
};

// events:
/** Host -> the review webview only: "review this branch instead". Never emitted to the panel's
 *  own server — the two views hold separate `RpcServer`s over separate channels. */
"review.target": { repoId: string; branch: string };
```

And the three `graph.*` keys gain the same optional range:

```ts
"graph.status":   { params: { repoId: string; range?: CommitRange };  result: /* unchanged */ };
"graph.loadMore": { params: { repoId: string; pages?: number; range?: CommitRange };
                    result: /* unchanged */ };

"graph.stream": {
  params: {
    repoId: string;
    /** Ignored when `range` is present — a ranged walk has no cache to resume from (§5.4's
     *  exclusion, made structural). */
    resumeThroughRow?: number;
    /** Present ⇒ walk `<base>..<branch>` instead of the repo's `graph.scope` rev set, against
     *  this repo's own separate review walk. Chunk shape is byte-for-byte the same. */
    range?: CommitRange;
  };
  chunk: /* completely unchanged — same PackedCommitChunk, same envelope */;
};
```

**No change to the chunk.** A chunk carries `repoId` and no walk discriminator, and needs none:
the panel's stream and the review's stream live in *different webviews*, on different transports,
with different `RpcServer`s. Within the review webview exactly one stream is ever open. Adding a
discriminator would be modelling a collision the architecture makes impossible.

**`graph.refresh` deliberately gains no `range`.** §6.8 gives the review view no refresh
affordance; adding a parameter with no caller is the "present but not exercised" §9 warns about.
See open questions 5 and 6.

## W1 — `core/src/model/review.ts`

Pure types and one pure function. No I/O — `packages/core`'s standing rule.

`resolveBase(input): BaseResolutionCore` where `input` is
`{ branch, branches, remoteBranches, originHead, candidates }` — everything already available
from a `for-each-ref` snapshot plus the single `symbolic-ref` answer, and nothing else. Returns
`{ base: string | null, reason, candidates: BaseCandidate[] }`; the *range state* is not this
function's business (it needs two more spawns, W4's job).

The three rules, in order, each with its own named test:

1. `upstreamShortName(branch.upstream)` — strip `refs/remotes/<remote>/` then `refs/heads/` —
   compared to `branch.shortName`. Different ⇒ that upstream's short form, reason `"upstream"`.
   Same, or no upstream at all ⇒ fall through.
2. `originHead` (already short, from `symbolic-ref --short`) if it names an existing
   remote-tracking ref; else the first `candidates` member that exists as a local branch or a
   remote-tracking branch, checked against the snapshot. Reason `"defaultBranch"`.
3. Neither ⇒ `base: null`, reason `"none"`.

`candidates` (the shortlist) is built in the same pass and is *ordered*: the upstream (when it
exists at all, even when rule 1 rejected it — the user may well want to compare against
`origin/feature-x` deliberately), `originHead`, then each existing `baseCandidates` member, then
the current HEAD branch when it is none of those. De-duplicated by ref name, first reason wins.

**Unit-tested exhaustively** — this is the one piece of P7 that is a classification with a table,
which is exactly what `AGENTS.md`'s unit-test rule says earns its keep: the same-name fall-through,
the different-name honour, the local-upstream case, `origin/HEAD` present/absent, each
`baseCandidates` member present/absent, the empty-repository case (no branches at all), and the
candidate list's ordering and de-duplication.

## W2 — `git/src/parse/log.ts` and `queries.ts`

**`parse/log.ts`.** `revSetArgs(scope)` becomes one member of a two-member walk description. The
cleanest expression, given `logSessionArgs`/`logSessionSkipArgs`/`logArgs`/`countCommits` all
consume it today:

```ts
export type WalkSpec =
  | { readonly kind: "scope"; readonly scope: "all" | "head" }
  | { readonly kind: "range"; readonly base: string; readonly branch: string };

export function walkArgs(walk: WalkSpec): string[] {
  return walk.kind === "scope" ? revSetArgs(walk.scope) : [`${walk.base}..${walk.branch}`];
}
```

`logSessionArgs`/`logSessionSkipArgs` take a `WalkSpec` in place of a `scope`. `revSetArgs` stays
exported and unchanged — its `--all --glob=refs/stash` reasoning is `scope`-specific and has a
doc comment worth keeping. The format string, `--topo-order`, `-z` and `--decorate=full` are
identical for both: a range walk is *the same walk*, which is what makes the chunk shape identical.

Two-dot, never three (D30). `${base}..${branch}` is built here, once, so no call site can
accidentally write `...`.

**`queries.ts`** gains three functions beside the existing `countCommits`:

- `countRange(driver, base, branch)` — `rev-list --count <base>..<branch>`. Same shape as
  `countCommits`; the two share the count-parsing helper rather than duplicating it.
- `mergeBase(driver, a, b)` — `merge-base <a> <b>`. Returns the sha, or `null` on the
  no-common-ancestor exit (V4 pins which exit code that is, and confirms it is distinguishable
  from a bad-ref error, which must *throw*, not silently read as "unrelated").
- `detectDefaultBranch(driver)` — `symbolic-ref --short refs/remotes/origin/HEAD`, returning the
  short name or `undefined`. V1 pins the exit code and stderr when `origin/HEAD` is unset (the
  common case in a freshly-cloned-with-`--single-branch` or locally-initialised repo) so that
  "not set" is `undefined` and never an error the UI has to render.

All three go through `driver.read()`, so `--no-optional-locks` is added structurally and
`classifyGitError` handles failures like every other read.

## W3 — `git/src/logSession.ts`

`LogSessionOptions.scope` becomes `LogSessionOptions.walk: WalkSpec`. Three internals follow:

- **`#spawn`** — `logSessionArgs(this.#walk)`. Nothing else changes; the pause/backpressure
  mechanism, the `RecordSplitter`, `#pendingRecords` and the page boundary are walk-agnostic.
- **`#countTotal`** — `rev-list --count <base>..<branch>` for a range, `revSetArgs` for a scope.
  The ranged session additionally accepts a **pre-computed total** through its options, because
  `resolveReviewBase` has already run exactly this count to decide `ready`/`empty` and running it
  twice for the same range in the same second is a spawn nobody asked for.
- **`captureRefSnapshot` / the `--skip` staleness guard** — the guard exists (§5.1.1's spliced-page
  hazard) because a reclaimed session resumed with `--skip=<n>` against moved refs silently serves
  the wrong records. For a *range* walk only two refs can move the answer: `base` and `branch`. A
  full `for-each-ref` snapshot would still be *correct*, just needlessly broad — a tag created in
  another window would invalidate a range walk that cannot possibly be affected by it. So the
  ranged session captures only its two endpoints (`for-each-ref` restricted to them, or
  `rev-parse` on each) and compares those. V3 confirms the narrowed guard still catches the real
  hazard: force-push the branch mid-pause, resume, and assert `stale`.

Every existing `logSession.test.ts` case keeps running against `{kind:"scope"}`; the range cases
are added beside them (`tests/integration/logSession.test.ts`, which already builds real repos).

## W4 — `RepoService`

The largest item, and the one everything after it assumes the shape of.

**The slot.** `RepoSession` gains `reviewWalk: ReviewWalk | undefined`, where

```ts
interface ReviewWalk {
  readonly range: CommitRange;           // what this walk IS — the key for "same range?"
  logSession: LogSession;
  readonly store: CommitStore;
  dictionaryMarks: Map<number, number>;
  nextSeq: number;
  lastRemaining: number;
}
```

Deliberately **not** a `RepoSession`: it has no driver of its own (it borrows the session's), no
watcher, no caches, no undo slot, no head. It has exactly the six fields a walk needs, which is
the honest statement of what a second walk actually is.

**`resolveReviewBase(repoId, branch, base?)`** — the whole of `review.resolveBase`'s host half:

1. `refs(repoId)` (cached; no spawn in the common case) for the ref snapshot.
2. If `base` was supplied, skip resolution and take it with reason `"override"`. Otherwise
   `detectDefaultBranch(driver)` (one spawn, only when rule 1 falls through) and `resolveBase(…)`
   from W1.
3. `base === null` ⇒ `{ range: { kind: "ask" } }`, done. No further spawns.
4. `mergeBase(driver, base, branch)` ⇒ `null` ⇒ `{ range: { kind: "unrelated" } }`, done.
5. `countRange(driver, base, branch)` ⇒ `0` ⇒ `{ range: { kind: "empty" } }`, else
   `{ kind: "ready", commitCount }`.

Steps 4 and 5 run concurrently (`Promise.all`) — both are independent reads and the pair is on the
≤300 ms path. A `GitError` from either propagates: a base that does not resolve at all is a
genuine failure the UI renders as an error, not silently as "unrelated" (V6).

**Ranged `streamGraph`.** When `opts.range` is present:

- If `session.reviewWalk` exists for a *different* range, dispose its `LogSession` and drop it.
- Ensure a `ReviewWalk` for this range (creating its `LogSession` with
  `{ kind: "range", … }` and the pre-computed total from the caller's most recent resolution).
- **Ignore `resumeThroughRow` entirely.** Read the first page, then emit chunks from row 0 with
  `source: "git"`, threading `dictionaryBase` through `#emitRange` exactly as the scoped path
  does. A re-open of the *same* range on the same walk replays what the store already holds rather
  than re-spawning — that is not §5.4 rehydration (the walk is dropped on hide), it is the
  ordinary `loadMore`-then-reopen round trip `GraphViewState.#runLoad` already performs, and
  breaking it would break Load more.
- `#ensureFresh`/`staleReason` are **not** consulted. The review walk is not part of the graph's
  invalidation story; see open question 5 for what a mid-review `refsChanged` should do.

`#emitRange` is refactored to take the walk's own `{store, dictionaryMarks, nextSeq, logSession}`
rather than reading them off `RepoSession` — a parameterisation, not a rewrite, and the scoped
path passes the session's own. This is the single change in `repoService.ts` most worth reviewing
carefully.

**`endReview(repoId)`** — disposes and drops the slot. Idempotent, and a no-op for a repo with no
open session (returns rather than throwing, matching `refresh`'s own precedent, L686).

**`close(repoId)`** and `#evict` both dispose the review walk alongside the rest. `#resetSession`
(the stale/evict path) does **not** touch it — a `refsChanged` that resets the graph's store must
not silently empty a review the user is reading.

`RepoServicePort` in `rpcHandlers.ts` gains `resolveReviewBase` and `endReview`.

## W10 — `ui/src/state/packedStream.ts` and `ui/src/state/review.ts`

**`packedStream.ts`** is the chunk-application core both consumers need, extracted verbatim from
`GraphViewState.#applyChunk`/`#reset` (`graphView.ts` L219–250): the reset-on-`from: 0` rule, the
`appendPacked` call, the corrupted-chunk recovery (log, re-open from row 0), and the
`loadedRows`/`remaining`/`exhausted`/`lastChunkSource`/`generation` refs. It owns a `CommitStore`
and nothing else — no layout, no bridge.

`GraphViewState` composes it and keeps everything that is genuinely its own: the `LayoutClient`
submission, `laneCount`, `onChunkLayout`, `loadMore`/`loadAll`/`refresh`/`cancelLoad` and the
`loading` state machine. **P4's behaviour must not change** — the extraction is mechanical, and
`commitList.spec.ts`/`graph.spec.ts` are the check that it was.

**`review.ts`** — `ReviewSessionState`, the view's whole state machine:

```
idle ──target(branch)──> resolving ──> ask | unrelated | empty | listing
                                            ^                      |
                                            └──── overrideBase ─────┘
```

- `setTarget(repoId, branch)` — aborts everything in flight, clears rows and expansions, requests
  `review.resolveBase`.
- `setBase(base)` — the override. Re-requests `review.resolveBase` **with** the base, then
  re-opens the stream. In place: the component never unmounts, the header updates, the list
  repaints. Session-scoped and never written anywhere (D30's "deliberately not persisted" is free
  here, because the view persists nothing at all).
- `open()` — `graph.stream` with `{ repoId, range }` through `packedStream`, `loadMore()` through
  `graph.loadMore` with the same range plus the re-open, mirroring `GraphViewState`'s two-round-trip
  shape (it is the same host contract).
- `expansions` — a `Map<sha, { detail: DetailState, actions: DetailActions }>`, created lazily on
  first expansion and **kept for the session** (§6.8 step 2: *"the tree for a commit is fetched on
  first expansion and kept for the session"*). Several rows may be expanded at once. Disposed

## Judgment calls this plan made

1. **One optional `range` on the existing `graph.*` keys, not a `review.stream` of its own.**
   §3.5's steer, and the cheaper answer: the chunk envelope, `PackedCommitChunk`, `appendPacked`'s
   ordering assert, the dictionary-delta protocol, `CHUNK_ROWS` and the Load-more round trip are
   all reused verbatim. A separate key would have duplicated every one of them to express one
   different argv.
2. **…but a separate host-side walk session.** Sharing `RepoSession`'s single walk state would
   destroy the panel's cache. The wire is shared; the session is not. Stated as the phase's
   central design fact rather than discovered in W4.
3. **The override is a second `review.resolveBase`, not a client-side re-walk.** `merge-base` and
   the range count must run for a chosen base exactly as for a detected one; one code path for
   both is what stops the override being a route around the guarantees.
4. **All four range states are decided before the first row.** "The walk produced nothing"
   distinguishes none of ask/empty/unrelated/failed, and §6.8 requires three of them to be
   distinguishable and named.
5. **The review list is not virtualized (D42).** A tree of expandable rows over a bounded range;
   §5.3's grid exists for 100k rows and cannot expand a row anyway. The bound is §5.1.1's page and
   Load more.
6. **The review view runs no layout worker.** It draws no lanes. A worker computing lanes nobody
   renders is cost with no consumer.
7. **The palette prompts inside the view, not through a host quick-pick.** Keeps the flow
   harness-testable and Playwright-screenshottable (the same reasoning P6's judgment call 6 gave
   for in-webview dialogs), and reuses the ask-state vocabulary §6.8 already establishes.
8. **`reviewView.ts` is a sibling of `panelView.ts`, not a shared base class.** They differ in the
   four things that matter; a base class hiding four differences behind three template methods
   reads worse than two short files.
9. **`FileTree.vue`'s merge-parent label degrades rather than being fixed.** A parent outside the
   range has no subject in the review's own store, and the existing code already handles that. A
   `commit.detail` per parent to enrich a `<select>` option is work no requirement asks for.
10. **No `range` on `graph.refresh`.** §6.8 gives the review no refresh affordance; a parameter
    with no caller is exactly the "present but not exercised" §9 warns about. What a mid-review
    `refsChanged` *should* do is open question 5, and is a decision, not an omission.
11. **`review.open` is a request, `review.target` an event, and both are needed.**
    `resolveWebviewView` seeds a cold view and does not run for a visible one; §6.8 requires
    reviewing a second branch to replace an open view's contents.
12. **No new perf file.** §5.1's ≤300 ms row already covers this surface; the metric joins
    `graphUi.ts` rather than inventing a budget nobody agreed to (P6's judgment call 11, same
    reasoning, opposite outcome only because §10's P7 row states the number explicitly).

## Open questions for the orchestrating session

Raised here rather than resolved by editing the spec. Each names this plan's own recommendation;
the implementer should treat a resolution as settled context.

1. **§3.5's request list names `graph.query`, which has never existed.** The contract has
   `graph.status`, `graph.loadMore` and `graph.refresh` plus the `graph.stream` stream, from P3
   onward. §3.5 also says *"`graph.query`/`graph.stream` take an optional commit range"*.
   **Recommendation: correct §3.5** — the request list drifted from the contract at P3 and nobody
   has needed to reconcile it until a phase had to add a parameter to a key that is not there.
   Name the real keys and say which three gain `range`. This plan designs against the tree.

2. **Where the palette command prompts for a branch.** §6.8 says
   *"`kiraVersion.reviewBranch` in the command palette, prompting for the branch"* without saying
   where the prompt lives. **Recommendation: in the view** (this plan's design) — harness-testable,
   Playwright-screenshottable, reuses the ask-state vocabulary, and needs no host-side quick-pick
   surface. The alternative is `vscode.window.showQuickPick` over `refs.list` in `extension.ts`,
   which is more native-feeling and untestable outside the `vscode` tier.

3. **The non-virtualized list's bound.** §6.8 says the range walk uses *"the same page size
   (§5.1.1)"*, i.e. 5,000. A non-virtualized tree of 5,000 expandable rows is a real cost on a
   degenerate input. **Recommendation: accept it as specified** — it takes a deliberate Load more
   on a case §6.8 itself calls rare. The lever, if the orchestrating session disagrees, is a
   smaller first page for ranged walks (say 500), which contradicts §6.8's sentence and would need
   a spec edit.

4. **The array setting.** `kiraVersion.review.baseCandidates` needs a type D25's schema does not
   have. **Recommendation: add `stringArray`** (W7) — the schema's whole point is being the one
   place, and D19's protected-branch patterns are the next array setting to arrive. The
   alternative is a comma-separated string, which avoids the schema change and pushes parsing into
   every consumer.

5. **What a mid-review `refsChanged` should do.** §6.8 says nothing, and the situation is real: a
   background fetch moves `origin/main` while the user is reading a review against it, and the
   list is now silently wrong. Options: (a) do nothing — the session is one-shot and the user can
   re-open; (b) re-resolve quietly and, if the count changed, show a "the comparison has changed"
   affordance the user clicks to re-walk; (c) re-walk automatically, which throws away the user's
   expansions and scroll position mid-read. **Recommendation: (b)** — it neither lies nor yanks
   the list out from under the reader, and it is one banner plus one re-request. This is the one
   place P7 would add behaviour §6.8 does not describe, so it needs a ruling before W11 renders it.

6. **Whether the review view gets a refresh affordance.** Directly downstream of 5: (b) implies a
   re-walk button, which is a refresh in all but name. **Recommendation: only as the affordance in
   5(b)** — a permanent `⟳` in the review header would invite the reading that the review is a
   long-lived surface, which is exactly what D29 says it is not.

7. **`CONTRACT_VERSION` 6 → 7.** Mechanical, but it is the fifth bump and every host, the harness
   mock and the UI move in one commit. Confirm.

8. **The `packedStream.ts` extraction.** W10 pulls `GraphViewState.#applyChunk`'s core out so the
   review session does not carry a second copy. It touches P4's hot path.
   **Recommendation: do it** — two callers justify one implementation, and `commitList.spec.ts`/
   `graph.spec.ts` are the guard that P4's behaviour is unchanged. The alternative is ~40
   duplicated lines in `review.ts` and P4's file untouched.

|---|---|---|

| D40 | How the sidebar view learns which branch to review | **`review.open` from the panel, `review.target` to an open review view, and the bootstrap island for a cold one — all three, because none covers the other's case.** `resolveWebviewView` runs only on reveal-from-hidden, and §6.8 requires reviewing a second branch to replace an already-open view's contents. The palette command reveals the view with no target and lets it ask, in the same ask-state vocabulary §6.8 already defines for a missing base — no host-side quick-pick surface, and the whole flow stays reachable in the harness tier. |
| D41 | How one bundle serves two views | **`mount({view})` selects the root, and the review view is handed a `NullViewStateStore`.** §6.8's "same bundle, different root, selected from the host's injected initial state" — so `vite.config.ts`'s one-build-one-entry rule holds and there is no second UI to keep in visual step. The null store is a named export, not an inline literal: "this view persists nothing" is a design statement (§5.4's exclusion) and must be greppable. The review view additionally runs no lane-layout worker — it draws no lanes. |
| D42 | Whether the review commit list is virtualized | **No — it is a tree of expandable rows over a bounded range.** §5.3's virtualized grid exists for 100k rows and cannot expand a row; §6.8's range is "tens or hundreds", and VS Code's own comparable surfaces (Source Control, Search Results) are non-virtualized trees at this scale. The bound is §5.1.1's page size with Load more as the gate, exactly as §6.8 specifies. The cost — 5,000 plain rows if a user presses Load more on a degenerate range — is accepted rather than paid for by virtualizing an expandable tree. |
| D43 | Array-valued settings | **`SETTINGS` grows a `stringArray` type; `kiraVersion.review.baseCandidates` is its first member.** D25's schema is the one place settings are defined and it could not express a list at all. Coercion follows the existing never-partly-valid rule (any non-string member falls the whole value back to the default with a logged problem), and `toVsCodeConfiguration` emits `{type:"array", items:{type:"string"}}`. Adding the type rather than encoding a list as a comma-separated string keeps the parsing in the schema instead of in every consumer — D19's protected-branch patterns are the next array setting to arrive. |

## Exit criteria

The phasing row's bar is: *"Review opens from both context menus and the palette, first commits
painted ≤300 ms on a 200-commit range; base resolves to the tracking branch when it names a
different branch, to the detected default branch when it does not, and to the ask-state when
neither exists; the override re-runs the comparison in place without reopening the view; a
fully-merged branch reports 'nothing to review' naming both refs rather than an empty list; every
row expands to the same tree P5 renders (renames, merge parent selector, binary/LFS) and every
file opens the same diff, with 'Go to file' landing on the mapped line in the virtual blob for a
branch that is not checked out; hiding the view drops the session and reopening re-resolves and
re-walks (no rehydration path, §5.4); Playwright interaction + visual coverage at sidebar widths
across all four theme kinds."* Complete when all of the following hold, verified by running them:

- [ ] `bun install && bun run check && bun run test` is green, `bun run build` produces every
      bundle, and `bunx playwright test --project=harness` passes with no regressions in the
      pre-existing specs.
- [ ] **Review opens from all three entry points**: the branch picker's context menu (kebab *and*
      right-click), a right-click on a branch ref badge in the message column, and
      `kiraVersion.reviewBranch` in the palette. A right-click on the same row *not* on a badge
      still opens the commit menu, and a right-click on a badge still selects the row.
- [ ] **Base resolution, all three rules and both fall-throughs**: a branch tracking
      `origin/<same-name>` falls through to the default branch; a branch tracking
      `origin/develop` resolves to `develop` with reason "upstream"; a branch tracking a local
      branch resolves to it; `origin/HEAD` is used when set and `baseCandidates` when it is not;
      with neither, the view enters the ask-state with the base picker focused and an empty list
      and **no walk is opened**. Verified against real git (W19) and unit-tested exhaustively over
      W1's table.
- [ ] **The override re-runs in place**: picking a different base from the header picker re-resolves,
      re-walks and repaints without the view root unmounting (asserted on DOM node identity, not on
      "the list changed"), and an overridden base gets the same `merge-base`/count checks a detected
      one does.
- [ ] **A fully-merged branch reports "nothing to review" naming both refs**, and a branch sharing
      no merge base says so *before* the walk — neither is an empty list, a spinner, or an error.
      Both proven against real git.
- [ ] **Every row expands to the tree P5 renders**: renames with the arrow, a merge's parent
      selector (functioning, with the out-of-range-parent label fallback recorded in Findings),
      binary and LFS labelled rather than rendered as garbage, per-file counts, the filter box, the
      tree/flat toggle, and the row cap. Two rows expanded at once; a re-expanded row does not
      re-request.
- [ ] **Every file opens the same diff**, as a full-height overlay at sidebar widths with a back
      affordance; arrow keys move between files with the diff following; `Esc` closes the diff,
      then collapses the row. "Open in editor" is present and calls `editor.openDiff`.
- [ ] **"Go to file" lands on the mapped line in the virtual blob for a branch that is not checked
      out** — asserted in the harness through the recorded editor action, and end to end in the
      `vscode` tier against a real repository with a real virtual document.
- [ ] **Hiding the view drops the session and reopening re-resolves and re-walks**: `endReview`
      disposes the walk, the first chunk after reopening carries `source: "git"`, and the review
      webview never calls `setState`. **And hiding the review view leaves the panel untouched** —
      no `setUiVisible(false)`, no armed eviction, the graph's loaded rows and selection unchanged.
- [ ] **The graph walk and the review walk are provably isolated**: with history loaded, a full
      review open/stream/page/end cycle on the same repo leaves the graph's `store.rowCount`,
      `dictionaryMarks` and `logSession` identical, and the next graph chunk appends cleanly.
- [ ] **First commits painted ≤300 ms on a 200-commit range**, recorded in
      `graphUi.budget.json` and gated by the same 20% rule, with V7's per-hop breakdown of the
      prelude recorded in Findings.
- [ ] **Playwright interaction + visual coverage at sidebar widths (300 px and 480 px) across all
      four theme kinds**, with committed Linux baselines, covering the list, an expanded row, the
      diff overlay, the open base picker, the ask state and the nothing-to-review state.
- [ ] **Accessibility**: axe reports no serious or critical violations on any review surface in any
      theme kind; the list is a real `tree`/`treeitem` with `aria-expanded` and a roving `tabindex`;
      focus returns to the disclosure control when the overlay closes and to the header trigger when
      the picker closes; every non-list state is announced.
- [ ] `CONTRACT_VERSION` is 7, `wireConformance.test.ts` covers every new wire type,
      `assertContractShape` covers the two requests and the event, and §3.1's tree carries this
      phase's new files.
- [ ] **`kiraVersion.review.baseCandidates` works end to end** — the `stringArray` type coerces
      (including rejecting a mixed array wholesale to its default with a logged problem),
      `contributes.configuration` is regenerated, and changing the setting changes which base is
      detected.
- [ ] **Nothing from P8+ is implemented.** If the diff contains a fetch/pull/push path, a stash, a
      reset, a search box, a PR badge, an operation on a review row, ref badges in the review list,
      or a lane graph in the sidebar, the phase overran.
- [ ] V1–V8 resolved and recorded below, including any decision made at the keyboard this plan did
      not anticipate.
