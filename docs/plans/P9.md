# P9 — Stash

**Goal (§10):** Stash create (incl. `-u`, message, pathspec), list, show, apply/pop/drop/branch,
stashes rendered in the graph, and the pop-prediction engine via `merge-tree` (§7.6) wired into
checkout resolution.

**Exit criteria (§10):** Prediction verified against actually-executed pops across clean and
conflicting cases; a dropped stash is recoverable through the undo slot.

P9 is the phase where a pre-flight stops being a *description* of the current state and becomes a
*prediction about a state that does not exist yet*. Every earlier pre-flight answered a question git
could already answer by looking: is the tree dirty, does this ref exist, is a merge in progress.
§7.6's pop prediction asks git to perform a merge it will not keep, in the object database, and then
promises the user the real merge will come out the same way. §7.6 states that promise as fact — "the
prediction is exact, not heuristic" — and that sentence is the reason the repo carries a git 2.38
hard floor (D2).

The probes below show the promise is true **only under a precondition the spec text does not state**
(`--merge-base=<stash^>` is mandatory, not stylistic — without it git silently reports a genuinely
conflicting pop as clean) and **only about the merge itself**. Two real, reproducible failure modes
make a pop fail after a clean prediction, and neither is a merge question: an untracked-file
collision (which applies half the stash and stops) and a dirty worktree overlapping the stash's own
paths (which applies nothing). Both are answerable pre-flight, by set intersection, the way §7.5
already answers checkout — so this plan answers them there rather than weakening §7.6's promise.

Everything else in this phase is smaller than it looks, because P4 already renders a stash node, P6
already built the executor, undo slot and checkout routes this phase plugs into, and `refs/stash`'s
awkwardness turns out to be concentrated in exactly two places: `git stash drop`/`pop` refuse a raw
sha, and `--glob=refs/stash` reaches only `stash@{0}`.

This plan is grounded in live probes run against **git 2.43.0** in this sandbox, against real
repositories built for each case. Output below is copied from those runs, not reconstructed.

## What the git probes settled

All run on git 2.43.0, `LC_ALL=C`, in throwaway repos. Output verbatim.

### Probe 1 — a stash entry's shape, and what `-u` actually adds

```
$ git stash push -u -m "with untracked"      # a.txt modified, untracked.txt + sub/s.txt new
$ git rev-list --parents -n1 refs/stash
980dc2af…  759a4040…  7c2c838b…  64800cfc…
   stash      stash^      stash^2     stash^3
$ git log --format=%s -n1 'refs/stash^3'
untracked files on main: 759a404 base
$ git ls-tree -r --name-only 'refs/stash^3'
sub/s.txt
untracked.txt
```

§7.6's model is exactly right: parent 1 is the base commit, parent 2 the index tree, parent 3 (with
`-u`) the untracked set — and `ls-tree -r --name-only stash^3` enumerates that set precisely, which
is the input probe 3's pre-check needs.

**But parent 3's presence means `-u` was *passed*, not that untracked content exists:**

```
$ git stash push -u -m "u but nothing untracked"   # nothing untracked in the tree
$ git rev-list --parents -n1 refs/stash | wc -w
4          # sha + 3 parents — an EMPTY untracked commit
$ git stash push -m "no -u"
3          # sha + 2 parents
```

So the model field is `includedUntracked`, never `hasUntracked`; the real file list comes from
`ls-tree`, which is legitimately empty in the degenerate case.

### Probe 2 — `--merge-base=<stash^>` is mandatory, and its absence produces a **false clean**

The exact stash-shaped twin of P6's probe P2. Setup: `C0` (`a.txt = ORIGINAL`), `main` advances to
`C1` (`a.txt = MAIN-CHANGE`), a stash on `main` that *reverts* to `ORIGINAL`, and a divergent
`side` branch from `C0` with `a.txt = SIDE-CHANGE`. Predict popping that stash onto `side`:

```
$ git merge-base HEAD $S          # 46c8aa44…  (= C0)
$ git rev-parse 'stash@{0}^'      # 61187ff4…  (= C1)

$ git merge-tree --write-tree --messages --name-only HEAD "$S"
ff1645484bd78f08908f7116cf7e8c6d23fea698
rc=0                                            # <-- CLEAN. Wrong.

$ git merge-tree --write-tree --messages --name-only --merge-base="$B" HEAD "$S"
6bcf3881d1d58858d0afb365f28ada7514d5170d
a.txt

Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
rc=1                                            # <-- CONFLICT. Right.

$ git stash pop
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
rc=1
```

Left to itself git picks `merge-base(target, stash)` — here `C0`, an ancestor of the stash's real
base — and the stash's diff *against that older base* is empty, so it reports clean. The stash's
diff against its **own** base is a revert, and that is what genuinely conflicts.

**Settled:** the argv is non-negotiable —
`merge-tree --write-tree --messages --name-only --merge-base=<stash^> <target> <stash>` — and
`mergeTreeArgs`'s existing `opts.mergeBase` is exactly the affordance. §7.6's prose already says
"using `stash^` as the merge base"; this probe upgrades that from a stylistic reading to a
correctness requirement, and W20 makes the spec say so.

### Probe 3 — prediction gap #1: an untracked collision, with **partial application**

Stash created with `-u` carrying `new.txt`; before popping, an unrelated `new.txt` is recreated in
the worktree with different content.

```
$ git merge-tree … --merge-base=$B HEAD $S
c3c8c41dea090b1e56376879888b62a0e5a8d7cd
rc=0                                     # clean — and, as a merge question, correct

$ git stash pop
rc=1
--- stdout:
On branch main
Changes not staged for commit:
	modified:   a.txt
Untracked files:
	new.txt
The stash entry is kept in case you need it again.
--- stderr:
new.txt already exists, no checkout
error: could not restore untracked files from stash

$ cat a.txt            # the TRACKED half was applied
base
edited
$ cat new.txt          # the worktree's own file, untouched
collision
$ git stash list
stash@{0}: On main: with untracked          # stash kept
```

**The worst outcome in the phase**: half the stash landed, the other half did not, and the stash is
still in the list — so a naive retry would double-apply the tracked half. merge-tree cannot see this
because untracked restoration is a checkout, not a merge.

**Settled:** this is a pre-flight *blocker*, computed as
`ls-tree -r --name-only <stash>^3` ∩ *paths that exist in the worktree*, not a prediction. Unlike
every other blocker in the phase it also needs a post-op story, because the failure is not atomic
(W7's `StashUntrackedCollision` kind and W13's copy).

### Probe 4 — prediction gap #2: a dirty worktree overlapping the stash's paths

Stash modifies `a.txt`; before popping, the worktree modifies `a.txt` differently.

```
$ git merge-tree … --merge-base=$B HEAD $S
d024e599167eb0f25b50de68953ff3de90a6e6b7
rc=0                                     # clean — again correct as a merge question

$ git stash pop
rc=1
--- stderr:
error: Your local changes to the following files would be overwritten by merge:
	a.txt
Please commit your changes or stash them before you merge.
Aborting
$ git stash list
stash@{0}: On main: s                    # nothing applied, stash kept
```

git refuses **before** merging. This is the §7.5 D∩T set intersection, not a merge — and
`classifyCheckout`'s `targetTreePaths` parameter is the seam that already exists to express it.

**Settled:** blocker, not prediction; atomic (nothing applied), so the remedy copy is simple.

### Probe 5 — a conflicting pop writes to **stdout**, with stderr empty

```
$ git stash pop >out 2>err ; echo rc=$?
rc=1
$ cat out
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
On branch main
Unmerged paths:
	both modified:   a.txt
The stash entry is kept in case you need it again.
$ wc -c < err
0
```

`classifyGitError` reads **stderr only**, so a real conflict classifies as `Unknown` with an empty
message.

**Settled:** conflict detection for apply/pop is `exitCode !== 0` **plus** the post-op status
read-back that `runOp` already performs unconditionally — never a stderr pattern. Note the
asymmetry: probes 3 and 4's failures *do* write stderr, so those two are pattern-classifiable and
the conflict case is not.

### Probe 6 — what state a conflicted pop leaves

```
$ ls .git | grep -iE 'MERGE|CHERRY|REVERT|rebase|sequencer|AUTO'
AUTO_MERGE
$ git status --porcelain=v2 -z | head -1
u UU N... 100644 100644 100644 … a.txt
```

None of `classifyInProgress`'s six state files — only `AUTO_MERGE`, which P6 probe P4 already
established is a stale artefact and deliberately excluded as an input. So the classification is
`unmergedOnly`: `canContinue: false`, `canAbort: false`.

**Settled:** the existing conflict banner renders this correctly with **no change**, but it offers
no Continue and no Abort — honestly, because git offers neither. The only remedies are "Resolve in
VS Code" (already wired) and the fact that the stash was kept. W13's copy must say the second part.

### Probe 7 — `--glob=refs/stash` reaches exactly one stash

```
$ git stash list
stash@{0}: On main: third
stash@{1}: On main: second
stash@{2}: On main: first
$ git log --all --glob=refs/stash --format='%h %d %s' | grep -c 'refs/stash'
1
```

`refs/stash` is *one ref*; `stash@{1..N}` live in its reflog and no glob reaches them. The walk also
pulls in each reachable stash's helper parents, which arrive as ordinary undecorated rows with
subjects `index on main: <sha> <subject>` and `untracked files on main: <sha> <subject>`.

**Settled:** §7.6's parenthetical — "`--glob=refs/stash` in the walk puts them there" — is true of
`stash@{0}` and false of every other stash. W12 passes stash shas explicitly and filters the helper
commits; W20 corrects the spec sentence.

### Probe 8 — apply/show/branch take a raw sha; **pop and drop do not**

```
$ S1=$(git rev-parse 'stash@{2}')
$ git stash apply "$S1"      ; rc=0        # works
$ git stash show --numstat -z -u "$S1"     # works
$ git stash pop  "$S1"
error: '81a5fb65…' is not a stash reference
rc=1
$ git stash drop "$S1"
error: '81a5fb65…' is not a stash reference
rc=1
$ git stash branch tmpb "$S1"              # rc=0, branch created, changes applied…
$ git stash list                           # …but THREE entries still — NOTHING was dropped
$ git stash branch tmpc 'stash@{2}'
…
Dropped stash@{2} (81a5fb65…)              # the stash@{N} form DOES drop
```

`git stash branch <name> <raw-sha>` is the trap: it succeeds, applies, and **silently skips the
drop**, because dropping needs a reflog position.

**Settled:** every argv that mutates the stack (`pop`, `drop`, `branch`) is addressed as
`stash@{N}`; `apply` and `show` may use the sha. Since `N` shifts under any concurrent stash write,
each such op carries **both** and the service verifies `git rev-parse stash@{N}` equals the expected
sha immediately before writing (probe 10 gives the failure shape when `N` is out of range).

### Probe 9 — drop → `stash store`, and the `%s` / `%gs` split

```
$ git stash drop
Dropped refs/stash@{0} (4e218c375eca77c785fdfb4ee5a7f1ead261d64d)
rc=0
$ git stash store -m "RESTORED-LABEL" "$SHA_OF_A_DIFFERENT_ENTRY"
rc=0
$ git stash list --format='%gd s=%s gs=%gs'
stash@{0} s=On main: second gs=RESTORED-LABEL     # <-- they diverge
stash@{1} s=On main: third  gs=On main: third
stash@{2} s=On main: second gs=On main: second
```

`%s` is the stash *commit's* subject, minted once at push time. `%gs` is the *reflog* subject, which
`stash store -m` sets, and is what `git stash list` itself displays. They are identical until a
`store` — i.e. until P9's own undo runs, at which point the existing `STASH_FORMAT`'s `%s` would
show the pre-drop label and hide the restored one.

Two more facts from the same probe:

- `store` restores at **index 0**, not at the entry's original position (visible above: the restored
  entry is `stash@{0}` and the old `stash@{0}` shifted to `stash@{1}`).
- `store` into an **empty/absent** `refs/stash` works: `rc=0`, one-entry stack.
- **Degenerate no-op:** `store` of a sha that already equals `refs/stash`'s current tip silently does
  nothing (git's `update-ref` treats a same-value write as no change and logs nothing). Only
  reachable when two byte-identical stash entries exist — same tree, same message, same second — so
  the same sha. Named as a known gap in W19, not engineered around.

### Probe 11 — `stash branch` decomposes into checkout + apply + drop, and is not atomic

`git stash branch <name> <stash@{N}>` is `git checkout -b <name> <stash>^` followed by an apply and,
on success, a drop. Because the new branch starts **at the stash's own base**, "ours" has no changes
relative to the merge base and the apply is clean *by construction* — there is nothing to predict.

It is not atomic. With a dirty tree overlapping the stash's paths:

```
$ git stash branch tmp 'stash@{0}'
Switched to a new branch 'tmp'
error: Your local changes to the following files would be overwritten by merge:
	a.txt
Aborting
Index was not unstashed.
rc=1
$ git stash list          # stash intact
```

The branch exists, HEAD moved to it, the stash was neither applied nor dropped.

**Settled:** `stash branch` needs a *hybrid* pre-flight (checkout of `stash^` + branch-name
validity), **no** pop prediction, and an error message that names the half-completed state. `runOp`'s
unconditional head read-back (step 4, success *or* failure) already reports the moved HEAD.

### Probe 12 — `stash show` reuses the existing diff parsers, and one spawn lists everything

```
$ git stash show --name-status -z -u -M -C stash@{0} | tr '\0' '|'
M|a.txt|A|sub/s.txt|A|untracked.txt|
$ git stash show --numstat -z -u -M -C stash@{0} | tr '\0' '|'
1	0	a.txt|1	0	sub/s.txt|1	0	untracked.txt|
```

Byte-identical framing to `diff-tree -r --numstat/-–name-status -z`, which
`parseNumstatRecords`/`parseNameStatusRecords` already consume. `-u` is harmless on a stash with no
third parent (`rc=0`, tracked entries only), so **one args shape covers both**.

And the list itself carries per-entry counts in a single spawn:

```
$ git stash list -z --numstat -M -C --format='%H%x1f%P%x1f%gd%x1f%at%x1f%gs' | tr '\0\037' '|~'
a5dcf020…~14eca2b5… 1af20aa1… 0b15eff8…~stash@{0}~1788679316~On main: three|
1	0	a.txt|1	0	b.txt|1	0	c.txt|790b6169…~14eca2b5… 449e5a0c…~stash@{1}~…~On main: two files|
2	0	a.txt|d38a1048…~…~stash@{2}~…~recovered|
1	0	b.txt|
```

Framing: a header record (ending in a `\n` to trim) then that entry's NUL-terminated numstat
records, repeating. A header always contains `\x1f`; a numstat record never does. **N stashes, one
spawn.** (`-u` in `stash list` means `--patch`, not `--include-untracked` — the untracked count is
not available here and comes from `stash^3` on demand.)

## The hard parts, settled before the work items

### 1. What the pop prediction promises, what it cannot, and how the UI says so

**The mechanism.** A stash's working-tree change is the diff `stash^ → stash`. Popping onto a target
commit `T` is the three-way merge (base `stash^`, ours `T`, theirs `stash`). Therefore:

```
git merge-tree --write-tree --messages --name-only --merge-base=<stash^> <T> <stash>
```

Exit 0 → clean, exit 1 → the conflicting paths, exit >1 → an execution error. This *is* the merge
git will run: same base, same sides, same merge machinery. §7.6's "exact, not heuristic" holds — for
the merge.

**`--merge-base` is not optional** (probe 2). Its absence is not a lost optimisation, it is a
silently wrong answer in the direction that matters most: reporting clean where the real pop
conflicts. `predictStashPop` therefore takes `baseSha` as a required parameter and there is no
overload without it.

**Three things it does not cover.** Only the third is irreducible:

| Gap | Detectable pre-flight? | Atomic? | How P9 handles it |
| --- | --- | --- | --- |
| Untracked collision (probe 3) | **Yes** — `ls-tree -r --name-only <stash>^3` ∩ worktree-existing paths | **No** — tracked half applies | Blocker `untrackedCollision` with the colliding paths; distinct `OpErrorKind` so the post-op copy can warn about the partial application |
| Local changes overwritten (probe 4) | **Yes** — stash's changed paths ∩ dirty tracked paths, i.e. §7.5's D∩T | Yes — nothing applies | Blocker `localChangesWouldBeOverwritten` with the overlapping paths |
| TOCTOU: the tree changes between pre-flight and pop | No | n/a | Post-op reconciliation, below |

The first two are computed from data the service already fetches for §7.5 and are reported as
**blockers on the pre-flight**, not as predictions. This keeps §7.6's promise narrow and true rather
than broad and false: *the merge* is predicted exactly; *the operation* is additionally gated on two
set intersections.

**How the UI communicates the residual gap.** Two rules, both concrete:

1. The dialog never says "this will work". It says what was predicted and what it was predicted
   *for*: "Popping `stash@{0}` onto `main` merges cleanly" or "…conflicts in 2 files: a.txt, b.ts".
   Blockers are stated as facts about the current tree, in their own section, with their own remedy.
2. **Every pop and apply is reconciled against reality, and a disagreement is announced.**
   `runOp` already returns `inProgress` read back after the write. `ops.ts` compares it with the
   prediction it acted on and, when they differ, surfaces the mismatch explicitly rather than
   letting the user infer it:

   ```ts
   /** Non-null only when the executed pop/apply disagreed with the prediction the user was
    *  shown. §7.6 promises an exact prediction; when reality differs (a race, or a gap the
    *  pre-flight could not see) we say so plainly rather than silently rendering the outcome. */
   export interface StashPredictionMismatch {
     readonly predicted: "clean" | "conflicts";
     readonly actual: "clean" | "conflicts" | "refused";
     readonly stashKept: boolean;
   }
   ```

   Copy: *"This pop conflicted, though the pre-flight predicted a clean apply — the tree changed in
   between. Your stash was kept."* The `stashKept` half is §7.6's own explicit requirement ("we say
   so, so the user knows their work is still recoverable") and is a **fact, not an assumption**:
   probes 3, 4 and 5 all confirm the stash survives every failure mode.

### 2. `refs/stash` against `RefRow`, `DecorationRef` and the graph

`refs/stash` is one ref with a reflog-shaped stack behind it. That single fact decides three things.

**It is not a `RefRow`, and `refs.list` does not touch it.** `RefRow` carries `refname`, `kind`,
`shortName`, `upstream`, `track`, `committerDate`, `isHead`, `checkedOutIn`, `annotation` — a
per-ref identity with branch/tag semantics. A stash has none of them and has a stack position
instead. `refs.list` is two `for-each-ref` spawns and `for-each-ref` sees exactly one `refs/stash`;
forcing the stack through it would mean inventing synthetic refnames (`refs/stash@{2}` names
nothing). **The stash list gets its own request** (`stash.list`) returning `StashEntry[]` — the model
that already exists for it. `RefKind` is untouched.

**`DecorationRef` gains a field, not a variant.** `{ kind: "stash" }` already exists but is
field-free, so a badge cannot say *which* stash and the row context menu has nothing to hit-test
(`badgeSpecFor` sets `refKind`/`refName` to `undefined` today). W5 widens it to
`{ kind: "stash"; index: number }`. The badge text becomes `stash@{N}` and the menu gets its target.
This is the natural shape: a stash entry decorates a commit exactly the way a branch tip does.

**The graph needs two fixes, and neither is cosmetic** (probe 7):

- *Reachability.* Only `stash@{0}` is reachable. The walk gains the remaining stash shas as explicit
  positional revs. They arrive with an empty `%D` (no ref decorates them), so the decoration is
  **synthesised by sha membership** against the stash list the service already holds, not parsed.
- *Helper-commit noise.* `stash^2` (`index on main: …`) and `stash^3` (`untracked files on main: …`)
  are reachable as parents and render as ordinary commits. They cannot be excluded with `^<sha>` —
  their own ancestor is the base commit, which is real history that would vanish with them. So they
  are filtered **by sha**, service-side, against the known helper set; and each stash commit's parent
  list is truncated to its first parent so the graph draws a stash hanging off its base with no
  dangling edges.

Both need the stash list before the walk starts — which is one cheap spawn the service already makes
alongside refs, refreshed by the same `onInvalidated` generation bump.

Gated by `kiraVersion.stash.showInGraph` (default `true`): when off, no extra revs, no filter set,
and `revSetArgs` drops `--glob=refs/stash` so `stash@{0}` disappears too rather than being the only
one shown.

### 3. `stash branch`: a hybrid pre-flight, and no prediction at all

`git stash branch <name> <stash@{N}>` is checkout **and** pop in one command, so the instinct is
that it needs both pre-flights. It needs neither in the obvious form.

- **No pop prediction.** The branch is created at `stash^` (probe 11). With base `stash^` and ours
  `stash^`, ours has no changes; the merge is clean by construction. Running merge-tree here would
  spend a spawn to prove `rc=0` every time. `StashBranchPreflight.prediction` does not exist.
- **A real checkout pre-flight** — against `stash^`, not against the stash — because the `checkout
  -b` half is a genuine checkout and can be blocked by a dirty tree, an in-progress operation, or a
  worktree conflict. `classifyCheckout` is reused unchanged.
- **Plus branch-name validity**, which `classifyCheckout` knows nothing about, in the shape
  `classifyTagCreate` already established for the analogous tag case.

So the hybrid is a *composition*, not a new engine:

```ts
export interface StashBranchPreflight {
  readonly name: { readonly valid: boolean; readonly error: string | undefined;
                   readonly exists: boolean };
  /** The `checkout -b <name> <stash>^` half, classified by the existing engine. */
  readonly checkout: CheckoutPreflight;
  readonly verdict: "clean" | "invalidName" | "blocked";
}
```

**Non-atomicity is a UI requirement, not just a note.** On failure the user is on a new branch they
did not have, with the stash still in the list. `runOp` step 4 reads HEAD back on failure as well as
success, so `OpResult.head` is already correct; W13's failure copy must name both halves: *"Created
and switched to `<name>`, but the stash could not be applied and was kept."*

### 4. Undo of a drop: what to capture, and how long "recoverable" is honest

`git stash drop` deletes a reflog entry. The commit object survives; nothing else does. So the
capture, taken **before** the write (the `#captureBranchDeleteUndo` pattern, third instance):

| Captured | From | Why |
| --- | --- | --- |
| `sha` (full) | `git rev-parse stash@{N}` | The only durable identity; also the pre-write race guard against `N` (probe 8) |
| `message` | `%gs` of that entry | `stash store -m` writes this **verbatim** as the new reflog subject; capturing `%s` instead would restore the wrong label after any prior restore (probe 9) |

```ts
{
  id, createdAt,
  label: `Dropped stash@{${n}}: ${message}`,
  recoverySha: sha,
  replay: [["stash", "store", "-m", message, sha]],
}
```

**How long "recoverable" honestly is — four bounds, stated plainly and in this order:**

1. **The slot**: cleared by the very next operation (§7.12). This is the shortest bound by far and
   the only one worth putting in the button's tooltip.
2. **The object**: unreachable the moment the reflog entry is gone. It survives an ordinary
   `git gc` (and auto-gc) because `gc.pruneExpire` defaults to `2.weeks.ago`; it is destroyed
   immediately by `git gc --prune=now` or `git reflog expire --expire-unreachable=now` + gc — probed
   directly.
3. **The verification**: `undoRun` already runs `cat-file -e <recoverySha>^{commit}` before
   replaying, so a pruned object produces a clean refusal, never a replay against something else.
   **No change to `undoRun`.**
4. **The restore is not positional**: the entry comes back at `stash@{0}`, not at `stash@{N}`
   (probe 9). The UI says so — "Restored as `stash@{0}`" — rather than letting the user discover it.

`recoverySha` is displayed by the existing "was `<sha>`" affordance, so bound 2 has a manual escape
hatch (`git stash store -m … <sha>`) even after bound 1 expires. That is the whole point of §7.12's
recovery-sha requirement and it lands here without new machinery.

The one known hole is probe 9's degenerate `store` no-op — two byte-identical stash entries produce
the same sha, so restoring one when the other is at the tip silently does nothing. Named in W19's
test list as an asserted-known limitation rather than papered over.

### 5. Where stash ops live in the contract: `op.run` arms, **not** a new key

D51 gave remote ops their own `remote.run` because `runOp` sets the undo slot unconditionally and
remote ops are killable, streaming, progress-reporting, and long. Every one of those reasons is
absent here, and one of them **inverts**:

| `op.run`'s property | Remote ops (D51) | Stash ops |
| --- | --- | --- |
| Sets the undo slot unconditionally | Wrong — a fetch has nothing to undo and would clear a real record | **Right** — `stashDrop` is undoable, and every other stash op *should* clear the slot |
| One synchronous `driver.write` per argv | Wrong — needs `writeStreaming` | Right — all five are local, sub-second, no network |
| No progress, no cancel | Wrong | Right — nothing to report and nothing worth killing |
| `UNDO_POLICY` totality forces a decision per kind | Neutral | **The mechanism the exit criteria depend on** |

So: five new `OpRequest` arms, five new `UNDO_POLICY` entries, `#prepareOp` grows five cases. No new
executor, no `writeStreaming`, no progress channel, no cancel. The write queue's existing
serialization is also load-bearing in a way worth stating: it is what prevents a stash push and a
drop from interleaving and invalidating the `stash@{N}` ↔ sha binding between the guard read and the
write.

The **reads** (`stash.list`, `stash.show`) and the **pre-flights** (`preflight.stashPop`,
`preflight.stashBranch`) get their own request keys, exactly as `refs.list` / `preflight.checkout`
already do.

### 6. Restoring the index (`--index`), and why it is opt-in

`git stash pop --index` restores the staged/unstaged split. Two facts decide the design: merge-tree
models trees, not index state, so **the prediction says nothing about `--index`**; and `--index`
fails on an already-conflicted index with `error: conflicts in index. Try without --index.` (probe
10) — a failure git itself resolves with a documented retry.

Design: `restoreIndex` is an explicit opt-in on `stashApply`/`stashPop`, default off, surfaced as
"Also restore staged changes". On the `conflicts in index` error the UI offers the retry git names,
one click, without `--index`. The pre-flight's `prediction` field is documented as covering the
worktree merge only, so nobody reads it as a promise about the index.

### 7. Stash create: the pathspec form, and a success that looks like a failure

`git stash push [-u] [--keep-index] [-m <msg>] [-- <pathspec>…]`. Two edges:

- **A clean tree is `rc=0`** with `No local changes to save` (probe 10). The op must **not** be
  rendered as an error; it must also not be rendered as a stash having been created. The service
  detects it by re-reading the stash list after the write and comparing the count, which it needs to
  do anyway to refresh the UI.
- **Pathspec** is a `readonly string[]` on the request, joined after a literal `--`. A pathspec that
  matches nothing is `rc=1` with `error: pathspec … did not match any file(s) known to git` →
  `NotFound`, an ordinary failure with a good message.

`--keep-index` is included: it is one flag, it is in git's own vocabulary for the same dialog, and
the alternative ("leave it out entirely") makes the "stash everything except what I've staged"
workflow impossible.

### 8. Wiring into checkout resolution and pull's autostash

**Checkout (§7.5).** `classifyCheckout`'s route rule already reads
`stashAvailable ? ["discard","stashAndCarry"] : ["discard"]` and is called with `false`. W9 passes
`true`. **No logic changes** — this is why P6 wrote the seam rather than the branch.

Executing the route is a three-step sequence the UI drives through existing ops, with the prediction
between steps 1 and 2:

1. `op.run { kind: "stashPush", message: "Auto-stash before switching to <target>", … }`
2. `preflight.stashPop { sha, target }` → clean? proceed : offer *switch without popping* (the
   stash stays in the list — §7.6's own wording)
3. `op.run { kind: "checkout", … }` then `op.run { kind: "stashPop", … }`

Ordering note: the prediction is computed **after** the push, because the stash does not exist
before it. If the prediction then says "conflicts", the user's choice is between popping anyway and
leaving the stash — never an un-doable state, since step 1 is fully reversible by a pop.

**Pull (§7.3, P8's seam).** `PullPreflight.routes` gains `"stashAndCarry"` when the pre-flight's only
blocker is `dirtyNonFastForward`. §7.3 requires this be "implemented as our own stash/pop", not
`--autostash`, and that is what the sequence above already is — same three ops with `pull` in the
middle. It reuses the same prediction, since the target commit is the fetched remote tip.

### W2 — `git/src/parse/stash.ts`

Three changes, one of them a bug fix.

```ts
/** `%gs`, not `%s`: `git stash list` displays the REFLOG subject, and `git stash store -m`
 *  (P9's drop-undo) sets only that. They are identical until a stash is restored, at which
 *  point `%s` shows the pre-drop label and hides the restored one (P9 probe 9). */
export const STASH_FORMAT = "%H%x1f%P%x1f%gd%x1f%at%x1f%gs";

/** ONE spawn for the whole list, counts included. `--numstat` interleaves each entry's
 *  NUL-terminated records after its header record; a header always contains \x1f, a numstat
 *  record never does, which is the framing discriminator (P9 probe 12). `-u` is deliberately
 *  absent: in `stash list` it means `--patch`, not `--include-untracked`. */
export function stashListArgs(): string[] {
  return ["stash", "list", "-z", "--numstat", "-M", "-C", `--format=${STASH_FORMAT}`];
}

/** Tracked AND untracked in one invocation, in exactly `diff-tree`'s `-z` framing, so
 *  `parseNumstatRecords`/`parseNameStatusRecords` consume it unchanged (P9 probe 12). `-u` on a
 *  stash with no third parent is a harmless no-op (rc=0). */
export function stashShowNumstatArgs(sha: string): string[] {
  return ["stash", "show", "--numstat", "-z", "-u", "-M", "-C", sha];
}
export function stashShowNameStatusArgs(sha: string): string[] {
  return ["stash", "show", "--name-status", "-z", "-u", "-M", "-C", sha];
}

/** The `-u` set, for the untracked-collision blocker. Empty when `-u` was passed with nothing
 *  untracked to save (P9 probe 1). */
export function stashUntrackedPathsArgs(untrackedSha: string): string[] {
  return ["ls-tree", "-r", "--name-only", "-z", untrackedSha];
}
```

`parseStashList(records)`: walk NUL records; a record containing `\x1f` opens a new entry (split on
`\x1f` into sha / parents / `%gd` / `%at` / `%gs`, trimming the trailing `\n`), any other non-empty
record is a numstat line for the open entry and increments `fileCount`. Parents split on space:
`[1]` → `baseSha`, `[2]` → `indexSha`, `[3]` → `untrackedSha`, and `includedUntracked` is
`parents.length === 4`. `index` comes from parsing `%gd`'s `stash@{N}` rather than from array
position, so a future `--skip`/filter cannot silently desynchronise it. `branch` is parsed from
`message`'s `WIP on <b>: ` / `On <b>: ` prefix, `null` for `(no branch)`.

**Done when:** the parser round-trips a fixture containing a `-u` stash, a pathspec stash, a stash
whose message contains `\x1f`-adjacent punctuation and a colon, and an empty stack (zero records,
not an error).

### W3 — `git/src/ops/stash.ts`

The whole argv table, with the sha-vs-`stash@{N}` split enforced by the signatures themselves —
`pop`/`drop`/`branch` take a *number*, `apply`/`show` take a *string sha*, so a caller cannot pass
the wrong one.

```ts
/**
 * §7.6's argv table. The addressing split is not stylistic: `git stash pop`/`drop` REFUSE a raw
 * sha (`error: '<sha>' is not a stash reference`), and `git stash branch <name> <sha>` is worse —
 * it succeeds, applies, and silently skips the drop (P9 probe 8). So every stack-mutating argv
 * takes an index and the service verifies the index still names the expected sha immediately
 * before writing.
 */
export function stashPushArgs(opts: {
  message?: string; includeUntracked?: boolean; keepIndex?: boolean;
  paths?: readonly string[];
}): string[] {
  const argv = ["stash", "push"];
  if (opts.includeUntracked) argv.push("-u");
  if (opts.keepIndex) argv.push("--keep-index");
  if (opts.message !== undefined) argv.push("-m", opts.message);
  if (opts.paths?.length) argv.push("--", ...opts.paths);
  return argv;
}

export function stashApplyArgs(sha: string, opts: { restoreIndex?: boolean } = {}): string[] {
  return ["stash", "apply", ...(opts.restoreIndex ? ["--index"] : []), sha];
}
export function stashPopArgs(index: number, opts: { restoreIndex?: boolean } = {}): string[] {
  return ["stash", "pop", ...(opts.restoreIndex ? ["--index"] : []), stashRef(index)];
}
export function stashDropArgs(index: number): string[] {
  return ["stash", "drop", stashRef(index)];
}
export function stashBranchArgs(branch: string, index: number): string[] {
  return ["stash", "branch", branch, stashRef(index)];
}

/** The undo replay for a dropped stash (§7.12's own table row). `-m` is written VERBATIM as the
 *  new reflog subject, so the caller must pass the captured `%gs`, not `%s` (P9 probe 9). The
 *  entry comes back at stash@{0}, not at its old position. */
export function stashStoreArgs(message: string, sha: string): string[] {
  return ["stash", "store", "-m", message, sha];
}

/** The pre-write guard: resolve `stash@{N}` and compare to the sha the request carried. */
export function stashRevParseArgs(index: number): string[] {
  return ["rev-parse", stashRef(index)];
}

const stashRef = (index: number) => `stash@{${index}}`;
```

**Done when:** each builder has a case in the integration suite that runs it against a real repo,
and `stashPushArgs({paths:["a.txt"]})` puts `--` before the path.

### W4 — `core/src/preflight/stashPop.ts`

Pure, no I/O — the classifier takes everything already read.

```ts
export function classifyStashPop(input: {
  readonly stash: StashEntry;
  readonly targetSha: string;
  /** From `parseMergeTreeOutput` — computed by the caller because it needs a spawn. */
  readonly prediction: MergeOutcomePrediction;
  /** Paths the stash changes (tracked half), from `stash show --name-only`. */
  readonly stashPaths: readonly string[];
  /** `ls-tree -r --name-only <stash>^3`, empty when `-u` was not used (P9 probe 1). */
  readonly stashUntrackedPaths: readonly string[];
  /** From `status --porcelain=v2` — the same `DirtyPath[]` §7.5 already builds. */
  readonly dirty: readonly DirtyPath[];
  /** Which of `stashUntrackedPaths` currently exist in the worktree. A path can collide while
   *  being neither tracked nor reported dirty — an ignored file, or one status elides — so
   *  membership in `dirty` is NOT a sufficient test (P9 probe 3). */
  readonly existingPaths: readonly string[];
  readonly inProgress: InProgressOperation | null;
}): StashPopPreflight;
```

Rules, in blocker order (`inProgressOperation` first — it moots every other remedy — then
`untrackedCollision`, then `localChangesWouldBeOverwritten`), mirroring `CheckoutBlocker`'s own
documented ordering:

- `untrackedCollision` ⇐ `stashUntrackedPaths ∩ existingPaths` non-empty.
- `localChangesWouldBeOverwritten` ⇐ `stashPaths ∩ {d.path | d.tracked}` non-empty. **This is
  §7.5's D∩T with the stash's tree standing in for the target's** — which is precisely what
  `classifyCheckout`'s reserved `targetTreePaths` parameter was written for.
- `verdict`: `blocked` if any blocker; else `willConflict` if `prediction.kind === "conflicts"`;
  else `clean`. A `prediction.kind === "unknown"` is `willConflict` — never `clean`; the UI states
  the reason and lets the user proceed, exactly as P6's revert dialog does.

`classifyStashBranch({ name, existingBranchNames, checkout })` composes `classifyCheckout`'s result
with name validation and returns `StashBranchPreflight`. It runs **no** merge-tree — the doc comment
must say why (probe 11), or a later reader will add one back.

**Done when:** unit tests cover both blockers alone, both together, a clean prediction with a
blocker present (verdict `blocked`, prediction still reported), and `unknown` never yielding

```ts

 *  goes away) and the reflog subject `%gs` written back verbatim (P9 probe 9). Best-effort:
 *  a stash that will not resolve yields null and the drop's own failure speaks for itself. */

}
```

## Judgment calls this plan made

1. **Stash ops go through `op.run`, not a new key.** D51's reasoning for `remote.run` inverts here:
   `runOp`'s unconditional undo-slot write is exactly what `stashDrop` needs and exactly what the
   other four should do (clear it). Adding a `stash.run` would mean reimplementing the undo capture
   and the read-back for no gain.
2. **The stash list is its own request, not part of `refs.list`.** `refs/stash` is one ref with a
   reflog stack; `RefRow`'s fields (upstream, track, `checkedOutIn`, annotation) are all meaningless
   for it and `for-each-ref` sees only the tip.
3. **`DecorationRef.stash` gains `index` rather than a second variant.** A stash decorates a commit
   the way a branch tip does; the missing piece was identity, not kind.
4. **The two prediction gaps become pre-flight blockers, not caveats on the prediction.** This keeps
   §7.6's "exact, not heuristic" literally true — of the merge — while making the *operation*
   honest. The alternative (widening `prediction` to a fuzzier union) would weaken a promise the
   2.38 floor was bought to make.
5. **Both blockers are computed from data §7.5 already fetches.** No new status read, no worktree
   scan — the untracked check `stat`s only the specific paths `ls-tree` names.
6. **`stash branch` gets no pop prediction.** It is provably clean by construction (probe 11);
   spending a spawn to confirm `rc=0` every time is waste, and a comment explains why so nobody adds
   one back.
7. **Stack-mutating ops are addressed by index, with a sha guard.** git leaves no choice (probe 8).
   The guard runs in `#prepareOp`, so a mismatch produces an `earlyError` and **no write at all**.
8. **`STASH_FORMAT`'s `%s` → `%gs` is treated as a bug fix, not a preference.** It is latent today
   (no production callers) and becomes visible the first time undo restores a stash.
9. **One spawn for the whole stash list, counts included** (probe 12), rather than N `stash show`
   spawns or a lazily-filled count that makes the list flicker.
10. **Untracked files are not counted in `fileCount`.** `stash list --numstat` cannot see them and
    `-u` means `--patch` there. The row shows `includedUntracked` as a marker and the detail pane
    gives the real list — better than N extra spawns for a number on a list row.
11. **Helper commits are filtered by sha, and stash parents truncated to the first.** `^<sha>`
    exclusion would take the base commit — real history — with them.
12. **`showInGraph: false` drops `--glob=refs/stash` too.** Showing only `stash@{0}`, because it is
    the one a glob happens to reach, is the least defensible of the three possible behaviours.
13. **`--keep-index` is in; `stash -p` is out.** One flag versus an interactive prompt that D2's
    no-hang guarantee forbids and no staging UI exists to replace.
14. **`--index` restore is opt-in and explicitly outside the prediction's scope**, with the retry
    git itself names offered on `conflicts in index`.
15. **`GATED_OP_KINDS` grows by three, not five.** Stashing and dropping during a conflicted state
    are legitimate; applying into one is not.
16. **`RevertPrediction` is renamed and aliased, not duplicated.** Two phases now produce the same
    three-armed merge-tree outcome.
17. **A conflicting pop is classified from the exit code plus the read-back, never a stderr
    pattern** — and `errors.ts` says so in a comment, because the natural instinct is to add one and
    it could never match (probe 5).
18. **The prediction-mismatch announcement is a required deliverable, not polish.** It is the only
    honest answer to the TOCTOU gap the pre-flight cannot close.
19. **The `No local changes to save` no-op is detected by a count comparison**, not by matching
    git's message — the service re-reads the list after every stash write anyway.

## Open questions for the orchestrating session

**OQ1 — Should the `stashAndCarry` route pop automatically when the prediction is clean?**
§7.6 says so explicitly ("the flow runs stash → switch → pop automatically"). *Recommendation:*
follow the spec — automatic on `clean`, with the announcement naming all three steps. The risk is a
TOCTOU pop failing after the switch already happened, and W13's mismatch reconciliation is exactly
the mitigation.

**OQ2 — Should `fileCount` include untracked files?** It cannot without N extra spawns.
*Recommendation:* no; ship the `includedUntracked` marker and put the real list in the detail pane.
Revisit only if the list row proves confusing in use.

**OQ3 — Where does `StashList.vue` live in the layout?** §3.1 names the file but not its home. The
candidates are a third tab beside `TagList.vue`/`BranchPicker.vue`, or a collapsible section in the
detail pane. *Recommendation:* beside `TagList.vue` — it is a list of repo objects with row actions,
which is exactly what that surface already is.

**OQ4 — Should a stash node be selectable in the graph like a commit?** It is a commit, and
`stash.show` gives it a file list. *Recommendation:* yes, with the detail pane showing the stash's
own changes rather than a commit diff. It costs nothing and makes the graph node useful rather than
decorative.

**OQ5 — `kiraVersion.stash.showInGraph` default.** `true` matches §7.6's "visible in two places".
*Recommendation:* `true`. Note that graph noise from the helper commits — the real reason a user
might want it off — is fixed by W12 rather than by the setting.

**OQ6 — Should a failed `stash branch` offer to delete the branch it created?** The user is left on
a branch they did not have (probe 11). *Recommendation:* no — say plainly what happened and let them
decide. An automatic rollback that itself needs a checkout could compound the failure, and the state
is not harmful.

**OQ7 — Does `stashApply` deserve a distinct confirmation from `stashPop`?** They differ only in
whether the stash survives. *Recommendation:* one dialog, with the verb and one sentence differing.
Two near-identical dialogs is the worse failure mode.

**OQ8 — Should the undo slot survive a `stashPush` following a `stashDrop`?** §7.12 says any
operation clears the slot, and P9 should not carve an exception. *Recommendation:* no exception —
but the drop confirmation should say the undo is available "until your next operation", which is the
honest bound (hard part 4).

**OQ9 — Pathspec source for `stash push -- <paths>`.** There is no staging UI, so the only natural
source is the changed-files selection in the detail pane. *Recommendation:* wire it from that
selection when non-empty, and leave the dialog's pathspec field empty (whole worktree) otherwise.
If that selection turns out not to be reachable from the stash dialog's context, ship whole-worktree
only and note it — a half-wired pathspec is worse than none.

**OQ10 — Should W10 (pull autostash) ship in P9 or wait?** It is P8's seam and one route, but it is
not named in §10's P9 row. *Recommendation:* ship it. The route helper is shared with checkout, so
the marginal cost is one classifier line and one test, and leaving `PullPreflight.routes` empty for
a second phase makes the seam look abandoned.

**OQ11 — `MergeOutcomePrediction` rename.** It touches P6 files for a naming reason alone.
*Recommendation:* do it, with the `RevertPrediction` alias kept so no import changes. If the
orchestrator prefers zero churn in P6's files, keep `RevertPrediction` as the name and add a comment
that P9 also produces it — the types are structurally identical either way.

**§7.6 (stash)** — four edits:

1. Step 2's argv becomes explicit and mandatory:
   `git merge-tree --write-tree --messages --name-only --merge-base=<stash^> <target> <stash>`,
   with a sentence recording *why*: without `--merge-base`, git picks `merge-base(target, stash)`
   and a genuinely conflicting pop is reported clean.
2. Step 4's "exact, not heuristic" is scoped: the prediction is exact **about the three-way merge**.
   Two failure modes it structurally cannot see — an untracked-file collision and a dirty worktree
   overlapping the stash's paths — are handled as pre-flight blockers by set intersection, and the
   untracked one is **not atomic**: git applies the tracked half, fails the untracked half, and
   keeps the stash.
3. Correct the parenthetical about `--glob=refs/stash` (see §4.4 above).
4. Record that a conflicting pop writes to **stdout** with an empty stderr and leaves no state file
   but `AUTO_MERGE`, so it classifies as `unmergedOnly` — no Continue, no Abort, resolve-in-editor
   and the kept stash are the remedies.

**§7.12 (undo)** — expand the stash row: capture is the full sha **and** the `%gs` reflog subject,

`gc --prune=now`; `undo.run`'s existing `cat-file -e` check turns a pruned object into a refusal
rather than a bad replay.

## Exit criteria

- [ ] `git stash push` with every combination of `-u`, `-m`, `--keep-index` and a pathspec produces
      the expected entry; a clean tree is reported as "nothing to stash", not as an error or a
      false success.
- [ ] The stash list renders message, date, base commit, and file count for every entry — including
      entries below `stash@{0}` — from one spawn.
- [ ] `stash show` populates the detail pane through the existing `FileTree`/`DiffView`, including
      the untracked half of a `-u` stash.
- [ ] Apply, pop, drop and branch all work from both the stash list and the graph row menu.
- [ ] **Every** stash entry appears as a node in the graph, visually distinguished, with no `index
      on …` or `untracked files on …` helper rows and no dangling edges.
- [ ] The pop prediction is computed with `--merge-base=<stash^>`, and an integration test asserts
      the prediction *without* it is wrong on a fixture built for the purpose.
- [ ] **Exit criterion 1:** prediction verified against actually-executed pops — clean predicted /
      clean executed, and conflicts predicted / the *same paths* conflicting when executed.
- [ ] A conflicting pop reports `StashConflict`, surfaces `unmergedOnly` in the existing banner, and
      states that the stash was kept.
- [ ] Both pre-flight blockers (untracked collision, local changes overwritten) block, name their
      paths, and give a remedy; the non-atomic outcome of forcing the first is pinned by a test.
- [ ] An executed pop that disagrees with its prediction is announced as a mismatch, never rendered
      silently.
- [ ] `stashAndCarry` is offered for a `blockedByTracked` checkout and runs stash → predict → switch
      → pop.
- [ ] A dirty non-fast-forward pull offers the same route, implemented as our own stash/pop with no
      `--autostash`.
- [ ] **Exit criterion 2:** a dropped stash is recoverable through the undo slot, restored with its
      original message, and the UI says it came back as `stash@{0}`.
- [ ] Undo after the object is pruned refuses cleanly and writes nothing.
- [ ] `CONTRACT_VERSION` is 10 and all four new request keys round-trip through the real codec.
- [ ] `bun run check`, `test:unit`, `test:integration`, `test:e2e` and `test:perf` are all green.
