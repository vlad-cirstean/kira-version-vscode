# P16 — FlatBuffers for the graph-stream payload

Plan for a new P16 row of `docs/SPEC.md` §10. Written before implementation per `AGENTS.md`.

**This phase exists because the project owner overrode a declined decision.** `docs/plans/P15.md`
measured FlatBuffers against this app's real production boundary and declined it in **D33**
(`docs/SPEC.md` §11.1). The measurements have not changed and this plan does not pretend
otherwise — they are restated in full below, plainly, because an implementer who does not know
what this phase is *not* buying will optimize the wrong thing. But the instruction is explicit
and unambiguous: **implement FlatBuffers for real, on top of what P7 landed.** So this plan does
not re-litigate the decision. It designs the best version of the thing that was asked for.

P15 anticipated exactly this and reserved a work program for it (its appendix, F1–F8). That
appendix is this plan's starting point. Where this plan diverges from it, it says so and why —
and it diverges in four places, because P15's appendix was a sketch written against a tree that
has since moved (P7 landed; `CONTRACT_VERSION` is 7, not 6; there is a second webview view and a
second host-side RPC surface) and against `flatc` research that is now a year old and, in one
concrete respect, out of date in this phase's favour.

**Goal:** `graph.stream`'s `PackedCommitChunk` — the only `ArrayBuffer`-bearing payload on the
whole contract, ~420 KB per 5,000-commit page, and the single highest-traffic thing this app
sends — crosses the wire as one FlatBuffer built from a checked-in `.fbs` schema, generated by a
pinned, provenance-recorded `flatc`, adapted by hand-written `toWire`/`fromWire` functions whose
drift against `packages/ipc`'s contract type is caught by the compiler wherever that is still
possible and by an exhaustive round trip everywhere it is not. Everything else on the contract is
untouched.

## The measurements this phase ships in spite of

Restated from P15's own probes, unedited, because they are the honest frame for every judgment
call below. Per 5,000-row chunk, on the boundary that actually ships (a `WebviewView`'s
`postMessage`, which carries neither a transfer list nor raw bytes — P15's W1 finding, confirmed
against a real VS Code 1.136.1):

| | base64 over the existing packed columns (shipping today) | FlatBuffers, then base64 |
|---|---|---|
| build / encode | 0.56 ms | 0.67 + 0.71 ms |
| `JSON.stringify` | 0.30 | 0.43 |
| `JSON.parse` | 0.44 | 0.22 |
| decode / access | 1.17 | 0.31 + 0.11 |
| **total** | **2.47 ms** | **2.45 ms** |
| wire bytes | 560,395 | 560,416 |

And on the contract's other large payload, a 1 MiB-capped `commit.fileDiff`, FlatBuffers is
**2.4x slower to encode** than `JSON.stringify` (10.84 ms vs 4.46 ms) for a 12% wire saving after
the base64 tax that this host forces on it.

Three consequences the implementer must hold onto:

1. **The win is not going to show up in a stopwatch.** If `hostBoundaryMs` after this phase is
   within noise of P15's committed 4.74 ms baseline, that is the *expected* outcome, not a
   failure of the implementation. W11 is built so that this is measured rather than assumed, and
   W11 says exactly what to do if the number disagrees materially in either direction.
2. **What this phase actually buys is a schema.** A `.fbs` file is a machine-checkable,
   language-neutral, version-disciplined description of the highest-traffic payload in the app,
   where today there is a hand-rolled column layout described only by doc comments in
   `commitStore.ts`. That is a real artefact and it is the thing to build well.
3. **The scope stays exactly where P15's appendix put it: `graph.stream` only.** A full
   conversion of ~45 contract types to save microseconds is not defensible on any reading of the
   numbers above, and the appendix said so. This is a partial conversion by design.

## The hard parts, settled before the work items

### 1. `flatc`: what gets used, from where, under what licence — and why nothing binary is committed

P15's research said neither npm route works. **Re-verified against the live registry while
writing this plan, and it still holds**, with one genuinely new option that did not exist then:

- **`flatc-bin@23.5.26`** — unchanged since 2023-08-18. Declares `"bin": {"flatc-bin":
  "bin/flatc"}`; that file is still absent from its own tarball, it still ships only a Mach-O and
  a `.exe`, and there is still **no Linux binary**. Unusable.
- **`flatc@1.1.0`** — unchanged since 2018. `license` is still the non-SPDX
  `"SEE SEPARATE LICENSE FILE"`, still compiles FlatBuffers 1.9 from source in a `postinstall`.
  Unusable, and a `postinstall` that compiles C++ is disqualifying on its own.
- **`flatc-wasm@26.1.32` — new since P15 (first published 2025-08-08, latest 2026-04-29).** This
  is the genuinely new option and it deserves an honest look, because it would delete this
  section's whole problem: `flatc` as a WebAssembly module, Apache-2.0, npm provenance
  attestation, platform-independent, offline after install. **Rejected**, for three reasons that
  are about supply chain rather than licence: it is published from a **third-party fork**
  (`DigitalArsenal/flatbuffers`), not from `google/flatbuffers`; it declares a runtime dependency
  on **`hd-wallet-wasm`** (12.9 MB, "BIP-32/39/44 multi-curve HD wallet") and ships homomorphic
  encryption and HD-key modules alongside the compiler — a compiler for a git UI's wire format
  has no business dragging a crypto wallet into the toolchain; and its shipped artefact is an
  8 MB emscripten blob built by a single maintainer from that fork. It clears `AGENTS.md`'s
  licence bar and fails its "well-maintained" spirit. Raised as open question 7 so the
  orchestrating session sees the option rather than only the verdict.

**What is used instead: Google's own release binary, pinned by version and digest, fetched on
demand, never committed.**

The decisive new fact, verified while writing this plan: **`google/flatbuffers` release tag
`v25.9.23` exists and publishes per-platform `flatc` binaries** — `Linux.flatc.binary.g++-13.zip`,
`Linux.flatc.binary.clang++-18.zip`, `Mac.flatc.binary.zip` (arm64), `MacIntel.flatc.binary.zip`,
`Windows.flatc.binary.zip` — and `25.9.23` is **exactly the version of the `flatbuffers` npm
runtime** (`flatbuffers@25.9.23`, Apache-2.0, zero dependencies, published by Google's own
maintainers `aardappel`/`dbaileychess`). Pinning both halves to the same release removes
generator/runtime skew entirely, which is the one correctness risk a codegen toolchain carries
that a plan can eliminate for free.

Concretely:

- **`scripts/flatc.lock.json`** (committed) records: `version: "25.9.23"`, the release tag URL,
  and per-platform `{asset, url, sha256}` for `darwin-arm64` and `linux-x64` — the two lanes this
  project has (D27's platform of record, plus P4c's Linux dev lane). Plus `license:
  "Apache-2.0"` and `source: "https://github.com/google/flatbuffers"`, so the provenance question
  is answered in the repo rather than in a plan document nobody re-reads.
- **`scripts/fetch-flatc.ts`** downloads the pinned asset for the current platform into `.flatc/`
  (gitignored, `.vscode-test`'s precedent), verifies the SHA-256 against the lock, refuses to
  proceed on mismatch, and is a no-op when the binary is already present. It is **not** a
  `postinstall`, it is **not** run by `bun run check`, and nothing but `gen:schema` calls it.
- **Nothing binary is committed.** A 2.4–2.6 MB ELF/Mach-O in a repo whose largest artefacts are
  PNG baselines earns nothing: the artefact everyone actually consumes is the *generated
  TypeScript*, and that **is** committed.
- **The digest pin is the integrity mechanism.** `v25.9.23` predates the SLSA attestation
  (`multiple.intoto.jsonl`) that later flatbuffers releases carry; the lock's recorded sha256,
  computed once at pin time and verified on every fetch, is what stands in for it. Recorded as a
  known limitation in the lock file itself, with the note that a future re-pin should prefer a
  tag that carries an attestation.

**`bun install` and `bun run check` stay deterministic and offline-capable.** This is a hard
requirement, not an aspiration, and it is what shapes W3:

| Command | Needs network? | Needs `flatc`? |
|---|---|---|
| `bun install` | registry only, lockfile-pinned, no postinstall | no |
| `bun run check` (incl. `check:schema`) | **no** | **no** |
| `bun run test` / `test:e2e` / `test:perf` / `build` | no | no |
| `bun run gen:schema` | yes, once, to fetch the pinned binary | yes |

### 2. `check:schema` without `flatc` — how the generated code stays honest offline

`gen-settings.ts --check` regenerates and diffs. That is only possible because its generator is
pure TypeScript. Ours is not, so a literal copy of the pattern would put a native binary on the
critical path of `bun run check` — which is precisely the failure P15 flagged and which this
project's Linux lane cannot accept.

**`check:schema` therefore checks a digest, not an output.** Two offline checks:

1. **Staleness.** `scripts/gen-schema.ts` writes a header into the generated file recording
   `flatc` version, the generator's own version, and the **SHA-256 of every `.fbs` input**.
   `--check` recomputes the input digests and fails with "run `bun run gen:schema`" if they
   differ. This catches the one failure that actually happens: someone edits the schema and
   forgets to regenerate.
2. **Source hygiene — F7's append-only rule, made mechanical.**
   `packages/ipc/schema/graphChunk.fields.json` (committed, written by `gen:schema`) records each
   table's field names **in declaration order**. `--check` re-parses the `.fbs` — a file this
   project owns, in a deliberately plain subset of the grammar — and fails unless the current
   field list is a **prefix-preserving extension** of the locked one: no renames, no reorders, no
   deletions (a retired field keeps its slot with `(deprecated)`), appends only. That is
   FlatBuffers' own evolution discipline enforced as source hygiene, exactly as F7 asks, and it
   runs in milliseconds with no toolchain.

What this deliberately does **not** catch: a generated file hand-edited to something the schema
would not have produced. That is a real gap and it is stated rather than papered over — the
mitigation is that the generated directory carries a "do not edit" header and is excluded from
Biome, so a hand edit is visible in review, and W14/V1 requires the implementer to confirm that a
clean `gen:schema` reproduces the committed file byte-for-byte.

### 3. How the codec learns it is looking at a graph chunk

This is the one structural problem P15's appendix left open, and it has a clean answer.

`codec.ts` today walks messages **generically** — it finds `ArrayBuffer`s by shape, with no idea
what payload they belong to (D36, deliberately: "a rule expressed as *every ArrayBuffer* cannot be
forgotten by the next phase that adds one"). A FlatBuffers encoding is the opposite: it applies to
**one named type**, and nothing else. The `Frame` union does not help — `{t:"chunk", id, seq,
chunk}` carries no method name, and structural sniffing ("does this object have seven
buffer-shaped fields?") is exactly the kind of guessing §3.5 forbids.

**But both chunk seams already know the method, from state they already hold:**

- Server side, `handleOpen(id, method, params)` closes over `method` when it builds `emit`
  (`rpc.ts` L390–408). It is right there.
- Client side, `case "chunk"` looks up `pendingStreams.get(frame.id)`, whose `PendingStream`
  already carries `readonly method: StreamKey` (L152) — it is used for the supersede rule.

So the seam is:

```ts
// codec.ts — the dispatch. rpc.ts calls only this; it never imports the schema adapter.
export function encodeStreamPayload(method: StreamKey, chunk: unknown): unknown;
export function decodeStreamPayload(method: StreamKey, payload: unknown): unknown;
```

keyed on `StreamKey`, with `"graph.stream"` delegating to `packages/ipc/src/graphChunkCodec.ts`
and every future stream key defaulting to pass-through. **D34 holds literally** — the encoding
lives in `codec.ts`; `rpc.ts` supplies only the method name it already has; no host, and no
handler, learns anything about the format.

Ordering with the existing base64 layer, which is the property that makes this compose:

```
emit(chunk)
  → encodeStreamPayload("graph.stream", chunk)     // 7 buffers + dictionary + decorations
                                                   //   → { $fb:"graphChunk/1", d: ArrayBuffer }
  → post() → wrapVersioned → encode(envelope, channel.bufferEncoding)
                                                   // "base64": that ONE buffer → one tagged string
                                                   // "native": that ONE buffer → the transfer list
```

FlatBuffers does not delete the base64 layer — **it feeds it**. Under `"base64"` the message goes
from seven tagged strings to one; under `"native"` from seven transfers to one. D36's generic rule
is untouched and still matters, because it is what carries the FlatBuffer itself.

### 4. Does this cover the review sidebar too? Yes — for free, and provably

The answer is yes, and the reason is structural rather than lucky:

- There is exactly **one `StreamKey`** — `"graph.stream"` (`validate.ts` L78). The panel walk and
  the review walk are the same key with a different `params.range` (P7/D38).
- There is exactly **one packing site** — `RepoService.#emitRange`, called from both
  `streamGraph` (panel) and `#streamReviewGraph` (review), producing the identical
  `PackedCommitChunk` from whichever `WalkLike` it is handed.
- There is exactly **one channel factory** — `createWebviewChannel`, used by `panelView.ts` and
  `reviewView.ts` alike, declaring the same `VSCODE_WEBVIEW_BUFFER_ENCODING`.
- The codec seam is **per-frame and stateless**. It has no notion of which view a channel belongs
  to and needs none.

**And it does not touch D38's isolation guarantee.** D38 is about *host-side session state* —
`LogSession`, `CommitStore`, `dictionaryMarks`, `nextSeq`, `lastRemaining` living on a separate
`reviewWalk` object so a ranged walk cannot corrupt the panel's cache. Nothing in this phase
reads, writes or shares any of it: the adapter is a pure function from one `PackedCommitChunk` to
one `ArrayBuffer` and back. The two views' `RpcServer`s remain entirely separate objects over
separate channels.

"Provably" matters more than "obviously", so W10 makes it a test rather than a paragraph: a ranged
`graph.stream` chunk must be shown to round-trip through the same path, from the same integration
harness, as a panel chunk. If someone later special-cases the panel, that test fails.

### 5. What the drift check actually protects today — and the strongest replacement

P15's appendix (F5) says the conversion costs `wireConformance.test.ts`'s compile-time
assignability check for the converted type. **Read against the current file, that is not quite
right, and the difference changes what the mitigation has to be.**

`PackedCommitChunk` is **not** in the `assertBothWays` list. The 22 `assertBothWays` cases cover
`HeadState`, `DecorationRef`, `SettingsSnapshot`, the P5 diff types, the P6 refs/ops/preflight
types and P7's two review types — not the packed chunk. What protects `PackedCommitChunk` today
is subtler and weaker than the appendix implies:

1. **A one-way, incidental compile-time check.** P15's runtime section passes `core`'s
   `packSlice(...)` return value into helpers annotated with **`ipc`'s** `PackedCommitChunk`
   (`snapshotColumns`, `expectColumnsMatchSnapshot`). That makes core → ipc assignability a `tsc`
   error if the two drift. There is no ipc → core direction and never has been.
2. **P15's runtime round trip**, which compares the seven columns byte-for-byte and feeds the
   result to `appendPacked`.

So the honest statement of what this phase costs is narrower and sharper than "the mechanism
stops working": **the hand-written adapter introduces a new failure mode in which a field is
silently not carried, and neither of the two protections above would notice**, because
`fromWire` would happily produce a chunk whose `dictionaryBase` is `0` and whose columns are all
present. FlatBuffers' read-a-default-for-an-absent-field behaviour is what makes it silent.

**The replacement, designed as four layers rather than lamented as a loss.** Three are
compile-time and one is runtime, and each closes a specific hole:

| Hole | Guard | Mechanism |
|---|---|---|
| A field is added to `PackedCommitChunk` and the adapter never **writes** it | **Exhaustive destructure in `toWire`** | `const {from, to, …, decorations, ...rest} = chunk; const _exhaustive: Record<string, never> = rest;` — a new field lands in `rest` and fails `tsc`. This is the single most valuable guard in the phase |
| A field is added and the adapter never **reads** it | **Annotated return type on `fromWire`** | `function fromWire(buffer: ArrayBuffer): PackedCommitChunk` constructing an object literal — a missing required property is a `tsc` error |
| A field is added to the contract type but never to the **schema** | **Accessor-name bridge** | A compile-time mapped type asserting every `keyof PackedCommitChunk` is also a key of the generated accessor class (flatc camel-cases `sha_width_bytes` → `shaWidthBytes()`, so the names line up by construction). A field with no accessor fails `tsc` |
| The adapter writes a field but writes it **wrongly**, and the test fixture happens to expect the FlatBuffers default | **The no-defaults round trip** | W9's fixture must have **no field at a FlatBuffers default value** — `from > 0`, `to > from`, `shaWidthBytes > 0`, every column `byteLength > 0`, `dictionaryBase > 0`, `dictionary.length > 0`, `decorations.length > 0` — asserted by the test itself before it compares anything. Then it iterates `Object.keys` of the real chunk and compares every key |
| A variant is added to `DecorationRef` (the one non-columnar field) | **`never` switch** | `toWire`'s `switch (ref.kind)` is exhaustive with a `never` default; adding a union member is a `tsc` error. `fromWire`'s reconstruction throws loudly on an unrecognised `kind` |

The fourth row is the important insight and it is worth stating as a rule the phase leaves
behind: **a FlatBuffers round-trip test whose fixture contains a default value is not testing that
field.** That is why the fixture's precondition is asserted rather than assumed.

Considered and rejected as a fifth layer: a **Biome lint rule** forbidding `PackedCommitChunk`
construction outside the adapter. Biome's rule surface here is `noRestrictedImports` on module
specifiers; expressing "this object literal must mention every field" would need a GritQL plugin,
which is more machinery than the `Record<string, never>` trick that already does the job at zero
cost. Named so nobody re-derives it.

Net honesty: this is **still a downgrade**, because the compiler cannot check that bytes written
equal bytes read — only a test can. But it is a much smaller downgrade than "the mechanism is
gone", and three of the four holes are closed at compile time.

### 6. The schema, exactly

One file, one root table, one nested table, no enums, no unions, no `include`s.

```fbs
// packages/ipc/schema/graphChunk.fbs
//
// The `graph.stream` chunk payload — `PackedCommitChunk` (`packages/ipc/src/contract.ts`,
// structurally mirroring `packages/core/src/store/commitStore.ts`). Append-only: never
// renumber, never reorder, never delete — retire with (deprecated). Enforced by
// `bun run check:schema` (P16 W3). CONTRACT_VERSION, not this file, is the compatibility
// authority (P16 D46).

namespace KiraVersion.Wire;

table DecorationRef {
  kind: string;        // the union discriminant, verbatim: branch|remoteBranch|tag|head|stash
  name: string;        // absent for "head" and "stash"
  is_head: bool;       // meaningful only for "branch"
}

table RowDecorations {
  row: uint32;         // chunk-relative, exactly as PackedCommitChunk.decorations carries it
  refs: [DecorationRef];
}

table PackedCommitChunk {
  from: uint32;
  to: uint32;
  sha_width_bytes: uint8;
  shas: [ubyte];
  parent_offsets: [ubyte];
  parent_shas: [ubyte];
  identity_ids: [ubyte];
  times: [ubyte];
  subject_bytes: [ubyte];
  subject_offsets: [ubyte];
  dictionary_base: uint32;
  dictionary: [string];
  decorations: [RowDecorations];
}

root_type PackedCommitChunk;
file_identifier "KVGC";
```

Two choices in there that are deliberate and could reasonably have gone the other way:

**`[ubyte]` for all seven columns, not `[uint32]` for the four that are `Uint32Array`s.** The
columns are opaque, host-endian, typed-array-backed byte ranges whose meaning is owned by §5.5 and
`commitStore.ts`. Declaring them as `[uint32]` would put a *second*, weaker statement of that fact
in the schema, and would import a contract FlatBuffers does not actually police here: FlatBuffers
vectors are little-endian by definition, while `packSlice` hands over a host-endian
`Uint32Array.buffer` and `appendPacked` reads it back host-endian. Both halves run in one process
pair on one machine, so this has always been fine — but it is fine *because* the bytes are opaque,
and `[ubyte]` says so. It also removes every 4-byte-alignment question from the adapter.

**`file_identifier "KVGC"` is an integrity tag, not a version.** `bufferHasIdentifier` is checked
on every decode and a mismatch throws — that is §3.5's "fails loudly" applied at the byte level,
and it is what turns "the codec was handed the wrong bytes" into an error instead of a plausible,
wrong graph. It is emphatically **not** a compatibility negotiation; see D46.

### 7. `decorations` — the one field with no natural FlatBuffers shape

`DecorationRef` is a five-member discriminated union with per-variant fields (`branch` carries
`isHead`, `head` and `stash` carry no `name` at all), and `exactOptionalPropertyTypes: true` means
`{kind:"head"}` must be reconstructed *without* a `name: undefined` property. P15's F2 offered two
shapes; this plan picks tables over a JSON string:

- **Tables (chosen).** The `.fbs` stays a complete description of what crosses the wire, which is
  the one durable artefact this phase is actually buying. The drift risk is closed by the `never`
  switch on write and by W9 covering **all five variants** explicitly.
- **A JSON string field (rejected).** Zero drift risk and trivially correct, but it makes the
  schema a partial description of its own payload — a JSON island inside the FlatBuffer — for a
  field carrying well under 0.1% of the bytes. Buying back a small drift risk with a permanent
  hole in the artefact is the wrong trade for this phase specifically.

### 8. What FlatBuffers cannot help with, restated so nobody tries

`appendPacked` costs **39.91 ms per 5,000-row page** (P15's committed
`streamRoundTrip.budget.json` baseline, its own V5) — roughly **8x** the entire wire hop. It is
the largest single cost on the graph streaming path and it is a *store* question: re-interning the
dictionary, hashing 500 shas per chunk into `ShaTable`, decoding subjects, rebuilding the parent
CSR. FlatBuffers' zero-copy read does not touch it, and this phase's adapter cannot even try: the
columns must land as `ArrayBuffer`s that `appendPacked` accepts, so `fromWire` slices them out of
the FlatBuffer exactly as `decodeBuffers` does today.

This is task **#53** in the orchestrating session's tracker, inherited unowned from P15's Findings.
**This phase does not touch it**, for the same reason P15's judgment call 6 gave: it is
`packages/core`'s hottest code and no row asks for it. What this phase does about it is re-confirm
the number (V6) so whoever picks it up starts from a measurement rather than a suspicion. Said

## W5 — `packages/ipc/src/graphChunkCodec.ts`

The adapters, in their own file rather than inside `codec.ts`: `codec.ts` owns *buffer
encodings*, this owns *one payload's schema*, and they are different concerns with different
reasons to change.

- `toWire(chunk: PackedCommitChunk): ArrayBuffer` — builds the FlatBuffer via
  `flatbuffers.Builder`, finishes it with the `"KVGC"` identifier, returns exactly-sized bytes.
  Opens with the exhaustive destructure + `Record<string, never>` guard.
- `fromWire(buffer: ArrayBuffer): PackedCommitChunk` — asserts `bufferHasIdentifier`, reads every
  field, returns an annotated object literal.
- The accessor-name bridge type and the `never`-defaulted `DecorationRef` switch.

Three implementation details that are easy to get subtly wrong and are called out because they
are load-bearing:

- **An empty vector must round-trip as a zero-length `ArrayBuffer`, never as `null`.**
  `rpc.test.ts`'s `emptyPackedChunk()` — used by every credit/cancel/ordering test — has five
  zero-length columns, an empty dictionary and empty decorations. `fromWire` must normalize a
  null/absent vector and an empty vector identically.
- **`from`, `to`, `dictionaryBase`, `shaWidthBytes` are scalars whose zero is a legitimate
  value.** FlatBuffers omits a scalar equal to its default; reading it back yields the default,
  which is correct here — but it is also exactly why W9's fixture must be all-non-default.
- **Every column must be copied into a fresh, exactly-sized `ArrayBuffer`**, not handed out as a
  view over the FlatBuffer, because `appendPacked` does `new Uint32Array(chunk.parentOffsets)` and
  a view over a larger buffer would silently carry the wrong length. `codec.ts`'s existing
  `decodeBuffers` already makes this exact `.slice()` and for the same reason — follow it.

**Done when:** `fromWire(toWire(c))` reproduces `c` field-for-field for a real `packSlice` chunk,
for `emptyPackedChunk()`, and for a chunk carrying all five `DecorationRef` variants; deleting one
field from `toWire` fails `tsc`; adding a field to `PackedCommitChunk` and to neither adapter fails
`tsc` in two places.

## Judgment calls this plan made

1. **The FlatBuffers packing is unconditional, not a third `BufferEncoding`.** P15's F4 sketched
   `"flatbuffers"` alongside `"native"`/`"base64"`. That conflates two orthogonal axes — what a
   *transport* can carry, versus how a *payload* is encoded — and would produce a combinatorial
   mess (a "flatbuffers" transport still needs base64 on VS Code and native on the harness). Two
   axes: `BufferEncoding` stays exactly as P15 left it, and the graph chunk is FlatBuffers
   everywhere. The decisive benefit is that the harness, both webviews, both e2e tiers and every
   unit test then exercise **the same payload format production does** — which is precisely the
   blindness that let P4c's 47 ms bug survive. The A/B measurement W11 needs does not require a
   production toggle: it calls both adapters directly.
2. **The schema covers `PackedCommitChunk` only, not the whole `graph.stream` chunk envelope.**
   The envelope's seven scalars (`repoId`, `seq`, `from`, `to`, `source`, `remaining`,
   `exhausted`) cost ~100 bytes and would put `source`'s union and `repoId` in a second place
   that must be kept in step with `contract.ts` for no measurable gain. The schema covers exactly
   the 13 fields that carry the bytes — which is also exactly the set W9's structural test can
   enumerate.
3. **`[ubyte]` for all seven columns.** Reasoned in "The schema, exactly": the columns' element
   types and endianness are §5.5's and `commitStore.ts`'s to state, and a second statement in the
   schema would be weaker, not stronger.
4. **flatc is fetched-and-verified, not vendored.** Committing 5 MB of platform binaries to get
   offline `gen:schema` buys nothing, because `gen:schema` is not on any lane's critical path —
   the *generated code* is, and that is committed. `bun install` and `bun run check` stay offline
   either way, which was the actual requirement.
5. **flatc and the runtime are pinned to the same version, `25.9.23`.** A matched pair eliminates
   generator/runtime skew, which is the one class of codegen bug a plan can design out entirely.
   The cost is forgoing the SLSA attestation that later tags carry; the digest pin covers
   integrity, and open question 6 hands the trade to the orchestrating session.
6. **A `.fbs` + `flatc`, not a hand-built `Builder` adapter.** P15's own probe hand-built the
   chunk "exactly as generated accessors would", and doing that in production would delete the
   toolchain problem completely — but it would also delete the only durable thing this phase
   buys. A hand-rolled binary layout with no schema is strictly worse than `packSlice`, which at
   least has doc comments. Named so nobody re-derives it as a shortcut mid-implementation.
7. **The drift downgrade is mitigated in four layers, and the residual gap is stated.** Three
   compile-time guards and one runtime rule ("a fixture with a default value is not testing that
   field"). What remains uncovered — bytes written not matching bytes read — is a test's job, and
   is said plainly rather than hidden behind "round-trip tested".
8. **`decorations` uses tables, not an embedded JSON string** — reasoned above; the schema stays a
   complete description of its own payload.
9. **`check:schema` checks a digest, not a regenerated output.** A deliberate, stated divergence
   from `gen-settings.ts --check`, forced by the native toolchain, and the only way `bun run check`
   stays offline.
10. **`commit.fileDiff` is left alone, on the measurement.** The override is about the graph
    stream; converting the diff would make the app measurably slower, and no instruction asks for
    that.
11. **Task #53 is named with a number and not touched** — P15's judgment call 6, restated because
    the brief asked for an explicit answer rather than an ambiguous one.
12. **The measured tradeoff is restated at the top, prominently, and the phase ships anyway.**
    Recording that the numbers point elsewhere is not hedging; it is what makes the next reader of
    this plan able to tell an implementation bug from an expected null result in W11.

## Open questions for the orchestrating session

Raised rather than resolved by editing the spec or proceeding on an assumption. Each carries this
plan's own recommendation.

1. **How should D33 be recorded now that it has been overridden?** D33 is an accurate record of a
   real measurement and deleting or rewriting it would destroy that. **Recommendation:** leave
   D33's text intact, prefix it with a short "**Superseded by D44** — overridden by the project
   owner; the measurements below still stand" note, and add **D44** ("FlatBuffers, implemented
   anyway") stating the override, who made it, and that the tradeoff was accepted rather than
   disproved. §12's strikethrough-plus-note pattern is the house precedent. This is a spec edit
   and belongs to the orchestrating session.
2. **Is P16 the right number, and what does the §10 row say?** Confirmed by reading the table:
   P0–P15 exist, P15 was inserted out of sequence, so **P16** is next. **Recommendation:** add a
   P16 row after P15's, titled "FlatBuffers for the graph-stream payload", with the same
   "designed and implemented out of sequence, by explicit instruction" note P15's row carries, and
   with this plan's exit criteria as the row's exit criteria. Confirm before the implementer
   writes the row.
3. **`CONTRACT_VERSION` 7 → 8.** **Recommendation: yes.** Both halves ship in one build, but VS
   Code recreates the webview on hide/reveal, and a stale bundle reading FlatBuffers as a plain
   object renders an empty graph rather than throwing — the exact half-working failure §3.5
   forbids. One line, effectively free.
4. **Should a bundle-size budget be introduced?** `flatbuffers` adds ~10–15 KB to each of two
   bundles and there is no budget to check it against. **Recommendation: no, not here.** Record
   the delta (V5) and let P13 (Ship), which owns packaging, decide whether a gated budget is
   wanted. Inventing one inside a wire-format phase is scope creep.
5. **Third-party attribution.** This is the first Apache-2.0 dependency to reach the shipped
   `.vsix`; the repo has an MIT `LICENSE` and no NOTICE/THIRD-PARTY file (Vue, SlickGrid and

6. **Pin `25.9.23` (matched pair, no attestation) or the latest release (attested, ~3 months of
   generator/runtime skew)?** **Recommendation: the matched pair.** Skew between generator and

   the digest pin. But it is a supply-chain judgment the orchestrating session may weigh
   differently.
7. **`flatc-wasm` instead of a fetched binary?** It would delete W1 entirely — Apache-2.0,

8. **What happens if W11 comes back materially worse?** The ladder is in W11 and the implementer

   orchestrating session pre-agrees that a measured regression is a Finding to be decided on, not

### V2 — `bun run check` is offline and flatc-free

Verified directly rather than by code inspection. `.flatc/` and `node_modules` were both deleted;

makes this possible: the schema-drift check never touches the toolchain at all in the common case,
only `gen:schema` (an explicit, separate command) does.

### V3 — The host-boundary regression (W11 escalation, two coordinator-directed follow-ups, final resolution)

Measured twice, independently, against a 100k-commit `largeBranchy` repo, using
`tests/perf/streamRoundTrip.ts`'s gated `hostBoundaryMs` metric (the shipping FlatBuffers
`toWire`/`fromWire` path across ten chunks) alongside the new recorded-only
`hostBoundaryBase64Ms`/`hostWireBytesBase64` pair (the old plain-JSON-plus-base64 path over the
identical chunks, same run, for direct A/B comparison):

| metric | baseline (P15) | run 1 | run 2 |
|---|---|---|---|
| `hostBoundaryMs` (gated) | 4.74 ms | 22.95 ms (+383.8%) | 24.74 ms (+421.4%) |
| `hostWireBytes` (gated) | 563,748 B | 563,697 B | 563,748 B |
| `hostBoundaryBase64Ms` (recorded) | — | ~3.03 ms | ~3.03 ms |
| `hostWireBytesBase64` (recorded) | — | 563,748 B | 563,748 B |

`hostWireBytes` is unchanged (within the gate, as expected — FlatBuffers' framing overhead on this
payload shape is negligible). `hostBoundaryMs`, however, is **materially worse**: FlatBuffers'
`toWire`/`fromWire` round trip on the host boundary costs roughly 7–8x what the old plain-JSON path
cost for the same ten chunks, not the modest overhead the plan's open question 8 budgeted for.
Two consecutive runs producing consistent ~4-5x regressions rules out a one-off scheduling fluke.

Per the pre-resolved escalation ladder (open question 8): "within ±20% → proceed & re-baseline;
materially worse → do NOT widen tolerance or silently revert, write up as a clearly-flagged Finding
for the orchestrating session, keep FlatBuffers implementation in place." This result is
unambiguously in the "materially worse" branch. Accordingly: `streamRoundTrip.budget.json` was
**deliberately left untouched** at its original P15 values (`hostBoundaryMs: 4.743741...`) — not
re-baselined, not tolerance-widened. `bun run test:perf` will continue to report this as a failing
regression on every future run, by design, as the visible signal that this decision point is still
open. The FlatBuffers implementation itself was **not** reverted or gated behind a flag; it ships
as built, per the override this plan operates under. **This is the one exit-criterion item that is
intentionally left in a "red" state pending a decision from the orchestrating session** — see the
escalation note under the exit-criteria checklist above.

No root-cause micro-profiling of the regression was performed (out of this phase's scope per the
ladder's instruction to record and flag, not to fix); a plausible contributor is that `toWire`
performs a full `Builder` construction plus a second `slice()` copy to produce an exactly-sized
buffer, and `fromWire` performs a `ByteBuffer` wrap plus per-column `slice()` copies — several more
allocation/copy passes than the old path's single `JSON.stringify`/base64 encode, on payloads whose
absolute byte counts are already small (hundreds of KB) enough that constant-factor overhead
dominates.

**Follow-up (post-checklist, coordinator-directed):** the coordinator reviewed the diff and this
Finding and, with a microbenchmark of their own, identified a specific root cause: flatc's generated
`create<Field>Vector()` wrappers for `[ubyte]` columns (`createShasVector`, `createParentOffsetsVector`,
`createParentShasVector`, `createIdentityIdsVector`, `createTimesVector`, `createSubjectBytesVector`,
`createSubjectOffsetsVector` in `packages/ipc/src/generated/graphChunk.ts`) loop `builder.addInt8()`
once per element — an *O(n)* call per byte — rather than using the `flatbuffers` runtime's own
`Builder.createByteVector(v: Uint8Array): Offset`, which does one bulk `this.bb.bytes().set(v,
this.space)` copy. `PackedCommitChunk` has seven such byte columns per chunk, and the coordinator's
microbenchmark (500,000-byte column, 20 iterations) measured 2.087 ms/iter for the loop vs.
0.578 ms/iter for the bulk method — a 3.6x difference on one column alone.

`toWire` in `graphChunkCodec.ts` was changed to call `builder.createByteVector(new
Uint8Array(...))` directly (the runtime's own bulk method) for all seven byte columns instead of
the generated per-column wrappers, passing the resulting offset to the same `add<Field>()` calls as
before. This is a wire-format-neutral change: a FlatBuffers `[ubyte]` vector is length-prefixed raw
bytes on the wire regardless of which builder method wrote it, so `fromWire`, the `.fbs` schema, all
four drift guards, and every existing round-trip/no-defaults test needed zero changes — confirmed by
re-running `bun run test:unit` (922 pass, 0 fail, unchanged) and `bun run test:integration` (230
pass, 0 fail, unchanged) after the edit, and by a clean `tsc --build --force`.

Re-measuring `hostBoundaryMs` twice, independently, against the same 100k-commit repo, after the
fix:

| metric | baseline (P15) | before fix (run 1 / run 2) | after fix (run 1 / run 2) |
|---|---|---|---|
| `hostBoundaryMs` (gated) | 4.74 ms | 22.95 ms (+383.8%) / 24.74 ms (+421.4%) | 12.17 ms (+156.4%) / 10.42 ms (+119.6%) |
| `hostWireBytes` (gated) | 563,748 B | 563,697 B / 563,748 B | 563,697 B / 563,748 B (unchanged) |

The fix **roughly halved** the regression — a real, substantial improvement, confirming the
coordinator's hypothesis was at least a major contributor — but `hostBoundaryMs` is **still
materially worse** than baseline, still well outside the ±20% ladder tolerance. Per the same
escalation ladder and the coordinator's own explicit instruction for this branch ("if it's still
materially worse even after this fix, leave the budget untouched"): `streamRoundTrip.budget.json`
remains **untouched** at its original P15 values; `bun run test:perf` continues to report
`hostBoundaryMs` as a failing regression by design. What this rules out: the byte-vector codegen
inefficiency was a large but not sole contributor. What remains unexplained: roughly a 2.2–2.6x
gap between the post-fix `hostBoundaryMs` (~10–12 ms) and the old plain-JSON-plus-base64 path's
~3 ms (`hostBoundaryBase64Ms`, recorded alongside, unaffected by this fix since it doesn't touch
FlatBuffers at all) — plausibly the remaining `Builder`/`ByteBuffer` construction and copy overhead
inherent to `toWire`/`fromWire`'s object-table structure (nested `RowDecorations`/`DecorationRef`
tables, the `dictionary` string vector, the nine separate typed-array `.slice()` copies in
`fromWire`'s `copyColumn`), none of which this scoped follow-up touched. A deeper investigation
(e.g. whether `fromWire`'s per-column `.slice()` copies could be views in cases where the caller
doesn't need an independent buffer) was not pursued in this scoped follow-up — see round 3 below,
where the coordinator explicitly closed off further speculative micro-optimization.

**Round 3 (post-checklist, coordinator-directed, final round):** the coordinator proposed one more
narrow, cheap attempt before accepting the residual as a cost: `toWire`'s `const builder = new
flatbuffers.Builder(1024)` starts every chunk at a hardcoded 1 KB capacity, and for a real chunk
(seven byte columns of tens of KB each) that forces several doubling reallocations — each copying
the entire buffer built so far — before the `Builder` settles at its final size. The fix tried:
compute an estimated capacity up front (the seven byte columns' summed `byteLength`, plus a
worst-case UTF-8 estimate for the `dictionary` strings, plus a fixed 4096-byte slack for
vtables/scalars/nesting) and pass that as the `Builder`'s initial size instead of 1024 — purely a
local allocation-strategy change in `toWire`, no schema/wire/`fromWire` change (confirmed: `tsc
--build --force` clean, `bun run test:unit` 922/922 unchanged, `bun run test:integration` 230/230
unchanged).

Re-measuring `hostBoundaryMs` twice, independently, against the same 100k-commit repo:

| metric | baseline (P15) | after round 2 (fix only) | after round 3 (fix + pre-sized capacity) |
|---|---|---|---|
| `hostBoundaryMs` (gated) | 4.74 ms | 12.17 ms / 10.42 ms | 11.37 ms / 10.80 ms |

The two pairs are statistically indistinguishable — a ~0.2 ms difference in the averages, well
inside this sandbox's demonstrated run-to-run noise floor (in the very same two round-3 runs,
`packMs` and `appendMs` — neither touched by any P16 code — swung 12.7%→38.6% and 6.4%→23.7%
respectively, purely from scheduling noise). Pre-sizing the `Builder`'s capacity made **no
measurable difference**: `flatbuffers`' `Builder.growByteBuffer` doubling strategy is evidently
cheap enough at this payload size (tens of KB, a handful of doublings at most) that avoiding it
isn't where the remaining cost lives. This attempt was **reverted** (`git diff` against the round-2
commit is empty for `graphChunkCodec.ts`), keeping only the round-2 byte-vector fix.

Per the coordinator's decision rule for this final round ("if this change makes no measurable
difference at all: revert just this one attempt ... and still re-baseline the budget to the numbers
from the previous round ... with the same accepted-cost framing" and "this is the end of the
performance-chasing loop for P16"): a fresh full baseline run was captured
(`bun run tests/perf/streamRoundTrip.ts --update-baseline`, `hostBoundaryMs: 11.10 ms`, consistent
with both round 2 and round 3's numbers), and only `hostBoundaryMs` (plus the two pre-existing
recorded-only keys `hostBoundaryBase64Ms`/`hostWireBytesBase64`, now included for completeness) was
taken from that run into `streamRoundTrip.budget.json` — every other metric's baseline (`packMs`,
`cloneMs`, `cloneMsNoTransfer`, `appendMs`, `wireBytesFirstPage`, `wireBytes100k`,
`roundTripMs100k`, `hostWireBytes`) was restored to its original, untouched P15 value, since this
investigation concerned `hostBoundaryMs` only and re-baselining unrelated metrics off one noisy run
would mask real future regressions in `packSlice`/`appendPacked`. Confirmed after the update:
`bun run tests/perf/streamRoundTrip.ts` passes `hostBoundaryMs` at 2.0% and (in a repeat run) fails
it once at 20.6% — a hair over the ±20% line — consistent with the noise level already documented
above; this occasional borderline flakiness at the tolerance boundary is a known property of
re-baselining onto real, noisy hardware rather than a defect, and is recorded here rather than
concealed.

**Final disposition:** `hostBoundaryMs`'s residual cost (~11 ms against a ~4.7 ms baseline, a
roughly 2.3x increase, down from the original ~5x) is accepted as a **documented tradeoff of the
D44 override** — the project owner's business decision to adopt FlatBuffers regardless of the
measured cost (SPEC.md D44) — distinct from, and not to be confused with, the byte-vector codegen
inefficiency fixed in round 2, which *was* a genuine implementation defect worth fixing. No further
performance work on this metric was pursued past this round, per the coordinator's explicit
instruction to close the loop here. `hostWireBytes` was unaffected throughout all three rounds
(563,748 B ↔ 563,697 B, always within its unrelated ±20% gate).

Re-measured fresh in this session (not re-cited): `appendMs` (the gated metric covering

### V7 — Sender-side heap cost

Measured with a standalone script (`/tmp/.../scratchpad/v7-heap-measure.ts`, not part of the
repository) against a real 500-row `packSlice` chunk drawn from a `largeBranchy(5000)`-generated
repository via the real `CommitStore`/`logSession` pipeline (not a synthetic fixture):

- Raw pre-existing columnar bytes (`shas` + `parentOffsets` + `parentShas` + `identityIds` +
  `times` + `subjectBytes` + `subjectOffsets`, byte lengths the sender already holds regardless of
  wire format): **41,528 bytes**.
- `toWire()`'s finished, exactly-sized FlatBuffer for the same chunk: **41,860 bytes** — a delta of
  only **332 bytes (+0.8%)** over the raw columns, matching the plan's own "~42 KB" estimate almost
  exactly.
- The `Builder`'s peak *transient* capacity (not the finished size) is larger during construction:
  `flatbuffers.Builder`'s doubling-growth strategy starting from `new flatbuffers.Builder(1024)`
  (the initial size `toWire` passes) means the backing buffer is a power-of-two multiple of 1024
  bytes at any moment — for a ~41.9 KB finished message the smallest doubling that fits is
  **65,536 bytes (64 KB)**, derived analytically from the growth strategy rather than measured
  directly (the finished buffer's own backing array, per `asUint8Array()`, is exactly this size
  before `toWire`'s final `.slice()` produces the exactly-sized copy returned to the caller).

Both the finished-size delta (332 B) and the transient peak (64 KB) are negligible against §5.1's
≤80 MB renderer budget — but note this cost sits on the **sender/host side** of `graph.stream`, not
the renderer the ≤80 MB budget actually governs, so this comparison is a sanity-magnitude check,
not a claim that the renderer's own budget is what bounds this cost.
